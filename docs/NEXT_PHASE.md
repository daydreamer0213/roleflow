# RoleFlow 下一阶段主控索引

> 更新于 2026-08-16。本文件记录四个独立课题的当前状态、边界和设计任务。课题 1、4 已按确认设计完成；课题 2、3 仍不因本文件而获得实施授权。

## 总体原则

- 四个课题相互独立。项目精简只针对整个代码库，不是另外三个产品功能的统一重构框架。
- 每次只设计、实现和验收一个课题；共享文件发生冲突时串行推进。
- 保持 v1.0 的 BOSS、安全、质量、数据基线和先验证后提交边界。
- 设计先确定真实用户流程、数据来源、失败边界和验收标准，再写实施计划。
- 不把历史 plan/spec 的待办状态当成当前需求。

## 课题 1：第一性原则项目审计与精简

### 目标

从不可替代的产品结果和安全/质量底线出发，证明哪些代码应删除、缩短、随功能迁移或保留。在不改变产品行为的前提下减少真实冗余。

### 状态

`██████████ 100%` 已完成设计、实施和本地验证；位于 `codex/first-principles-audit`，未推送、未合并、未发布。

### 完成结果

- 正式产品扫描和恢复入口只接受 `trusted_pane`；`search_page_api` 的研究实现和历史失败证据保留，但不能进入产品链路。
- 扫描状态文字由 today view model 统一负责，SQLite 持久化状态到真实 HTTP 页面已有回归覆盖。
- 删除两个无消费者模块和逐项证明无调用的旧函数；没有拆分大文件，也没有删除 BOSS 安全、存储兼容、恢复或质量代码。
- 六个严格低薪边界已迁入正式质量测试入口；删除了未注册的孤立测试，测试入口审计无孤儿文件。
- 生产 CommonJS 可达性为 `97/98`，唯一不可达项是通过 HTTP 提供的 `src/dashboard/assets/workflow.js`。
- 生产代码只有用户主动启动工作台时的一次 `browser.bringToFront`；扫描、JD、分析、消息、沟通、轮询、重试和恢复路径均无调用。
- 当前共注册 97 项离线检查：本轮允许的 96 项全部通过；`startup_scripts_smoke.js` 因其未签名 `msedge.exe` 测试桩被 360 拦截而未运行；更早 beta.4.x 保留完整 97 项通过的历史证据。
- 本轮真实 BOSS 访问和外部写均为 0。

### 保留结论

- `src/dashboard/server.js`、`src/cli.js` 和 `src/adapters/sites/boss.js` 仍是职责集中点，但只在后续独立功能实际触碰时迁移职责。
- 不以文件大小或删行数继续扩大精简；新的删除候选仍必须重新证明无生产价值并通过对应回归门。
- 课题 1 到此结束，不作为课题 2、3、4 的统一改造框架。

### 非目标

- 不追求预设删行比例。
- 不做大爆炸模块拆分、换框架、换数据库或微服务化。
- 不以删除安全、诊断、恢复或质量测试换取更少代码。

## 课题 2：消息发现的岗位理解与回复草稿

### 目标

对已沟通岗位的招聘方回复和 HR 主动新招呼，结合岗位详情与消息原文，向用户解释岗位并生成可人工复制的推荐回复草稿。

### 当前证据

- 当前消息模型能接收招聘方消息原文，但岗位输入只有标题、公司、薪资和地点，没有完整 JD 或已有岗位分析。
- 已沟通岗位通常可复用本地完整 JD；HR 主动新招呼可能没有本地岗位详情。
- 当前消息正文只在内存中处理并清理，页面不会向 BOSS 填写、粘贴或发送消息。

### 详细设计必须回答

- 如何区分并处理“已知岗位回复”和“HR 主动机会”？
- 本地完整 JD、已有分析、当前消息页只读详情的使用优先级是什么？
- 新招呼缺少稳定详情入口时如何停止并避免编造？
- 如何用一次模型调用同时生成岗位介绍、匹配点、风险和最多两条草稿？
- 面试邀约、缺失候选人事实和敏感问题如何保留人工确认边界？
- 如何继续做到消息正文不落日志、不长期保存、绝不自动发送？

### 前置证据

实施前需要一次最小、只读的真实消息页 DOM 校准，确认新招呼是否存在稳定且可验证的岗位详情入口。没有证据不得设计搜索页或独立详情页兜底。

## 课题 3：通用模式与继承模式

### 目标

让用户明确知道哪些条件控制平台采集，哪些条件用于 RoleFlow 本地精筛，并为通用模式和继承模式提供各自合适的设置。

### 当前证据

- 每日主工作流目前以 `inherited` 模式启动。
- BOSS 当前搜索页决定平台原生采集边界；RoleFlow 方案仍参与关键词、方向、排除词、活跃度、工作制、薪资偏好、经验弹性和推荐排序。
- 当前表单混合展示两类设置，造成“本地方案几乎不生效”的用户感受。

### 详细设计必须回答

- 模式如何保存到方案并冻结到工作流快照，保证恢复一致？
- 通用模式如何配置城市、平台薪资档位、经验、学历、岗位类型、关键词和预算？
- 继承模式如何自动展示 BOSS 当前条件，并聚焦语义方向、证据匹配、排除词、活跃度、工作制、薪资偏好和经验弹性？
- 如何避免平台范围和本地偏好使用同名字段造成冲突？
- 现有方案如何兼容迁移，新用户默认模式如何通过质量验证后决定？

### 质量门

任何实质筛选变化都使用全新空 operational baseline，并量化召回、推荐分布、完整 JD 覆盖和运行成本。不得静默降低质量。

## 课题 4：逐岗位进度与明确进度条

### 目标

让用户准确理解扫描、JD、分析和沟通正在处理什么、已完成多少、还剩多少，同时消除不必要的整页刷新和闪烁。

### 状态

`██████████ 100%` 已完成设计、实施、Chrome 隔离验收和本地验证；位于 `codex/first-principles-audit`，未推送、未合并、未发布。

### 完成结果

- SQLite 读模型统一提供四条独立进度：扫描岗位、完整 JD、分析岗位和沟通岗位；没有制造缺乏真实权重依据的总百分比。
- 扫描与 JD 保持交错：`completed`、`partial`、`failed` 都计入已处理搜索目标；JD 分母严格使用 `read + pending`，无需详情的 `notRequired` 岗位不进入分母。
- 扫描适配器只把已经观察到的卡片、详情和目标终态写入 checkpoint；浏览器命令调用数回归证明没有增加 BOSS 操作，也没有改变随机节奏、冷却或失败即停边界。
- 分析页服务端渲染岗位名称和公司，约 2.5 秒的轻量轮询只返回任务 ID、位置、状态和允许的错误码；沟通页按不可变批次条目 ID 更新。完整 JD、分析内容、消息、沟通证据和任意内部错误正文不进入轻量响应。
- 同阶段逐岗位变化只局部更新。页面隐藏时零请求，恢复可见时立即读取，始终最多一个请求在途；阶段结构变化、沟通歧义、批次或岗位集合漂移和终态最多整页刷新一次。
- Chrome 本地隔离验收覆盖 `scanning`、`analyzing`、`paused`、`review_required`、`interrupted` 五个状态和 4 个视口，共 20 页；零浏览器/请求/外部请求错误、零横向溢出、零运行中动画。证据保存在 `.runtime/workflow-progress-evidence/`。
- 212 个 JavaScript 文件语法检查全部通过；允许执行的 96/97 项离线检查全部通过，唯一未运行的是会生成未签名 `msedge.exe` 测试桩并触发 360 的 `startup_scripts_smoke.js`。
- 当前真实 BOSS 访问和外部写均为 0。生产代码仍只有 `workspace-tabs` 在用户主动启动工作台时的一次前台引导调用；两个浏览器适配器保留实现该能力所需的传输方法，其他流程没有调用。

## 推荐设计顺序

1. `[已完成]` 第一性原则项目审计与精简。
2. `[已完成]` 逐岗位进度与明确进度条。
3. `[下一步]` 消息发现的岗位理解与回复草稿；需要少量真实只读页面证据。
4. `[待设计]` 通用模式与继承模式；对召回和推荐质量影响最大，最后结合全新基线验证。

顺序只用于控制风险，不表示四个课题互相从属。新主控应先逐份提交设计给用户确认，再为已确认设计编写实施计划。
