# RoleFlow 用户旅程验收修复设计

> 日期：2026-08-29
>
> 状态：用户已批准推荐方向，等待书面设计复核
>
> 范围：消息发现与回复、求职体检、定向简历、模拟面试的本地用户体验收口

## 1. 目标

修复用户视角验收中已经稳定复现的问题，使正常操作、刷新恢复和模型失败都不会让用户丢失当前输入、看到旧草稿或误以为操作没有生效。

本轮不改变阶段一至阶段四的产品方向，不新增外部能力，不访问真实 BOSS，也不重新设计岗位分析、积分路线、漏斗算法、简历优化契约或面试生成契约。

## 2. 已确认事实

### 2.1 异步错误会绕过 Dashboard 外层错误处理

定向简历和模拟面试的异步 HTTP 处理函数以 `return handler(...)` 返回 Promise。处理函数内部的模型或服务异常发生在外层 `try` 返回之后，因此不会进入外层 `catch`。在 Node.js 当前运行方式下，未处理的 Promise 拒绝会让本地服务退出。

本地假模型稳定复现：提交面试回答后模型抛错，浏览器进入 `ERR_CONNECTION_REFUSED`，服务进程退出码为 1。

### 2.2 消息草稿已保存，但本次发现快照覆盖了持久化结果

消息草稿输入停止约 600 毫秒后已写入 SQLite。只要本次消息发现结果仍保存在控制器内存中，页面刷新就优先渲染运行快照里的旧文字，而不是 SQLite 中最新的 `current_text` 和 `revision`。

本地验收稳定复现：数据库是用户修改后的文字和修订号 1，刷新页面却恢复到修订号 0 的原始草稿。

### 2.3 未提交的面试回答没有本地草稿

面试回答框只在提交成功后写入 SQLite。用户输入长回答后刷新、误关页面或遇到模型错误，当前未提交文字没有恢复来源。

### 2.4 成功结果位于首屏之外

定向简历生成/启用、面试结束/重答都重定向到没有页面锚点的基础 URL。重定向后浏览器回到顶部，结果区在桌面短窗口和移动宽度下可能完全位于首屏之外。

## 3. 方案比较

### 方案 A：只修服务退出和草稿回退

改动最少，但仍保留面试输入丢失、成功结果不可见、表单原始 JSON 错误和消息卡片低效等已确认问题。不能通过本轮用户体验收口。

### 方案 B：针对性收口（采用）

修复三个阻塞问题，同时使用现有 HTML、CSS、浏览器本地存储、SQLite 和服务端路由完成小型体验改进。没有新依赖、数据库迁移或架构层。本方案覆盖验收发现，又不会扩成页面重写。

### 方案 C：重写为前端单页应用

可以统一状态和错误提示，但会引入前端框架、构建链和新的状态模型，风险与当前问题不成比例，明确不采用。

## 4. 设计

### 4.1 统一接住定向简历和模拟面试异步错误

- Dashboard 路由必须 `await` 定向简历和模拟面试的异步处理函数，使异常进入现有外层错误边界。
- 正常成功响应仍使用现有 303 重定向，不改变服务接口和幂等语义。
- 页面脚本拦截定向简历生成/启用和模拟面试开始/回答/结束/重答表单：
  - 提交时禁用当前按钮并显示“处理中…”；
  - 成功时跳转到服务器返回的最终页面；
  - 失败时留在当前页面，在表单附近显示可读错误并恢复按钮；
  - 输入框当前文字保持不变，用户可以直接修改或重试；
  - 不增加二次确认。
- JavaScript 不可用时，服务仍不得退出；服务器错误响应继续保留请求编号供诊断。

### 4.2 消息草稿以 SQLite 当前版本为页面权威值

- 消息发现仍可保留内存中的 HR 消息、计数、岗位理解和运行状态。
- 页面渲染本次运行结果前，使用当前开放草稿覆盖内存快照中的草稿文字和修订号。
- 已关闭、已发送或已放弃的草稿不因旧运行快照重新出现。
- 公开状态接口继续不返回草稿正文。
- 每条可编辑草稿显示独立的“有修改待保存 / 正在保存 / 已自动保存 / 保存失败”状态；发送和离页前仍沿用现有串行保存链。

### 4.3 未提交面试回答使用浏览器本地草稿

- 复用当前专用浏览器环境的 `localStorage`，不新增数据库表或 API。
- 草稿键由会话 ID、题号和用途组成；当前问题与每道重答互不覆盖。
- 输入时本地保存；重新进入同一会话和题号时恢复。
- 对应提交成功后删除该题草稿；提交失败时保留。
- 已完成的历史回答、用户事实和回答记忆规则不变，未提交草稿不会进入任何模型上下文或候选人事实。

### 4.4 成功后直接定位到结果

- 定向简历生成后定位到新草稿标题，启用后定位到“已启用新版本”。
- 面试开始和提交回答后定位到当前问题或结束入口，生成复盘后定位到复盘结论，保存重答后定位到对应题目的重答对比。
- 使用现有 URL fragment 和稳定元素 ID，不增加客户端路由。
- 页面首次进入且没有选中草稿/会话时仍从顶部开始。

### 4.5 消息卡片保持关键信息优先

默认可见内容按以下顺序收敛：

1. HR 原文或安全卡片摘要；
2. 当前沟通结论；
3. 岗位机会结论、主要工作、匹配与工作安排；
4. 可编辑回复草稿及复制、确认发送入口。

公司业务、资料来源和其他补充字段放入原生 `<details>`，需要时展开。删除“岗位理解 / 结论”连续重复标题。单条和批量发送的不可变授权、后台串行执行和安全停止规则不变。

“已手动发送”改为更明确的“我已在 BOSS 手动发送”，并保持次要按钮样式，避免与“确认发送”混淆。

### 4.6 模拟面试和求职体检的小型可理解性修复

- 进行中的面试逐题记录只显示已经回答的题；当前未回答问题不在下方重复显示“等待回答”。
- “面试类型”改为“题目侧重”，“通用沟通”改为“自我介绍与沟通”。训练范围仍保持通用/岗位专项两种模式。
- 求职体检指标“等待 48 小时”改为“等待反馈成熟”，说明直接显示“至少 48 小时；周末顺延”。
- “修改完成”表单提交前必须至少选择招呼语或求职策略；未选择时在当前页面显示浏览器原生校验提示，不导航到 JSON 错误页。

## 5. 数据与安全边界

- 不新增数据库迁移、依赖、模型调用或后台任务。
- 不改变消息发送批次、目标冻结、文字冻结、串行执行、访问额度、随机节奏或风险停止规则。
- 不把面试本地草稿写入回答记忆、候选人事实或模型上下文。
- 不访问真实 BOSS，不执行填写、粘贴、发送、简历同意/拒绝、投递或申请。
- 不推送、不合并、不打包、不改版本号、不创建 Release。

## 6. 回归与用户验收

自动回归必须先证明旧代码会失败，再验证修复：

1. 定向简历或模拟面试服务抛错时，HTTP 请求得到受控错误，Dashboard 进程仍可继续响应。
2. 完成的消息发现运行中，草稿保存后刷新页面显示 SQLite 最新文字与修订号；关闭草稿不会被旧快照恢复。
3. 面试当前回答和重答草稿刷新后恢复，成功提交后清除。
4. 进行中面试的逐题记录不重复当前未回答问题。
5. 定向简历与面试成功重定向包含正确锚点。
6. 求职体检不选择调整类型时留在当前页面并提示。
7. 现有单条/批量确认发送、阶段二轮次、定向简历原子启用和面试幂等测试继续通过。

最终使用本地假数据在 1440×980 和 375×812 下重走消息、求职体检、定向简历和模拟面试流程，检查：

- 没有横向溢出或控制台错误；
- 输入刷新恢复；
- 模型失败不离开当前页面且服务不中断；
- 成功后结果进入当前视口；
- 消息卡片仍能完成编辑、复制、单条确认和批量选择。

## 7. 非目标

- 不做公司/行业研究、外部题库、语音面试或真实面试效果评估。
- 不重写 Dashboard、不引入前端框架、不拆微服务。
- 不修改 30/50/70、48 小时/周末成熟算法或策略轮次归属。
- 不扩展尚无真实 DOM 证据的位置确认、面试排期等 BOSS 卡片。
- 不执行真实消息发送验收。
