# RoleFlow 四档结果统计与反馈闭环设计

## 1. 目标

增加一个本地、只读的结果统计面板。它帮助用户观察：

1. 四档推荐后续分别积累了哪些人工记录结果。
2. 哪些搜索关键词持续出现相同的人工反馈或结果状态。
3. 当前样本是否足以支持人工讨论规则或权重调整。

第一版只帮助观察，不自动给出“模型好坏”结论，更不会自动改提示词、二维表、权重、排序、默认勾选或沟通批次。

## 2. 已确认边界

- 四档推荐仍是唯一的岗位推荐体系：`primary`（主投）、`apply`（可投）、`caution`（慎投）、`not_recommended`（不推荐）。
- `analysis_pending` 与 `refresh` 是诊断状态，不是第五或第六档推荐；它们必须单独显示，且不参与四档横向比较。
- 结果状态沿用现有本地状态：`pending`、`review`、`later`、`applied`、`skipped`、`no_reply`、`interview`、`rejected`、`invalid`、`salary_mismatch`。
- “已投”“无回复”“约面”等都是用户或现有工作流记录，不代表平台实时状态，也不构成因果证明。
- 调整二维表、阈值或提示词前，必须先向用户展示统计和偏差并获得确认。
- 不访问 BOSS、不读取 Cookie、不调用模型、不读取或输出简历正文、提示词、模型配置、岗位 JD、公司名或岗位标题。
- 不新增数据库表、不迁移 schema、不缓存统计结果；每次页面请求只从现有本地记录重算。

## 3. 现状与缺口

岗位“时效、重复、JD 变更、招聘方活跃度”等底层规则已经存在，现有代码会产生 `possible_duplicate`、`detail_changed`、`needs_recheck`、`stale_or_unknown_active` 等标签，并在岗位详情中展示。现有反馈也能记录跳过原因和关键词。

当前缺的是聚合视图：用户无法一眼比较四档推荐分别积累了多少后续结果，也无法以统一、可复核的方式观察不同搜索关键词的历史反馈。因此本项目只补充汇总层，不重写已有质量规则或反馈记录。

## 4. 数据与派生规则

统计只接受每个岗位的最小安全投影：

```js
{
  decisionBucket: "primary" | "apply" | "caution" | "not_recommended" | "analysis_pending" | "refresh",
  applicationStatus: "pending" | "review" | "later" | "applied" | "no_reply" | "interview" | "rejected" | "invalid" | "salary_mismatch" | null,
  keyword: string | null
}
```

输入和输出都不得含岗位 ID、标题、公司、URL、JD、简历证据、模型原始输出或沟通正文。

每个四档行包含：

- `total`：进入该档的岗位数。
- `outcomes`：各人工结果状态的数量。
- `recordedOutcomeCount`：除 `pending`、`review`、`later` 外的已记录终态数。
- `unresolvedCount`：`pending`、`review`、`later` 的数量。

页面只显示计数，不显示“成功率”“转化率”“模型准确率”等带因果暗示的结论。样本量不足时应明确提示“仅供观察，不足以调参”。

第一版的“方向”采用岗位保存时的搜索关键词，而不是模型推断的语义赛道。界面使用“搜索方向（关键词）”，并把空值归为“未记录关键词”。

## 5. 架构

```text
现有岗位观察 + 候选人状态
          |
          v
listDecisionPool(db, { planId })
          |
          | 投影为 decisionBucket / applicationStatus / keyword
          v
src/core/outcome_analytics.js  (纯确定性聚合)
          |
          v
getOutcomeAnalyticsSnapshot(...) (只读存储适配)
          |
          v
现有 /queue 页面中的统计面板
```

纯聚合器不接触数据库。存储适配器不写数据库。页面渲染器只接受已聚合的统计对象，不能重新读取岗位详情或把岗位识别信息输出到 HTML。

## 6. 用户界面

在现有岗位队列页面、队列筛选区之后展示“结果统计（只读）”面板：

1. 显示当前方案、纳入岗位数、已记录终态数。
2. 显示主投、可投、慎投、不推荐四行计数。
3. 单独显示“待分析或待刷新（不纳入四档比较）”。
4. 最多显示 12 个搜索方向（关键词），其余合并为“其他关键词”。
5. 固定提示：统计仅用于人工复盘；调整二维表、权重或提示词前须经用户确认。

如果没有历史结果，面板仍可显示四档存量和“暂无已记录结果”，而不是空白或虚假的比率。

## 7. 错误处理与安全

- 方案不存在或聚合器异常时，队列页面保持可用，面板显示“统计暂不可用”，并只记录固定错误码。
- 不把异常 message、SQL、岗位字段、简历内容或模型内容写入日志。
- 输入未知档位或未知结果状态时，计入明确的 `unclassified` 计数，不静默归入四档。
- 不执行扫描、补读、重试分析、沟通、状态变更或数据修复。

## 8. 验收标准

- 同一最小输入投影必定生成相同统计结果。
- 四档总数只包含四个合法推荐档；待分析/待刷新完全隔离。
- 关键词总数、四档总数、未知项均可复核，聚合后不含岗位识别字段。
- 实际 SQLite smoke 证明新快照路径不写 schema、不改变岗位或候选人状态。
- 页面可在无结果、混合结果、未知字段和关键词超过上限时正确显示。
- 离线测试不调用模型、网络、BOSS 或真实浏览器。

## 9. 非目标

- 不把结果统计自动反馈为筛选权重或二维表修改。
- 不评估岗位真假、公司风险或 Ghost Job；这些属于后续独立可信度项目。
- 不生成 STAR 故事、岗位专用简历、公司调查、Offer 比较或公开 ATS 抓取。
- 不使用真实历史岗位或真实简历作为自动化测试夹具。
