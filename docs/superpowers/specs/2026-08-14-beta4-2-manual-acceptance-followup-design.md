# RoleFlow beta.4.2 人工验收后续整改设计

**日期：** 2026-08-14
**状态：** 设计待书面复核
**范围：** 新用户人工验收提出的模型设置、关键词展示、岗位筛选进度和真实自动沟通阻塞

## 1. 结论

本轮不重写 RoleFlow，不启动 Wave 5，也不改变 `trusted_pane` 采集主线。整改只处理
当前人工路径已经真实触发的五个问题：

1. 共享厂商和 API Key 填写后仍要向下滚动，且两套任务各有一个“测试连接并保存”；
2. “下一步：填写简历”在未验证时完全消失，缺少稳定流程引导；
3. 页面把 Search Plan 的 14 个候选词误称为“本轮关键词”；
4. 搜索目标和完整 JD 进度只在技术明细中，本轮概览没有随抓取过程更新；
5. 自动沟通第二次真实出现 `COMMUNICATION_RESULT_AMBIGUOUS`，结果观察器没有捕获任何
   建联请求。

采用最小现有架构方案：

- 模型设置继续使用本地设置文件、Windows 加密密钥和现有连接测试器；
- 每轮关键词仍由现有 workflow planner 选择 3 个，不裁剪 Search Plan 候选词库；
- 本轮概览继续消费现有 workflow progress snapshot；
- 沟通继续使用固定搜索标签和固定消息标签、一次点击上限和歧义人工处理门；
- 复用现有 `EdgeControlAdapter.clickAt()` 与 Edge Control 网络日志能力；
- 不增加运行时依赖、前端框架、浏览器窗口或 BOSS 标签。

## 2. 已确认事实

### 2.1 模型设置

- 共享厂商和 API Key 已位于页面顶部，但没有自己的提交动作。
- 共享 API Key 只能在下方任一任务卡点击“测试连接并保存”时写入。
- 深度分析和批量筛选分别保存连接状态。
- 当前“下一步：填写简历”只在深度分析连接已验证时渲染；未验证时 DOM 中完全没有
  该入口。

### 2.2 关键词

当前人工验收 workflow：

- Search Plan #1 保存 14 个候选关键词；
- workflow `772781ab-66dd-43a0-b180-f76228077714` 实际只冻结并执行 3 个：
  `AI应用开发`、`RAG`、`Agent开发`；
- 页面 `scopeView()` 读取 `planner.keywordSource.keywords`，因此把 14 个方案候选词
  显示成“本轮关键词”；
- 这是展示来源错误，不是本轮真的访问了 14 个搜索词。

用户已选择：保留候选词库和现有每轮 3 个关键词策略，只修正显示，不降低后续轮次
召回。

### 2.3 抓取和完整 JD 进度

- `/api/workflow-status` 已提供 `scanTargets.total/completed/pending` 和
  `details.collected/read/pending`；
- 技术明细已显示这些数字；
- 本轮概览只有“第 N / 5 阶段”和聚合后的“剩余工作”，无法直接看出搜索目标和
  完整 JD 的推进；
- 前端轮询已经能在 workflow 状态不变时按 `progressRevision` 更新概览字段。

### 2.4 自动沟通

当前批次 #1：

- 第 1 项“初级AI Agent开发工程师 / 广州壹凡科技有限公司”为 `ambiguous`；
- `clickCount=1`，观察证据为
  `{"endpoints":[],"pageState":"no_matching_request"}`；
- 后两个岗位为 `pending`、`clickCount=0`；
- 固定消息标签只有两条 HR 主动招呼会话，没有目标岗位或目标公司的沟通记录；
- 本轮没有登录失效、风控、标签丢失或窗口漂移。

当前代码：

- 在允许点击前把条目持久化为 `click_dispatched`，确保进程崩溃后不会重复点击；
- 页面脚本调用 `element.click()` 并返回 `{clicked:true}`；
- 该返回值只证明 JavaScript 调用了 DOM 点击，不证明 BOSS 建联请求发生；
- 页面内观察器只看到白名单请求时才能判断接受、拒绝或网络失败；
- 本次及 2026-08-11 的一次真实失败都没有匹配请求；2026-08-11 另一个岗位使用相同
  DOM 点击成功；
- 点击后的中间弹层和页面状态没有持久化，搜索标签恢复后无法事后区分“动作未触发”
  和“平台要求额外操作”。

因此可以确认的产品根因是：**派发状态机把页面内 DOM 点击调用当成一次派发，但
真正决定建联结果的浏览器输入、网络请求和点击后页面分支没有形成稳定、可诊断的
证据链。**

## 3. 方案比较

### 方案 A：只改文案并继续使用 DOM `.click()`

改动最少，但第三次真实运行仍可能再次出现相同 `no_matching_request`，无法解除
当前产品阻塞。拒绝。

### 方案 B：复用现有浏览器能力补齐证据链

页面脚本只做最终身份和坐标核验；Edge Control 执行一次浏览器级坐标点击，并在点击
前后读取严格白名单网络日志和脱敏页面快照。保留歧义即停和人工确认。采用。

### 方案 C：将沟通改为接口直调或新增第三个专用标签

接口直调会改变平台交互路径和风控边界；第三个标签违反固定双标签约束。拒绝。

## 4. 模型设置设计

### 4.1 页面结构

“共享厂商和 API Key”模块内始终包含：

- 共享模型厂商；
- 共享 API Key；
- 共享连接状态；
- `测试连接并保存` 主按钮；
- DeepSeek 开放平台链接；
- `下一步：填写简历` 引导。

用户填完共享厂商和 API Key 后，无需滚动到任务卡片。

“下一步：填写简历”始终渲染：

- 未验证时使用灰色禁用样式、`aria-disabled="true"` 和不可聚焦状态；
- 共享连接验证成功后变为可用主引导；
- 不使用只靠颜色表达状态，旁边保留“请先测试连接”的文字。

### 4.2 保存和测试语义

顶部只保留一个共享 `测试连接并保存` 动作。一次提交：

1. 读取共享厂商和 API Key；
2. 使用当前已保存的深度分析和批量筛选模型配置分别执行连接检查；
3. 两项都通过后，原子保存共享凭据和两项连接状态；
4. 任一失败时不写入部分成功状态，页面指出失败的任务配置；
5. API Key 继续只写入 Windows 加密密钥文件，不进入 HTML、日志、SQLite 或设置 JSON。

任务卡片不再各自提供“测试连接并保存”：

- 默认推荐参数无需额外保存；
- 用户修改任务模型参数时，卡片只提供“保存模型参数”；
- 保存参数会把共享连接标记为待重新验证；
- 用户回到顶部执行一次共享测试即可重新启用下一步。

备用模型仍是独立凭据和独立连接，不纳入共享按钮。

## 5. 关键词展示设计

### 5.1 执行规则不变

- Search Plan 可以保留 14 个候选词；
- workflow planner 继续按优先级、历史使用和预期收益选择本轮 3 个；
- 不把每轮关键词改成 6 个；
- 不降低 Search Plan 候选词上限；
- 不改变 BOSS 页面访问预算和风控节奏。

### 5.2 页面来源修正

workflow view model 的“本轮关键词”必须读取当前 workflow 的不可变
`workflow.keywords`，而不是 `planner.keywordSource.keywords`。

技术明细可以另行显示：

- `本轮实际关键词：3 个`；
- `方案候选词：14 个`，默认不展开完整长串。

页面不得再把候选词库描述为已经执行的关键词。

## 6. 本轮概览进度设计

本轮概览在现有字段基础上增加两个首层指标：

1. **采集进度**
   - 示例：`搜索目标 2 / 3 · 已获取 45 个岗位`
   - 数据源：`progress.scanTargets` 和 `progress.details.collected`
2. **完整 JD**
   - 示例：`已读取 38 / 45 · 待补 7`
   - 数据源：`progress.details`

要求：

- 两个字段在抓取过程中随现有 2.5 秒轮询更新；
- 页面状态不变时也必须更新；
- 窄屏不横向溢出；
- “剩余工作”继续显示面向行动的聚合说明；
- 技术明细继续保留搜索目标、详情、分析、超时和最近活动，用于诊断，但不再是用户
  唯一能看到抓取进度的位置。

## 7. 自动沟通派发与诊断设计

### 7.1 不变的安全边界

- 用户确认不可变岗位清单后才允许执行；
- 固定搜索标签负责岗位详情，固定消息标签保持 `/web/geek/chat`；
- 单标签串行，一次只处理一个岗位；
- 每个条目最多一次外部点击；
- 登录、风控、目标错位、标签丢失立即停止；
- 点击结果不明确时不自动补点；
- 当前批次 #1 不自动解决、不恢复。

### 7.2 点击前

1. 继续核验 URL、岗位 ID、标题、公司、招聘状态和唯一“立即沟通”按钮；
2. 页面脚本只返回按钮中心坐标和脱敏身份，不执行 `.click()`；
3. 在固定搜索标签启动 Edge Control 网络日志：
   - 只匹配聊天配置和建联请求路径；
   - 限制条目数、响应体数量和单体字节；
   - 原始 URL、`securityId`、聊天身份和响应正文不得持久化；
4. 再次用 `elementFromPoint()` 确认坐标下仍是同一按钮；
5. 保持点击前写入 `click_dispatched`，防止点击后进程崩溃造成自动重放。

### 7.3 点击和结果

使用已有 `browser.clickAt(tabId, {x, y})` 发送一次
`Input.dispatchMouseEvent` 鼠标序列，不调用 DOM `.click()`。

点击后同时读取：

- 白名单网络日志的 endpoint kind、HTTP 状态、脱敏业务码和耗时；
- 按钮是否变为“继续沟通”及 `data-isfriend`；
- 成功提示或内嵌聊天状态；
- 是否出现需要用户处理的可见中间弹层；
- 当前岗位身份是否仍一致。

结果规则：

- 建联请求成功且页面/聊天证据一致：`succeeded`；
- 白名单请求明确拒绝：`platform_rejected`；
- 白名单请求网络失败：`transport_failed`；
- 没有匹配请求且页面没有变化：条目仍进入 `ambiguous`，错误码改为
  `COMMUNICATION_ACTION_NOT_TRIGGERED`；
- 出现非成功中间弹层：条目仍进入 `ambiguous`，错误码改为
  `COMMUNICATION_USER_ACTION_REQUIRED`，只保存脱敏弹层类别；
- 请求和页面证据冲突：保留 `COMMUNICATION_RESULT_AMBIGUOUS`；
- 所有非明确成功路径都不自动重试。

网络日志在每个条目结束时停止并清理；搜索标签随后恢复原 URL 和滚动位置。

### 7.4 当前批次处置

代码修复前保持批次 #1 原样。修复通过后，用户可在沟通中心把第 1 项标记为停止，
依据为：

> 消息页无对应岗位会话，结果观察器未捕获建联请求，无法确认已沟通；为避免重复操作停止该岗位。

该操作只处理本地状态，不得再次点击第 1 个岗位。剩余两个岗位是否继续，必须在
新实现完成离线验证后由用户重新确认。

## 8. 测试与验收

### 8.1 离线回归

模型设置：

- 未验证时下一步入口存在但禁用；
- 顶部共享按钮可见且任务卡没有重复测试按钮；
- 一次共享测试两项均通过时原子保存；
- 任一任务检查失败时不产生部分验证状态；
- 修改任务参数后共享连接失效；
- API Key 不出现在页面、日志、SQLite 和设置 JSON。

关键词：

- Search Plan 14 个候选词保留；
- workflow 3 个冻结词完整展示；
- 页面不把 14 个候选词渲染成“本轮关键词”。

进度：

- 本轮概览包含采集进度和完整 JD；
- 同状态轮询更新两个字段；
- 技术明细仍保留诊断数据。

沟通：

- 最终页面守卫只返回坐标，不调用 DOM `.click()`；
- 网络日志先于 `clickAt()` 启动；
- 只执行一次 `clickAt()`；
- 成功、平台拒绝、网络失败、动作未触发、中间弹层和证据冲突分别落入预期状态；
- 任一歧义路径不执行第二次点击；
- 网络证据持久化前完成脱敏；
- 固定消息标签不导航，固定搜索标签最终恢复。

运行聚焦测试后执行完整离线套件和多视口 UI 验收。

### 8.2 真实页面

实现阶段不运行新岗位抓取，不恢复当前沟通批次，不发送消息。

完整离线门通过后：

1. 先只读核验固定双标签、登录、风控和一个候选岗位按钮；
2. 真实点击仍需用户对该单岗位再次明确授权；
3. 只执行一个不可变岗位；
4. 核对脱敏网络结果、按钮状态和消息会话；
5. 任一不一致立即停止。
