# RoleFlow 可恢复任务进度与双模型配置设计

**日期：** 2026-08-06
**状态：** 已确认
**关联问题：** `docs/runtime_flow_review.md` 中的 P-002、P-028、P-048、P-051
**依赖设计：** `2026-08-05-portable-standalone-workflow-design.md`、`2026-08-05-startup-login-readiness-design.md`

## 1. 背景与实测证据

2026-08-06 使用全新绿色副本完成首次用户流程，并在项目专用 Edge 中启动第一轮继承模式。

本轮真实状态：

- 工作流 ID：`63693e1b-ec39-4281-a955-3ab6623c0ed2`
- 扫描批次：`1`
- 搜索关键词：`AI应用开发`、`RAG`、`Agent开发`
- 采集岗位：127 个
- 完整 JD：120 个
- 因详情预算待补读：7 个
- 批量分析模型：`deepseek-v4-flash`
- 批量分析并发：1

网页采集完成后，工作流进入 `analyzing`。约 34 分钟内，约 20 个岗位结束一次完整的岗位级分析尝试：

- 4 个完成完整 `matchJob` 管线；
- 16 个以 `MODEL_TIMEOUT` 失败；
- 扫描子进程、租约和心跳在此期间保持正常；
- 工作台始终显示“正在用模型分析岗位”，没有已处理数量、失败数量、最近活动或预计剩余时间；
- 数据库中的 `analyzed` 和 `saved` 始终为 0。

根因位于当前整批处理边界：

1. `mapWithConcurrency()` 等全部岗位返回后才结束；
2. 所有分析结果先保存在进程内存中的 `analyzedJobs` 数组；
3. 只有整个数组完成后才统一执行 `upsertJob()`；
4. 用户停止任务或进程异常退出时，已经成功但尚未统一落库的结果一起丢失。

因此，当前问题不是单纯缺少一个进度条，而是任务状态、结果保存、错误恢复和页面反馈使用了错误的整批边界。

## 2. 目标

本次设计需要同时实现以下目标：

1. 每个岗位分析完成后立即持久化，整批未结束也不会丢失成功结果。
2. 工作台展示来自数据库的真实进度，不依赖内存计数或手动刷新。
3. 支持安全暂停、继续和结束本轮。
4. 单个岗位在一个恢复周期内发生可重试超时时自动重试一次。
5. 当前恢复周期累计 10 个岗位在重试后仍最终超时时，自动暂停。
6. 用户通过模型连接测试并恢复本轮后，创建新的恢复周期；先处理上一周期的最终超时岗位，再继续未尝试岗位。
7. 深度分析与批量筛选使用两套独立任务参数。
8. 普通用户默认共用模型厂商和 API Key；高级设置允许拆分厂商、Key 和备用模型。
9. 展示基于真实吞吐的剩余时间区间；样本不足时明确显示“正在估算”。
10. 不提高 BOSS 网页访问并发，不削减岗位采集覆盖率或推荐质量目标。

## 3. 非目标

本次不处理以下内容：

- 不制作图形化安装启动器；
- 不重做首次使用向导；
- 不拆分粘贴简历的多模块输入框；
- 不重做匹配偏好卡的信息架构；
- 不重做继承模式执行前的关键词确认页；
- 不改变每日目标、轮次数量、网页预算和沟通配额；
- 不自动开始 BOSS 扫描或沟通；
- 不提高 BOSS 导航、列表滚动、右栏详情读取或沟通点击的并发；
- 不把分析进程拆成新的常驻后台服务；
- 不因提高速度而减少完整 JD、双侧证据或现有语义契约。

这些问题继续保留在后续首次体验与界面改造范围中。

## 4. 已确认的产品决策

### 4.1 超时与自动暂停

- 单个岗位在一个恢复周期内第一次发生可重试错误后，最多自动重试一次。
- 只有同一个岗位在该周期的第二次尝试后仍以 `MODEL_TIMEOUT` 结束，才计入当前周期的“最终超时岗位”。
- 同一个岗位在一个恢复周期内最多计数一次。
- 当前恢复周期累计 10 个最终超时岗位后，停止领取新岗位并安全暂停。
- 第一次超时后重试成功的岗位不计入 10 个最终超时。
- 鉴权失败、配置无效等不可重试错误不消耗重试次数，直接触发对应的配置暂停原因。
- 自动暂停后不会自行清空熔断状态或继续运行。用户必须先让当前批量模型或新配置通过一次连接测试，再主动继续本轮。
- 继续本轮会创建新的恢复周期并把上一周期的最终超时岗位重新放入优先队列。每个周期仍最多两次岗位级尝试；完整历史尝试次数继续保留，不会因新周期而覆盖。

### 4.2 模型厂商与 Key

- 普通设置默认共用一个厂商和一个经验证的 API Key。
- 深度分析与批量筛选分别保存模型名、思考模式、思考强度、超时和并发。
- 高级设置允许两套任务使用不同厂商和不同 Key。
- 高级设置允许配置一个经过连接测试的批量备用模型。
- 默认不启用备用模型，不允许系统静默切换。

### 4.3 备用模型

第一版备用模型只参与单岗自动重试：

- 备用模型关闭时，第二次尝试继续使用主批量模型。
- 备用模型开启时，第一次 `MODEL_TIMEOUT` 后的第二次尝试使用备用模型。
- 备用模型不会在成功一次后静默替换整批主模型。
- 每个岗位保存实际使用的模型和配置版本。
- 数据面板明确展示当前请求使用主模型还是备用模型。
- 主模型和备用模型都失败的岗位按最终错误进入失败或暂停统计。

### 4.4 暂停与结束

界面同时提供：

- 主操作：`暂停本轮`
- 次要危险操作：`结束本轮…`

暂停可恢复，结束不可恢复。

暂停和恢复始终属于同一轮，不增加当天轮次数。

结束本轮的计数规则：

- 如果尚未发生任何 BOSS 页面访问，不占用当天轮次；
- 如果已经导航、滚动、读取岗位卡或读取详情，则占用当天轮次；
- 已消耗的 BOSS 安全预算不会因结束本轮而返还；
- 结束前的二次确认必须明确展示是否占用轮次。

### 4.5 进度页

用户确认采用“数据面板”布局。默认展示：

- 当前阶段；
- 采集岗位数；
- 完整 JD 数与待补读数；
- 完成分析数；
- 成功并已保存数；
- 自动重试中数量；
- 最终超时数量与暂停阈值；
- 尚未尝试数量；
- 最近活动时间；
- 最近几条脱敏活动；
- 预计剩余时间区间；
- 暂停和结束操作。

页面自动局部更新，不要求用户手动刷新。

## 5. 总体架构

继续使用现有 Dashboard 和扫描子进程，不新增常驻服务。

```text
Dashboard
  -> 创建 workflow_run
  -> 创建或恢复 scan child process
  -> 读取数据库中的聚合进度
  -> 接收 pause / resume / stop 控制

Scan child process
  -> 读取已冻结的 BOSS 范围与关键词
  -> 完成网页采集和详情 checkpoint
  -> 为每个待分析岗位创建 workflow_job_task
  -> 从数据库领取一个岗位
  -> 调用主模型或备用模型
  -> 在同一事务内保存分析结果、尝试记录和任务终态
  -> 再领取下一个岗位

SQLite
  -> workflow_runs：本轮阶段、控制状态和聚合快照
  -> workflow_job_tasks：每个岗位的可恢复任务状态
  -> job_analysis_attempts：每次岗位级尝试的脱敏指标
  -> job_observations：最终岗位事实与分析结果
```

数据库是进度与恢复的唯一权威。Dashboard 内存中的 `scanRuns` 只用于持有当前子进程句柄和短期输出尾部，不再作为进度事实来源。

## 6. 工作流状态与控制状态

### 6.1 工作流状态

在现有工作流状态中新增 `paused`：

| 状态 | 含义 |
| --- | --- |
| `created` | 本轮已创建，尚未开始采集 |
| `scanning` | 正在操作 BOSS 并保存采集 checkpoint |
| `analyzing` | 正在处理本地已保存 JD |
| `paused` | 已安全暂停，可以继续或结束 |
| `review_required` | 分析完成，等待用户确认沟通清单 |
| `communicating` | 正在执行已经确认的沟通批次 |
| `completed` | 本轮已完成 |
| `interrupted` | 进程或环境异常，需要恢复判断 |
| `failed` | 不可恢复失败 |
| `stopped` | 用户明确结束本轮 |

本次暂停机制只覆盖扫描和岗位分析。沟通阶段继续遵循现有独立的批次暂停与歧义处理边界。

### 6.2 控制状态

`workflow_runs` 增加独立控制状态：

| `control_state` | 含义 |
| --- | --- |
| `none` | 没有待执行控制 |
| `pause_requested` | 停止领取新工作，完成当前安全单元后暂停 |
| `stop_requested` | 停止领取新工作，保存后进入 `stopped` |

控制请求与阶段状态分开，避免点击暂停后立刻把仍有请求在收尾的进程伪装成已经暂停。

### 6.3 安全单元

不同阶段的安全暂停边界：

- BOSS 扫描：当前一次导航、卡片切换或详情读取完成并 checkpoint 后；
- 模型分析：当前一个岗位级尝试成功、失败或超时并落库后；
- 报告生成：当前数据库事务完成后。

收到控制请求后不再领取新安全单元。

### 6.4 恢复阶段

`workflow_runs.resume_phase` 保存暂停前阶段：

- `scanning`
- `analyzing`

继续本轮时返回该阶段。分析恢复顺序固定为：

1. 上一恢复周期最终超时、并在用户恢复后重新进入 `retry_pending` 的任务
2. 当前恢复周期的其他 `retry_pending`
3. 因异常退出遗留并恢复的任务
4. `pending`

已经 `succeeded` 的岗位永远不重做，除非用户未来通过独立功能明确要求重新分析。

用户继续自动暂停的工作流前，必须满足以下条件：

1. 当前选择的批量模型配置已经在暂停后重新通过连接测试；
2. 服务端增加 `recovery_generation`；
3. 当前周期的熔断计数归零，但本轮累计最终超时历史继续保留；
4. 上一周期因最终超时进入 `failed` 的任务转为新周期的 `retry_pending`；
5. 不可重试的鉴权、配置或输入错误不会因此转回待处理。

## 7. 岗位任务数据模型

### 7.1 `workflow_job_tasks`

每个工作流与岗位组合只有一行：

```text
id
workflow_run_id
job_id
observation_id
status
recovery_generation
attempt_count_in_generation
total_attempt_count
last_attempt_model_revision
last_error_code
last_error_stage
total_latency_ms
lease_owner
leased_at
started_at
finished_at
created_at
updated_at
```

唯一约束：

```text
UNIQUE(workflow_run_id, job_id)
```

允许的状态：

| 状态 | 含义 |
| --- | --- |
| `pending` | 尚未尝试 |
| `running` | 已被当前 worker 领取 |
| `retry_pending` | 首次可重试错误，等待第二次尝试 |
| `succeeded` | 分析成功并已写入 observation |
| `failed` | 已用尽重试或发生不可重试岗位级错误 |
| `skipped` | 本地硬边界或详情不足，不需要模型分析 |

`skipped` 不是模型失败。它仍需保存明确的规则结论或待补读状态。

### 7.2 `job_analysis_attempts`

每次岗位级尝试保存一行脱敏记录：

```text
id
task_id
attempt_number
recovery_generation
profile_kind
provider
model
model_config_revision
thinking_mode
reasoning_effort
backup_used
status
model_call_count
prompt_tokens
completion_tokens
total_tokens
latency_ms
error_code
error_stage
started_at
finished_at
```

不得保存：

- API Key；
- 完整简历；
- 完整 JD；
- 完整提示词；
- 模型原始输出；
- Cookie、Token 或账号信息。

### 7.3 原子保存

一个岗位成功后，必须在同一数据库事务中完成：

1. 更新 `job_observations.analysis_json`、分数、风险和推荐结果；
2. 写入 `job_analysis_attempts`；
3. 将 `workflow_job_tasks.status` 更新为 `succeeded`；
4. 增加 `workflow_runs.progress_revision`；
5. 更新 `workflow_runs.last_activity_at`。

任一步失败则整个事务回滚，任务保持可重试状态，不能出现“任务显示成功但岗位结果不存在”。

失败尝试同样需要原子保存尝试记录、任务状态、错误码和进度版本。

## 8. 执行器

### 8.1 领取任务

岗位分析不再把整批任务装入一个等待统一保存的数组。

worker 循环执行：

1. 检查 `control_state`；
2. 按恢复优先级查询一个可领取任务；
3. 使用事务把任务从 `pending/retry_pending` 更新为 `running`；
4. 执行岗位分析；
5. 立即提交成功或失败；
6. 继续领取下一项。

并发 2 时运行两个 worker 循环。数据库领取必须保证同一任务不会被两个 worker 同时处理。

### 8.2 可重试错误

以下错误在每个恢复周期内允许一次岗位级自动重试：

- `MODEL_TIMEOUT`
- 明确的网络连接中断
- HTTP `429`
- HTTP `5xx`
- 提供商声明的临时不可用

以下错误不做岗位级盲目重试：

- API Key 缺失或鉴权失败；
- 模型名无效；
- Base URL 配置无效；
- 用户取消；
- 本地输入或模型配置契约无效。

模型输出契约修复继续属于单次模型调用内部行为，不额外增加岗位级尝试次数。

同一个恢复周期内，一个岗位最多执行两次岗位级尝试。只有用户在自动暂停后完成模型连接测试并明确继续，才会创建下一恢复周期；系统不能自动循环创建新周期。

### 8.3 超时熔断

每个在当前恢复周期最终以 `MODEL_TIMEOUT` 失败的唯一岗位使 `circuit_timeout_job_count` 增加 1。本轮全生命周期的 `lifetime_timeout_job_count` 同时累加，但不用于刚恢复后的即时熔断。

达到 10 时：

1. 将 `control_state` 设为 `pause_requested`；
2. 不再领取新岗位；
3. 等正在运行的最多两个岗位完成当前尝试并落库；
4. 工作流进入 `paused`；
5. 暂停原因为 `MODEL_TIMEOUT_CIRCUIT_OPEN`；
6. 页面提供“测试模型连接”“调整批量模型”“继续本轮”和“结束本轮”。

如果其他不可用错误表明模型配置整体失效，可以在未达到 10 个超时前使用更具体的暂停原因停止，例如 `MODEL_AUTH_REQUIRED`。

用户成功测试模型并继续后：

- `recovery_generation` 增加 1；
- `circuit_timeout_job_count` 归零；
- `lifetime_timeout_job_count` 保留；
- 上一周期最终超时的任务优先进入新周期；
- 新周期再次达到 10 个最终超时岗位时重新自动暂停。

### 8.4 进程异常退出

恢复检查发现：

- 扫描子进程不存在或心跳过期；
- `workflow_job_tasks.status = running`；
- 任务租约已超时；

则把这些任务恢复为：

- `retry_pending`，如果尚有岗位级重试额度；
- `failed`，如果重试额度已用尽。

成功任务不变。工作流进入 `interrupted`，由用户确认继续后重新启动子进程。

### 8.5 暂停

`POST /api/workflow-control` 接收：

```text
action=pause
workflowRunId=<id>
```

重复请求必须幂等。

暂停期间：

- 不领取新岗位；
- 当前模型请求按原超时规则收尾；
- 不强杀子进程；
- 保存当前阶段和进度；
- 安全单元全部结束后释放租约并进入 `paused`。

### 8.6 结束

`action=stop` 需要二次确认页面提交。

服务端必须返回并展示：

- 已采集岗位；
- 已完成分析；
- 失败和未完成数量；
- 已消耗网页预算；
- 是否占用当天轮次。

确认后：

- 设置 `stop_requested`；
- 安全保存；
- 释放扫描租约；
- 工作流进入 `stopped`；
- 不再允许继续；
- 已采集岗位和已完成分析继续保留。

如果子进程未能在当前安全单元的最大超时后退出，Dashboard 可以终止精确匹配该 runId 的子进程，但数据库控制状态和已保存结果仍是权威。

- 岗位任务编号；
- 成功保存；
- 首次超时；
- 开始第二次尝试；
- 最终失败；
- 自动暂停；
- 模型配置版本切换。

## 10. 数据面板

页面每 2～3 秒轮询一次本地进度接口。

选择轮询而不是 WebSocket 或 SSE 的原因：

- 现有页面已经使用轻量轮询；
- 本地单用户场景不需要长连接复杂度；
- 页面刷新和 Dashboard 重启后能自然恢复；
- 可以使用 `progressRevision` 避免没有变化时重绘。

页面行为：

1. 首次加载直接渲染数据库快照；
2. `progressRevision` 变化时更新阶段、数字、活动和控制按钮；
3. 不整页刷新；
4. 接口暂时不可用时显示“无法读取任务状态”，按钮进入安全禁用；
5. `lastActivityAt` 超过运行健康阈值时显示“任务可能失去活动”，不能继续显示普通运行文案；
6. 状态进入 `paused/review_required/interrupted/failed/stopped/completed` 时立即切换对应操作区。

### 10.1 耗时估计

耗时估计只用于岗位分析阶段。

- 完成样本少于 3 个时显示“正在估算”；
- 使用最近最多 10 个终态岗位的真实完成间隔估算吞吐；
- 缓存命中和真实模型调用都按实际完成速度计入，因为用户关心墙钟时间；
- 根据近期完成间隔的波动给出区间，不显示单点精确值；
- 将 `retry_pending` 和当前重试比例纳入上界；
- 模型配置版本改变后重新积累该配置的估算样本；
- 暂停期间不倒计时；
- 页面明确显示样本数，例如“基于最近 10 个完成岗位估算”。

## 11. 双模型配置

### 11.1 任务配置

新增两个任务配置：

| 配置 | 用途 |
| --- | --- |
| `deep_analysis` | 简历解析、候选人画像、搜索建议、匹配偏好卡和用户主动生成的沟通内容 |
| `batch_screening` | 岗位理解、岗位与简历批量匹配 |

### 11.2 新用户推荐参考值

深度分析：

- 模型：`deepseek-v4-pro`
- 思考模式：开启
- 思考强度：`high`
- 并发：1
- 超时：120 秒

批量筛选：

- 模型：`deepseek-v4-flash`
- 思考模式：关闭
- 并发：2
- 超时：90 秒

这些是可恢复的推荐参考值，不是不可修改的硬编码限制。

设置页始终显示：

- 当前值；
- 推荐参考值；
- 当前值是否偏离推荐；
- `恢复推荐值` 操作。

### 11.3 兼容现有用户

数据库或设置迁移不得静默改变现有模型行为：

- 当前已验证厂商和 Key 迁移为共享凭据；
- 两套任务配置初始都复制现有模型参数；
- 页面提示用户存在新的任务配置，并展示推荐参考值；
- 只有用户点击“恢复推荐值”或明确修改后，才切换到新的 Pro/Flash 推荐组合；
- 新安装且没有历史设置时直接使用推荐组合。

### 11.4 配置版本

每次成功保存并测试模型设置后生成不可变的 `model_config_revision`。

创建本轮时保存两套任务配置快照。

暂停期间修改配置并继续：

- 已成功岗位保留原模型结果；
- 未完成岗位使用新配置版本；
- 每次尝试记录实际版本；
- 缓存继续把模型、思考模式、推理强度和管线版本纳入身份；
- 页面按配置版本重新计算耗时估计。

## 12. API 与权限边界

新增：

```text
POST /api/workflow-control
```

支持：

- `pause`
- `resume`
- `stop`

服务端必须重新验证：

- workflow 是否存在；
- 当前状态是否允许该操作；
- runId 与活动扫描进程是否一致；
- 恢复时模型配置是否已验证；
- 继承模式恢复时保存的浏览器权威是否完整；
- BOSS 风控和互斥租约是否允许恢复网页阶段。

分析阶段恢复只使用已保存 JD，不访问 BOSS，因此不要求 BOSS 页面保持原岗位或重新导航。

停止和暂停只影响指定 workflow run，不允许按端口、进程名或站点广泛终止其他任务。

## 13. BOSS 安全边界

- 网页采集继续单标签串行。
- 批量岗位模型并发只发生在 JD 已经保存到本地以后。
- 增加模型并发不得同时增加 BOSS 页面并发。
- 暂停扫描时只在当前平台安全单元结束后停止，不连续点击、不重复导航。
- 恢复分析阶段不重新访问 BOSS。
- 登录失效、风控、页面丢失和身份错位仍立即停止网页操作。
- 已确认沟通清单和“开始沟通”的双重授权不变。

## 14. 数据迁移

迁移需要：

1. 为 `workflow_runs` 增加 `paused` 状态支持、控制字段、恢复阶段、最后活动和进度版本；
2. 新建 `workflow_job_tasks`；
3. 新建 `job_analysis_attempts`；
4. 为查询活动任务和恢复队列增加索引；
5. 保留所有现有岗位、observation、模型缓存、画像、简历、Search Plan 和沟通记录。

旧的活动工作流迁移规则：

- `scanning/analyzing` 且进程健康：保持现状，由新执行器接管前必须完成一次兼容检查；
- 进程不存在或心跳过期：转为 `interrupted`；
- 已有 batch observation 但没有 task 行：根据 observation 的分析状态补建 `succeeded/skipped/pending` 任务；
- 不把旧规则结果伪装成新模型成功；
- 不删除历史批次。

迁移必须在临时副本和真实数据库备份上分别验证完整性。

## 15. 测试策略

### 15.1 存储与状态机

覆盖：

- 任务唯一约束；
- 原子成功保存；
- 原子失败保存；
- `pending -> running -> succeeded`；
- `running -> retry_pending -> running -> succeeded`；
- `running -> retry_pending -> running -> failed`；
- 暂停、恢复和结束的合法/非法转换；
- 重复控制请求幂等；
- 异常退出后的 running 任务恢复；
- 已成功岗位不重复分析。

### 15.2 超时与熔断

使用 fake model 注入：

- 首次超时、第二次成功；
- 同一岗位在一个恢复周期内两次超时；
- 当前恢复周期内 9 个最终超时不暂停；
- 当前恢复周期的第 10 个最终超时触发安全暂停；
- 未经用户恢复不能自动创建新恢复周期；
- 连接测试通过并恢复后，新周期优先重试上一周期的最终超时岗位；
- 新周期计数归零，但全生命周期超时历史保留；
- 备用模型关闭时使用主模型重试；
- 备用模型开启时第二次尝试使用备用模型；
- 鉴权失败直接配置暂停；
- HTTP `429` 遵循可重试与冷却；
- 契约修复不错误增加岗位级尝试次数。

### 15.3 进度与耗时

验证：

- 每个岗位结束后 `progressRevision` 增加；
- API 数量与数据库任务状态一致；
- 页面无需整页刷新；
- 样本少于 3 个不显示预计时间；
- 达到样本门槛后显示区间；
- 暂停后 ETA 停止变化；
- 配置版本改变后重新估算；
- 状态接口失败时页面不伪装成任务继续运行。

### 15.4 双模型设置

验证：

- 新用户推荐值；
- 现有用户迁移不静默改模型；
- 两套配置共用 Key；
- 高级模式独立厂商和 Key；
- 推荐值恢复；
- 配置保存前连接测试；
- 备用模型必须先验证；
- 实际请求携带对应任务的思考模式和推理强度；
- 缓存身份包含配置版本所代表的推理参数。

### 15.5 停止与轮次

验证：

- 平台访问前结束不占轮次；
- 平台访问后结束占轮次；
- 暂停/恢复不重复占轮次；
- 已消耗网页预算不返还；
- 结束后不能继续；
- 停止只影响目标 runId；
- 租约正常释放。

### 15.6 小批真实验收

离线测试全部通过后：

1. 使用全新隔离数据库；
2. 使用 1 个继承范围和 1～2 个关键词；
3. 最多采集 5～10 个完整 JD；
4. 验证每个岗位完成后数据库立即可见；
5. 验证数据面板数字随完成逐次变化；
6. 人工暂停并继续一次；
7. 注入或使用受控短超时验证一次自动暂停；
8. 不开始 BOSS 沟通；
9. 不直接扩大到 127 个岗位。

只有小批真实验收稳定后，才讨论更大的正式批次。

## 16. 实施顺序

1. 数据库迁移、任务表和状态转换；
2. 单岗位原子保存和可恢复 worker 循环；
3. 暂停、继续、结束和租约释放；
4. 超时重试、熔断和异常退出恢复；
5. 进度接口与耗时估计；
6. 数据面板；
7. 双模型设置、推荐值和高级备用模型；
8. 离线故障回归；
9. 数据库迁移验证；
10. 5～10 岗位真实验收。

## 17. 备选方案与取舍

### 17.1 仅增加内存计数

拒绝。它能让页面数字变化，但不能解决用户停止或进程退出时丢失成功结果。

### 17.2 保留整批数组，只定期复制进度

拒绝。进度和真实结果会形成两个事实来源，恢复时仍难以判断哪些岗位已安全完成。

### 17.3 独立常驻任务服务

暂不采用。它扩展能力更强，但会增加安装、启动、升级和排障成本，不符合当前单机绿色项目的复杂度。

### 17.4 WebSocket 或 SSE

暂不采用。现有本地轮询足以支撑 2～3 秒级进度，且重启和页面刷新恢复更简单。

### 17.5 自动永久切换备用模型

拒绝。不同模型可能带来成本和推荐行为变化。第一版备用模型只用于明确可见的单岗第二次尝试。

## 18. 验收标准

本设计完成的最低门槛：

1. 任意时刻终止分析子进程，所有已成功岗位仍已落库；
2. 页面显示的成功、失败、重试和剩余数量与数据库一致；
3. 单岗在每个恢复周期内最多两次岗位级尝试，系统不能自动创建无限恢复周期；
4. 当前恢复周期的第 10 个最终超时岗位触发自动暂停；
5. 恢复先处理超时岗位；
6. 暂停、继续和结束均可从页面完成；
7. 结束正常释放租约；
8. 新用户能够看到 Pro/Flash 明确选项和两套推荐值；
9. 现有用户升级后模型配置不会被静默改写；
10. 5～10 个真实岗位验收中，进度逐岗变化且无成功结果丢失；
11. BOSS 网页访问保持单标签串行；
12. 不降低 JD 覆盖、匹配证据和推荐质量门槛。
