# RoleFlow 渐进式模块化重构总设计

日期：2026-08-10

状态：已批准进入分阶段实施

基线提交：`e36bee8`（`merge: restore BOSS search pane detail reads`）

## 1. 结论

RoleFlow 保持一个本地 Node.js 应用和一个 SQLite 数据库，不改写为微服务，也不在本轮引入 React、Vue、Express、ORM 或依赖注入框架。

重构采用“模块化单体 + 随功能迁移”：

1. 先固定产品质量、安全和恢复语义。
2. 把展示、应用编排、领域规则和外部适配器之间的依赖方向写清楚。
3. 优先改善用户每天直接使用的仪表盘。
4. 用影子积分卡验证岗位分析改造，不直接替换现有推荐结果。
5. 把自动沟通的技术校准和人工端到端验收拆成不同状态。
6. 只在 BOSS 主流程稳定后建立多平台通用骨架。
7. `server.js`、`storage.js`、`cli.js` 和 `boss.js` 不做一次性大拆分；每个阶段只迁移本阶段触碰的职责。

| 文件 | 当前职责 |
|---|---|

## 3. 目标依赖方向

```text
展示层 dashboard
      |
      v
应用用例 application
      |
      v
领域规则 core

应用用例 --> 存储/模型/浏览器/平台端口
适配器 adapters --> 实现端口
```

### 3.1 展示层

负责：

- HTTP 请求和响应。
- 表单字段解析及用户可理解的错误展示。
- 页面、组件、样式和小型浏览器脚本。
- 把应用层返回的状态转换为界面。

不负责：

- 直接拼装扫描或沟通子进程参数。
- 直接判断推荐档位。
- 直接读写 BOSS 页面。
- 在页面函数里编写新的 SQL 或业务状态转换。

### 3.2 应用层

新增 `src/application/`，仅在实际迁移用例时创建子目录。

负责：

- “开始本轮”“继续本轮”“暂停本轮”等用户用例。
- 扫描、分析、复核和沟通阶段的顺序。
- 调用存储、模型、浏览器和站点适配器。
- 事务和幂等边界。

第一批只迁移展示层实际需要的工作流查询/命令，不先搭建空框架。

### 3.3 领域层

继续使用 `src/core/`，保持：

- 推荐策略和积分计算为纯确定性逻辑。
- 工作流状态转换有明确合法边界。
- 候选人、岗位和批次状态不依赖 HTTP、DOM 或浏览器。
- 模型负责语义提取，代码负责算术、门槛、上限和工作流选择。

### 3.4 适配器层

继续使用 `src/adapters/`：

- `models/` 实现模型调用。
- `browser/` 实现浏览器传输。
- `sites/` 实现平台页面能力。
- 后续 SQLite 存储适配器在真正拆分 `storage.js` 时再建立，不提前创建空仓库接口。

## 4. 前端目标

### 4.1 技术选择

- 保留 Node `http` 和服务端渲染。
- 不引入 SPA 框架。
- 样式改为项目内静态 CSS 文件和语义化设计变量。
- 前端交互继续使用少量原生 JavaScript。
- 图标使用项目内 SVG 或纯 CSS，不依赖在线 CDN。

### 4.2 信息结构

主导航统一为：

1. 今日任务
2. 当前岗位
3. 本轮执行
4. 沟通清单
5. 简历与画像
6. 设置与诊断

默认入口必须在十秒内回答：

- 当前处于哪个阶段。
- 当前数据是否安全。
- 阻塞原因是什么。
- 用户现在唯一建议执行的动作是什么。

### 4.3 展示层文件边界

在实际实现中逐步形成：

```text
src/dashboard/
  server.js                 HTTP 服务器和路由组装
  http/                     请求解析、响应和通用错误
  pages/                    按页面职责渲染
  ui/                       页面壳、导航、状态、按钮和表单组件
  assets/                   本地 CSS、SVG 和少量浏览器脚本
```

第一阶段只拆页面壳、全局导航、设计变量和“今日任务”页面。队列、沟通、设置等页面在后续阶段随实际改造迁移。

### 4.4 视觉工作流

前端执行任务必须：

1. 先输出 RoleFlow 专属视觉方向和桌面/窄屏线框。
2. 使用真实中文状态和真实页面信息密度制作原型。
3. 经主控审查后才改生产页面。
4. 使用截图检查 1440、1024、768 和 375 像素宽度。
5. 检查键盘焦点、文字对比度、减少动画偏好和危险操作层级。

`frontend-design` 负责视觉主张，`ui-ux-pro-max` 只用于无障碍、响应式和交互检查，不直接采用它自动生成的通用配色。

## 5. 岗位分析目标

### 5.1 当前事实

当前推荐已经包含积分：

- `matched = 1`
- `transferable = 0.5`
- `missing = 0`
- 核心要求 70%
- 支持要求 30%
- 职责与要求联合分
- 证据覆盖率门槛
- 最后使用方向与加权符合度矩阵分档

已保存的诊断表明，一部分波动来自模型语义状态在 `transferable` 和 `missing` 间变化，而不是本地算术随机。

### 5.2 选定方案

新增“影子积分卡”，但不直接改变生产推荐：

1. 复用已经验证的结构化语义输出。
2. 硬性冲突、证据覆盖率和风险上限保持独立门槛，不能被普通加分抵消。
3. 分别报告职责方向、核心要求、支持要求和约束条件。
4. 计算一个只读影子总分和候选档位。
5. 现有矩阵继续决定正式档位和默认沟通选择。
6. 使用冻结语义输出比较策略敏感度。
7. 使用同一完整 JD 的重复模型分析比较语义稳定度。

只有新鲜基线满足以下条件后，才讨论替换：

- 优质岗位召回不下降。
- 明显不合适岗位进入默认沟通的数量不增加。
- 阈值附近重复运行的跳档减少。
- 每个分数能追溯到 JD 和简历证据。
- 用户批准权重、阈值和替换方案。

### 5.3 数据基线

岗位详情读取规则已经发生实质变化。不得使用变化前的岗位历史验证新积分卡。

比较运行必须：

- 保留候选人画像、简历、Search Plan 和模型设置。
- 建立新的空岗位历史基线。
- 使用新读取的完整 JD。
- 历史数据库只作为恢复证据，不作为新准确率样本。

## 6. 自动沟通目标

自动沟通状态拆为：

| 状态 | 含义 |
|---|---|
| `implemented` | 主要代码路径存在 |
| `calibrated` | 页面结构和受控动作已有校准证据 |
| `e2e_pending` | 尚未完成用户人工端到端验收 |
| `accepted` | 人工端到端验收通过 |
| `disabled` | 主动关闭生产执行 |

当前产品状态定义为：

```text
implemented = true
calibrated = true
acceptance = e2e_pending
```

当前 `executionEnabled: true` 只能表示技术执行门已打开，不能表示用户已经验收整个流程。

人工端到端验收至少覆盖：

1. 从“今日任务”进入待复核岗位。
2. 确认不可变沟通清单。
3. 开始一个小批次。
4. 串行验证岗位身份和动作状态。
5. 核对成功、已经沟通、不可用和结果不明确的展示。
6. 暂停或停止后能够恢复或人工处理。
7. 全程没有额外标签页、并行 BOSS 操作或风险信号。

验收前不扩展自动回复、自动跟进、后台定时执行或其他平台沟通。

## 7. 多平台目标

多平台保持低优先级。目标边界：

- 平台注册表声明列表、详情、模板、筛选、沟通和消息能力。
- 统一岗位只保存通用字段和来源元数据。
- BOSS 专用沟通能力不传播到其他平台。
- 多平台扫描串行执行。
- 每个平台拥有独立访问预算、检查点和错误状态。
- 先用假第二平台完成离线证明，再接入真实智联。
- 真实智联实现前必须取得最小只读页面证据并单独设计。

## 8. 分阶段路线

### 阶段 0：已完成基线

- 岗位详情右栏读取修复已合并。
- 暂停、冷却、增量保存和恢复已合并。
- 75 项离线检查通过。
- 保留人工继续本轮验收门。

### 阶段 1：可并行的低冲突工作

并行执行：

1. 前端视觉系统和“今日任务”高保真原型，不改生产业务逻辑。
2. 岗位影子积分卡和离线比较器，不改正式推荐。
3. 自动沟通验收状态模型和文档一致性，不执行真实沟通。

这三项写入不同文件域，可以并行。

### 阶段 2：前端生产落地

阶段 1 的原型通过主控审查后：

- 抽出页面壳、导航、设计变量和静态资源。
- 重做“今日任务”和“本轮执行”信息层级。
- 保持所有现有 URL、表单字段和 API 行为兼容。
- 浏览器人工验收后再合并。

此阶段独占 `src/dashboard/server.js`，其他修改该文件的工作排队。

### 阶段 3：应用用例抽取

按实际调用链依次抽取：

1. 工作流查询与控制用例。
2. 沟通批次创建与控制用例。
3. 岗位分析重试用例。

每次只抽一个用例，原 URL、CLI 命令、错误码、数据库事务和恢复行为保持不变。

### 阶段 4：存储边界

在应用用例稳定后，把 `storage.js` 按调用群拆成小型存储模块：

- candidate/profile/plan/matching card
- jobs/analysis
- scan/batch/lease
- communication
- workflow/task/attempt

顺序是依赖约束，不是文件偏好：候选人、方案和匹配卡是岗位决策的上游，岗位又被扫描复用和沟通资格判断使用；workflow 连接 scan、job、communication 和 recovery，因此最后拆。

继续使用同一个 SQLite 连接、schema 和迁移入口。`openDb`、migration/backfill、共享 mapper 和统一事务原语先留在 `src/core/storage.js`。旧 `storage.js` 在迁移期间保留为兼容门面，继续导出相同函数名、参数和返回结构；跨表操作保留原子事务，不拆成多个独立 store 提交。

`getWorkflowHealthSnapshot` 先作为跨域读模型保留。communication 的主体状态机目前位于 `src/core/communication_batches.js`，该阶段必须明确完整 owner，不能只移动一个历史回填函数就宣称通信存储已拆分。该阶段不改表结构，不引入 ORM。

### 阶段 5：平台注册表

- 用普通对象/函数建立静态平台注册表和能力声明，不引入插件框架或 DI 容器。
- 未注册平台必须 fail closed，不能回退到 BOSS；能力缺失必须在执行前明确拒绝。
- 用 deterministic fixture 假第二平台验证 list/detail/template-read 边界。假平台不联网、不启动浏览器，并明确拒绝 communication、apply、login 和 live filter discovery。
- 把 BOSS 的“选择与能力检查”迁移到注册表；DOM helper、固定双 tab、随机 pacing/cooldown、预算、checkpoint、right-pane identity 和恢复仍由现有模块负责。
- 默认平台保持 BOSS；注册表不得增加导航、详情读取或安全动作次数。
- 经用户决定真实第二平台并批准一次最小只读探针后，才设计其 selector/filter mapping。假平台不能被表述为真实多平台已接入。

## 9. 并行与合并规则

允许并行：

- 只修改 `src/dashboard/**` 的前端任务，与只修改决策核心/离线基准的任务。
- 只修改沟通状态核心/文档的任务，与岗位积分任务。
- 文档、fixture 和只读审查任务，只要文件不重叠。

禁止并行：

- 两个任务同时修改 `server.js`。
- 两个任务同时修改 `storage.js`。
- 两个任务同时修改 `cli.js`。
- 任何任务与 BOSS 验收同时修改 `boss.js`。
- 任何推荐策略改动与新基线采集同时进行。

每个分支从最新已合并 `main` 创建。第一批并行分支完成后，由主控确定顺序，后合并分支必须先吸收最新 `main` 并重跑验证。

## 10. 质量门

每个实现分支至少满足：

1. 定向回归先失败后通过，或为纯迁移提供行为等价检查。
2. `git diff --check` 通过。
3. 完整离线测试通过。
4. 没有真实 BOSS、真实沟通或真实模型副作用。
5. 没有降低 JD 覆盖、召回、推荐准确性或恢复能力。
6. 没有增加新依赖，除非单独获得批准。
7. 独立代码审查没有遗留重要问题。
8. 合并前建立回溯标签。
9. 合并后从 `main` 再跑完整检查。

前端额外要求：

- 桌面和窄屏截图验收。
- 键盘焦点和文字对比度检查。
- 每页只有一个主要操作。

评分额外要求：

- 正式推荐和默认沟通选择字节级保持不变。
- 新输出只读、可关闭、带策略版本。
- 使用新鲜基线后才允许讨论替换。

沟通额外要求：

- 不执行真实沟通。
- `e2e_pending` 不得展示为“已完整验收”。
- 真实端到端验收必须由用户显式启动。

## 11. 回滚

- 每阶段合并前在 `main` 创建 annotated checkpoint 标签。
- 功能分支和工作区保留到该阶段人工验收完成。
- 前端回滚不迁移数据库。
- 影子积分卡关闭后，正式推荐完全不受影响。
- 沟通验收状态改造失败时恢复现有执行门，但不得伪造 `accepted`。
- 平台注册表改造失败时恢复 BOSS 原入口，不删除 BOSS 专用能力。
