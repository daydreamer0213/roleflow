# 消息发现：文字消息与人工操作通知分流设计

日期：2026-08-25

## 目标与边界

消息发现继续复用现有只读链路，不重做读取器、岗位上下文、候选人事实、语义模型、草稿、进度事件或检查点。新增设计只解决一个缺口：在消息进入语义模型前，先依据真实页面结构区分纯文字消息和需要用户在 BOSS 完成的人工操作通知。

本设计覆盖两条路线：

1. 招聘方纯文字消息：读取本轮新文字，结合本地候选人资料和岗位上下文生成本地草稿，用户自行复制到 BOSS 发送。
2. 结构化人工操作通知：例如索要简历、要求确认公司位置、选择或确认面试时间。系统只告诉用户需要完成什么，不调用文字回复模型、不生成草稿、不点击卡片中的按钮。

任何真实填写、上传、确认、发送、投递或申请仍需针对当前不可变目标取得明确授权。本设计不授权任何外部写入。

## 当前代码证据

现有实现具有应当保留的基础：

- `boss_message_reader` 绑定同一 Edge 窗口的固定消息标签页，串行选择会话，并在选择前后校验标签页、会话身份、风险和登录状态。
- `message_discovery` 只取候选人最后一次发言之后的招聘方消息，限制消息条数和总长度，对已经处理的消息做幂等去重。
- 岗位上下文优先复用完整可信的本地 JD；缺少上下文时才允许使用受控的 `message_discovery_detail` 后台临时详情页。
- 纯文字消息已经通过独立 `messageIntent` 区分正式面试邀约、意向询问、信息请求、信息补充和普通沟通，并在本地契约失败时降级为人工判断。
- 结果页只显示安全投影和本地草稿；原始招聘方消息、草稿及模型原始输出不写入长期进度事件。

当前缺口位于 DOM 快照：

- `messageContentKind` 只明确识别语音、图片和附件，其他消息元素全部默认为 `text`。
- 行预览只依据少量状态元素和预览文字区分已读、送达、平台通知、已知不支持内容和可能的招聘方回复。
- 系统方向的消息目前不会进入文字语义模型；已知的非文字招聘方消息会使本轮发现安全停止。
- 离线夹具没有简历索取、位置确认或面试时间选择卡片，因而目前没有证据支持这些卡片的选择器、方向、字段或状态判断。

用户已说明当前真实消息页存在一个简历投递窗口，但本设计阶段没有重新打开或读取真实 BOSS 页面。该事实说明有合适的后续样本，不等于已经验证其 DOM 结构。

## 方案比较

### 方案 A：在现有快照中增加基于证据的内容形态（采用）

只在获得真实页面 DOM 和脱敏截图证据后，为已验证的卡片增加稳定形态。文字消息继续走现有语义链；已识别人工通知直接生成本地人工操作结果；未知结构安全停止。

该方案改动集中、可验证，并且不会让模型根据展平后的可见文字猜测按钮或卡片含义。

### 方案 B：将卡片可见文字交给语义模型

实现较快，但文本无法证明按钮、选择项、完成状态或发起方。模型可能把操作卡片当成普通沟通，也可能生成实际上无效的回复，因此不采用。

### 方案 C：所有非文字内容统一标记为人工处理

安全但信息价值低，无法告诉用户究竟需要上传简历、确认位置还是选择时间，并且会把语音、图片、附件和交互卡片混为一类，因此不作为目标设计。

## 推荐数据流

### 1. DOM 形态是唯一来源

在现有消息快照中增加一个窄的内容路由结果：

- `text`：经过验证的招聘方纯文字消息；
- `manual_action`：经过真实 DOM 证据确认的人工操作卡片；
- 现有 `voice`、`image`、`attachment`；
- `unknown`：结构不符合任何已验证形态。

`manual_action` 再携带一个有限枚举，例如 `resume_request`、`location_confirmation`、`interview_scheduling`。最终枚举、选择器和可读取字段必须由真实样本确定；在取证前不添加猜测性实现。

行预览只用于决定是否需要打开会话，不能作为人工操作类型的最终证据。最终类型必须来自已选中会话的消息 DOM，并经过会话身份复核。

### 2. 纯文字路线保持不变

仅当本轮待处理内容全部是经过确认的招聘方文字消息时，才调用现有一次深度模型分析，继续复用岗位上下文、候选人事实、`messageIntent`、本地安全契约和草稿生成。

结构化通知的可见文字不得混入文字消息组，也不得作为提示词传给模型。

### 3. 人工操作路线

当本轮出现已识别的 `manual_action`：

- 不调用语义模型；
- 不生成回复草稿；
- 不点击卡片、按钮、时间选项或上传入口；
- 将对应岗位推进或保持在 `needs_user_action`；
- 页面先显示自然结论，例如“招聘方希望你提交简历”，再显示“请前往 BOSS 完成”；
- 只保存卡片类型、岗位/会话安全标识、处理状态和时间，不保存完整 DOM 或原始消息正文；
- 成功写入进度事件和预览检查点后，按现有随机节奏继续串行检查其他会话。

若同一轮同时存在纯文字与人工操作卡片，人工操作路线优先，本轮不生成草稿。真实样本证明可以安全拆分之前，不尝试为混合内容自动生成部分回复。

### 4. 未知与失败处理

- 未知消息结构、无法确认卡片类型、卡片状态含糊或消息方向含糊：停止整轮发现，不提交该会话为已处理，使其可在修复后重新读取。
- 登录失效、风控、页面丢失、固定标签页变化、会话身份漂移：沿用现有立即停止规则。
- 已确认的人工操作通知不是异常；在本地结果和检查点写入成功后继续串行处理。
- 现有语音、图片和附件的保守停止行为暂不改变，除非后续有独立产品需求和真实证据。

## 用户界面

消息结果继续以用户关心的顺序呈现：

1. 对方希望你做什么；
2. 对应岗位和机会结论；
3. 下一步。

纯文字路线的“下一步”显示本地草稿。人工操作路线显示自然语言操作提示，不显示内部枚举、选择器名称或冗余安全说明，也不提供会触发 BOSS 写操作的按钮。

## 取证与验证顺序

实现结构化通知前，需要一次单窗口、低频、只读取证：

1. 恢复 `BOSS-SEARCH` 与 `BOSS-COMMUNICATION` 固定标签页，重新解析实际数值标签页 ID；
2. 在不调用 `Page.bringToFront`、不点击通知卡片的前提下，读取简历投递窗口的外层消息元素、稳定类名/属性、方向、可见标题、按钮或状态元素；
3. 保存脱敏 DOM 夹具和截图证据，不保存招聘方姓名、原始消息正文、会话密钥或其他个人信息；
4. 立即复核页面、会话和标签页身份；若无法证明仍在同一目标，停止取证；
5. 先用夹具补失败回归检查，再实现最小选择器和路由；真实页面只做一次低频只读复核。

离线回归至少证明：

- 普通文字仍进入现有语义与草稿链；
- 简历投递卡片进入人工操作路线，模型调用次数为零；
- 人工操作结果保存检查点后继续下一个会话；
- 混合内容不生成草稿；
- 未知卡片停止且不提交检查点；
- 任何路径都不调用编辑、发送、上传、确认或前台抢占能力。

## 非目标

- 不重写消息读取器、岗位上下文或候选人进度系统；
- 不建立通用页面理解引擎或卡片插件框架；
- 不让模型推断交互卡片语义；
- 不在没有真实 DOM 证据时预留大量枚举或选择器；
- 不实现自动回复、自动投递简历、自动确认地点或自动选择面试时间；
- 不改变 `message_discovery_detail` 的单后台临时页、安全额度或清理规则。
