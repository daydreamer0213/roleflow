# BOSS 独立详情读取与项目标签组设计

日期：2026-08-09
状态：已完成对话方案确认，等待书面规格复核
目标分支：`codex/boss-pane-switch-repair`
基线：`main@109d6ac`

## 1. 目标

修复 BOSS 搜索结果中“只有默认第一张卡片能读到完整 JD，其余卡片大量报
`BOSS_PANE_SWITCH_TIMEOUT`”的质量阻塞，同时保持以下边界：

- 不执行 BOSS 沟通、投递、发送或申请动作；
- 继续使用一个登录会话、一个窗口和两个固定 BOSS 标签页；
- 扫描串行执行，不创建逐岗位标签页；
- 每次详情读取都验证岗位身份，验证失败不得保存为成功；
- 不降低逻辑覆盖目标；受访问额度限制的岗位保留为待恢复任务；
- 保留随机等待、阶段冷却、访问审计、风险页即停和可恢复检查点。

项目标签组作为后续独立阶段：把 RoleFlow 工作台、`BOSS-SEARCH` 和
`BOSS-COMMUNICATION` 收纳进一个名为 `RoleFlow` 的标签组，但标签组只负责界面整理，
不得替代现有安全身份校验。

## 2. 已确认事实

### 2.1 真实扫描证据

隔离的新基线广泛扫描发现 71 个唯一岗位：

- 5 个详情成功；
- 66 个详情失败，错误均为 `BOSS_PANE_SWITCH_TIMEOUT`；
- 每个关键词恰好只有默认第一张卡片成功；
- 66 个失败岗位没有 JD，语义状态只能进入待刷新。

该结果不能作为推荐质量基线。

### 2.2 真实页面只读探针

对非默认卡片依次验证了三种激活方式：

1. 当前产品的 DOM `click()`；
2. CDP 原生坐标点击卡片；
3. CDP 原生坐标点击经 `elementFromPoint` 确认的岗位链接。

三种方式都没有改变右栏岗位 ID。探针后仍保持一个窗口和两个固定 BOSS 标签页，
没有进入沟通或投递流程。根据项目安全规则，不再继续猜测选择器或增加点击变体。

### 2.3 代码证据

当前 `scanBrowser()` 已经在进入详情循环前冻结了本搜索目标的岗位标题、卡片事实和稳定
`/job_detail/<jobId>.html` URL。失败发生在 `readCardDetail()`：

- 先调用 `__bossOpenCard()` 点击左卡；
- 最多轮询 8 次右栏身份和 JD；
- 未切换到目标岗位时抛出 `BOSS_PANE_SWITCH_TIMEOUT`。

项目已有 `readDetail()`，能够在同一标签页直接进入独立详情 URL，并通过 URL 中的岗位 ID
验证页面身份。

## 3. 方案比较

### 方案 A：继续修补左卡点击

优点：

- 页面跳转少；
- 沿用当前右栏访问额度。

缺点：

- 三种真实交互机制均已失败；
- 继续猜测框架事件或选择器缺少当前页面证据；
- 容易再次出现“工具报告点击成功，但页面身份未变化”的假成功。

结论：拒绝。

### 方案 B：冻结列表后，在 `BOSS-SEARCH` 中串行读取独立详情

流程：

1. 在搜索页完整收集并冻结本目标的岗位卡片和稳定 URL；
2. 若当前可见右栏已经精确匹配目标岗位，可只读复用该详情，不执行点击；
3. 其余岗位在同一个 `BOSS-SEARCH` 标签页中依次进入独立详情 URL；
4. 同一批岗位之间直接从一个详情进入下一个详情，不逐条返回列表；
5. 下一搜索目标开始时，再进入新的搜索 URL。

优点：

- 不依赖已失效的左卡激活；
- 不创建新标签页，不使用沟通标签页；
- 冻结后的岗位 URL 使列表离开页面后仍能串行完成本批读取；
- 现有独立详情身份校验和风险页检查可以复用。

代价：

- 独立详情属于 `detail_open`，必须使用比右栏读取更严格的访问额度；
- 广泛扫描可能跨额度窗口恢复，不能承诺一次运行读完全部岗位；
- 扫描状态、访问指标和日志需要从“右栏详情”改为能区分“可见右栏复用”和“独立详情”。

结论：采用。

### 方案 C：复用 `BOSS-COMMUNICATION` 作为只读详情载体

优点：

- 搜索页可以一直保留；
- 详情页和列表页职责物理分开。

缺点：

- 会复用原本为沟通阶段保留的标签页；
- 增加详情读取与沟通互斥、标签身份和恢复逻辑；
- 与本轮“不触碰 BOSS 沟通或投递”的最小范围不符。

结论：本轮不采用。

## 4. 详情读取设计

### 4.1 数据流

```text
搜索 URL
  -> 收集并冻结岗位卡片
  -> 复用可信缓存
  -> 可见右栏身份恰好匹配时只读复用
  -> 其余岗位按冻结 URL 串行进入独立详情
  -> 岗位 ID + 页面状态 + JD 完整度验证
  -> 成功岗位立即进入当前目标结果
  -> 失败岗位保留 errorCode 和待恢复状态
  -> 下一搜索目标
```

### 4.2 可见右栏复用

可以保留一个无点击的只读优化：

- 只读取当前已经显示的右栏；
- `currentJobId` 必须与冻结 URL 中的目标岗位 ID 完全相同；
- 没有可靠岗位 ID 时不得复用右栏，直接进入独立详情；
- 标题只能作为岗位 ID 匹配后的附加一致性检查，不能单独启用复用；
- JD 清洗前长度必须达到现有完整度门槛；
- 身份不匹配时直接进入独立详情，不尝试点击左卡。

现有 `__bossOpenCard()` 及其点击路径从正式扫描中移除。若相关页面 helper 没有其他调用者，
同时删除，避免未来误用。

### 4.3 独立详情读取

独立详情读取必须：

1. 只接受经过 `normalizeBossUrl()` 规范化并通过 BOSS 主机校验的 URL；
2. 导航前预留 `detail_open` 访问额度；
3. 导航后立即检查登录页、风控页和页面丢失；
4. 从 `location.pathname` 提取岗位 ID，并与预期 ID 完全匹配；
5. 读取 JD、薪资、经验、学历和招聘方活跃字段；
6. JD 未达到完整度门槛时按节奏重试；
7. 重试结束仍不完整时抛出稳定错误码 `BOSS_DETAIL_LOAD_TIMEOUT`；
8. 岗位身份不匹配继续使用 `BOSS_DETAIL_PAGE_LOST`，并作为致命页面错误停止；
9. 不返回空对象冒充一次成功读取。

### 4.4 访问额度与恢复

不得把独立详情访问伪装成 `pane_detail_read`。继续使用当前 `detail_open` 策略：

- normal：10 分钟 8 次、1 小时 25 次、24 小时 60 次；
- recovery：10 分钟 5 次、1 小时 15 次、24 小时 30 次。

达到额度时：

- `BOSS_ACCESS_BUDGET_EXHAUSTED` 保持致命停止语义；
- 当前目标和已冻结岗位必须写入检查点；
- 已完成岗位不得丢失或重复分析；
- 未访问岗位不得被标记为详情失败或成功，应保持待恢复；
- 工作流必须保存 `retryAt` 或能从错误中恢复该时间；
- 后续恢复从未完成目标继续，不降低关键词、岗位卡片或 JD 覆盖目标。

历史 `pane_detail_read` 事件继续用于旧运行审计；新的工作流详情用量需要同时正确统计：

- 可见右栏复用：`pane_detail_read`；
- 独立详情读取：`detail_open`。

## 5. 错误与审计

每次详情尝试继续产生不含岗位私密文本的结果审计，至少包含：

- `outcome`：`succeeded` / `failed`；
- `errorCode`；
- `accessMode`：`visible_pane` / `standalone_detail`。

不得在访问结果事件中保存岗位标题、公司、完整 URL、JD 或错误原文。诊断日志可以保留当前
受控字段，但不得泄露 API Key、简历正文或完整 JD。

以下错误立即停止本轮浏览器访问：

- `BOSS_RISK_CONTROL`
- `BOSS_LOGIN_REQUIRED`
- `BOSS_ACCESS_BUDGET_EXHAUSTED`
- `BOSS_DETAIL_PAGE_LOST`
- `BROWSER_TIMEOUT`
- `BROWSER_DISCONNECTED`
- `BROWSER_COMMAND_FAILED`
- `SCAN_CHECKPOINT_FAILED`
- `SCAN_LEASE_LOST`

普通单岗位 `BOSS_DETAIL_LOAD_TIMEOUT` 只影响该岗位，岗位保留为待刷新，扫描可以按现有节奏
继续。

## 6. TDD 测试范围

实现前先增加失败测试，至少覆盖：

1. 非默认岗位不调用 `__bossOpenCard()`，而是导航到冻结的独立详情 URL；
2. 同一目标的多个岗位连续详情导航，中间不返回搜索页；
3. 下一目标开始时重新进入搜索 URL；
4. 可见右栏 ID 精确匹配时可以复用，且不发生导航；
5. 可见右栏缺少岗位 ID，或标题相似但岗位 ID 不同，都不得复用；
6. 独立详情岗位 ID 不匹配时立即失败；
7. JD 长度不足在重试后抛出 `BOSS_DETAIL_LOAD_TIMEOUT`；
8. 登录、风控、断连和页面丢失保持致命即停；
9. `detail_open` 额度耗尽时保留已完成结果和未完成目标；
10. 工作流用量同时统计历史右栏读取与新的独立详情读取；
11. 审计结果只保存状态、错误码和访问模式，不包含岗位事实文本；
12. 原有 74 项离线测试继续通过。

测试必须完成 RED -> GREEN；回归测试在恢复旧实现时必须失败。

## 9. 项目标签组后续阶段

### 9.1 目标行为

启动工作区后，尽可能把以下标签页放入 `RoleFlow` 标签组：

- RoleFlow 工作台；
- `BOSS-SEARCH`；
- `BOSS-COMMUNICATION`。

默认不折叠，颜色使用固定项目色。标签组创建失败只产生可见警告，不得阻止工作台启动、
扫描恢复或安全检查。

### 9.2 安全身份

标签组标题、颜色和 group ID 都不是安全身份。以下规则保持不变：

- 标签页必须有真实 `tabId`；
- BOSS 标签页必须有可靠 `windowId`；
- 两个固定 BOSS 标签页必须属于同一窗口；
- 操作前必须重新验证 URL、页面类型、登录状态、风险状态和目标岗位身份；
- 不允许根据标签组顺序、标题或颜色推断操作目标。

### 9.3 技术边界

当前便携版控制层使用 CDP，公开 CDP 协议没有标签组管理命令。Chromium/Edge 扩展 API
提供 `tabs.group()` 和 `tabGroups.update()`。

后续实现应先增加可选浏览器能力接口，例如：

```js
browser.capabilities.tabGroups === true
browser.groupTabs(tabIds, { title: "RoleFlow", color: "blue", collapsed: false })
```

不支持该能力的适配器返回 `unsupported`，不使用键鼠模拟浏览器标签栏。便携版自动分组需要
单独验证受限 MV3 扩展桥接或其他受支持接口，必须另写实现计划和安全测试，不与详情读取修复
混在同一提交中。

## 10. 非目标

本轮不做：

- BOSS 沟通、投递、发送、申请或首次会话点击；
- 提高 `detail_open` 访问额度；
- 多标签并发读取详情；
- 创建逐岗位标签页；
- 修改推荐阈值、模型提示词或岗位匹配规则；
- 删除历史数据库、私有 benchmark、分支或工作树；
- 把标签组作为权限或安全边界。
