# RoleFlow 暂停后筛选变更与可读错误恢复设计

**日期：** 2026-09-02  
**状态：** 已实现并通过离线门禁，待用户在修复版本中继续真实验收

## 背景

真实首次使用验收暴露了一个组合问题：用户开始一轮岗位发现后点击暂停，随后在 BOSS 搜索页修改筛选条件，再回到 RoleFlow 继续本轮。暂停请求已经写入本地，但扫描进程仍在当前列表采集阶段继续滚动；页面条件变化前后的岗位被同一个内存集合累计，进度数量超过冻结目标上限后，检查点保存失败。本轮最终进入中断状态，随后恢复检查又遇到页面响应超时。

现场证据同时表明：

- 点击暂停后，扫描仍继续执行了约 29 秒的列表滚动。
- 失败前已有 42 个岗位成功写入本地检查点，数据库完整性检查正常。
- 失败发生在第一个搜索目标的列表采集阶段，冻结上限为 50；当前集合代码允许一次合并后超过上限，而存储层正确拒绝超过冻结上限的检查点。
- 本轮开始时冻结的搜索范围没有平台筛选参数，恢复时搜索页已经出现新的城市和地铁筛选参数。
- 当前服务仍在运行，但工作流已中断，不会自动继续访问 BOSS，也没有发生沟通或投递。
- 现有通用错误响应会隐藏 500 级异常的具体用户含义；运行状态前端又会丢弃服务端返回的错误说明，只展示泛化提示或内部错误编号。

## 目标

- 暂停请求在下一处安全浏览器边界生效，不继续发起新的列表滚动或详情访问。
- 页面明确区分“正在暂停”和“已经暂停”，避免用户误以为后台已停稳。
- 扫描过程中发现搜索范围变化时立即停止当前目标，不把变化前后的岗位混入同一批次。
- 用户在真正暂停或可恢复中断后修改筛选，可以明确选择按新条件重新开始当前逻辑轮次。
- 按新条件重新开始时不额外占用今日轮次；旧批次保留为本地历史，但不进入新结果、分析或沟通清单。
- 用户首先看到发生了什么、数据是否保留和下一步操作；内部错误编号只作为次要诊断信息。

## 非目标

- 不允许在岗位分析、清单确认、沟通或消息阶段替换本轮筛选范围。
- 不把旧筛选与新筛选的岗位混入同一批次。
- 不静默修改用户当前 BOSS 筛选，也不自动替用户选择继续旧条件或使用新条件。
- 不改变每天轮次上限、轮次间隔、访问预算、随机节奏、风险控制、固定标签页和串行执行规则。
- 不改变岗位分析、二维表判断、沟通、消息发现或回复发送逻辑。
- 不新增错误处理框架、前端组件库或第三方依赖。
- 不使用真实 BOSS 页面做常规自动化测试。

## 方案选择

### 采用：显式替换当前采集轮次的筛选快照

如果当前工作流仍处于采集阶段，且没有分析任务、沟通批次或外部写入，用户可以明确选择“按新条件重新开始本轮”。系统保留旧扫描批次作为历史证据，在同一个工作流中创建新的扫描批次并绑定新的冻结筛选快照。工作流记录仍只占当天一个逻辑轮次。

该方案符合用户修改筛选的真实目的，又能保持每个实际扫描批次内部条件一致。

### 不采用：恢复时强制使用旧条件

该方案实现最简单，也能保持旧批次一致，但会忽略用户刚完成的筛选修改。用户容易再次误以为新条件已经生效。

### 不采用：把新条件直接合并进旧批次

该方案表面连续，实际会让同一批次包含不同搜索范围，后续无法解释岗位来源，也会削弱验收、诊断和恢复证据，因此禁止。

## 用户流程

### 1. 请求暂停

1. 用户点击“暂停本轮”。
2. 工作流进入 `pause_requested`，页面立即显示“正在暂停，系统会在当前安全步骤完成后停止；确认显示已暂停前，请不要修改 BOSS 搜索页”。
3. 暂停按钮禁用，不显示可用的“继续本轮”。页面继续轮询本地状态。
4. 扫描在下一处安全边界保存已经确认的进度，然后进入 `paused`。
5. 只有状态变为 `paused` 后，页面才显示“本轮已暂停”和“继续本轮”。

安全边界指浏览器动作之间的本地检查点。已经发出的单次只读页面读取可以完成，但暂停请求后不得再发起新的列表滚动、页面导航或详情读取。

### 2. 暂停后没有修改筛选

用户点击“继续本轮”时，服务端重新读取当前搜索页并与本轮冻结范围比较。范围一致则沿用现有恢复逻辑，从已保存检查点继续，不重新读取已经确认完成的岗位。

### 3. 暂停后修改了筛选

第一次点击“继续本轮”只做只读比较，不修改工作流。如果当前搜索范围与冻结范围不同，页面显示：

- 标题：“搜索条件已经变化”。
- 说明：“本轮开始时的条件与当前 BOSS 搜索页不同。旧结果不会与新结果混合。”
- 主操作：“按新条件重新开始本轮”。
- 次操作：“继续开始时的条件”。
- 辅助入口：“返回本轮”。

选择主操作即视为本次替换确认，不再弹出第二次确认。选择次操作时，恢复仍使用开始时冻结的条件；RoleFlow 可以按现有扫描导航逻辑重新打开该冻结搜索目标，但不得改写冻结快照。

### 4. 运行中直接修改筛选

每次读取新的列表卡片前，扫描验证当前搜索页的规范化范围仍与当前目标一致。检测到城市、地区、地铁、薪资、经验、学历、职位类型、关键词或其他已识别平台筛选发生变化时：

- 不接纳这次页面读取返回的新卡片；
- 保存此前已经确认的检查点；
- 以可恢复原因 `BOSS_SEARCH_SCOPE_CHANGED` 停止当前扫描；
- 页面给出与“暂停后修改筛选”相同的两种恢复选择。

无法识别但确实出现在搜索 URL 中的平台筛选参数也纳入范围指纹，不能因为本地没有中文标签而忽略。

## 服务端约束

### 暂停检查

- 复用现有工作流 `control_state` 和安全停止异常，不新增第二套暂停状态机。
- 访问预算控制器在每次预留浏览器动作前调用现有 `assertActive`，而不是只在额度冷却等待期间检查。
- 列表增量检查点写入后再次检查工作流控制状态，确保下一次滚动前响应暂停。
- 暂停异常继续走现有受控收尾路径，最终状态必须是 `paused`，不能误记为普通扫描失败。

### 卡片上限

- 列表唯一卡片集合在接纳新卡片时执行冻结 `cardLimit`，而不是只在最终返回时切片。
- 增量回调中的 `jobs` 和 `total` 都不得超过冻结上限。
- 存储层的冻结边界校验继续保留，不能通过放宽数据库约束掩盖采集错误。

### 搜索范围一致性

- 复用现有搜索范围规范化、平台筛选解析和范围指纹能力。
- 比较对象是当前目标的关键词、城市及平台筛选参数；参数顺序和 URL 编码差异不应造成误判。
- 仅比较产品认可的搜索范围，不把无关的追踪参数、页面内部瞬时参数或标签标题纳入指纹。
- 识别到登录、风控、页面丢失或页面身份不明确时，继续使用现有更高优先级的停止原因，不降级成筛选变化。

### 使用新筛选重新开始当前轮次

仅在以下条件全部满足时允许：

- 工作流处于 `paused`，或处于可恢复的采集阶段 `interrupted`；
- `resume_phase` 为扫描阶段，且旧扫描进程、租约和浏览器动作已经结束；
- 尚未创建或执行任何岗位分析任务；
- 尚未创建沟通批次，也没有外部写入；
- 当前 BOSS 搜索页通过登录、风险控制、固定标签页和页面身份检查；
- 当前搜索范围可以生成完整的新冻结执行快照；
- 请求明确来自“按新条件重新开始本轮”操作。

执行时先在一个本地事务中完成状态替换：

1. 再次核对上述前置条件和旧工作流版本。
2. 确认旧扫描运行和批次已经处于现有终态，保留已经保存的岗位和原冻结快照；新恢复入口不再引用该批次。
3. 在工作流规划快照中记录本次范围替换的时间、旧范围指纹、旧批次编号和新范围指纹；不记录完整页面内容。
4. 清除当前工作流与旧扫描运行的活动绑定，安装新的冻结筛选快照。
5. 增加恢复代次，并把工作流置为等待启动新扫描的已提交状态；工作流主键和当日轮次序号保持不变。

事务提交后才启动新的扫描进程。启动失败沿用现有工作流启动失败收尾，不回滚已经提交的范围替换，也不重连旧批次；用户再次恢复时仍只能从新冻结范围继续。事务内任一步失败则全部回滚，旧批次和工作流保持原可诊断状态，不启动扫描进程。

## 用户可读错误

### 表达结构

错误页面和工作流中断卡片统一按以下顺序展示：

1. **发生了什么：** 面向用户的短标题。
2. **当前影响：** 是否已停止、已保存数量或是否需要人工确认。
3. **下一步：** 一个推荐主操作，必要时提供一个次操作。
4. **技术信息：** 折叠区域内显示错误编号和请求编号，并保留诊断入口。

内部错误编号不得再充当中断卡片的主说明，也不得拼接英文内部错误消息直接展示给普通用户。

### 最小映射范围

复用现有状态标签和错误响应函数，只增加当前用户流程实际出现或已有明确恢复动作的映射：

- `SCAN_CHECKPOINT_FAILED`：本轮采集进度未能继续保存；说明已保存进度仍保留，并根据状态提供重新开始或返回本轮。
- `BOSS_SEARCH_SCOPE_CHANGED`：搜索条件已变化；提供新条件重新开始或继续旧条件。
- `BROWSER_TIMEOUT`：BOSS 页面响应较慢，本次检查已停止；提示等待页面加载完成后重新检查，不自动重试扫描或外部动作。
- `BOSS_WORKSPACE_NOT_READY`：固定页面尚未确认；提示检查搜索页和沟通页后重新检查工作区。
- 现有登录、风险控制、模型配置和沟通歧义错误继续使用各自已有恢复说明。
- 未知错误使用保守回退：“操作未完成，当前进度已保留。返回本轮查看状态；若再次发生，请复制诊断信息。”

API 继续返回稳定 `errorCode` 和 `requestId`，同时返回可直接展示的用户说明。运行状态前端必须优先展示服务端用户说明，不能在失败分支中丢弃响应正文。

## 数据与兼容

- 不迁移或删除现有岗位、批次、工作流和访问记录。
- 历史中断工作流没有范围替换记录时继续按旧格式读取。
- 新范围替换信息放入现有工作流规划或指标 JSON，不新增数据库表。
- 当前真实验收产生的中断工作流只能在安装包含本修复的版本后使用新恢复入口；现有安装不得直接重放。
- 重新开始只影响当前工作流的新扫描批次，不改动候选人资料、简历、Search Plan、匹配偏好卡或模型设置。

## 验证

至少保留以下回归：

1. 正常列表采集在最后一次增量跨过上限时，只接纳到 `cardLimit`，增量检查点和最终结果均不越界。
2. 无额度等待时，访问动作开始前也会检查暂停请求；暂停后不会继续预留下一次列表滚动。
3. `pause_requested` 页面显示“正在暂停”，不显示“已经暂停”或可用继续按钮；变为 `paused` 后才显示继续入口。
4. 搜索范围未变化时，恢复继续使用原批次检查点。
5. 搜索范围变化时，第一次恢复只返回选择，不修改工作流、不创建扫描运行。
6. 选择新条件后，旧批次保留，新批次使用新冻结范围，旧岗位不进入新批次，工作流和当日轮次序号不变。
7. 已进入分析、已建沟通批次、旧进程仍活动、租约未释放或当前页面不安全时，拒绝范围替换且不产生部分写入。
8. 运行中搜索范围变化时，不保存变化后的卡片，并以 `BOSS_SEARCH_SCOPE_CHANGED` 可恢复停止。
9. `BROWSER_TIMEOUT`、`BOSS_WORKSPACE_NOT_READY`、`SCAN_CHECKPOINT_FAILED` 和未知错误均展示用户说明、下一步和折叠技术信息；运行状态前端不丢弃服务端说明。
10. 关键定向检查、完整离线门禁和 `git diff --check` 通过。

所有自动化验证使用临时数据库和假浏览器，不访问真实 BOSS。修复版本安装后，再由用户从当前验收场景人工验证暂停、修改筛选和重新开始；任何沟通或投递仍需当次明确授权。
