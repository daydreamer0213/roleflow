# BOSS 搜索页右栏详情复用设计

日期：2026-08-10
状态：已批准，待实施

## 1. 结论

正常扫描恢复“搜索页岗位卡片切换 + 右栏详情读取”，不再把独立岗位详情页作为自动回退路径。

现有卡片枚举、右栏字段提取、岗位身份核验、访问额度、检查点和后续分析流程继续复用。实现只补回可靠的岗位卡激活，并把固定次数短等待改为条件等待。

独立详情读取能力继续保留，供人工批准的补读、沟通页检查及现有专用恢复流程使用；普通扫描不自动调用。

## 2. 已确认事实

### 2.2 页面事件链

真实页面的岗位卡组件名为 `JodCard`，其 `clickJobCard()` 方法向父组件发送 `click-job`。父组件 `PageJobs.clickJobCardAction()` 更新 `currentJob`，随后调用 `loadJobDetail()` 请求并刷新右栏。

旧实现调用原生 DOM `target.click()`，没有验证上述组件事件链是否真正执行。

### 2.3 旧超时窗口

旧实现先等待 `card` 3～5 秒，再执行 8 次 `card_retry` 0.3～0.7 秒，完整窗口约 5.4～10.6 秒。真实请求耗时 11.8 秒，因此旧逻辑可能在右栏响应返回前抛出 `BOSS_PANE_SWITCH_TIMEOUT`。

历史 66 次右栏失败可能同时包含激活路径不可靠和等待窗口不足。单次校准直接证明了本次样本的慢接口问题，但不把全部历史失败武断归因于同一个原因。

## 3. 目标与非目标

### 3.1 目标

- 每个待读岗位都在 `BOSS-SEARCH` 固定搜索页内完成激活和读取。
- 激活前后都使用精确岗位 ID，不使用标题或列表序号授权操作。
- 一次岗位只触发一次组件激活，不因加载缓慢重复点击。
- 等待期间持续检查标签页绑定、搜索页身份、登录和风控状态。
- 右栏岗位 ID、标题和 JD 完整性全部满足后才返回成功。
- 超时或组件不可用时保留岗位为待处理，不自动导航独立详情页。
- 不降低卡片覆盖、JD 覆盖或匹配质量。

### 3.2 非目标

- 不删除现有 `readDetail()`、沟通页检查或人工补读能力。
- 不新增浏览器标签页、窗口或并发扫描。
- 不修改模型提示词、评分阈值、推荐逻辑或岗位覆盖目标。
- 不增加新的浏览器依赖、DOM 框架或通用抽象层。
- 不执行新的真实 BOSS 点击；现有一次校准证据足以支持离线实现。

## 4. 页面辅助函数

### 4.1 精确激活岗位卡

在现有 `PAGE_HELPERS` 中增加 `window.__bossActivateCard(jobId)`：

1. 使用 `__bossCards()` 获取当前可见岗位卡；
2. 只按卡片链接中的精确岗位 ID 定位目标；
3. 从目标卡向上查找 `.job-card-wrap` 及其 Vue 组件实例；
4. 同时要求组件 `data.encryptJobId` 等于目标岗位 ID；
5. 要求组件存在 `clickJobCard()`；
6. 滚动目标卡到列表可见区域；
7. 只调用一次 `clickJobCard()`；
8. 返回结构化结果，不返回岗位标题、公司或 JD。

目标卡、组件、方法或组件岗位 ID 任一不满足时，返回失败原因。不得回退到原生 `target.click()`、标题匹配或列表序号。

### 4.2 分离三个岗位身份

扩展 `__bossPaneState()`，明确分离：

- `activeJobId`：当前高亮卡片的岗位 ID；
- `componentCurrentJobId`：页面父组件的当前岗位 ID；
- `paneJobId`：右栏详情 DOM 自身链接中的岗位 ID。

现有实现把高亮卡链接作为右栏 ID 的回退来源，可能在右栏仍是旧内容时提前报告目标 ID。新实现取消这个回退；`paneJobId` 只能来自右栏 DOM。

状态同时返回 `jobDetailLoading`。若页面版本无法读取组件加载字段，则仍可依靠 `paneJobId + title + JD` 判断完成，但不得因为缺少加载字段而伪造成功。

## 5. 适配器流程

扩展现有 `readVisiblePaneDetail(tabId, job, signal, assertTabBindings)`，让它在右栏尚未匹配时完成一次组件激活和条件等待。继续使用现有方法名可以保留当前调用和测试接缝，不增加兼容包装。

执行顺序：

1. 检查中止信号、固定标签页绑定和搜索页身份；
2. 从冻结 URL 提取目标岗位 ID；缺失时失败；
3. 为该岗位预留一次 `pane_detail_read`；
4. 读取一次 `__bossPaneState()`：
   - 若右栏已经精确匹配且 JD 完整，直接复用；
   - 若高亮卡或组件当前岗位已经匹配目标，说明该岗位正在加载，只等待而不重复激活；
   - 只有当前选择不是目标时才调用一次 `__bossActivateCard(jobId)`；
5. 激活结果必须成功，且返回岗位 ID 与目标一致；
6. 最多执行 60 次现有 `card_retry` 条件轮询，约 18～42 秒：
   - 每次先检查中止、标签页绑定、搜索页、登录和风控；
   - `activeJobId` 和 `componentCurrentJobId` 出现时必须等于目标；
   - 只有 `paneJobId`、标题与目标精确匹配且 JD 长度不少于 120 时成功；
   - 正确右栏可滚动但字段不完整时，最多滚动一次并继续等待；
7. 成功后把右栏恢复到顶部并返回现有字段结构；
8. 条件窗口结束仍未完整时，抛出 `BOSS_PANE_SWITCH_TIMEOUT`。

等待只增加无操作时间，不产生重复点击、页面导航或额外标签页。

## 6. 扫描路由

普通 `scanBrowser()` 详情循环调整为：

- 删除 `visiblePaneProbeAvailable`；
- 每个详情目标都调用 `readVisiblePaneDetail()`；
- 成功结果的 `accessMode` 固定为 `visible_pane`；
- 不再从空右栏结果自动调用 `readDetail()`；
- `BOSS_PANE_SWITCH_TIMEOUT` 继续按单岗位失败处理，保存 `detailRead: false` 和错误码；
- 登录、风控、标签页丢失、浏览器断连和检查点失败继续按现有致命规则立即停止。

现有目标完成、详情结果、岗位合并和检查点回调保持不变，因此后续分析工作流不需要修改。

## 7. 访问额度与恢复

- 每次岗位详情尝试只消耗一次 `pane_detail_read`。
- 普通扫描不产生 `detail_open`。
- 组件不可用或右栏超时不会自动升级成更高风险访问。
- 失败岗位保留为待处理，后续从检查点恢复。
- 人工补读和沟通页检查继续按现有 `detail_open` 限额运行，不提高额度。
