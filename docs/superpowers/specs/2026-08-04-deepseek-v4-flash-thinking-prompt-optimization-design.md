# DeepSeek V4 Flash 思考模式切换与提示词整理设计

> 日期：2026-08-04
>
> 状态：待用户书面复审
>
> 目标分支：`codex/multi-track-recall-integration`

## 1. 目标

RoleFlow 将岗位分析模型从 `deepseek-v4-pro` 切换为
`deepseek-v4-flash`，首轮开启思考模式并使用
`reasoning_effort=high`。

模型切换和提示词整理必须分阶段进行：

1. 第一阶段只切换模型和推理配置，保持当前提示词、结构化契约、
   v4.7 四档决策规则和冻结输入不变。
2. 使用原 3 条诊断样本观察结构稳定性和语义判断差异。
3. 3 条通过后，使用同一批 20 条人工确认岗位完成验收。
4. 只有真实偏差证明提示词存在问题时，才进行最小提示词修正。
5. Flash 行为稳定后，再单独整理和减重完整提示词。

这样可以区分模型差异、思考模式差异、提示词差异和本地决策规则
差异，避免多项变化同时发生后无法定位根因。

## 2. 不变的产品边界

本设计不修改以下规则：

- 四档建议保持
  `primary/apply/caution/not_recommended`。
- 默认批量沟通只包含主投和可投。
- 人工主投或可投不得遗漏出默认沟通集合。
- 人工慎投或不推荐不得进入默认沟通集合。
- 主投与可投互换不阻断验收。
- 慎投与不推荐互换不阻断验收。
- 冻结二维表不修改。
- 核心要求 70%、支持要求 30%不修改。
- 主要职责证据轴和 v4.7 晋级、封顶规则不修改。
- 模型不计算最终四档，最终建议继续由本地代码计算。
- `modelRecommendation` 在 split 模式继续关闭，不作为最终决策输入。
- 技术失败、结构失败、空响应或证据不完整继续进入
  `needs_retry`，不得伪装成四档建议。

任何二维表或权重调整仍需先取得用户确认。

## 3. 冻结验收输入

20 条正式样本继续使用此前由用户人工确认并冻结的岗位池，不重新
抽样，也不由 Flash 重新生成标准答案。

- 岗位池：
  `D:\DevData\RoleFlow-private-benchmark\confirmed-sample-pool-v1-20260730`
- 岗位数据原始 SHA-256：
  `612547b099d71f13fc5dd58e78a31756b4b56c7ad9375f7b3d182d73b5e0d35b`
- 人工标签原始 SHA-256：
  `97b4e5830fbf0fad8a694a3cfc1fcedfd5918b3e9723b811ebba09f1fb46da39`

运行前必须重新计算并核对两个哈希。任何不一致都立即停止，不运行
真实模型。

3 条诊断继续使用现有零基索引 `4,9,10`，不得进行减一转换。

冻结复用的内容：

- 20 条岗位原文；
- 人工四档标签；
- 冻结候选人证据；
- 当前产品提交和决策策略；
- 当前岗位理解与候选人匹配提示词。

禁止复用的内容：

- Pro 的模型输出；
- 旧的模型缓存；
- 旧的 3 条缓存到 20 条；
- 旧运行目录。

## 4. 首轮模型调用配置

第一轮候选配置固定为：

```json
{
  "model": "deepseek-v4-flash",
  "thinkingMode": "enabled",
  "reasoningEffort": "high",
  "jsonMode": true
}
```

行为要求：

- 请求发送 `thinking: {"type":"enabled"}`。
- 请求发送 `reasoning_effort: "high"`。
- 思考模式开启时省略 `temperature`，不发送无效参数。
- 继续发送 `response_format: {"type":"json_object"}`。
- system 或 user prompt 中继续保留当前明确的 JSON 输出要求和字段契约。
- 保持当前非流式解析和结构化契约校验。
- `reasoning_content` 只作为供应商响应中的推理数据，不写入产品
  分析、缓存报告、日志或用户页面。
- 产品只解析最终 `content` 中的 JSON。

首轮不使用 `reasoning_effort=max`。只有 `high` 在 3 条中出现明确
语义判断不足，且结构与契约均正常时，才允许用同 3 条做一次
`high/max` 对照。

## 5. 模型设置设计

### 5.1 新设置字段

模型运行时设置新增：

```json
{
  "thinkingMode": "enabled",
  "reasoningEffort": "high"
}
```

约束：

- `thinkingMode` 只接受 `enabled` 或 `disabled`。
- `reasoningEffort` 只接受 `high` 或 `max`。
- DeepSeek V4 的默认值保持 `disabled/high`，确保升级后不自动改变
  现有用户行为。
- 本次实验通过显式设置改为 `enabled/high`。
- 非 DeepSeek V4 模型不得收到 DeepSeek 专用的
  `thinking` 和 `reasoning_effort` 参数。
- `disabled` 时不发送 `reasoning_effort`。

### 5.2 设置页面

DeepSeek V4 Pro 或 Flash 被选中时，模型设置页面显示：

- “思考模式”：开启/关闭；
- “推理强度”：高/high、最高/max。

推理强度仅在思考模式开启时可编辑。页面用中文说明：

- `high` 用于日常岗位分析；
- `max` 更慢、输出推理更多，只用于小样本诊断。

其他供应商和 Mock 模型不显示这两个字段。

### 5.3 连接验证

连接验证继续使用最小 JSON 请求，并固定关闭思考模式，避免连接
测试因推理输出消耗过多 token。连接测试只验证：

- API Key；
- base URL；
- 模型名称；
- JSON Output 基本可用。

正式分析请求才应用保存的思考模式和推理强度。

## 6. 缓存与分析版本隔离

当前缓存键已经包含供应商和模型名称，因此 Pro 与 Flash 不会共用
模型缓存；但同一个 Flash 模型的思考与非思考结果仍需额外隔离。

新增稳定推理指纹，至少包含：

```json
{
  "provider": "openai_compatible",
  "baseUrl": "https://api.deepseek.com",
  "model": "deepseek-v4-flash",
  "thinkingMode": "enabled",
  "reasoningEffort": "high"
}
```

推理指纹必须参与：

- 模型设置连接指纹；
- `cachedModelCall` 缓存键；
- 分析 revision；
- 分析陈旧原因判断；
- 私有验收 manifest。

任一字段变化后：

- 不得命中旧模型缓存；
- 旧岗位分析标记为 `model_inference_changed`；
- 必须重新运行岗位理解和候选人匹配。

不得把 API Key、完整配置内容或推理内容写入指纹、manifest 或日志。

## 7. 两次模型调用保持不变

首轮不重构调用链，继续使用：

1. `understandJob`：理解岗位、招聘分支、要求、职责和风险；
2. `matchJob` split：
   - 匹配主要职责；
   - 匹配岗位要求；
   - 本地合并结构化证据。

两次调用都使用同一个 Flash 思考配置。首轮不得使用“一次思考、
一次非思考”的混合配置，避免增加无法归因的变量。

如果 Flash 全思考模式在性能或稳定性上不合格，后续独立方案才可以
评估：

- 岗位理解非思考、候选人匹配思考；
- Flash 岗位理解、Pro 候选人匹配。

这两项不是首轮实施范围。

- 隐私、安全、缓存和证据门禁全部通过。

如果失败，不直接运行 20 条。

## 9. 失败归因顺序

3 条失败时按以下顺序定位：

1. 结构问题：空响应、JSON 解析、缺字段、非法枚举、截断；
2. 语义问题：岗位方向、职责或要求状态判断与事实不符；
3. 本地决策问题：模型证据合理，但 v4.7 计算结果与人工边界不符；
4. 性能问题：延迟或 token 消耗不可接受。

第一轮失败后，不立即改提示词。先使用同一 3 条、同一 Flash 模型、
同一提示词做一次 `thinkingMode=disabled` 对照。

- 思考开启失败、关闭通过：优先检查思考模式行为和推理配置。
- 开启关闭都在同一语义点失败：再考虑 Flash 专用提示词修正。
- 模型证据合理但最终分组错误：检查本地量化路径，不修改提示词，
  且不得自行修改冻结二维表。

- 不覆盖旧目录；
- 保持同一模型、思考模式、推理强度、提示词和产品提交。

正式行为门禁：

- 所有结构、隐私、安全和缓存隔离门禁通过。

所有四档差异仍需逐条记录，用于后续提示词分析，但不再要求固定
`18/20 exact`。

## 11. Flash 提示词修正阶段

只有 3 条或 20 条证明存在可重复的模型语义问题时，才进入本阶段。

修正原则：

- 一次只解决一类已观察偏差；
- 优先缩短和澄清已有定义，不增加大量反复自检；
- 保持跨职业通用，不增加 AI、Java、销售等职业专用关键词；
- 保留 `responsibilityMatches`、`requirementMatches` 和结构化
  `hardBlockers`；
- 不要求模型计算分数、权重或最终四档；
- 不修改 v4.7 二维表和权重；
- 每次提示词变化提升对应 pipeline version；
- 每次变化使用新缓存，并按 3 条到 20 条顺序验收。

优先允许的调整：

- 对称定义 `matched/transferable/missing/unknown`；
- 为每个状态保留一个跨职业正例和一个反例；
- 强调比较工作对象、动作和交付物；
- 删除重复的输出警告和本地计算说明；
- 缩短不参与模型任务的产品政策说明。

禁止为了单个样本增加职位名称或行业关键词补丁。

## 12. 提示词整体整理阶段

Flash 通过完整 20 条行为门禁后，提示词整体整理作为单独 checkpoint
执行，不与模型切换提交混合。

整理目标：

- 减少重复指令；
- 让岗位理解和候选人匹配各自只承担一种职责；
- 保留所有影响四档安全边界的结构化字段；
- 降低输入 token、输出 token 和契约修复次数；
- 保持或改善 20 条行为门禁。

整理前后的比较至少包含：

- 提示词字符数和估算 token；
- 平均调用延迟；
- 平均输入/输出 token；
- JSON 解析成功率；
- 契约修复率；
- 空响应率；
- 默认沟通边界结果；
- 逐项职责与要求状态变化。

## 13. 提交与分支边界

所有工作继续在 `codex/multi-track-recall-integration` 完成。

提交必须拆分：

1. 设计文档；
2. Flash 思考配置、缓存隔离和离线测试；
3. 3 条/20 条验收 checkpoint 文档；
4. 必要的 Flash 最小提示词修正；
5. 后续提示词整体整理。

不得修改或合并 `main`，除非用户另行明确要求。每个通过复审的独立
checkpoint 才允许推送。

## 14. 完成标准

本阶段只有同时满足以下条件才算完成：

- Flash 思考模式配置显式、可回退且不会污染缓存；
- 所有现有离线测试和新增目标测试通过；
- 3 条诊断通过；
- 20 条人工确认岗位的默认沟通边界通过；
- 结构、隐私、安全和缓存门禁通过；
- 所有偏差和性能数据已记录；
- 是否需要提示词修正有真实数据依据；
- 通过复审的提交已推送当前开发分支；
- `main` 未被修改。
