# 岗位主体方向与要求证据双层匹配设计

## 状态

用户已完成书面审阅并确认设计，现进入实施计划阶段。代码实施仍须按对应计划逐任务执行并通过
离线测试、小样本真实模型诊断和分阶段验收。

## 结论

岗位匹配分成两个相互独立、最后合并的判断层：

1. **岗位职责层**：先判断岗位实际在做什么，再把岗位主体方向与候选人经历做语义匹配；
2. **岗位要求层**：把任职要求拆成可独立核对的条目，逐条匹配候选人证据。

最终只由本地确定性规则把两层结果合并为：

- `primary`：主投；
- `talk`：可投；
- `backup`：慎投，默认不勾选；
- `not_recommended`：不推荐投递。

正常路径仍然只有现有两次模型调用，不增加第三次裁判调用，也不使用本地关键词相似度救回。

## 为什么需要两层

真实保存 JD 中有两个相邻岗位：

- AI 辅助前端岗位的工作主体是 UI 组件库、多端视觉和前端工程，AI 只是开发方法；
- AI 辅助全栈岗位的工作主体是企业业务系统交付，候选人已覆盖 Python/FastAPI、接口、测试、
  调试和需求拆解，但缺少前端与完整全栈交付。

只看要求关键词时，两者都有“AI 编程工具”；只看是否命中任意一条 `central` 时，相同的 AI
辅助全栈岗位又曾在三个独立缓存中得到一次 `talk`、两次 `backup`。

人类判断之所以能区分，是因为会先看整体工作对象与交付结果，再看具体条件。系统需要明确保存
这两个层次，而不是把整体职责压缩成一组平级要求后直接计数。

## 目标

- 让岗位主体方向成为独立、可核对的分析结果；
- 区分工作方法与工作对象，避免“都会使用 AI”掩盖前端、后端、视觉等方向差异；
- 允许同方向但能力不完整的岗位进入可投，保持机会召回；
- 让只有少量相邻能力、没有岗位根基的岗位进入慎投而不是默认勾选；
- 不把简历未写的经历直接判成不一致；
- 不因方向模型判断单独制造硬淘汰；
- 保留岗位要求层的根基、主线和明确硬条件；
- 不增加正常模型调用次数、外部依赖、职业分类表或数据库迁移。

## 非目标

- 不要求模型绝对准确地排序所有岗位；
- 不建立前端、后端、运营、销售等职业枚举库；
- 不使用职位标题代替完整 JD；
- 不依赖“岗位职责”“任职要求”等标题的位置或格式；
- 不让用户偏好、聊天内容或未经确认的事实充当简历证据；
- 不改变真实沟通、投递或招聘平台访问边界。

## JD 的职责与要求如何划分

招聘 JD 经常存在以下问题：

- 岗位职责与任职要求混写；
- 标题缺失或标题错误；
- 在要求部分描述实际工作，在职责部分堆放工具；
- 把加分项写成必备条件。

因此不能按标题或段落位置机械切割。`understandJob` 阅读完整 JD 后按语义分工：

### 岗位职责层

只保留能说明以下内容的句子：

- 主要工作对象；
- 主要工作动作；
- 最终交付结果；
- 持续承担的业务场景。

示例：

```text
工作对象：SaaS/App 前端页面和 UI 组件
工作动作：开发、封装、适配、视觉还原
交付结果：企业级 UI 组件库与一致的多端体验
```

工具、学历、年限、软技能和单纯的“熟悉某技术”不能单独定义岗位主体。

### 岗位要求层

保留可对候选人进行事实核对的条件，包括：

- 技术与专业能力；
- 项目或行业经历；
- 交付经验；
- 学历、证书、年限和资格；
- 明确的地点、出差或其他条件。

同一句 JD 可以同时贡献职责证据和要求证据，但两个结果承担不同作用，不共享推断。

## 第一次模型调用：理解岗位

继续使用现有 `understandJob`，不新增调用。为控制 JSON 复杂度，只增加平铺字段和一个布尔值：

```json
{
  "roleSummary": "利用AI编程工具交付企业业务系统的全栈开发",
  "responsibilityEvidence": [
    "JD：快速完成企业业务系统的前后端开发、联调与上线",
    "JD：负责数据库设计、API开发和第三方服务集成"
  ],
  "requirements": [
    {
      "label": "Python或Node.js后端开发",
      "foundation": true,
      "central": false,
      "indispensable": false,
      "evidence": "JD：后端熟悉Python或Node.js"
    }
  ],
  "eligibility": [],
  "riskSignals": []
}
```

这里的 `requirements` 是模型原始输出字段；通过现有契约校验后，内部仍规范化为
`coreRequirements`。实现不得同时维护两套含义不同的要求数组。

### `roleSummary`

必须用一句话同时概括：

- 工作对象；
- 主要动作；
- 交付结果。

“负责 AI 应用开发”“使用 AI 工具提高效率”信息不足，不能作为合格的岗位主体。

### `responsibilityEvidence`

- 必须引用 JD 原文短句并以 `JD：` 开头；
- 最多保留四条直接支持岗位主体的职责证据；
- 不复制整篇 JD；
- 没有足够职责证据时允许为空，后续主体匹配必须进入 `insufficient_evidence`；
- 标题、薪资、公司名和模型猜测不能充当职责证据。

### 原子要求与 `foundation`

要求层沿用上一版已确认的根基能力设计：

- `foundation=true` 表示该要求直接支撑岗位主要交付物；
- `central=true` 表示该要求定义岗位特色并能区分相邻岗位；
- `indispensable=true` 只表示 JD 明确写出的不可替代条件；
- 三者相互独立。

复合要求必须拆开：

```text
错误：全栈技术基础

正确：
- 前端开发能力
- 后端开发能力
- 数据库与接口能力
- AI 编程工具实践
```

“Python 或 Node.js 或 Java 后端”可以保留为一条替代关系，因为满足任意一种即可证明同一个后端
根基。前端、后端和数据库不能合成一条。

学习、沟通、Git、责任心、年限、学历以及没有工作对象的“会使用 AI”不能单独标成根基能力。

## 第二次模型调用：匹配主体与要求

继续使用现有 `matchJob`，一次完成两个任务：

1. 岗位主体与候选人经历的语义匹配；
2. 岗位要求的逐条证据匹配。

输出保持扁平：

```json
{
  "roleAlignment": "mostly_aligned",
  "roleResumeEvidence": [
    "简历：使用Python和FastAPI参与企业级AI应用后端开发",
    "简历：具备接口联调、测试和日志排查经验"
  ],
  "roleGaps": [
    "前端开发和完整全栈交付尚未证明"
  ],
  "matches": [],
  "eligibility": []
}
```

`roleResumeEvidence` 只能引用已确认画像、简历版本和匹配卡中的事实。`userNotes` 仍只表示偏好，
不得作为经历证据。

这里的 `matches` 是模型原始稀疏输出；通过现有契约校验后，内部仍规范化为
`requirementMatches`。`roleAlignment`、`roleResumeEvidence` 和 `roleGaps` 同时进入规范化后的
分析对象，供本地分桶与用户解释共用。

## 岗位主体匹配的五种内部状态

### `aligned`：一致

候选人有同类工作对象、主要动作和交付结果的直接证据。工具或行业可以存在少量差异，但不能
改变工作主体。

### `mostly_aligned`：基本一致

候选人与岗位具有相同工作对象或主要交付链路，并已覆盖一个实质性交付方向，只缺部分环节、
工具或相邻能力。

AI 辅助全栈岗位中，候选人已有 Python/FastAPI 后端、接口、测试与调试，但缺少前端和完整
全栈交付，属于该状态。

### `partially_aligned`：部分一致

候选人只覆盖岗位主体的一小部分，或只有可迁移的相邻能力，尚不能证明能承担主要交付。

只有 Agent/RAG 工作流、没有企业业务系统前后端交付时，匹配 AI 全栈岗位属于该状态。

### `misaligned`：不一致

候选人的明确经历指向不同工作对象或交付结果，重合内容只属于通用方法、工具或软技能。

AI 后端/Agent 经历匹配以 UI 组件库、多端视觉为主体的 AI 前端岗位，属于该状态。该状态本身
只允许降级，不直接制造硬淘汰。

### `insufficient_evidence`：证据不足/待确认

JD 没有足够职责证据，或候选人材料没有足够事实，无法可靠判断方向。它不同于“不一致”，不能
写成候选人明确不会，也不能自动产生硬缺口。

这个状态只在内部保存。用户最终仍只看到主投、可投、慎投、不推荐四档。

## 主体匹配的证据规则

模型必须同时比较：

1. `roleSummary`；
2. `responsibilityEvidence`；
3. 候选人事实。

比较对象是“工作对象 + 工作动作 + 交付结果”，不能只比较工具词：

- RAG、Agent 不能证明 UI 组件开发；
- 通用 AI 编程工具使用不能证明组件库、多端视觉或前端框架能力；
- Python/FastAPI、接口、测试和调试可以证明业务系统的后端交付部分；
- LangGraph 工作流不能证明 ComfyUI、图片生成、ERP 或其他未出现的工作对象；
- 用户目标方向不能替代经历证据。

### 行业、平台与技术栈的边界

行业、业务域、客户类型、指定平台、框架和技术栈本身不定义岗位主体。模型必须先比较不随行业
变化的“工作方式 + 交付物”：

- 同样是开发、集成、部署和维护软件或 AI 应用，只是从知识库换到电商、ERP 等业务域，主体
  仍可为 `mostly_aligned`；行业经验、专用接口和业务规则进入要求缺口；
- 同样是交付 AI Agent，只是岗位指定 Dify、Coze、RPA 或特定云平台，平台差异进入
  `requirementMatches`，不能单独把主体降成 `partially_aligned` 或 `misaligned`；
- 同样是业务系统后端或全栈交付，只是 Python、Java、前端框架或垂直系统不同，已证明一个
  实质性交付方向时仍可为 `mostly_aligned`，缺失栈和领域经验继续限制主投；
- 只有主要工作方式或交付物不同，才使用 `partially_aligned` / `misaligned`。例如 UI
  组件库与多端视觉工程不同于后端业务系统交付，销售获客不同于软件实施。

这条规则不能反向证明候选人具备未出现的行业、平台或技术栈经验。它只决定“是否属于同一岗位
主体”，具体要求仍必须逐项按简历证据匹配。

状态约束：

- `aligned`、`mostly_aligned`、`partially_aligned` 必须至少有一条非空
  `roleResumeEvidence`；
- `misaligned` 必须同时存在职责证据、候选人事实和非空 `roleGaps`，不能只因简历没写而输出；
- `insufficient_evidence` 必须有具体缺少什么证据的 `roleGaps`；
- 非法枚举、缺字段或证据约束不成立时进入现有的一次契约修复；修复后仍非法则安全失败。

## 岗位要求匹配

要求层继续使用现有稀疏证据匹配：

- `matched`：同一能力的直接事实；
- `transferable`：底层能力相同，但工具、行业或场景不同；
- `unknown`：没有足够事实；
- `missing`：存在明确、可核对的不满足事实；
- eligibility 只在候选人事实与硬资格明确冲突时使用 `conflict`。

requirement match 在本地继承对应要求的 `foundation`、`central`、`indispensable`，第二次模型
无权修改。

要求是否影响最终等级，必须继续服从这三个权重字段：

- `foundation=true`、`central=true` 或 `indispensable=true` 的要求属于决策要求，其未证明、
  可迁移或明确冲突状态可以影响主投、可投、慎投和不推荐；
- 三个字段均为 `false` 的普通附带要求只用于解释和沟通准备。其 `matched` 可以作为补充匹配
  理由，但 `transferable`、`unknown` 或 `missing` 不得单独降低最终等级；
- 培训同事、制作手册、效果量化、通用沟通等内容，除非 JD 明确表明它定义岗位主要工作或
  不可替代交付，否则默认属于普通附带要求；
- 普通附带要求仍保留在 `requirementMatches`、`softGaps` 或 `questionsToVerify` 中，不丢失
  信息，只是不再充当分桶门槛；
- eligibility、结构化硬冲突和现有本地硬边界不受此放宽影响。

根基覆盖状态：

- `none`：新分析没有合法根基要求，兼容地回退现有主线证据规则；
- `unproven`：存在根基要求，但没有任何根基正向证据；
- `partial`：至少一条根基要求为 `matched` / `transferable`，仍有根基未证明；
- `complete`：全部根基要求都有正向证据；存在 `transferable` 时仍不能直接主投。

## 两层综合分桶

先应用现有硬边界，再应用主体和要求的组合。硬边界优先级最高，任何软判断都不能覆盖。

| 主体匹配 | 要求根基 | 最终上限 | 默认行为 |
|---|---|---|---|
| `aligned` | `complete` | 可继续判断 `primary` | 满足其余质量条件时主投 |
| `aligned` | `partial` | `talk` | 可投 |
| `aligned` | `unproven` | `backup` | 慎投，不默认勾选 |
| `mostly_aligned` | `complete` / `partial` | `talk` | 可投 |
| `mostly_aligned` | `unproven` | `backup` | 慎投，不默认勾选 |
| `partially_aligned` | 任意非硬冲突 | `backup` | 慎投，不默认勾选 |
| `misaligned` | 任意非硬冲突 | `backup` | 慎投，不默认勾选 |
| `insufficient_evidence` | 任意非硬冲突 | `backup` | 慎投/待确认，不默认勾选 |
| 任意 | 结构化硬冲突 | `not_recommended` | 不推荐 |

`primary` 仍必须同时满足现有证据完整、岗位质量正常、置信度、经验和风险条件。两层新判断只能
降级或设置上限，不能绕过现有保护把岗位抬升。

不推荐投递继续保留给：

- 学历、资格等明确冲突；
- 安全或合规风险；
- 地点、实习、薪资下限、用户排除词等现有硬边界；
- 具有双侧明确证据的不可替代核心冲突。

主体 `misaligned` 本身不直接进入不推荐，符合当前“投递成本低、召回优先”的产品原则。

## 三个争议岗位的预期结果

### AI 辅助前端

```text
岗位主体：AI 辅助前端与 UI 工程化
主体匹配：misaligned
根基匹配：unproven
最终结果：backup / 慎投
默认勾选：否
```

AI 工具经验不能代替前端、UI 组件库和多端视觉证据。

### AI 辅助全栈

```text
岗位主体：AI 辅助企业业务系统全栈交付
主体匹配：mostly_aligned
根基匹配：partial
最终结果：talk / 可投
默认勾选：是
primary：不允许
```

Python/FastAPI、接口、测试与调试证明一个实质性交付方向；缺少前端和完整全栈使它不能主投。

### AI 应用落地

```text
岗位主体：把 Agent、RAG 和自动化流程交付到企业业务场景
主体匹配：aligned / mostly_aligned 均可接受
根基匹配：complete
普通附带缺口：培训非技术同事、效果量化
最终结果：primary / 主投或 talk / 可投均可接受
验收下限：talk / 可投
默认勾选：是
```

候选人已经有企业 RAG、Agent 工作流、工具调用和独立自动化工具的直接证据。培训推广和效果
量化属于入职后的附带职责或普通要求，缺少简历证据时可以提示，但不能单独把岗位降到
`backup` / 慎投。该岗位位于主投与可投的合理边界，验收不得强制模型猜中唯一一档；
`primary` 和 `talk` 都视为产品可接受结果。

## 候选人 AI 编程工具事实

用户现实中已使用 Claude Code、Codex 等 AI 编程工具完成代码阅读、修改、测试、调试和问题
定位，但当前已确认画像没有明确记录该事实。

实现不得从聊天记录自动写入已确认画像，只能生成一条待用户查看、修改并确认的匹配卡建议：

```text
AI 编程工具实战｜在真实项目中使用 AI 编程工具完成代码阅读、修改、测试、调试和问题定位
```

确认前不能用于正式匹配。

## 模型契约、缓存与兼容

- `understandJob` 增加 `responsibilityEvidence:string[]`；
- requirement 增加必填 `foundation:boolean`；
- `matchJob` 增加 `roleAlignment`、`roleResumeEvidence`、`roleGaps`；
- 新字段缺失、类型非法或证据约束不成立时只允许一次契约修复；
- 提升两个模型阶段和本地决策规则版本，旧缓存不得冒充新语义；
- 不修改数据库 schema，不批量改写历史岗位；
- 历史分析继续可读，重新分析时才产生新字段；
- 正常路径保持两次模型调用；契约修复仍只在非法输出时触发；
- 新输出增加少量文本，实际耗时必须先做单条实测，不能提前宣称无影响。

## 用户可见解释

主投、可投和慎投必须显示两个层面的原因：

```text
岗位主体：AI 辅助企业业务系统全栈交付
主体匹配：基本一致
已匹配要求：Python/FastAPI 后端、接口、测试与调试
待确认要求：前端开发、完整全栈交付
建议：可投，先沟通确认前端工作占比
```

不得把 `unknown` 或 `insufficient_evidence` 写成“不会”，也不得显示内部枚举名和模型提示词。

## 失败处理

- 职责证据为空：主体状态只能是 `insufficient_evidence`；
- 岗位要求为空：不能产生 `primary`，进入慎投/待确认；
- 第二次模型遗漏主体字段：契约修复一次，仍失败则进入现有待分析状态；
- 模型只引用 AI、Agent 等工具词：不得通过主体证据校验；
- 历史分析缺少新字段：继续展示原结果，重新分析后才切换新规则；
- 任一模型阶段失败：不使用本地关键词猜测结果。

## 测试与验收

### 离线红绿回归

先写失败测试，再修改实现。至少覆盖：

1. AI 工具重合、工作对象不同：`misaligned + unproven -> backup`；
2. 同为业务系统交付，后端已匹配、前端未知：
   `mostly_aligned + partial -> talk`；
3. 同一主体且根基完整：才允许继续判断 `primary`；
4. 只有 Agent/RAG 相邻能力：`partially_aligned -> backup`；
5. JD 缺少职责证据：`insufficient_evidence -> backup`；
6. 简历证据不足不能写成 `misaligned`；
7. 复合全栈要求必须拆成前端、后端、数据库等独立要求；
8. 非法主体枚举、空证据和非法 `foundation` 触发一次契约修复；
9. 模型不能修改 requirement 的 `foundation`、`central`、`indispensable`；
10. 结构化硬阻断和其他现有硬边界不放宽；
11. 工作流默认勾选与四档分桶一致；
12. 正常路径没有第三次模型调用；
13. 不存在中文双字、技术词集合或相似度本地救回。

### 少量真实保存 JD

离线全绿后，只使用保存 JD 与正式模型，不访问招聘网站：

1. AI 辅助前端岗位使用三个独立新缓存各运行一次；
2. AI 辅助全栈岗位使用三个独立新缓存各运行一次；
3. 前端岗位三次均为 `misaligned + unproven + backup`；
4. 全栈岗位三次均为 `mostly_aligned + partial + talk`；
5. 每次正常运行都只有现有两次模型调用；
6. 记录两个模型阶段和总耗时、输出长度、契约修复次数与最终证据；
7. 任一结果不稳定或耗时不可接受时停止，不运行新的 20 条。

### 20 条验收

两条岗位的六次小样本稳定后，才运行新的 20 条保存 JD 验收。人工标签新建版本，不覆盖历史：

- AI 辅助前端：主体 `misaligned`，`review/backup`，`keep`，默认不勾选；
- AI 辅助全栈：主体 `mostly_aligned`，`review/talk`，`keep`，默认勾选。

继续检查机会保留率、明显错岗排除率、硬误杀、待分析数量、契约修复和耗时。不得修改人工标签
来迎合模型结果。

如果 20 条验收发现模型仍把行业、平台或技术栈差异误判为主体方向不一致，先停止全量验收，
只使用五条保存 JD 做回归：

- 一条以 UI 组件库、多端视觉为主体的前端岗位必须保持 `backup`；
- 电商 AI Agent、Java AI 应用、Agent 平台实施、Python/ERP 后端四条同类软件交付岗位
  至少进入 `talk`；
- 每条正常路径仍只有一次岗位理解和一次岗位匹配；允许一次既有契约修复，但不得增加第三个
  常规模型阶段。

## 安全边界

- 所有开发只在隔离 worktree 和隔离分支进行；
- 离线阶段不得访问 BOSS 或其他招聘平台；
- 保存 JD 验证不得操作浏览器；
- 不读写主项目 `data/jobs.sqlite`，不启动或操作 8787；
- 不复制、打印或提交模型密钥、端点和模型身份；
- 私有简历、画像、匹配卡、JD 与真实结果只留在
  `D:\DevData\RoleFlow-private-benchmark`，不得提交 Git；
- 本设计不授权真实沟通、投递或招聘平台写操作。
