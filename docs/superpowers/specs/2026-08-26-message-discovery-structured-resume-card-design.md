# 消息发现：简历请求卡片与文字消息混合分流设计

日期：2026-08-26

## 目标与结论

本设计在现有消息发现链路上补齐结构化消息识别，不重写读取器、岗位上下文、语义模型、草稿、候选人进度或浏览器安全控制。

采用的产品行为是：

1. 招聘方纯文字消息继续结合本地候选人资料和岗位上下文生成本地回复草稿；
2. 已验证的简历请求卡片显示为“需要在 BOSS 人工处理附件简历请求”，不点击“同意”或“拒绝”；
3. 同一轮同时出现纯文字和简历请求时，两条路线分别处理，页面同时显示人工操作提示和文字回复草稿；
4. 已验证的平台竞争情况卡片不交给语义模型，也不冒充招聘方消息；
5. 未经真实结构验证的卡片继续安全停止，不能根据“面试”“位置”“简历”等可见文字猜测类型。

草稿只保存在本地，当前仍由用户手动复制发送。任何真实发送、简历同意/拒绝、位置确认或面试时间选择都不在本次授权范围内。

本设计补充并覆盖 `2026-08-25-message-discovery-content-routing-design.md` 中“混合内容整轮不生成草稿”的保守结论。真实页面现已证明纯文字消息和简历请求卡片拥有可独立识别的 DOM 形态，因此可以安全拆分，同时保留未知卡片停止规则。

## 真实页面证据

2026-08-25 至 2026-08-26 使用用户现有的同一登录 Edge 窗口，只读检查了固定 `BOSS-COMMUNICATION` 标签页。检查前后复核了窗口、标签页和当前会话身份，没有点击卡片、按钮或发送入口，也没有填写任何字段。

当前选中会话中，招聘方最后一轮内容依次包含：

1. BOSS 平台的岗位竞争情况卡片；
2. 招聘方纯文字问题，询问英语和粤语水平；
3. 招聘方索要附件简历的交互卡片。

简历请求卡片的稳定结构为：

- 外层为招聘方方向的 `li.message-item.item-friend`，并带有效消息 ID；
- 卡片容器为 `.message-dialog-both.message-card-wrap.boss-green`；
- 类型图标为 `.dialog-icon.resume`；
- 标题区域为 `.message-card-top-title.message-card-top-text`；
- 操作区域为 `.message-card-buttons`；
- 操作项为两个 `.card-btn`，可见文字严格为“拒绝”和“同意”；
- 标题表达“希望获得附件简历并询问是否同意”。

岗位竞争情况卡片的稳定结构为：

- 外层同样是招聘方方向的消息元素，但卡片容器为 `.message-card-wrap.blue`；
- 不含 `.dialog-icon.resume`；
- 标题区域为 `.message-card-top-title`，表达岗位竞争情况；
- 只有一个 `.card-btn.one-btn`，可见文字为“查看详细分析”。

招聘方纯文字消息没有 `.message-card-wrap`，正文位于现有 `.text` / `.text-content` 结构。

当前读取器把以上三项都归为 `text`，因此会把平台卡片和简历操作卡片一起展平成文字交给模型。这是本次问题的直接根因。

本轮获得了完整 DOM 证据，但没有取得可保存的脱敏截图：后台截图接口超时，Windows 捕获在 Edge 再次最小化后没有产生文件。截图缺失不会被描述为真实视觉验收通过；实现验证使用按上述真实 DOM 缩减的离线夹具，真实页面不做点击验证。

## 方案比较

### 方案 A：严格结构子类型与混合分流（采用）

在现有 `contentKind` 上只增加已验证的 `resume_request` 和 `platform_notice`。消息分组时将文字送入现有模型，将简历卡片转换为固定本地人工操作，将平台通知排除；未知结构保持停止。

该方案能同时满足草稿和人工操作提示，改动集中在现有 DOM、读取、核心编排和结果展示四个位置，不增加模型调用或新架构。

### 方案 B：一旦出现卡片就停止整轮

安全但会丢失同一轮可独立处理的纯文字问题。真实结构已经足以证明文字和简历卡片可以拆分，因此不再采用。

### 方案 C：把卡片文字交给模型猜类型

模型无法仅凭展平文字证明按钮、方向和卡片状态，容易把“提到简历/面试”误判为真实操作，不采用。

## 数据与控制流

### 1. DOM 内容类型

`boss_message_dom` 的消息内容类型扩展为：

- `text`：招聘方普通文字结构，且不存在消息卡片；
- `resume_request`：同时满足已验证图标、标题区、按钮区和“拒绝/同意”动作集合；
- `platform_notice`：同时满足已验证蓝色竞争卡、单按钮和标题结构；
- 现有 `voice`、`image`、`attachment`；
- `unknown`：存在卡片但不符合任一完整签名，或结构含糊。

判断顺序先保留现有语音、图片和附件，再识别消息卡片；没有卡片才允许落入 `text`。节点端夹具读取和浏览器内表达式必须使用相同规则。

标题文字只作为完整结构签名的一部分，不得单独触发类型。按钮必须来自已验证的卡片操作区，不能把正文中出现的“同意”“拒绝”当成按钮。

### 2. 消息分组

只处理候选人最后一次发言之后的招聘方消息，保留现有条数、文字长度和消息 ID 校验：

- `text` 进入模型输入；
- `resume_request` 不进入模型，转换为有限枚举人工操作；
- `platform_notice` 不进入模型，也不生成回复或人工操作；
- `voice`、`image`、`attachment`、`unknown` 继续返回 `BOSS_MESSAGE_CONTENT_UNSUPPORTED`，不提交预览基线，使修复后可以重读。

同一已处理组中，文字和简历卡片的消息 ID 都进入组摘要与消息级幂等记录，避免只处理了草稿却反复提示同一张简历卡片。平台卡片在混合组中也进入组摘要，防止页面结构变化导致重复分组；若本轮只有平台通知，则不产生用户结果，只提交现有行预览基线，因为它不是招聘方沟通或用户待办。

### 3. 分类与人工操作

人工操作只允许本地固定值：

```text
kind: resume_request
title: 招聘方请求附件简历
instruction: 请在 BOSS 消息卡片中人工选择“同意”或“拒绝”。
```

上述文字由本地代码产生，不接受 DOM 或模型提供任意展示文案。结果只保存安全类型和消息摘要键，不长期保存招聘方原文、按钮目标、完整 DOM 或模型原始输出。

处理规则：

- 只有文字：保持现有一次语义理解和草稿生成；
- 只有简历请求：不调用模型，生成 `manual_review / other` 的本地安全结论，阶段为 `needs_user_action`；
- 文字加简历请求：模型只接收文字；保留模型草稿和语义结论，同时附加人工操作，并把本轮建议阶段提升为 `needs_user_action`；
- 平台通知加文字或简历请求：平台通知不改变语义，只参与本轮防重复摘要；
- 只有平台通知：静默提交预览基线，不新增候选人进度结论。

历史已进入 `interview_invited` 或 `interview_scheduled` 的岗位仍沿用现有“不倒退”规则。

### 4. 页面顺序

消息结果继续先显示用户真正关心的岗位与沟通结论。在“下一步”区域内，顺序固定为：

1. 需要在 BOSS 完成的人工操作；
2. 可复制的本地回复草稿；
3. 现有人工完成确认入口（如适用）。

混合消息不能因为存在人工操作而隐藏草稿，也不能因为存在草稿而隐藏简历请求。页面不显示 `resume_request`、选择器、消息 ID 等内部字段，也不提供可触发 BOSS 外部写的按钮。

## 错误处理与隐私

- 卡片签名缺少任一关键结构、动作数不符或类型含糊：按未知内容停止；
- 消息 ID、方向、固定标签页、会话身份、登录或风险状态异常：沿用现有立即停止；
- 模型或本地契约失败：保留现有人工判断降级，同时仍显示已确定的简历人工操作；
- 清理消息快照时同时清空文字和消息 ID，不保存卡片 DOM；
- 真实发送、点击、上传和确认接口不参与本实现，也不因测试夹具增加任何浏览器写能力。

## 最小回归验证

实现前先保留会失败的检查，至少证明：

1. 按真实结构缩减的三条消息分别识别为 `platform_notice`、`text`、`resume_request`；
2. 缺图标、缺按钮区、动作集合不符或未知卡片不会落入 `text`；
3. 读取器允许新类型并继续校验完整快照；
4. 混合组只把英语/粤语纯文字问题交给模型；
5. 同一结果同时包含简历人工操作和本地草稿，建议阶段为 `needs_user_action`；
6. 只有简历请求时模型调用次数为零；
7. 只有平台通知时不产生用户结果，只提交预览基线；
8. 未知结构停止且不提交预览基线；
9. 页面先显示人工操作，再显示草稿，并过滤任意未批准的操作类型或文案；
10. 进度事件不保存招聘方正文、草稿、按钮文字或 DOM。

针对性检查通过后运行完整 `npm test`、`git diff --check`、`git status`，再使用离线夹具和本地 Dashboard 模拟人工验收。真实 BOSS 只保留已经完成的低频只读 DOM 取证，不执行真实交互验收。

## 非目标

- 不实现自动发送、自动同意/拒绝简历、自动确认位置或自动选择面试时间；
- 不在没有真实结构证据时实现位置或面试卡片；
- 不建立通用卡片框架、页面理解引擎、消息仓库或第二套模型任务；
- 不修改 BOSS 固定标签页、随机节奏、冷却、访问额度、后台详情页或 checkpoint 安全规则；
- 不修复、启用或验证 `search_page_api`，不恢复 `standalone_detail`；
- 不把平台营销/竞争提示作为招聘方沟通交给模型。
