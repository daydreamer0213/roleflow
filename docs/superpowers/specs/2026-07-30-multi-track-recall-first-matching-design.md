# 多招聘分支与宽松召回匹配设计

## 状态

用户已完成书面审阅并确认本设计方向。本文只定义岗位理解、证据匹配和最终分档，不改变招聘平台访问、真实沟通、投递或账号安全边界。

## 结论

RoleFlow 继续使用现有的两次模型调用：

1. `understandJob` 理解完整 JD；
2. `matchJob` 根据已确认简历画像匹配岗位。

本次不增加按招聘分支重复调用模型的流程。第一调用识别一份 JD 中相互独立的招聘分支，第二调用只选择最符合候选人证据的一个分支，并只匹配该分支及全局要求。

最终仍只展示四档：

- `primary`：主投；
- `talk`：可投；
- `backup`：慎投；
- `not_recommended`：不推荐。

## 已确认的真实问题

历史 JD“Python AI 算法工程师/助理”同时招聘三类候选人：

1. 大模型应用开发；
2. Python 全栈开发；
3. Python 算法开发。

候选人明确匹配第一类。如果把三类要求合并成一张平铺清单，后续规则会因为候选人缺少前端、运维和深度学习算法而错误降级。

另一个已确认问题是“相邻方向”的参照物。相邻方向必须从候选人简历中的既有证据向外扩展，而不是从岗位标题中的“AI”关键词向外扩展。Agent、RAG、Python 后端和 API 集成与当前简历相邻；纯前端、视觉算法、模型训练不能仅因使用 AI 工具而视为相邻。

## 目标

- 多招聘分支 JD 不再把互斥分支要求合并；
- 岗位职责用于判断主体工作，不自动变成候选人必须已有的经历；
- 岗位要求只在所属招聘分支内逐项匹配；
- 行业、指定平台和工具差异不冒充主体方向差异；
- 主体方向匹配时优先保留求职机会，避免模糊能力描述造成误删；
- 明显不同的主体工作、硬性资格冲突和薪资下限冲突仍能可靠拦截；
- 正常路径仍为两次模型调用，不恢复高耗时的逐分支重复分析。

## 非目标

- 不建立完整职业分类库；
- 不要求模型绝对精准地排序所有岗位；
- 不把每条岗位职责转换为任职要求；
- 不因为标题出现 AI、Agent 或算法就提高匹配等级；
- 不使用关键词相似度代替简历事实；
- 不修改 BOSS 采集器、浏览器节奏、沟通或投递行为；
- 不读取或修改正式项目的 `data/jobs.sqlite`。

## 设计原则

### 1. 先确定招聘分支，再做要求匹配

只有 JD 明确存在相互独立的招聘对象时才拆分，例如“第一类/第二类/第三类”、“岗位 A/岗位 B”或分别列出不同职责和要求。普通 JD 始终只有一个默认分支。

模型不得为了规避要求而凭空拆分分支。每个分支必须有 JD 原文职责证据。

### 2. 主体工作由职责决定

主体工作比较：

- 工作对象；
- 主要动作；
- 最终交付物。

行业只是业务环境。电商、金融、教育或 ERP 不会单独改变前端、后端、Agent 或 RAG 的主体工作；但量化策略回测、工业 PLC 控制、视觉模型训练等确实改变工作对象和交付物，必须保留在主体工作中。

### 3. 相邻方向以简历证据为中心

候选人当前已有企业级 RAG、Agent 工具调用、LangGraph、多 Agent、Python/FastAPI、API 集成、检索和自动化证据。因此这些能力的同类交付可视为一致或基本一致。

没有前端组件库、计算机视觉训练、GPU 推理优化、PLC 控制等证据时，不能因为岗位使用 AI 工具就认定为相邻方向。

### 4. 宽松召回不等于忽略硬缺口

求职投递成本低，误删一个可尝试岗位的代价高于多保留一个边界岗位。因此：

- 主体方向一致或基本一致且没有硬冲突时，默认至少保留到“可投”；
- “系统稳定性、客户沟通、方案设计、学习能力、文档意识”等宽泛职责只用于解释，不得单独把岗位降为慎投；
- 核心技术栈、主体交付、明确工作年限、硬资格或核心行业系统经验存在明显缺口时，可以降为慎投；
- 主体工作明显不同且没有实质性桥接证据，或存在学历、薪资等硬冲突时，才进入不推荐。

## 第一调用：`understandJob`

### 输出结构

在现有岗位理解结构上增加有限的分支信息，不把完整要求对象重复嵌套到每个分支：

```json
{
  "industryContext": "法律服务",
  "hiringTracks": [
    {
      "id": "T1",
      "label": "大模型应用开发",
      "roleSummary": "使用 Python、Agent 和 RAG 交付法律 AI 应用",
      "responsibilityEvidence": ["JD：熟悉 Agent 搭建并根据需求搭建工作流"]
    },
    {
      "id": "T2",
      "label": "Python 全栈开发",
      "roleSummary": "维护和扩展 Python 全栈工具链",
      "responsibilityEvidence": ["JD：拆解维护模块并补充文档"]
    },
    {
      "id": "T3",
      "label": "Python 算法开发",
      "roleSummary": "研发和交付深度学习算法",
      "responsibilityEvidence": ["JD：熟悉深度学习底层原理"]
    }
  ],
  "requirements": [
    {
      "label": "Agent 与 RAG 应用开发",
      "trackIds": ["T1"],
      "foundation": true,
      "central": true,
      "indispensable": false,
      "evidence": "JD：熟悉 Agent 搭建并有 AI 产品落地经验"
    }
  ],
  "eligibility": [],
  "riskSignals": []
}
```

### 结构限制

- 新版 `understandJob` 原始输出只接受 `industryContext`、`hiringTracks`、`requirements`、`eligibility` 和 `riskSignals`；不再同时维护一套含义不同的顶层 `roleSummary` / `responsibilityEvidence`；
- `hiringTracks` 为 1–4 项；普通岗位固定为一个 `T1`；
- 每个分支只保留 `id`、`label`、`roleSummary` 和最多四条职责证据；
- `requirements` 仍是唯一要求清单，每项通过 `trackIds` 归属一个或多个分支；
- 全局要求使用全部分支 ID；
- `requirements` 总数继续不超过 16，避免 JSON 膨胀；
- `eligibility` 只保留对整份招聘有效的硬资格；分支特有能力写入对应 `requirements`；
- 分支 ID、要求归属或证据不合法时进入现有的一次契约修复；修复失败后安全进入待分析，不允许退回“合并全部要求”的旧行为。

### 旧顶层主体字段的处理

- 单分支新结果可以在内部读取层派生兼容别名：`roleSummary = hiringTracks[0].roleSummary`，`responsibilityEvidence = hiringTracks[0].responsibilityEvidence`；
- 多分支新结果不得生成职责证据并集，也不得选择第一分支冒充整个岗位主体；
- `matchJob` 选出 `selectedTrackId` 后，分析结果中的主体摘要和职责证据只取所选分支；
- 决策、解释和页面展示必须读取“所选分支主体”，不能继续直接读取未选择的整份 JD 顶层主体字段；
- 兼容别名只服务旧单分支缓存和旧展示，不参与多分支决策。

### 兼容旧结果

历史 `jobUnderstanding` 没有 `hiringTracks` 时，读取层将其规范化成单一 `T1`，现有 `roleSummary`、`responsibilityEvidence` 和全部要求均归入该分支。无需数据库迁移。

新验收必须使用新提示词哈希和新缓存，不能用旧岗位理解缓存证明新规则有效。

## 第二调用：`matchJob`

### 输出变化

模型新增：

```json
{
  "selectedTrackId": "T1",
  "roleAlignment": "aligned",
  "roleResumeEvidence": ["简历：参与企业级 Agentic RAG 检索链路开发"],
  "roleGaps": [],
  "matches": [],
  "eligibility": []
}
```

### 选择规则

- 只能选择 `jobUnderstanding.hiringTracks` 中存在的一个 ID；
- 根据已确认简历事实选择最相关分支，不使用目标岗位名称或用户偏好代替经历证据；
- 存在多个可能分支时选择证据最充分者，并把其余缺口留在解释中，不增加第三次模型调用；
- 没有任何分支具备足够证据时仍选择职责证据最接近的一支，同时使用 `insufficient_evidence` 或 `partially_aligned` 表达不确定性；
- `requirementMatches` 只覆盖所选分支和全局要求；其他分支要求不得出现、不得形成缺口、不得形成 blocker；
- 契约层校验所选分支存在、相关要求恰好覆盖一次、非相关要求没有泄漏。

## 本地确定性分档

本地规则按以下顺序合并结果：

1. 薪资下限、学历或资格冲突、地点等现有硬边界；
2. 所选招聘分支的主体方向；
3. 所选分支及全局要求的证据匹配；
4. 岗位质量和安全风险；
5. 输出主投、可投、慎投或不推荐。

分档下限与上限：

- `aligned` / `mostly_aligned` 且无硬冲突：通常不得低于 `talk`；
- 主体高度一致、核心要求有直接证据且无明显中央缺口：可进入 `primary`；
- 主体相邻但核心栈、完整交付或年限存在明显缺口：进入 `backup`；
- `misaligned` 本身只限制升级，不自动制造硬淘汰；仍有实质性软件交付桥接证据时可保留 `backup`；
- 主体工作不同且只有外围通用能力重合，或存在明确硬冲突：进入 `not_recommended`。

宽泛通用能力不得单独形成中央缺口或硬 blocker，包括：沟通、责任心、学习能力、稳定性意识、方案设计、文档意识和一般性问题排查。JD 明确要求过去承担某类交付且该交付属于岗位主体时，才能作为具体经验要求处理。

## 验收标准

### 离线契约与规则

- 单分支旧结构可兼容读取；
- 多分支结构只匹配所选分支；
- 不相关分支要求无法进入 `requirementMatches` 或 blocker；
- 全局硬资格仍对所有分支有效；
- 非法分支 ID、重复 ID、空证据和错误要求归属稳定触发契约错误；
- 模糊通用职责不能单独把方向匹配岗位降为慎投或不推荐。

### 真实模型小样本

先运行三条：

1. 多招聘分支岗位；
2. AI 辅助前端岗位；
3. Agent 实施岗位。

三条结构和结论稳定后再运行冻结的 20 条，不用每次修改都等待完整 20 条。

### 20 条最终验收

- 精确四档命中不少于 18/20；
- 预期主投、可投、慎投的 15 条不得进入不推荐；
- 预期不推荐的 5 条不得进入主投；
- 多招聘分支关键样本必须精确命中主投；
- 每条仍只允许正常的两次模型调用；契约修复只在格式不合规时触发一次；
- 输出逐条显示所选招聘分支、主体方向、关键证据、核心缺口和最终分档，便于人工复核。

如精确命中为 18/20 或 19/20，必须展示错例并由用户判断能否接受，不得只报告汇总分数。
