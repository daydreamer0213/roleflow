# 消息岗位身份关联修复设计

**日期：** 2026-08-30

**范围：** 消息发现读取 HR 新消息后，将会话关联到本地岗位卡片
**不在范围内：** 真实 BOSS 填写或发送、历史岗位数据的大规模合并、岗位分析与反馈阈值

## 问题与目标

正式数据库中的 3 条未解决会话实际只涉及 2 个岗位：法本的同一岗位留下了两条会话记录，华丰国际贸易留下了一条。当前规则把 BOSS 的“广州”与本地的“广州·越秀区·东风中路”或“广州·白云区·嘉禾”按全文比较，因此把同城岗位误判为 `BOSS_MESSAGE_CITY_MISMATCH`。

华丰岗位还暴露了第二个问题：扫描链路把岗位编号保存为 `boss:<jobId>`，消息详情链路却保存为裸 `<jobId>`，使同一 BOSS 岗位产生两个本地身份。当前候选关联又先要求“岗位名称全局唯一”，没有先利用更可靠的岗位编号和既有会话绑定，因此同名岗位会放大歧义。

本次目标是让能够确定身份的会话自动关联并继续生成草稿，同时保留真正冲突或无法证明身份的会话供用户处理。

## 方案比较

### 方案 A：只放宽城市比较

把城市比较改成前缀或包含关系。改动最少，但华丰的重复岗位编号和同名岗位歧义仍会存在，下一次很可能从“城市冲突”变成“岗位不唯一”。不采用。

### 方案 B：分层身份关联并统一 BOSS 岗位编号（采用）

先规范 BOSS 岗位编号，再按可靠程度逐层缩小候选：

1. 有 `sourceJobId` 时，先匹配规范化后的 BOSS 岗位编号；
2. 有既有会话绑定时，优先保留会话标识一致的候选；
3. 再使用岗位名称、公司、薪资和基础城市验证；
4. 最后仍有多个候选或出现真实字段冲突时，保持未解决，不猜测绑定。

该方案修复共同根因，不增加依赖或新数据库表，沿用现有候选列表和未解决记录。

### 方案 C：迁移并合并所有历史重复岗位

直接改写历史 `jobs`、岗位卡片、观察记录、草稿和事件的外键。可以清理存量数据，但风险和改动范围远大于这次消息识别问题；同一岗位也可能合法存在不同会话，自动合并可能丢失进度。暂不采用。

## 关联规则

### BOSS 岗位编号

产品内部统一使用 `boss:<jobId>`。输入为裸 BOSS 岗位编号时只在进入本地存储和比较前补前缀；已有规范编号保持不变。消息详情的真实 URL仍使用裸 `jobId`，不改变 BOSS 地址格式。

该规范化放在消息岗位上下文边界和候选比较共用的小函数中，不修改其他平台身份。

### 基础城市

只把可明确识别的层级分隔符之后内容视为区、街道或商圈，例如：

- `广州` 与 `广州·越秀区·东风中路`：一致；
- `广州` 与 `广州 白云区 嘉禾`：一致；
- `广州` 与 `深圳·南山区`：冲突；
- 任一侧为空：不据此判冲突，继续依赖其他身份字段。

基础城市比较不使用任意字符串包含，避免“广”之类的短文本被误认为同城。

### 候选优先级

候选选择不再先要求岗位名称全局唯一：

1. 从当前有效 BOSS 岗位卡片开始；
2. 若会话提供岗位编号，优先保留规范编号一致的候选；
3. 若候选中存在当前或兼容旧版会话标识完全一致的记录，优先该记录；
4. 依次验证岗位名称、公司、薪资和基础城市；
5. 只剩一个候选才成功；零个返回对应的明确冲突原因，多个返回 `BOSS_MESSAGE_CARD_AMBIGUOUS`。

若岗位编号指向的卡片已经绑定到另一个无法兼容的会话，仍返回会话冲突，不自动覆盖原绑定。

## 存量未解决记录与页面

底层继续按会话保存未解决记录，不因标题、公司、薪资和城市相同就删除或合并。原因是相同岗位信息仍可能来自不同招聘者或不同会话，直接按展示摘要去重会隐藏真实待办。

修复上线后，当前可见的未解决会话会在下一次只读发现时重新进入队列；能够通过新规则证明身份的记录会按既有流程生成草稿并清除。已不再出现在消息页的旧记录仍保留，用户可以使用现有“关联、创建或忽略”入口处理。

因此页面仍显示真实未解决会话数，不把 3 条记录伪装成 2 条。后续若要按岗位分组展示，应保留组内会话数量和每条处理入口，另行设计。

## 数据与失败边界

- 不读取或持久化新的 HR 原文；本次只处理已有结构化身份字段。
- 不更改已绑定卡片的会话标识。
- 不自动删除或合并历史岗位、草稿、事件和进度。
- 任何真实城市、公司、薪资或会话冲突继续阻止自动关联。
- 不增加真实 BOSS 访问；验收使用 fixture 和临时数据库。

## 回归验证

至少覆盖以下场景：

1. `广州` 能匹配 `广州·越秀区·东风中路`；
2. `广州` 不能匹配 `深圳·南山区`；
3. 同名岗位存在多家公司时，`sourceJobId` 能选中正确岗位；
4. `boss:<jobId>` 与裸 `<jobId>` 视为同一 BOSS 身份，消息详情不会再创建第二个岗位；
5. 同一岗位编号存在多个候选时，既有会话标识选择正确卡片；
6. 岗位编号一致但会话标识冲突时不覆盖绑定；
7. 未解决记录仍逐条持久化，页面数量不隐瞒待办；
8. 现有不同城市、不同公司、不同薪资和歧义保护继续生效。
