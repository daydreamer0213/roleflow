# RoleFlow Wave 4 验收整改问题台账与设计

- 日期：2026-08-11
- 状态：待实施
- 依据：`docs/superpowers/reports/2026-08-11-wave-0-4-live-manual-acceptance-addendum.md`

## 1. 结论

Wave 0–4 的离线实现已经合并，真实 Edge 验收也证明了扫描、岗位详情读取、单岗位沟通成功路径和底层消息读取具备可用基础，但当前仍不能进入 Wave 5。

整改采用“闸门式推进”：

1. Gate A：先关闭推荐正确性、外部动作安全和消息产品链三个断点。
2. Gate B：再把 Dashboard 收敛为结果、进度、阻塞原因和下一步。
3. Gate C：最后处理性能、隐私、旧页面一致性和诊断噪声。
4. Gate D：建立新鲜质量基线，评测正式二维表和影子积分卡，决定是否进入后续规则迁移。

本轮不做全面重写，不引入前端框架，不启动 Wave 5，也不在整改实现阶段执行新的真实 BOSS 沟通。

## 2. 已确认事实

### 2.1 推荐质量

- 本轮扫描得到 104 个唯一岗位，102 个完整 JD，2 个详情待补，详情读取失败为 0。
- 54 个 `primary/apply/caution` 中有 6 个违反 Search Plan 严格薪资边界，占 11.1%。
- 至少 3 个明显跨技术栈岗位被提升到 `primary`。
- 根因不是二维表本身突然改变，而是 `applyPlatformRuntimePolicy()` 把 BOSS 页面采集条件写回了推荐配置。
- 当前正式决策仍是本地加权二维表；影子积分卡没有进入正式推荐或默认沟通选择。
- 104 个岗位中仍有 5 个 `MODEL_CONTRACT_INVALID`，需要单独统计原因，不能混入规则效果结论。

### 2.2 自动沟通

- 批次 8 对“广东睿云”执行了一次授权点击，最终为 `ambiguous`；BOSS 页面和消息页均未发现建联成功。
- 批次 9 对“趋势智能”执行了一次授权点击，页面按钮、成功弹窗、消息会话、审计事件和进展卡一致，成功路径通过。
- 两次都走相同 DOM `.click()` 路径，因此不能把第一次失败简单归因于“DOM 点击一定无效”或“网页加载慢”。
- RoleFlow 没有观察真正决定结果的 `/wapi/zpgeek/friend/add.json` 异步响应，第一次失败的精确原因已无法追溯。
- 最多一次点击、身份复核、固定双 tab 和串行执行边界工作正常，必须保留。

### 2.3 消息读取

- 底层 `boss_message_reader` 在当前普通 Edge 中成功读取 40 个会话，并通过目标会话身份和消息方向核验。
- Dashboard `/messages` 默认创建 `CdpBrowserAdapter({ port: 9222 })`，没有复用当前 Edge Control，因此产品入口以 `BROWSER_DISCONNECTED` 停止。
- 页面提交没有即时呈现 POST 失败，错误文本也没有对 `BROWSER_DISCONNECTED` 做用户可理解的映射。

### 2.4 Dashboard 与许可证

- 侧栏倒字、流程体检过密、原始 `multiBusinessDistrict` 参数、自动沟通入口不清楚等均已在普通 Edge 复现。
- 根目录没有 `LICENSE`；`package.json` 的 `private: true` 不能替代许可证。
- AGPLv3 允许商业使用，不满足“禁止他人盈利使用”的硬要求。许可证必须作为独立决策处理。

## 3. 方案比较

### 方案 A：闸门式增量整改（采用）

保留现有分层成果和安全状态机，先修三个底层契约，再迁移页面和做质量评测。

优点：

- 每个问题都有独立回归和回滚点。
- 能并行处理推荐、沟通、消息三条互不重叠的链路。
- 不降低 JD 覆盖、召回和安全检查。
- 不需要引入新的框架或依赖。

### 方案 B：先做 Dashboard 视觉重构（不采用）

能够较快改善观感，但底层推荐结果、沟通失败解释和消息浏览器连接仍然不可信，页面验收会被错误数据污染。

### 方案 C：按标准分层全面重写（不采用）

当前代码仍有较多逻辑集中在 `src/dashboard/server.js` 和 `src/cli.js`，但 Wave 0–4 已经抽出了 application、storage、view model 和 page 模块。此时全面重写会扩大回归面，也无法直接解决真实验收发现的三个断点。

## 4. 目标架构

### 4.1 采集与推荐策略分离

```text
BOSS 页面状态
  -> Acquisition Policy
  -> 搜索 URL、城市、平台筛选、读取预算
  -> 候选岗位与完整 JD

Search Plan + Matching Card + Candidate Profile
  -> Recommendation Policy
  -> 薪资/地点/经验硬边界、证据、风险、权重、阈值
  -> 正式推荐与批次候选
```

约束：

- 采集范围可以比推荐范围宽，以保留召回。
- 平台当前筛选不得覆盖 Search Plan 的推荐硬边界。
- `platformPolicy` 可参与采集和来源说明，但不得清空风险规则、排除词、活跃度、作息偏好或正式薪资边界。
- 每个分析结果必须记录 Recommendation Policy 的版本和哈希；采集策略版本单独记录。

### 4.2 统一浏览器权威

```text
Dashboard browser authority
  -> Edge Control（默认）
  -> Portable/CDP（显式备用）

同一 authority
  -> 扫描
  -> 岗位详情读取
  -> 自动沟通
  -> 消息只读发现
```

Dashboard 子模块不得自行硬编码浏览器端口或创建第二套浏览器选择规则。

### 4.3 沟通派发与结果观察分离

```text
身份复核
  -> 最多一次点击
  -> 观察 chat config / friend add 脱敏结果
  -> 页面状态复核
  -> 消息会话复核
  -> succeeded / platform_rejected / transport_failed / ambiguous
```

约束：

- 观察器只保留 endpoint 类别、HTTP 状态、脱敏业务码、耗时和错误类别。
- 不保存 `securityId`、聊天身份参数、Cookie、请求体或完整响应。
- HTTP 200 不能单独代表成功；页面与目标会话身份仍需二次复核。
- 点击后任何证据不唯一都进入 `ambiguous`，禁止自动补点。

### 4.4 结果导向的 Dashboard

主页面只回答：

1. 当前在哪一步；
2. 已完成多少；
3. 得到多少可用结果；
4. 是否被阻塞；
5. 用户下一步只需要做什么。

岗位标题流水、请求日志、重试细节、未解析参数和历史累计默认进入折叠技术详情或诊断页。

## 6. 依赖与并行边界

### 第一并行组

- Lane A：RF-A01，推荐策略分离。
- Lane B：RF-A02、RF-A04、RF-A05，沟通观察和安全恢复。
- Lane C：RF-A03，消息浏览器接线。

三个 Lane 可以在独立 worktree 中并行。合并时先 A，再 B，再 C；每次合并后运行完整离线测试。

### 第二并行组

必须等待相应底层契约稳定：

- Lane D：RF-B01、RF-B04、RF-B07、RF-B10、RF-B11，工作流与 shell。
- Lane E：RF-B02、RF-B08、RF-B09，自动沟通中心，依赖 Lane B。
- Lane F：RF-B03，消息中心，依赖 Lane C。
- Lane G：RF-B06，隐私脱敏，可独立。

`src/dashboard/server.js` 是共享热点。Lane E、F 的 server 接线不能同时直接修改同一工作区；优先让页面进入独立 `pages/` 与 `view_models/` 文件，最后串行接入路由。

### 第三组

- RF-B05 性能读模型在页面信息收敛后实施，避免为即将删除的同步数据计算做优化。
- RF-C01–C03 在核心页面稳定后实施。
- RF-D01、RF-D02 必须使用 RF-A01 修复后的新鲜基线。

## 7. 统一验收标准

### 自动化

- 每个缺陷必须有最小回归测试，行为修改先看到测试失败再实现。
- 分支运行聚焦测试、`git diff --check` 和 `npm.cmd test`。
- 不增加真实浏览器、网络、模型或私有数据库依赖到默认测试。
- 不新增依赖，除非单独获得批准。

### 真实 Edge

- 默认使用用户当前普通 Microsoft Edge。
- 始终保持一个登录会话、一个窗口和两个固定 BOSS tab。
- 只读验收可以直接执行；真实沟通和发送消息仍需单独明确授权。
- 页面相关结论必须核对 DOM 身份、URL 和最终 UI 状态，不能只信工具返回成功。

### 产品质量

- 不降低 JD 覆盖、召回、匹配准确性、随机节奏、冷却、检查点或恢复能力。
- 规则变化后的评测只能使用新鲜基线；旧数据库只作为恢复证据。
- Wave 5 继续暂停，直到 Gate A–D 的相应验收报告明确通过。

## 8. 完成定义

Wave 4 验收整改完成必须同时满足：

1. RF-A01–RF-A05 全部通过离线回归；
2. 推荐结果使用未受平台筛选污染的新鲜基线；
3. Dashboard 消息只读发现从产品入口在真实 Edge 通过；
4. 自动沟通成功、明确失败、超时和歧义均有可解释状态，且无自动重复点击；
5. 主流程页面在 Edge 桌面和窄屏通过人工验收；
6. 隐私、性能和诊断默认视图达到 Gate C 门槛；
7. 正式二维表与影子积分卡的评测结论单独成文；
8. Wave 5 仍由用户在整改验收后决定是否启动。
