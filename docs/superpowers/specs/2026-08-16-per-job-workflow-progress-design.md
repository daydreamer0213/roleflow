# RoleFlow 逐岗位进度与明确进度条设计

**日期：** 2026-08-16

**状态：** 已确认，待实施计划

**课题：** 扫描、完整 JD、岗位分析和沟通的逐岗位进度

**基线：** `ca54c1c`（课题 1 已完成且全量安全验证通过）

## 1. 背景与当前证据

当前产品已经具备可靠的持久化基础，但四个阶段没有形成一致、直观的进度表达：

- 扫描目标保存在冻结执行快照中，目标终态保存在 `scan_target_results`；列表岗位主要在一个搜索目标完成时批量 checkpoint。
- 成功读取的完整 JD 已按岗位写入 `job_observations`，但当前页面用“全部已发现岗位减去完整 JD”计算待补数，会把本来无需读取详情的硬排除岗位也算进待补。
- 分析任务已在 `workflow_job_tasks` 中逐岗位持久化，每次尝试也有独立记录；这部分数据足以生成逐岗位状态。
- 沟通条目已在不可变批次的 `communication_batch_items` 中逐岗位持久化，现有 `/api/communication-status` 已能读取当前条目状态。
- `/api/workflow-status` 使用本地 SQLite 聚合状态，页面可见时约每 2.5 秒轮询，隐藏时停止。
- 当前只有一条偏向分析阶段的进度条；扫描和沟通主要显示数字。
- 工作流的沟通轮询在任一计数变化时请求整页刷新；暂停、控制状态或阶段状态变化也可能造成不必要的结构刷新。
- 当前生产路径只有用户主动启动工作台时的一次 `browser.bringToFront`；本课题不得增加调用。

相关离线基线已经通过：

- `tests/workflow_progress_smoke.js`
- `tests/workflow_dashboard_smoke.js`
- `tests/communication_application_smoke.js`
- `tests/dashboard_communication_batch_smoke.js`

## 2. 目标

1. 用户始终能看懂当前在处理哪一类工作、已完成多少、还剩多少。
2. 扫描、完整 JD、岗位分析和沟通分别有真实、明确、可访问的进度条。
3. 分析和沟通展示逐岗位状态；扫描和 JD 在总数尚未稳定时明确显示增长中的分母及当前处理序号。
4. 逐岗位状态变化只局部更新，不再因一个岗位完成就整页刷新。
5. 所有进度继续来自 SQLite 已保存事实，不引入内存计数或第二套进度来源。
6. 不增加任何 BOSS 页面操作、并发、焦点切换或覆盖损失。
7. 保持暂停、恢复、冷却、风控即停、页面丢失即停和不确定沟通结果人工确认边界。

## 3. 非目标

- 不引入 WebSocket、SSE、前端框架、常驻进度服务或新依赖。
- 不创建新的进度事件表，不复制现有任务和沟通状态机。
- 不把四个阶段压成一个看似精确但没有真实权重依据的总百分比。
- 不改变扫描预算、JD 覆盖目标、关键词、推荐规则、模型并发或沟通配额。
- 不改变 BOSS 选择器、页面识别、固定标签、风险控制或沟通执行语义。
- 不在轻量轮询接口中返回完整 JD、岗位分析、消息正文、沟通证据或错误正文。
- 不要求真实 BOSS 验收才能完成第一轮实现；真实页面操作仍需另行遵守当前授权边界。

## 4. 已确认的产品决策

### 4.1 四条独立进度轨道

页面固定展示四条轨道，不计算跨阶段综合百分比：

| 轨道 | 权威数据 | 分母语义 | 用户看到的主要内容 |
| --- | --- | --- | --- |
| 扫描岗位 | 冻结的执行目标、`scan_target_results` | 搜索目标总数在开始时固定 | 已处理目标 / 总目标、成功/部分/失败、当前目标序号 |
| 完整 JD | 当前批次 `job_observations` | 扫描未结束前随新岗位增长，扫描结束后固定 | 已读 / 当前需读、待补、无需详情、当前岗位序号 |
| 岗位分析 | `workflow_job_tasks` | 分析任务创建后固定 | 已完成 / 总数、等待、运行、重试、失败、跳过及逐岗位状态 |
| 沟通 | 不可变 `communication_batch_items` | 用户确认清单后固定 | 已终态 / 已确认岗位、当前处理序号、成功、停止、歧义及逐岗位状态 |

“已处理搜索目标”包括 `completed`、`partial` 和 `failed` 三种终态。它与“成功完成目标”不是同一个数字。当前实现把部分完成和失败目标仍算进 pending，本课题需要纠正这项语义。

### 4.2 扫描与 JD 是交错阶段

BOSS 扫描按搜索目标执行：读取一个目标的岗位卡后，会立即读取该目标的部分完整 JD，再进入下一个目标。因此页面不能伪装成“先完成全部扫描，再开始 JD”。

整体阶段改为以下四个用户阶段：

1. 准备本轮；
2. 采集岗位与完整 JD；
3. 分析岗位；
4. 确认清单与执行沟通。

第二阶段内部同时展示“扫描岗位”和“完整 JD”两条轨道。当前动作可以在“正在读取搜索结果”和“正在读取第 N 个岗位详情”之间切换，但整体阶段不会倒退。

### 4.3 逐岗位展示和隐私边界

- 分析阶段进入时，服务端从当前工作流任务表渲染岗位名称、公司和初始状态。
- 后续轮询只返回当前工作流内的任务 ID、位置和状态，客户端按 ID 更新已有行；不在轻量状态接口重复返回岗位标题。
- 沟通页面已经服务端渲染不可变批次的岗位清单。轮询现有沟通状态接口后，只用条目 ID 更新计数和状态。
- 扫描期间岗位集合仍在增长，轻量状态接口只显示当前搜索目标、目标序号、已发现数量和当前详情序号，不返回新发现岗位的标题或描述。
- 进入分析阶段允许一次结构刷新，此时完整的逐岗位分析列表由服务端安全渲染。

### 4.4 结构刷新边界

以下变化只局部更新：

- 新搜索目标或新岗位 checkpoint；
- 完整 JD 成功或待补数量变化；
- 分析岗位从等待、运行、重试到终态；
- 沟通岗位从等待、打开、核验、点击到终态；
- 冷却倒计时、ETA、最近活动、暂停请求和控制按钮可用性变化。

只有需要替换整块操作界面的状态变化允许一次整页刷新：

- 采集与 JD 转入分析，需要服务端渲染完整分析岗位列表；
- 分析完成转入人工确认清单；
- 清单确认后转入沟通执行；
- 沟通产生歧义，需要出现人工核验表单；
- 工作流或沟通批次进入最终完成、停止、失败或中断页面。

扫描和分析中的暂停/继续如果仍属于同一阶段，不触发结构刷新；页面已经同时具备运行和暂停控制区，可以局部切换。

## 5. 总体架构

继续沿用现有单机结构：

```text
BOSS adapter
  -> 在现有列表提取和详情读取节点发出本地进度回调
  -> 不增加导航、滚动、详情读取或前台焦点操作

CLI / scan store
  -> 使用现有 checkpointScanProgress / checkpointScanTarget
  -> 写入新增岗位 observation
  -> 更新冻结批次 runtime.scanProgress
  -> 对真实进度 checkpoint 增加 workflow progress revision

SQLite
  -> batches.filter_snapshot_json.runtime.scanProgress：当前扫描动作（有界、可覆盖）
  -> scan_target_results：搜索目标终态
  -> job_observations：岗位发现和完整 JD
  -> workflow_job_tasks：逐岗位分析状态
  -> communication_batch_items：逐岗位沟通状态

Dashboard
  -> /api/workflow-status 返回轻量进度和逐任务 ID/状态
  -> /api/communication-status 返回当前不可变批次状态
  -> 可见页面 2.5 秒轮询并局部更新
```

数据库仍是唯一权威。浏览器适配器回调只是把已经观察到的事实交给现有 checkpoint，不成为独立状态源。

## 6. 扫描期 checkpoint

### 6.1 列表岗位 checkpoint

`collectCards()` 在现有 DOM 提取轮次中已经可以识别新增卡片。本课题增加一个可选回调，只传递本轮新出现且已经去重的卡片，而不是每轮反复传递全部卡片。

回调遵守以下边界：

- 每次 DOM 提取增长最多执行一次本地批量 checkpoint，不为每张卡单独开启事务；
- 使用现有 `upsertJob()` 和 `(batch_id, job_id)` observation 唯一约束，重复观察只更新当前批次事实；
- checkpoint 失败时，在下一次 BOSS 操作之前停止扫描并保留明确错误；
- 不增加 `evalValue`、滚动、导航、详情读取、等待或重试；
- 不改变随机节奏、访问预算和安全暂停边界。

这使“已发现岗位数”在列表增长时更新，而不必等整个搜索目标及其 JD 全部结束。

### 6.2 当前扫描动作

复用 `batches.filter_snapshot_json.runtime`，增加有界字段 `scanProgress`：

```json
{
  "version": 1,
  "activity": "searching|reading_detail|target_complete",
  "targetKey": "frozen-target-key",
  "targetPosition": 2,
  "targetTotal": 5,
  "targetDiscovered": 18,
  "detailPosition": 4,
  "detailTotal": 11,
  "updatedAt": "2026-08-16T00:00:00.000Z"
}
```

该字段不保存岗位标题、JD、URL、Cookie、页面内容或账号信息。目标显示名称从同一批次的冻结执行快照按 `targetKey` 解析，不能接受运行期未冻结的文本。

只有以下事实会提升 `workflow_runs.progress_revision`：

- 新岗位 observation 已提交；
- 搜索目标终态已提交；
- 当前动作或详情序号发生变化。

仅保存 `bossPacing` 的节奏 checkpoint 不提升用户进度版本，避免无意义重绘。

## 7. 完整 JD 计数语义

当前批次岗位分为三类：

- `read`：已满足完整 JD 判定；
- `pending`：明确需要详情且仍带有 `detail_unverified`；
- `notRequired`：本地硬边界已经排除，不需要消耗 BOSS 详情读取。

显示值为：

```text
required = read + pending
```

进度条使用 `read / required`，而不是 `read / collected`。同时单独显示：

- 已发现岗位 `collected`；
- 当前需读 `required`；
- 待补 `pending`；
- 无需详情 `notRequired`。

扫描未结束时，页面必须显示“当前需读，总数可能随扫描增加”；扫描结束后去掉该提示，分母固定。禁止把分母增长表现成进度倒退或错误。

## 8. 分析逐岗位进度

`getWorkflowProgressSnapshot()` 已读取当前工作流的所有 `workflow_job_tasks`。在不增加历史查询的前提下，返回每个任务的：

```text
id、position、status、lastErrorCode
```

初始 HTML 页面额外请求当前工作流范围内的岗位显示信息，渲染紧凑列表：

- 岗位名称；
- 公司；
- 当前位置；
- 等待分析；
- 分析中；
- 等待重试；
- 已完成；
- 详情待补；
- 分析失败；
- 已停止。

轮询响应只用任务 ID 和状态更新列表，不返回标题、公司、JD、分析内容或错误正文。`lastErrorCode` 只能从明确允许的错误码白名单中返回，用于有限状态标签；不直接展示模型错误消息或任意内部错误文本。

分析进度条分子为所有终态任务：

```text
succeeded + failed + skipped + stopped
```

`retry_pending` 和 `running` 仍属于未完成。现有 ETA、重试、熔断和暂停语义保持不变。

## 9. 沟通逐岗位进度

沟通批次确认后分母不可变。进度条使用：

```text
terminal / total
```

沟通页面为每个已有条目增加稳定 DOM hook，并用一个小型独立静态脚本轮询现有 `/api/communication-status`：

- 更新批次总数、终态、成功和剩余；
- 按条目 ID 更新状态标签；
- 标记当前正在 `opening`、`verified` 或 `click_dispatched` 的条目；
- 页面隐藏时停止轮询；重新可见时立即读取一次；
- 相同状态不重绘；一次只允许一个请求在途。

以下情况停止局部更新并只刷新一次：

- 出现 `ambiguous`，需要服务端渲染人工核验表单；
- 批次进入完成、停止、失败或中断；
- 批次 ID 或不可变条目集合与页面初始快照不一致。

不自动解决歧义、不重试不确定结果、不改变沟通授权和单次点击边界。

## 10. 页面布局与可访问性

“本轮概览”下面增加四条紧凑轨道。每条包含：

- 阶段名称；
- 原生 `<progress>`；
- 明确的文字分数；
- 当前动作；
- 状态拆分。

未知或仍增长的分母不伪造百分比：

- 尚未开始且没有分母时显示“等待上一阶段”；
- 活跃但分母仍为 0 时使用无 `value` 的原生不确定进度条；
- JD 分母增长时保留真实 `read / required`，并显示增长提示；
- 不能把“已发现岗位数”当成“需要读 JD 的总数”。

可访问性要求：

- 每条 `<progress>` 有唯一可见标签和 `aria-describedby`；
- 不能只用颜色表示等待、运行、成功、失败或歧义；
- 当前动作使用单个 `aria-live="polite"` 区域，只有状态键变化时更新，避免每次轮询重复朗读；
- 逐岗位行使用文字状态并对当前行设置 `aria-current="step"`；
- 不增加持续动画；继续尊重 `prefers-reduced-motion`。

## 11. 轮询和错误处理

轮询规则保持简单：

- 页面可见且任务活动：每 2.5 秒一次；
- 页面隐藏：不发网络请求；
- 页面重新可见：立即读取一次，再恢复 2.5 秒节奏；
- 终态或页面离开：停止计时器；
- 任意时刻最多一个请求在途。

接口失败时：

- 保留最后一次成功快照，不把进度归零；
- 显示“无法读取任务状态”；
- 禁用可能重复启动或改变外部状态的操作；
- 不因一次读取失败整页刷新；
- `lastActivityAt` 超过现有健康阈值时继续显示失活警告。

## 12. 安全与质量边界

- 不增加任何 BOSS 操作；列表 checkpoint 发生在现有 DOM 提取之后。
- 保留既有 `BOSS-SEARCH` 和 `BOSS-COMMUNICATION` 两个操作员固定标签，不新建标签或窗口；所有工作串行，每次只操作当前职责对应的一个固定标签。
- 不调用或新增 `Page.bringToFront`；唯一启动引导保持不变。
- 不启用、校准、修复或删除 `search_page_api`；产品详情路径仍只允许 `trusted_pane`。
- 不降低卡片覆盖、JD 覆盖、召回、分析质量或沟通核验要求。
- 风控、登录失效、页面丢失、标签漂移、目标不一致和结果不明确仍立即停止。
- 扫描 checkpoint 不改变筛选结论，只让已经观察到的岗位更早安全落库。
- 轻量工作流状态接口继续不返回岗位标题、JD、简历、模型输出、沟通证据或消息正文。

## 13. 方案比较

### 13.1 推荐：补 checkpoint，复用 SQLite 和轮询

优点：所有数字来自已有事实表；没有新服务和迁移；可以真实显示逐岗位变化；恢复语义自然一致。

代价：需要在现有扫描回调、进度快照和两个页面脚本中增加少量明确字段。

### 13.2 只做四条聚合进度条

优点：代码最少。

拒绝原因：扫描仍按目标大段跳变，JD 分母仍会误算，也没有逐岗位状态，不能满足用户目标。

### 13.3 新建事件流、SSE 或 WebSocket

优点：可以构造更细的历史时间线。

拒绝原因：现有 SQLite 已有任务和沟通状态；新事件流会成为第二套事实来源，并增加安装、恢复、连接和测试复杂度。

## 14. 测试策略

### 14.1 扫描与存储

- 现有卡片提取轮次只对新增唯一卡片触发 checkpoint；
- checkpoint 前后 BOSS `evalValue`、滚动、导航和详情读取调用数完全不变；
- 卡片批量 checkpoint 使用同一事务并保持 observation 唯一；
- 运行期 `scanProgress` 与 `bossPacing` 合并保存，不能覆盖冻结执行快照；
- 节奏-only checkpoint 不提升进度版本；真实岗位、详情和目标 checkpoint 会提升；
- 租约丢失、批次不一致或 checkpoint 失败时立即停止。

### 14.2 进度语义

- `completed`、`partial`、`failed` 都计入已处理目标，只有未出现终态的目标计入 pending；
- 无需详情岗位不进入 JD 分母；
- 扫描中 JD 分母可以增长，扫描结束后固定；
- 分析分子只包含终态任务；
- 沟通分子与批次 `terminal` 一致；
- 暂停、中断和恢复继续映射到真实原阶段。

### 14.3 HTTP 与隐私

- 工作流状态响应只包含允许的任务 ID、位置、状态和错误码；
- 不包含岗位标题、公司、URL、JD、分析、简历或沟通证据；
- 状态读取仍只查询当前冻结批次和当前工作流，不访问计划级历史表；
- 查询条数和返回行数预算按新增逐任务状态重新设定明确上限。

### 14.4 页面与客户端

- 四条轨道的标签、数值、原生 `<progress>` 和可访问关联存在；
- 扫描、JD、分析、沟通的同阶段变化不刷新页面；
- 只有已列出的结构转换刷新一次；
- 页面隐藏不轮询，重复可见事件只保留一个计时器；
- 重新可见后立即读取；
- 接口失败保留旧数据、显示错误并禁用危险操作；
- 沟通条目按 ID 更新，歧义和终态只刷新一次。

### 14.5 回归和人工验收

- 运行所有与扫描、工作流、沟通、恢复和 Dashboard 相关的离线检查；
- 再运行当前安全环境允许的完整离线套件；
- `startup_scripts_smoke.js` 继续不在本机运行，因为其未签名 `msedge.exe` fixture 会被 360 拦截；
- 使用本地隔离数据库和 fake browser 做 5～10 个岗位的可视化验收；
- 不访问真实 BOSS，不执行任何沟通或其他外部写；如果未来需要真实只读验收，另行按当时明确授权和当前固定标签边界执行。

## 15. 验收标准

1. 四个阶段分别有真实进度条和文字分数，没有伪造综合百分比。
2. 扫描列表增长时，已发现岗位数在搜索目标结束前即可更新。
3. 列表 checkpoint 不增加任何 BOSS 浏览器命令。
4. JD 进度只统计真正需要详情的岗位，并明确分母是否仍在增长。
5. 分析列表逐岗位显示等待、运行、重试和终态，完成一个岗位不会整页刷新。
6. 沟通页面逐岗位更新，普通状态变化不会整页刷新。
7. 歧义、人工确认和终态等结构变化最多刷新一次。
8. 隐藏页面零轮询，恢复可见立即读取，始终最多一个请求在途。
9. API 失败不清空进度、不伪装运行成功，也不允许重复启动危险操作。
10. 不新增 `Page.bringToFront`，不启用 `search_page_api`，不降低 JD、召回、匹配或沟通安全质量。
11. 所有本地自动检查和隔离人工验收通过后才允许提交功能实现。
