# 沟通单岗位续验与前台点击修复设计

日期：2026-08-14
状态：用户已批准设计方向，待书面规格确认

## 1. 背景与已确认事实

当前全新安装产生的数据可以继续使用，不需要重新完成简历解析、求职偏好、
岗位扫描和匹配：

- 当前沟通批次包含 12 个不可变岗位快照；
- 第 1 项为 `ambiguous`，`click_count=1`，没有匹配到 BOSS 请求，页面状态也未
  证明成功；
- 后续 11 项仍为 `pending`、`click_count=0`；
- 现有恢复入口会在人工解决第 1 项后继续执行全部待处理项；
- `runCommunicationBatch()` 没有“只处理一项”的执行边界；
- `BossSiteAdapter.dispatchCommunication()` 会向固定 BOSS 搜索标签发送浏览器级
  点击，但目前没有在点击前激活并确认该标签处于活动状态。

因此，下次人工验收可以复用本轮数据，但不能直接使用现有“继续串行执行”：
它既可能一次处理剩余全部岗位，也没有消除后台标签接收不到点击的主要风险。

## 2. 目标

1. 保留现有候选人资料、模型设置、筛选方案、61 个岗位、工作流和沟通批次。
2. 第 1 个结果不明的岗位只允许人工解决，绝不自动重放。
3. 在端到端验收仍为 `e2e_pending` 时，每次明确授权只执行当前下一条
   `pending` 岗位，处理一项后立即停止进程。
4. 授权必须绑定具体的不可变沟通条目 ID，并在页面显示岗位名称和公司。
5. 真正派发点击前激活固定 `BOSS-SEARCH` 标签，再次检查标签、窗口、岗位身份、
   登录、风控、按钮和点击坐标，之后最多点击一次。
6. 点击结果不明确时继续保持 `ambiguous`，不自动重试。
7. 产出可覆盖安装且保留现有数据的 `0.1.0-beta.4.3` 本地安装包，供下一次从
   沟通环节验收，避免用不同代码重复构建同名 beta.4.2。

## 3. 非目标

- 不创建新的沟通批次，不复制现有 11 个待处理条目。
- 不自动把第 1 项判定为成功或失败。
- 不在实现或离线测试期间操作真实 Edge、切换前台标签或触发 BOSS 写动作。
- 不改变 `trusted_pane`，不启用 `search_page_api`，不使用
  `standalone_detail`。
- 不启动 Wave 5，不调整扫描召回、JD 覆盖或匹配质量。
- 不处理卸载器双提示和残留 bridge 进程；它们作为独立问题保留。
- 不创建标签、不推送远端、不发布公开版本，除非用户随后明确授权。

## 4. 设计决策

采用“原批次 + 精确单条续验”，不增加数据库结构。

### 4.1 第 1 项的处理

第 1 项继续保持 `ambiguous`，直到用户在沟通页面填写可核验说明并选择：

- “确认已沟通”；或
- “标记停止”。

本轮证据无法证明成功，因此下一次验收推荐选择“标记停止”，说明只陈述事实：
当时没有匹配到 BOSS 请求、页面没有可确认变化，因此停止该项以防止重放。

这是用户触发的本地状态更新，不访问 BOSS。解决后保留原
`click_count=1`、原始证据和人工处理审计，执行器不得再次选择该条目。

### 4.2 单岗位验收动作

当批次状态为 `confirmed`、`paused` 或 `interrupted`，不存在未解决
`ambiguous`，且校准状态仍为 `e2e_pending` 时，沟通页只提供单项验收动作：

- 页面显示下一条 `pending` 条目的岗位名称和公司；
- 表单提交批次 ID、`start_one` / `resume_one` 动作和该条目的不可变 item ID；
- 服务端重新读取批次，确认提交的 item ID 仍是排序后的第一条 `pending`；
- 条目已变化、不是当前下一条、存在歧义或批次状态变化时返回 409，不启动进程；
- `e2e_pending` 期间，普通全批次 `start` / `resume` 请求由服务端拒绝，防止通过
  旧页面或手工 HTTP 请求绕过单项边界；直接运行 `communicate` CLI 时也必须
  提供精确的 `--single-item`。

校准状态以后变为 `accepted` 时，现有完整串行模式可以继续使用；本设计不负责
改变验收状态。

### 4.3 执行进程边界

服务端只为已验证的 item ID 启动隐藏 CLI 进程，并通过
`--single-item <itemId>` 把该 ID 传入。
执行器启动后再次确认：

- 批次处于可执行状态；
- 不存在未解决歧义；
- 指定条目仍为第一条 `pending`；
- 指定条目 `click_count=0`。

执行器只认这一条授权。该条目进入任一终态后：

- 若结果为 `succeeded`、`already_communicated`、`job_unavailable`、
  `target_mismatch` 或 `action_unavailable`，批次写入受控单项检查点并停止；
- 若点击后结果不明确，沿用现有 `ambiguous` + `interrupted` 路径；
- 若出现登录、风控、页面丢失、标签漂移或浏览器断开，立即中断；
- 剩余条目保持 `pending`，不等待随机间隔，也不选择下一条；
- 即使本条使工作流成功目标暂时达到，也先保留剩余条目并停在验收检查点，
  不在本次单项授权内批量结束它们。

受控检查点复用现有 `interrupted` 状态和恢复能力，使用明确的
`COMMUNICATION_SINGLE_ITEM_CHECKPOINT` 代码；不增加新状态或数据库迁移。
批次和关联工作流一起记录检查点，避免进程已经退出但工作流仍显示“执行中”。

### 4.4 点击前激活与重新校验

只读检查阶段继续允许固定 BOSS 标签在后台运行。只有用户已授权的单项真正准备
点击时，执行以下顺序：

1. 从本次 Edge 绑定重新取得数值型固定 tab ID；
2. 确认 `BOSS-SEARCH` 和 `BOSS-COMMUNICATION` 仍在同一绑定窗口；
3. 调用浏览器现有 `bringToFront(tabId)` 激活固定 `BOSS-SEARCH`；
4. 重新读取标签列表，确认该 tab 存在、窗口一致且 `active=true`；
5. 重新读取页面快照，检查登录、风控、岗位 ID、标题、公司、招聘状态、
   唯一可用“立即沟通”按钮和点击坐标；
6. 启动受限网络日志并记录水位；
7. 发送一次浏览器级点击；
8. 结合 BOSS 网络请求、成功状态、页面身份和会话身份核验结果。

激活失败或激活后身份发生变化时不得点击。由于现有 at-most-once 状态机会在
派发前先持久化点击意图，这类派发阶段异常继续按结果不明处理，不允许自动补点。

CLI 进程结束时沿用现有固定标签恢复逻辑，把 `BOSS-SEARCH` 导航回冻结的搜索
URL 和滚动位置。实现、测试和构建阶段不连接真实 Edge，因此不会抢用户前台。

## 5. 页面行为

沟通页在歧义未解决时仍只显示人工处理表单，不出现执行按钮。

歧义解决后，`e2e_pending` 页面显示：

- “下一次仅验收 1 个岗位”；
- 下一条岗位的名称和公司；
- “验收这个岗位并自动暂停”按钮；
- 明确说明不会继续第三个岗位，结果不明也不会重试。

单项检查点返回后，页面显示本条结果和剩余待处理数量。用户必须再次明确操作才
能处理下一条。

## 6. 错误处理与安全边界

- 提交条目不是当前第一条 `pending`：拒绝启动，提示刷新。
- 存在 `ambiguous`：继续要求人工解决。
- 校准、登录、风控、运行时冷却或标签绑定检查失败：拒绝启动或立即中断。
- 激活后 tab 不是活动标签：不点击。
- 点击已派发但成功证据不足：`ambiguous`，不重试。
- 进程启动失败：沿用现有 `COMMUNICATION_PROCESS_START_FAILED`。
- 单项检查点写入失败：不启动下一项，按中断状态报告。
- 所有真实浏览器动作保持串行；不创建新窗口、新 BOSS 会话或每岗位标签。

## 7. 最小实现范围

预计只修改现有路径：

- `src/application/communication/index.js`：校验单项动作与精确 item ID；
- `src/dashboard/view_models/communication.js`：给页面提供下一条不可变岗位；
- `src/dashboard/pages/communication.js`：渲染单项授权说明和表单；
- `src/dashboard/server.js`：把精确 item ID 传给隐藏 CLI；
- `src/cli.js`：解析并传递单项 ID；
- `src/core/communication_executor.js`：限制为一条并写入检查点；
- `src/adapters/sites/boss.js`：点击前激活并确认固定标签；
- 现有对应 smoke tests：覆盖服务端防绕过、精确条目校验、只处理一项、
  剩余项保持 pending、歧义不重试和激活后才点击。

不新增依赖，不新增通用任务调度器，不重构沟通状态机。

## 8. 验证

实现采用测试先行：

1. 先增加会失败的应用层测试，证明 `e2e_pending` 普通恢复被拒绝、精确单项动作
   只启动指定条目。
2. 先增加会失败的执行器测试，证明两条 pending 中只处理第一条，第二条保持
   `pending`，批次和工作流停在单项检查点。
3. 先增加会失败的 BOSS adapter 测试，证明 `bringToFront` 和 active 校验发生在
   `clickAt` 之前，激活失败时点击次数为 0。
4. 运行沟通应用层、执行器、页面和 BOSS adapter 定向 smoke tests。
5. 运行完整离线套件。
6. 构建后续本地安装器，检查版本、文件哈希、安装阶段禁入文件和覆盖安装的数据
   保留规则；不进行真实沟通。

下一次真实人工验收仍需用户针对页面显示的具体岗位明确授权。Codex 只观察日志、
服务和页面状态，不替用户点击“标记停止”或“验收这个岗位并自动暂停”。
