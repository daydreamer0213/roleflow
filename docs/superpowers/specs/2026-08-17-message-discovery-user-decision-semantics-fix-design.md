# 消息发现：用户决策与消息语义修正设计

日期：2026-08-17

状态：设计已确认，等待书面规格复核后编写实施计划

范围：消息发现结果卡的信息结构、消息语义分类、消息摘要和本地回复草稿边界

本设计是对已完成的“消息发现岗位理解与推荐回复草稿”和“消息发现决策卡内容”设计的验收修正。发生冲突时，本设计只在上述范围内覆盖旧设计；后台只读详情、岗位身份、冷却、访问预算、隐私清理和外部写边界继续沿用原设计。

## 1. 真实反馈与代码证据

真实验收暴露的不是几个标题不自然，而是产品组织信息的出发点错了。

- 页面按系统已有的岗位分析字段顺序展示，先讲岗位、公司、匹配和薪资，最后才给机会结论。用户必须读完系统的分析过程，才能找到自己最关心的判断。
- 页面把内部的数据边界说明直接展示成“公司资料不足，不能评价公司本身”等免责声明。它对实现者有意义，对用户没有决策价值，还打断阅读。
- 真实消息只是业务描述中提到了“线上面试”，并没有向候选人发出面试邀请。配置的语义模型将它判断为 `other`，但 `message_reply_analyzer` 随后用“只要出现面试或邀约字样”覆盖了模型结果，最终错误显示为“面试邀请”。
- 当前模型契约和结果投影把“生成本地草稿”也当成危险动作，禁止面试邀请生成草稿。但消息发现页面没有填写、粘贴或发送 BOSS 消息的能力；本地生成草稿和对外沟通不是同一种风险。

因此，本轮修正必须同时解决信息结构、消息语义和动作边界，不能只替换文案。

## 2. 用户真正要完成的任务

用户打开消息发现结果，不是来审计模型用了哪些字段，而是要尽快完成四个判断：

1. 这份机会值不值得我继续投入时间；
2. 对方这条消息到底在表达什么，是否要求我采取行动；
3. 这个岗位做什么、公司或业务做什么、我是否匹配、薪资如何；
4. 如果要继续，我下一步可以怎么回复。

页面应按这条决策路径组织信息。内部枚举、匹配证据数组、质量保护规则和数据免责声明继续留在系统内部，不要求用户理解。

## 3. 方案比较

### 方案 A：以用户决策为中心重排结果，并由同一次模型调用输出消息语义摘要

采用本方案。机会建议前置；消息真实意图紧随其后；岗位、公司、匹配和薪资作为判断依据；最后给本地回复草稿。消息分类采用模型的语义结果，不再由关键词覆盖。

该方案直接解决用户看到什么、按什么顺序看以及错误分类的根因。它复用现有模型调用，不增加 BOSS 访问、数据库迁移、第三方依赖或第二次模型请求。

### 方案 B：只改标题顺序并删除“面试”关键词规则

不采用。虽然改动更小，但页面仍只能显示“其他沟通”等抽象类别，用户仍不知道对方实际表达了什么，不能完整完成消息理解任务。

### 方案 C：同时增加公司外部调查和完整公司评价

本轮不采用。公司调查需要新的数据来源、公司身份核对、缓存、失败处理和质量验收，是独立课题。当前只诚实展示 JD 已有的公司或业务信息。

## 4. 新的信息结构

每个结果卡先显示职位和公司名称，然后按以下固定顺序展示。

### 4.1 建议

- 第一屏最先展示 `opportunityVerdict` 和一条最重要原因。
- 标题使用“建议”，结论措辞继续明确针对当前岗位机会，例如“值得继续聊”“可以了解，但要先确认关键问题”“不建议优先投入时间”。
- 不把这一结论写成对公司整体经营、文化或稳定性的评价。

### 4.2 对方说了什么

- 显示同一次消息模型调用输出的一句 `messageSummary`，说明招聘方当前表达的主要意思以及是否在要求候选人行动。
- 摘要是语义概括，不复制整段消息，不展示内部枚举，也不根据单个词推断意图。
- 消息类别保留为中文辅助标签，用于进度和识别，但不能代替语义摘要。
- 摘要缺失或模型结果不合法时显示“这条消息需要人工确认”，不得自行猜测。

### 4.3 岗位概况

- 使用已有完整岗位分析中的 `roleSummary`，用一至两句话说明工作对象、主要动作和交付结果。
- 标题使用“岗位概况”，不再使用生硬的问句“这个岗位是做什么的”。
- 分析缺失时显示“岗位职责分析尚未完成”，不根据职位名称补写。

### 4.4 公司及业务

- 显示已核验的公司名称和 JD 中明确存在的业务场景。
- 没有业务证据时只显示“JD 暂未说明公司的具体业务”。
- 不再显示 `companyScope` 或任何“不能评价公司本身”的免责声明。
- 通过“建议”明确指向岗位机会来表达范围，不让用户阅读实现层的免责说明。

### 4.5 匹配情况

- 显示高、中、低或待确认，以及一句最重要的匹配结论。
- 不展示“匹配依据”“硬性阻断”“待补信息”“建议核实”等内部分析列表。

### 4.6 薪资

- 显示身份核验后保存的原始薪资文本。
- 缺失时显示“薪资未说明”，不换算、不推断奖金、股票或税后收入。

### 4.7 下一步

- 有可用草稿时显示最多两份“推荐回复”，供用户在本机复制。
- 没有可用草稿时用一句话说明还需要用户确认什么。
- 页面不增加填写、粘贴、发送、沟通或投递按钮。

## 5. 消息语义设计

### 5.1 分类依据

`messageCategory` 必须描述招聘方这轮消息的沟通意图，而不是消息中出现过哪些名词。

- “邀请候选人参加面试、确认面试时间或面试安排”才属于 `interview_invitation`。
- “描述产品具备线上面试能力”“介绍曾参与面试系统项目”“说明岗位会接触面试业务”等仅提及面试的内容，不属于面试邀请。
- 薪资、到岗、资格、项目事实等类别同样按对方正在陈述或要求什么判断，不用关键词直接覆盖模型结论。

生产分析器删除本地关键词分类覆盖。模型输出仍必须通过现有允许枚举、事实引用、覆盖完整性和草稿数量校验；无效结果继续安全降级为可见的人工确认结果。

### 5.2 消息摘要

现有一次 `draftMessageGroup` 模型输出增加 `messageSummary`：

- 一句中文，概括当前招聘者消息组的主要意图和所需行动；
- 不超过 160 个字符；
- 不照抄长消息，不包含 `securityId`、内部字段名或模型推理过程；
- 不改变岗位 JD 和岗位分析结论；
- 只保存在本次 Dashboard 结果的短期内存中，不写入候选人进度事件或轻量状态接口。

消息正文继续只在本次模型调用内存中使用，调用结束后清空，不写入数据库、日志或页面状态接口。

## 6. 草稿与外部动作边界

安全边界放在真正会改变外部状态的动作上，而不是本地文本生成上。

- 真实的面试邀请允许生成本地回复草稿，不再因为类别是 `interview_invitation` 而强制清空草稿。
- 消息中仅出现“面试”字样时，不额外覆盖类别，也不额外压制模型草稿。
- 草稿仍最多两份，只能使用已提供并通过校验的候选人事实；缺失或过期事实不得被编造。
- 薪资、隐私和岗位身份不明类别本轮继续沿用现有人工处理规则。它们是否也应生成草稿是独立产品决定，不借本次面试误判修正扩大范围。
- 消息发现仍不会在 BOSS 输入框填写或粘贴内容，不会点击发送、沟通或投递，不会调用任何外部写接口。
- 用户复制草稿、进入 BOSS 并决定是否发送，始终是独立的人工动作。以后若增加自动沟通，仍必须针对当次不可变样本取得明确授权，不能复用本次设计作为许可。

进度语义保持独立：真实面试邀请仍可进入 `interview_invited`，是否存在本地草稿不改变“已经收到邀请”这一事实。

## 7. 数据流与最小实现边界

数据流调整为：

`稳定消息岗位身份 → 同观察完整 JD 与分析 → 单次模型语义分类、摘要和草稿 → 契约校验 → 用户决策卡`

只修改现有消息结果链路：

- 模型提示与 Mock 适配器：输出语义类别、`messageSummary` 和草稿；
- 消息回复分析器：停止用关键词覆盖语义类别；
- 消息回复契约：校验摘要，并允许面试邀请携带合规草稿；
- 消息发现安全投影与 Dashboard 控制器：短期传递已裁剪摘要，删除无用 `companyScope`；
- 消息结果视图：按用户决策顺序渲染。

不得增加新的浏览器命令、BOSS 页面访问、模型调用、数据库字段、依赖或通用摘要框架。常规 JD 主线仍只使用 `trusted_pane`；`search_page_api` 保留但不修不验；不引入通用 `standalone_detail`。

## 8. 失败处理

- 模型结果不合法：岗位机会建议仍显示；消息区显示“这条消息需要人工确认”；不生成草稿。
- `messageSummary` 缺失、超长或类型错误：整个消息模型结果视为不合法，避免类别与摘要来自不同结果。
- 岗位分析未完成：匹配和机会建议安全降级，不根据基础字段猜测。
- 公司业务资料不足：只显示单行未知说明，不显示免责声明。
- 草稿引用缺失、过期或未提供事实：契约拒绝草稿，原消息保留为人工处理结果。

## 9. 验证与验收

### 9.1 最小自动回归

- 模型返回 `other`，输入文本只是描述“项目提供线上面试与简历管理能力”时，分析器必须保留 `other`，不能改成面试邀请。
- 模型返回真实 `interview_invitation` 和合规草稿时，契约允许最多两份草稿，并保持 `interview_invited` 进度。
- 面试邀请草稿若编造或引用未验证事实，仍被现有事实契约拒绝。
- `messageSummary` 经过长度和类型校验，只出现在短期页面结果，不进入轻量状态接口或持久化事件。
- 页面中“建议”位于“对方说了什么”和岗位信息之前；使用“岗位概况”；不出现旧问句、`companyScope` 免责声明和内部枚举。
- 公司业务缺失时只显示“JD 暂未说明公司的具体业务”。
- 页面仍没有 BOSS 填写、粘贴、发送、沟通或投递能力。

### 9.2 本地真实验收

使用新的隔离数据库重新处理已观察的真实消息样本，确认：

- 该消息不再显示为面试邀请，而是与模型语义一致的普通消息类别和一句准确摘要；
- 机会建议在结果卡最前，用户无需先读分析过程；
- 岗位、公司及业务、匹配和薪资内容简洁，没有内部免责声明；
- 如模型给出合规草稿，页面允许展示，但没有发生任何平台填写、粘贴或发送；
- 两张固定 BOSS 标签保持不变，没有临时详情残留，读取不抢占前台，访问继续遵循冷却和预算。

验收期间不使用生产数据库，不调用 `Page.bringToFront`，不执行任何真实外部写。

## 10. 非目标

- 不增加公司外部调查、公司评分或整家公司“是否值得加入”的结论；
- 不修改岗位推荐算法或匹配等级算法；
- 不开放薪资、隐私和岗位身份不明类别的草稿；
- 不设计或实现自动沟通；
- 不调整 BOSS 浏览器安全、冷却、预算和标签页规则；
- 不做消息系统或 Dashboard 的整体重构。
