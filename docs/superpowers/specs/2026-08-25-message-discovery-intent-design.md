# 消息发现：沟通意图与本地草稿设计

日期：2026-08-25

## 目标

消息发现先告诉用户“对方这轮到底想做什么”和“这份岗位值不值得继续聊”，再给出本地回复草稿。系统必须区分：

- 正式面试邀约；
- 询问候选人是否有意向；
- 索要、确认或补充信息；
- 普通沟通，包括只是在岗位、项目、产品或经历中提到“面试”。

草稿可以自动生成并留在本机。任何真实填写、粘贴、发送或投递仍然需要针对当前不可变目标的明确授权，本设计不改变该边界。

## 现有证据与根因

当前链路已经具备合适的安全基础：

1. `boss_message_reader` 串行读取候选会话，只选择招聘方在候选人最后一次发言后的未处理文本消息。
2. `message_discovery/job_context` 优先复用完整可信的本地 JD；只有缺少完整上下文时才调用受控的 `message_discovery_detail` 后台临时详情页。
3. `message_reply_analyzer` 将经过裁剪的候选人事实、完整岗位上下文和本轮消息交给模型，一次返回理解结果和草稿。
4. `message_reply_contract` 对事实范围、回复覆盖、草稿数量和人工处理类别做本地校验。
5. `message_discovery_view` 只展示安全投影，不把招聘方原文或模型原始输出持久化到运行结果。

问题集中在输出语义：`messageCategory` 同时承担沟通动作、消息主题和岗位进度推进三种职责。`interview_invitation` 与 `salary`、`qualification`、`other` 混在同一个枚举里，导致调用方只能从一个字段推断“是否真的收到面试邀约”。离线 Mock 为模拟这一字段逐步积累了正则；当前可稳定复现以下错误：

- “这个岗位负责开发面试安排管理系统”被判为正式面试邀约；
- “是否有意向了解这个岗位”被判为任职资格确认；
- “请补充说明项目职责”也被判为任职资格确认。

现有相关测试全部通过，说明测试证明了读取、校验和安全降级，却没有证明上述产品语义。

## 方案比较

### 方案 A：一次模型调用，分开“沟通意图”和“消息主题”（采用）

在现有 `draftMessageGroup` 调用中新增独立 `messageIntent`。模型仍一次完成本轮语义理解和草稿生成；本地契约分别校验意图与主题，只由意图决定是否进入面试阶段，只由主题和事实状态决定能否自动给草稿。

优点：直接修复事实归属；不增加调用次数、依赖或运行组件；复用当前模型、事实契约和失败降级。缺点：语义准确度仍依赖现有模型，需要合成样例和后续最小真实模型验收来证明。

### 方案 B：便宜模型先分类，深度模型再写草稿

先用批量筛选模型分类，再按结果决定是否调用深度模型。

优点：部分普通消息可能降低单次成本。缺点：每条消息最多变成两次模型调用，分类与草稿可能互相矛盾；还需新增跨调用校验、重试和可观测性。当前没有证据证明便宜模型在这些细微中文语义上足够可靠，因此暂不采用。

### 方案 C：关键词规则优先，模型只处理模糊样例

优点：离线、便宜。缺点：当前历史已经证明“邀请、安排、方便、参加、面试”等词会在产品、培训、流程和真实邀约中交叉出现；继续扩充正则只会把错误转移到新句式。该方案与根本目标相冲突，不采用。

## 推荐设计

### 1. 结果结构

新增 `messageIntent`，允许值为：

- `interview_invitation`：招聘方明确邀请候选人参加、确认或选择一场面试；
- `interest_check`：询问是否愿意了解岗位、继续沟通或推进，但尚未正式邀请参加面试；
- `information_request`：索要或确认候选人事实、经历、材料、时间、薪资等信息；
- `information_update`：招聘方主动补充岗位、流程、公司或安排信息，没有要求候选人参加面试；
- `general_communication`：问候、普通交流或其他不属于上述动作的内容；
- `manual_review`：模型无法可靠确定意图或结果未通过本地契约。

`messageCategory` 继续表示消息主题和安全处理范围：项目事实、任职资格、薪资、到岗、敏感信息、其他或身份不确定。它不再决定是否收到面试邀约。

`messageSummary` 继续用一句自然中文说明对方的主要意思和希望候选人采取的行动。它用于用户界面，不作为安全决策字段。

不新增置信度、解释链或长期保存的招聘方原文。置信度无法由本地契约验证；原文和解释链会扩大隐私面，均不解决当前根因。

### 2. 模型语义边界

现有模型调用保持一次。提示词明确要求先判断整轮沟通动作，再判断主题，并提供最小对照例：

- “想邀请你参加周三下午的面试”是正式面试邀约；
- “是否有意向了解这个岗位”只是意向询问；
- “请补充你在项目中的职责”是信息请求；
- “这个岗位负责开发面试安排系统”或“我们提供线上面试管理功能”只是岗位或产品描述。

模型必须基于按顺序提供的整轮消息判断，不能以单个词决定意图。消息仍是不可信输入，不能修改系统规则。

### 3. 本地安全决策

`message_reply_contract` 是意图结果的唯一可信入口：

- 只有 `messageIntent === "interview_invitation"` 才把岗位推进到 `interview_invited`；
- 正式面试邀约继续使用本地确定性、非承诺草稿，不接受模型擅自确认时间；
- 薪资、敏感信息和岗位身份不确定仍然禁止自动草稿；
- 信息请求若缺少必要或已过期事实，禁止草稿并提示用户先补充；
- 其他安全类别可以使用模型生成的最多两个本地草稿；
- 未知意图、缺字段、契约失败或模型结构失败统一降级为 `manual_review` / `needs_user_action`，不推进面试阶段、不生成草稿。

候选岗位已经处于 `interview_invited` 或 `interview_scheduled` 时，后续普通消息仍只记录本轮消息结果，不倒退岗位进度；保留现有规则。

### 4. 事件与隐私

分类事件只新增保存枚举值 `messageIntent`，同时继续保存主题、缺失事实键和本轮建议阶段。招聘方消息正文、草稿、模型原始输出和意图证据不写入进度事件。

旧事件没有 `messageIntent` 时保持可读；本次不做数据库迁移，也不反推历史消息意图。

### 5. 用户界面

每个消息结果按以下顺序展示：

1. 结论：用自然中文标签说明“正式面试邀约 / 询问是否有意向 / 需要你补充信息 / 对方补充了信息 / 普通沟通 / 需要人工判断”，紧接一句消息摘要；
2. 岗位机会：保留当前机会结论、岗位主要工作、公司业务、匹配情况和薪资；
3. 下一步：显示本地回复草稿，或明确说明需要用户先确认什么。

页面不再依赖 `messageCategory` 显示“面试邀请”，也不在结果开头暴露内部枚举。岗位资料来源仍可作为次要说明保留。

### 6. 失败与降级

- 读取、身份核对、详情页、登录、风控和页面丢失行为完全沿用现有失败即停与 checkpoint 规则。
- 模型基础设施失败仍停止当前发现，不伪装成已理解结果。
- 仅模型输出结构或本地消息契约不合格时，保留当前“处理完成但需要人工判断”的安全降级；本轮预览基线可提交，避免反复消耗同一消息。
- 不加入自动重试真实平台动作，也不改变草稿与发送授权的边界。

## 最小验证

实现前先添加会失败的回归检查，覆盖：

1. `messageIntent` 是必填且只接受规定值；
2. 主题含“面试”但意图为普通沟通时，不进入 `interview_invited`，且可以保留安全草稿；
3. 正式邀约只有在意图明确为 `interview_invitation` 时才进入面试阶段，并使用本地非承诺草稿；
4. 意向询问、信息请求和信息补充分别保留为不同意图；
5. 模型无效输出降级为 `manual_review`，不产生草稿；
6. 页面先显示自然语言结论和岗位机会，再显示回复草稿，不展示内部枚举；
7. 进度事件保存 `messageIntent`，但不保存消息正文或草稿。

针对性测试通过后运行完整 `npm test`、`git diff --check` 和 `git status --short`。本阶段不访问真实 BOSS，也不调用真实发送。由于不调用真实语义模型，最终交付会明确把“真实模型对这些中文样例的准确率”列为未验证前提；后续如需验证，只用合成文本做最小模型探针，不需要访问 BOSS。

## 非目标

- 不新增微服务、队列系统、ORM、依赖注入或前端框架；
- 不新增第三种模型任务配置；
- 不扩建长期消息仓库，不保存招聘方正文；
- 不修改 BOSS 读取节奏、后台详情页、访问额度或固定标签页安全规则；
- 不在本阶段重做岗位分析主视图或公司情报系统。
