# 消息发现：岗位理解与推荐回复草稿设计

日期：2026-08-16

状态：已实现，自动回归与真实后台只读人工验收均已完成

范围：消息发现、消息岗位详情读取、岗位理解、回复草稿展示

## 1. 目标

消息发现不应只告诉用户“有一条新消息”，还应在可靠岗位资料的基础上说明：

- 对方正在沟通什么岗位；
- 岗位职责和关键要求是什么；
- 该岗位与当前候选人的主要匹配点、差距和风险是什么；
- 当前消息属于普通沟通、面试邀请、事实缺失还是敏感问题；
- 在允许生成草稿的情况下，给出每个岗位最多两份可复制的推荐回复。

本功能仍是只读辅助工具。它不向 BOSS 输入框填写内容，不点击发送、沟通或投递按钮，也不把草稿自动交给任何外部平台。

## 2. 已验证事实

### 2.1 代码事实

- `listMessageDiscoveryCandidates` 当前只提供职位、公司、薪资和城市等基础字段，没有完整 JD 和已有分析。
- `resolveUniqueCandidate` 当前调用模型时也只带这些基础字段，因此模型无法可靠完成岗位理解。
- 主动联系岗位当前会创建空 `description` 的 `inbound_unassessed` 记录。
- 当前“关联、创建或忽略”共用结案路径，导致关联或创建本地记录后，原始消息已经无法继续完成岗位分析和草稿生成。
- 当前卡片绑定使用消息队列的 `conversationKey`，后续发现却重新计算旧摘要，存在同一会话无法再次匹配的问题。
- 当前页面只有存在草稿时才渲染结果，因此“面试邀请、缺少事实、敏感问题”等无草稿结果会消失。
- 当前草稿清洗把整个批次限制为两份，而需求是每个岗位最多两份。

### 2.2 真实页面事实

在现有登录 Edge 会话中完成了最小只读校准：

- 消息页选中岗位的 `ConversationPositionInfo` 组件包含 `conversation$.encryptJobId` 和 `conversation$.securityId`。
- 组件现有点击逻辑使用这两个字段构造可信的 `/job_detail/{jobId}.html?securityId=...` 地址。
- 原生点击会在同一窗口新开并激活岗位详情标签；这种方式会改变用户当前可见标签，不能用于产品实现。
- 校准产生的详情页具有稳定岗位 ID，岗位标题与消息页一致，并提供公司、薪资和完整 JD；校准样本正文长度为 313 个字符。
- 校准期间没有登录异常或风控提示，临时页已经关闭，两个固定 BOSS 标签页已经恢复。

因此，产品无需点击岗位卡片。它可以只读取得组件中的地址参数，经严格校验后，用 Edge 原生的 `active: false` 能力在后台创建临时详情页。

## 3. 方案比较与决定

### 方案 A：只处理本地已有完整 JD 的岗位

风险最低，但主动联系的新岗位长期无法获得岗位理解和草稿，不能满足目标。

### 方案 B：点击岗位卡片，让 BOSS 自行新开详情页

能够取得完整 JD，但真实页面会激活新标签。即使不调用 `Page.bringToFront`，仍会打断用户当前浏览，因此拒绝。

### 方案 C：后台临时详情页，缺资料时才打开

这是采用方案。消息页只读取得可信岗位地址；命中完整本地缓存时不访问 BOSS；缓存缺失时，经过共享冷却和访问预算后，在同一窗口以 `active: false` 创建一张临时详情页，读完立即关闭。

该方案同时满足岗位资料完整、低频访问、不抢前台和最小改动四个目标。

## 4. 浏览器结构和前台边界

### 4.1 常驻基线

正常静止状态保留两张固定 BOSS 标签页：

- `BOSS-SEARCH`：常规扫描和 `trusted_pane` JD 主线；
- `BOSS-COMMUNICATION`：消息列表和对话读取。

消息发现允许短暂增加一张 `message_discovery_detail` 详情页，但同一时刻最多一张，而且必须与两张固定页处于同一 Edge 窗口和同一登录会话。

### 4.2 不抢前台是硬条件

消息详情读取必须同时保证：

- 不调用 `Page.bringToFront`；
- 不调用 `focus_tab`；
- 不使用 `active: true` 创建或更新标签；
- 不聚焦 Edge 窗口，不添加焦点恢复逻辑；
- 不模拟岗位卡片原生点击；
- 创建前后的 Edge 活动标签 ID 保持不变；
- 用户当前使用的应用窗口不因读取而切换。

工作区启动助手中已经确认的单次前台引导例外保持不变，但不得复用于消息发现。

如果浏览器能力、页面结构或运行时状态无法证明 `active: false` 生效，当前岗位保持待处理。能用返回的数字标签 ID 或精确目标 URL 证明归属的临时页立即关闭；无法证明归属的新页面绝不猜测关闭，而是停止并提示人工恢复浏览器基线。本功能不得以前台打开作为降级方案。

## 5. 详情读取流程

每个待处理会话严格串行执行：

1. 重新列出当前标签页，取得新的数字型标签 ID，确认两个固定页仍在同一窗口。
2. 从 `BOSS-COMMUNICATION` 获取快照，检查路径、登录、风控、唯一选中会话、`conversationKey` 和职位标题。
3. 从选中会话的 `ConversationPositionInfo.conversation$` 只读取得 `encryptJobId` 和 `securityId`。
4. 只接受 `https://www.zhipin.com/job_detail/{合法ID}.html` 形式的同源地址；拒绝缺字段、异常协议、异常主机、用户名、密码和非岗位路径。
5. 按已经验证的稳定岗位 ID 查询本地缓存。只有不存在完整 JD 时才继续浏览器访问。
6. 记录当前活动标签 ID，执行共享冷却和访问预算预留。
7. 通过现有 Edge 浏览器适配器在同一窗口创建 `active: false` 临时页。
8. 再次列出标签，只允许新增一张数字型、同窗口、非活动的可信 BOSS 详情页；同时确认原活动标签未变化。
9. 等待页面就绪，检查登录、风控和详情根节点。
10. 用 URL 岗位 ID、页面岗位 ID 和消息页职位标题共同核对身份；任何不一致都停止。
11. 读取并标准化职位、公司、薪资、城市、经验、学历、标签、活跃状态和完整 JD。
12. 先用本地事务写入岗位观察；再运行当前候选人分析，并在单独事务中写入与该观察对应的分析。
13. 岗位和分析都成功提交后，再生成并提交消息发现结果检查点；不得在数据库事务中等待模型或浏览器。
14. 在 `finally` 清理中关闭可明确归属于本次操作的临时页，确认固定标签和创建前的浏览器标签基线已经恢复，并再次检查消息页身份、登录和风控状态。若浏览器命令失败且新页面尚未形成可信目标 URL，不得因它是“同窗口唯一新页”就猜测关闭；应停止并交给用户检查。
15. 关闭页面后执行详情阶段冷却，保存可恢复的节奏状态，然后才允许处理下一条消息。

任何已经发出的临时详情请求，无论成功、失败还是结果不明确，都算一次真实访问。结果不明确时不得自动重试。

## 6. 冷却、访问预算和恢复

消息详情不建立独立计时器，而是加入现有 BOSS 详情访问体系：

- 每次访问前使用 `pane_detail_read` 的随机间隔，当前策略为 8–14 秒；
- 同时预留 `detail_open` 和详情读取访问预算；
- 每累计 18–26 个受控动作，额外随机冷却 4–7 秒；
- 每读取 6–8 个详情，额外冷却 15–25 秒；
- 每读取 16–20 个详情，阶段冷却 90–150 秒；
- 普通模式的 `detail_open` 当前上限是 10 分钟 8 次、1 小时 25 次、24 小时 60 次；
- 恢复模式的 `detail_open` 当前上限是 10 分钟 5 次、1 小时 15 次、24 小时 30 次；
- 详情读取还共享现有 3 分钟、10 分钟、1 小时和 24 小时预算；
- 达到预算时保存未完成队列和节奏检查点，延后恢复，不减少逻辑岗位覆盖。

实现必须直接读取 `PRODUCT_POLICY` 和现有访问控制器，不复制这些数值到第二份运行时代码。规格中的数值用于说明当前策略；以后策略调整只改权威策略对象。

本地缓存命中不访问 BOSS，因此不消耗浏览器访问预算。

## 7. 岗位数据和分析

### 7.1 已知岗位

如果稳定岗位 ID 已经存在完整本地 JD，则直接复用，不打开临时页。岗位分析必须来自当前候选人、当前搜索方案和同一岗位观察，不能把旧 JD 与新分析拼接。

### 7.2 新岗位

后台详情读取成功后：

- 使用 BOSS 稳定岗位 ID 去重；
- 保存不带 `securityId` 的规范岗位 URL；
- 保存完整 JD 和页面明确提供的岗位字段；
- 按当前候选人和搜索方案生成新的分析；
- 将会话绑定到该稳定岗位记录。

只有 JD 和语义分析都完整时，才允许生成基于岗位匹配的回复草稿。详情读取或分析失败时，消息保持待处理，不用基础字段猜测岗位职责。

### 7.3 敏感数据

- `securityId` 只允许在本次后台导航的内存中短暂存在；
- 不把 `securityId` 写入数据库、日志、状态接口、错误消息或截图；
- 招聘者消息正文仍只在本次模型调用内存中使用；
- 数据库只保存岗位资料、岗位分析、稳定会话摘要和处理状态，不保存消息正文。

## 8. 模型输入和输出

完整上下文包括：

- 当前候选人资料；
- 当前搜索方案；
- 当前岗位完整 JD；
- 与该 JD 对应的完整岗位分析；
- 本次会话中需要理解的招聘者消息；
- 明确的上下文来源：`local_cache` 或 `message_discovery_detail`。

每个符合条件的岗位复用现有一次模型请求，不增加第二套岗位理解调用。模型输出：

- 简短岗位概括；
- 主要职责和硬性要求；
- 候选人的匹配点；
- 明显差距、风险和待确认问题；
- 当前消息类型和已覆盖事实；
- 最多两份推荐回复草稿。

以下情况不生成草稿，但仍返回可见结果和人工处理提示：

- 面试邀请；
- 回复依赖缺失的候选人事实；
- 薪资、隐私或其他敏感问题；
- 岗位身份、JD 或分析不完整；
- 模型结果无法通过结构校验。

草稿数量限制按岗位计算，不是整个发现批次合计两份。

## 9. 会话生命周期

消息队列提供的 `conversationKey` 是新流程的规范会话标识。

- 已经绑定卡片时继续使用卡片中的会话标识；
- 未绑定时使用队列的 `conversationKey`；
- 读取时兼容旧摘要，避免升级后丢失历史未完成项；
- 新写入不再生成第二套旧摘要。

“关联岗位”或“创建本地岗位”只建立关系，不自动把原始消息结案。以下情况才进入终态：

- 完整岗位理解和消息结果已经生成并提交；
- 结果明确要求人工处理且已经形成可见结果；
- 用户明确忽略该消息。

详情失败、预算等待、页面异常和分析失败都保持待处理，可以从检查点恢复。

## 10. 界面

每个岗位结果都显示，不再以“是否有草稿”作为渲染条件。结果顺序为：

1. 职位和公司；
2. 已知岗位或新沟通岗位；
3. 上下文来源和资料完整状态；
4. 岗位概括、匹配点和风险；
5. 当前消息分类和人工处理提示；
6. 存在时显示最多两份可复制草稿。

界面不新增“填写到 BOSS”或“发送”操作。结果沿用现有短期内存和过期策略，不新增消息正文查询接口。

## 11. 错误处理

以下任一条件出现时立即停止当前详情读取并保持消息待处理：

- 登录失效或风控信号；
- 固定标签丢失、窗口变化或数字型 ID 变化未重新绑定；
- 无法取得可信岗位地址；
- 新标签不是唯一、同窗口、后台和可信 BOSS 详情页；
- 原活动标签发生变化；
- 岗位 ID 或标题不一致；
- 页面根节点、JD 或公司等必要字段缺失；
- 关闭临时页后没有恢复到固定基线；
- 访问预算耗尽或操作被用户停止。

结果不明确时不自动重试，也不调用搜索页、`search_page_api` 或通用 `standalone_detail` 兜底。

## 12. 实施边界

- 常规扫描仍只使用 `trusted_pane`。
- `search_page_api` 保留现状，不修复、不验证、不删除。
- 不恢复面向扫描、Gate D 或全产品的 `standalone_detail`。
- 新详情通道只服务于消息发现中“本地没有完整 JD 的新沟通岗位”。
- 不引入新依赖，不新建通用浏览器框架；复用现有 Edge 适配器、BOSS 页面帮助函数、节奏状态和访问预算控制器。
- 不做 Wave 5 或无关重构。
- 不改变外部写授权规则。

## 13. 验证和验收

### 13.1 自动回归检查

实施计划至少覆盖以下最小回归：

- 缓存命中时不创建浏览器标签；
- 缓存缺失时只创建一个 `active: false`、同窗口临时页；
- 创建前后活动标签 ID 不变；
- 假浏览器记录的命令中，任何路径都不出现 `Page.bringToFront`、`focus_tab` 或活动标签切换；
- 非可信 URL、缺字段、登录、风控和身份漂移都会停止；
- 临时页在成功、可归因失败和中止路径都关闭；无法归因的新页不被误关，并触发基线未恢复停止；
- 发出的失败请求也计入访问预算和详情节奏；
- 节奏状态可检查点保存和恢复，恢复后不能突发访问；
- `securityId` 不出现在数据库、日志、API 结果和错误中；
- 完整新岗位会写入稳定岗位 ID、JD 和同观察分析；
- 关联或创建不会提前清除未完成消息；
- 新旧会话标识兼容；
- 无草稿结果也能渲染；
- 每个岗位最多两份草稿；
- 只读发现不会触发填写、发送或投递。

### 13.2 本地人工验收

功能代码完成后，在用户现有 Edge 主窗口中使用一个明确样本验证：

- 用户当前前台应用和 Edge 可见标签始终不变；
- 临时页确实以后台标签存在并且只有一张；
- 详情身份、JD 和本地结果一致；
- 冷却等待和进度对用户可见；
- 临时页关闭后固定基线恢复；
- 全程没有外部沟通或回复动作。

用户已经长期允许这类只读、非沟通、非回复的真实页面检查，因此不需要逐次重复申请。任何外部沟通、回复、投递或其他写操作仍要求针对当前样本单独、明确授权。

## 14. 完成标准

只有同时满足以下条件，本功能才算完成：

- 已知岗位优先复用完整缓存；
- 新沟通岗位可以在不抢前台的情况下取得并保存完整 JD；
- 所有真实详情访问遵循共享冷却和访问预算；
- 岗位理解只基于完整、同观察的 JD 和分析；
- 无草稿结果可见，每个岗位草稿不超过两份；
- 消息正文和 `securityId` 不落盘；
- 不触发任何未经授权的外部写；
- 自动回归通过，并完成一次本地后台读取人工验收。

## 15. 最终实施与验收结果

- 设计、实施计划、功能实现和安全复审已经完成，初始实现提交为 `c11f38a` 至 `73ae57b`，真实验收最终修复提交为 `15a3dab`。
- 当前分支真实样本证明：本地缺少完整 JD 时只创建一张同窗口、`active: false` 的临时详情页；初始空白地址会在严格标签归属和前台不变检查下等待；独立详情 DOM 的岗位身份和完整 JD 核验成功后页面关闭，固定基线恢复。
- 真实验收发现并修正了硬边界岗位的消息上下文分析死锁，以及消息已经转为已读后的恢复身份核验。内部分析能力不再由网页请求参数决定，并有伪造请求回归保护。
- 最终恢复运行直接复用本地完整缓存，没有再次创建详情页。页面显示一条面试邀请结果、岗位理解、匹配证据和明确的人工处理理由；按安全规则没有生成草稿，也没有向 BOSS 填写或发送任何内容。
- 最终代码树明确排除会触发 360 的 `startup_scripts_smoke.js` 后，其余 100/101 项离线检查全部通过；独立只读复审结论为 Ready。静态检查确认消息发现路径没有 `Page.bringToFront`、活动标签切换、`search_page_api` 或一般用途的 `standalone_detail`。
- 正式生产数据库和模型设置未修改；未执行任何外部沟通、回复、投递、推送、合并或发布。完整验收证据见 `docs/superpowers/reports/2026-08-17-message-discovery-job-understanding-reply-drafts-acceptance.md`。
