# RoleFlow beta.4 新用户发布与文件整理设计

**日期：** 2026-08-14

**状态：** 方案已获用户确认，正在实施

**范围：** Windows beta.4 发布、GitHub Release 资产、标准安装包内容与源码入口整理

## 1. 目标

让第一次接触 RoleFlow 的 Windows 用户从 GitHub Release 直接下载标准安装程序，不再把源码 ZIP、`Install.bat` 或便携脚本误认为推荐安装方式。

同时保留仍然有效的开发、便携和故障恢复入口，不为了整理目录破坏现有工作流。

## 2. 已确认的事实

- 当前 `main` 已合并 beta.4 第一阶段整改，提交为 `33f16be5c26fc9ddee581a8f5d897ec6a4a1e726`。
- `package.json` 仍是 `0.1.0-beta.3`。
- 现有 `v0.1.0-beta.3` 标签指向旧提交，Release 只有便携 ZIP，没有安装程序。
- GitHub 自动生成的 Source code ZIP 固定包含仓库文件，项目无法单独隐藏其中的 BAT。
- `Install.bat`、`Start.bat` 和便携脚本仍被便携包、文档或回归测试使用，直接从源码删除会破坏有效入口。
- 标准安装后的快捷方式使用 `scripts/launch-installed.ps1`，并不依赖根目录的 `Install.bat`。
- 当前安装器不打包未取得明确再分发许可的 Edge Control 组件；该限制继续保留。

## 3. 发布形态

创建新的预发布版本 `v0.1.0-beta.4`，不移动、不覆盖也不删除历史标签和 Release。

Release 资产按以下顺序和定位提供：

1. `RoleFlow-Setup-0.1.0-beta.4.exe`：普通 Windows 用户的推荐入口。
2. `RoleFlow-Setup-0.1.0-beta.4.exe.sha256`：安装程序完整性校验文件。
3. `RoleFlow-v0.1.0-beta.4-portable.zip`：明确标注为“高级用户 / 免安装 / 开发与恢复用途”，不作为新用户首选。

Release 说明和 README 首屏均先引导下载 EXE，并解释 GitHub 的 Source code ZIP 不是安装包。

## 4. 文件整理边界

### 4.1 标准安装程序

标准安装目录只放运行产品和阅读必要说明所需的文件。

以下旧入口不进入标准安装包：

- `Install.bat`
- `ScanPortable.bat`
- `StartPortableEdge.bat`
- 只用于构建发布物的脚本和测试文件

`Start.bat` 是否进入标准安装包以实际恢复用途为准：如果标准快捷方式和故障提示都不依赖它，则一并排除；如果仍是当前可触发的恢复入口，则保留并在说明中标为高级入口。实施前通过现有调用关系和安装烟雾测试确定，不凭名称猜测。

标准安装包仍保留：

- `scripts/launch-installed.ps1` 及其真实运行依赖；
- 许可证、NOTICE、安全与必要使用说明；
- 固定 Node 运行时和生产依赖；
- 安装、启动、自检、升级和卸载所需脚本。

### 4.2 源码仓库

根目录 BAT 暂不进行大规模搬迁：

- 保留 `Install.bat`、`Start.bat` 和便携入口，避免破坏源码安装、便携运行和已有文档。
- README 把它们归为“高级 / 源码 / 故障恢复入口”。
- 不把构建脚本迁入新目录；这种整理对新用户下载 Release 没有实际收益，却会扩大文档和测试改动。

### 4.3 便携 ZIP

便携 ZIP 保留当前源码式结构和 BAT 入口，以兼容高级用户工作流。文件名增加 `portable`，Release 文案明确说明：

- 这是免安装高级版本；
- 普通用户应下载 EXE；
- Source code ZIP 不能代替标准安装器。

## 5. 版本与发布流程

- 将 `package.json` 和 `package-lock.json` 的版本同步为 `0.1.0-beta.4`。
- 新增 `docs/releases/v0.1.0-beta.4.md`，如实记录人工验收成果、已知限制和许可边界。
- 发布流程必须在同一提交上完成离线测试、便携包构建和安装器构建。
- 标签只在本地验证和发布检查通过后创建。
- GitHub Release 上传三个明确资产：EXE、SHA-256 和高级便携 ZIP。
- 历史 beta.3 Release 保持不变，避免让旧标签对应到新代码。

GitHub Actions 若能在固定工具版本下可靠构建安装器，则把三项资产统一交给标签工作流发布；如果 Inno Setup 的许可或 CI 安装方式在本轮不能可靠固定，则不临时引入不透明下载，改为本地复现构建并通过 GitHub CLI 上传三项资产。无论采用哪条路径，Release 中的资产必须来自同一已验证提交。

## 6. 新用户模拟验收

发布前使用全新临时目录模拟第一次下载，不能复用当前项目运行数据。

验收至少覆盖：

1. 从最终 EXE 安装，不运行源码 `Install.bat`。
2. 安装向导、进度、开始菜单、桌面快捷方式和卸载入口可见。
3. 首次启动进入模型配置页。
4. 安装包不包含数据库、简历、模型密钥、日志、报告、浏览器 profile 或测试文件。
5. 缺少浏览器连接组件时给出清楚说明，不静默换用其他浏览器 authority。
6. 卸载默认保留用户数据，并明确显示保留位置。
7. Release 页面能让普通用户一眼区分 EXE、便携 ZIP 和 Source code。

本轮不执行真实 BOSS 抓取、沟通、发送或申请；新用户安装与启动验收不改变现有 BOSS 安全边界。

## 7. 验证与完成标准

- 完整离线套件 fresh 通过。
- Windows 安装器烟雾测试 fresh 通过。
- 生成文件名、应用版本、Release 标签和发布说明一致。
- 对安装器 stage 做禁止文件扫描。
- 对最终 EXE 和 ZIP 计算 SHA-256，并记录构建提交。
- 在 GitHub Release 页面重新读取资产列表、大小和下载链接，确认上传成功。
- 下载已发布的 EXE 到新的临时目录后再次核对哈希。
- Git 工作区干净，`main` 与 `origin/main` 一致。

## 8. 已知限制

- 安装器尚未代码签名，Windows 可能显示信誉提示，Release 说明必须如实说明。
- Edge Control 当前不随安装器公开分发，因此不能宣称在全新电脑上无需额外准备即可完成全部 BOSS 流程。
- AGPL-3.0-only 允许商业使用；用户关于限制他人盈利使用的偏好仍需单独许可证决策，不阻塞本次 beta.4 发布。
- Inno Setup 的商用许可边界不能被发布自动化掩盖；如果当前编译器许可不适合目标发布场景，只记录并停止对应发布动作，不私自替换安装技术。

## 9. 非目标

- 不删除历史 Release 或标签。
- 不全面重构安装脚本和仓库目录。
- 不引入自动更新、MSIX 或代码签名采购。
- 不修改 BOSS 浏览器链路、`trusted_pane`、`search_page_api` 或岗位筛选逻辑。
- 不启动 Wave 5。
