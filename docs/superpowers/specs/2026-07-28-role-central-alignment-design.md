# 岗位主线匹配与默认沟通分档设计

## 背景

轻量召回优先链路已经把单岗位分析压缩为两次模型调用：

1. `understandJob` 从完整 JD 提取岗位要求；
2. `matchJob` 只返回有候选人证据的要求编号。

这套设计减少了输出字段、重复输入和契约修复，但当前把两个不同概念混在了
`indispensable` 中：

- 招聘方是否把一项要求写成不可缺少的硬门槛；
- 一项要求是否定义了这个岗位的主要工作方向。

真实岗位 `AI推理部署工程师` 暴露了这个问题。模型正确概括出岗位主线是大模型
推理部署、硬件适配和性能优化，但因为相关要求多用“熟悉、了解、优先”等措辞，
它们都不是硬门槛。候选人只匹配“基础开发能力”和“问题排查能力”后，岗位被判为
`review`，随后又被统一映射为 `talk` 并默认勾选。

这不属于浏览器采集错误，也不是模型没有读懂 JD，而是本地决策缺少“主线是否匹配”
这一层，并把“保留可见”错误地等同于“默认沟通”。

## 目标

- 保持每个岗位两次模型调用，不增加第三次方向判断。
- 保持轻量 JSON，不恢复旧版职责、技术栈、成果预期和职业分类等大契约。
- 只硬排除有明确双侧证据的资格、核心硬门槛或安全冲突。
- 岗位主线与候选人方向明显不一致时，保留为备选，但不默认勾选沟通。
- 主线一致、只缺少次要工具、行业或偏好项时，仍可进入 `talk`。
- 不使用某个职业专属的技术词表，规则对技术、运营、设计等岗位通用。

## 非目标

- 不新增职业分类模型、固定职业枚举或行业模板。
- 不用关键词规则猜测 Python、Java、算法、运营等具体职业方向。
- 不把简历没有写某项能力直接解释为候选人明确不能做。
- 不改变 BOSS 浏览器访问、沟通执行、搜索预算或每日轮次。
- 不在本次改动中重新设计全部推荐枚举或页面布局。

## 核心概念

岗位要求增加一个轻量布尔字段：

```json
{
  "label": "国产卡部署经验",
  "central": true,
  "indispensable": false,
  "evidence": "JD：优先考虑具备国产卡部署经验者"
}
```

字段含义：

- `central=true`：该要求直接服务于岗位持续承担的主要工作，而且能把本岗位与相邻岗位
  区分开，能够说明岗位真正干什么。
- `indispensable=true`：JD 明确把该要求表达为不可替代条件；只有候选人存在明确不兼容
  证据时，才允许形成硬阻断。

两个字段互不推导：

- 一项要求可以定义岗位主线，但不是硬门槛；
- 一项要求可以是明确资格门槛，但不代表主要日常工作；
- 通用素质可能重要甚至必需，但不能仅凭“学习能力、沟通能力、基础开发、问题排查”
  证明候选人与具体岗位主线一致。

## 模型契约

### `understandJob`

保留现有紧凑结构，只在 `requirements` 每项增加 `central`：

```json
{
  "roleSummary": "负责大模型推理部署、硬件适配与性能优化",
  "requirements": [
    {
      "label": "推理框架与性能优化",
      "central": true,
      "indispensable": false,
      "evidence": "JD：熟练掌握至少一种主流推理框架"
    }
  ],
  "eligibility": [],
  "riskSignals": []
}
```

提示词要求：

- 先用 `roleSummary` 概括岗位真实主线；
- `central=true` 只看该要求是否直接服务于主要、持续承担的工作；
- 使用“辨别性测试”：只知道这项要求时，是否足以区分该岗位与相邻岗位；基础开发、
  学习、沟通、责任心、通用排错等跨岗位能力一律不能单独标成 `central=true`；
- “优先、熟悉、了解”不能阻止一项要求成为 `central=true`；
- `indispensable=true` 仍要求 JD 表达不可替代的硬条件；
- 通用素质不能因为容易匹配就替代岗位主线要求。

兼容策略：

- 新结果应输出严格 boolean；
- 旧缓存或旧 fixture 没有 `central` 时，以 `indispensable` 作为保守兼容值；
- 提示词和派生规则使用新的分析管线版本，正常的新分析不得复用修改前的岗位理解缓存；
- 缺少这个软分档字段不得单独触发模型契约修复或第二次请求；
- 无法可靠识别主线时保持原有召回行为，不形成硬排除。

### `matchJob`

不增加新字段，不改变现有稀疏证据结构。

模型继续只返回 `R*` / `E*` 编号及有证据的 `matched`、`transferable`、`missing` 或
资格状态。本地代码把这些结果与 `understandJob.requirements[].central` 合并。

因此第二次请求不会增加新的嵌套对象、理由文本或职业分类。

## 本地决策

本地代码从逐项匹配派生两个内部信号：

- `centralRequirementCount`：本次提取到的主线要求数量；
- `centralEvidenceCount`：其中有 `matched` 或 `transferable` 候选人证据的数量。

### 主线未得到证据

满足以下全部条件时，标记 `role_core_unproven`：

1. `centralRequirementCount > 0`；
2. `centralEvidenceCount === 0`；
3. 岗位详情和语义分析均完整；
4. 候选人只匹配通用能力，或没有任何主线证据。

这个信号是强降级信号，不是硬阻断：

- 推荐结果可以继续保留为 `review`；
- 最终分桶进入 `backup`；
- 不进入本轮默认勾选清单；
- 不生成 `hardBlocker`；
- 不写成候选人“不能胜任”的事实。

### 主线有直接或可迁移证据

只要至少一项 `central=true` 要求有 `matched` 或 `transferable` 证据，就不触发
`role_core_unproven`。

随后继续使用现有规则：

- 核心硬门槛明确冲突：`not_recommended`；
- 主线匹配但存在次要未知项、工具差距或岗位质量关注：`talk`；
- 主线和其他关键要求证据充分：可进入 `primary`；
- 信息采集或模型分析未完成：保持 `refresh` / `analysis_pending`。

### 没有提取到主线要求

如果模型没有输出任何 `central=true` 要求，不得据此降级为方向不符。继续使用当前
召回优先规则，并记录可观测计数，供后续检查模型是否长期漏标。

## 工作流展示与默认选择

- `primary`、`talk` 保持现有可选与默认勾选行为。
- `role_core_unproven` 产生的 `backup` 不默认勾选，不占用沟通成功目标。
- 岗位仍保留在当前岗位/备选视图，显示“岗位主线与当前简历证据偏离”。
- 页面不得把该信号显示为“明确不符合”或“硬性淘汰”。
- 如果用户以后在偏好卡中明确排除某类方向，可由现有用户排除规则进入
  `not_recommended`；本设计不自动升级。

## 示例

### 推理部署岗位

- 主线要求：推理框架、硬件适配、国产卡部署、性能优化；
- 候选人证据：RAG、Agent、应用后端；
- 结果：主线要求有提取，但没有直接或可迁移证据；
- 分桶：`backup`，不默认勾选。

### Agent / RAG 应用岗位

- 主线要求：Agent 工作流、RAG、Python API 集成；
- 候选人证据：LangGraph、检索链路、工具调用；
- 结果：至少一项主线有直接证据；
- 分桶：继续按证据完整度进入 `talk` 或 `primary`。

### 主线匹配但缺少低代码工具

- 主线要求：AI 应用开发；
- 次要要求：Coze、Dify 或某一行业经验；
- 候选人有 AI 应用开发证据，但缺少次要工具；
- 结果：不得触发主线偏离，可保留为 `talk`。

## 性能与失败处理

- 模型调用次数保持两次。
- `matchJob` 输出完全不变。
- `understandJob` 只为每条已有要求增加一个 boolean。
- `central` 缺失不触发契约修复，避免因软分档字段产生额外请求。
- 任何 `central` 解析问题只能让岗位维持原有宽松分档，不能造成硬淘汰。
- 不增加新依赖、职业词表、额外数据库查询或网络访问。

## 测试与验收

### 离线回归

至少覆盖：

1. 主线要求全部无证据时进入 `backup`，且没有 hard blocker；
2. 只匹配“基础开发、学习、沟通、排错”等通用能力不能解除主线偏离；
3. 任一主线要求有直接证据时不触发主线偏离；
4. 任一主线要求有可迁移证据时不触发主线偏离；
5. 只缺少非主线工具或行业经验时仍可进入 `talk`；
6. 缺少 `central` 的旧缓存与 fixture 继续可读且不增加修复调用；
7. 资格、核心硬门槛、安全风险等旧防护不放宽；
8. 全量离线测试通过。

### 真实分阶段验收

1. 先只分析 `AI推理部署工程师` 一条，记录两次模型调用耗时、修复次数和最终分桶；
2. 与本次修改前同岗位结果比较，要求变为 `backup` 且不默认勾选；
3. 再选择五条真实岗位：
   - 两条明显主线偏离；
   - 两条主线匹配；
   - 一条边界岗位；
4. 五条结果合理且没有新增契约修复或明显耗时回退后，才决定是否重新运行二十条；
5. 任何可能降低召回的进一步收紧都必须先量化，再由用户决定。

## 完成标准

- 示例推理部署岗位不再进入默认沟通清单；
- 主线匹配的 Agent / RAG 岗位不因次要未知项被统一降为备选；
- 真实单岗位运行仍为两次模型调用；
- `central` 不得导致额外契约修复；
- 旧硬边界与安全规则全部保持；
- 离线测试通过，真实五条抽样未显示明显召回回退。
