# 通用模式与继承模式设计

状态：用户已确认设计提案；书面规格待用户复核

日期：2026-08-16

## 1. 目标

RoleFlow 的筛选方案需要明确区分两种“平台岗位从哪里来”的方式，同时继续复用同一套本地岗位理解、证据匹配和推荐规则：

- **继承模式**：使用 `BOSS-SEARCH` 当前页面已经选择的平台范围，只替换 RoleFlow 的岗位关键词。
- **通用模式**：由用户在 RoleFlow 中保存城市、BOSS 薪资档、经验、学历和职位类型，RoleFlow 据此生成 BOSS 搜索地址并扫描。

两种模式只改变平台采集范围，不改变候选人画像、匹配偏好卡、完整 JD 分析和推荐分级的质量标准。

本设计同时解决当前三个已证实的问题：

1. “执行一轮”入口写死为继承模式，通用模式只能从高级扫描或命令行进入。
2. 方案页把平台采集条件和 RoleFlow 本地精筛条件混在一起，并始终按通用模式校验；因此页面虽提示继承模式可不填城市，保存时仍会报错。
3. 已启动任务会在执行阶段再次读取可变的当前方案；通用模式也会临时解析平台筛选条件，不能证明恢复后仍执行启动时看到的同一套条件。

## 2. 非目标

本课题不做以下工作：

- 不修改岗位匹配算法、推荐等级或消息回复草稿逻辑。
- 不修复、验证、启用或删除 `search_page_api`。
- 不恢复通用的 `standalone_detail`；岗位详情仍只走 `trusted_pane`。
- 不增加第二个 Edge 会话、第二个 BOSS 窗口或并行岗位标签页。
- 不把新用户默认模式改为通用模式。
- 不重建数据库表，不批量改写历史方案，不启动全项目重写。

## 3. 已核实的当前事实

以下结论来自当前代码，而不是历史计划推断：

- `src/application/workflow/index.js` 的新一轮入口固定调用继承模式解析器，并以 `acquisitionMode: "inherited"` 校验方案。
- `src/cli.js` 和高级扫描入口已经认识内部值 `generated` 与 `inherited`，通用模式不是一个全新浏览器能力。
- `src/dashboard/server.js` 保存方案时固定以 `generated` 校验，页面展示则允许继承模式城市为空，两者互相矛盾。
- `search_plans.plan_json` 可以保存版本化 JSON，无需新增数据库表。
- `workflow_runs.planner_json` 已经保存任务的规划信息；扫描批次的执行快照也已包含模式、搜索模板、平台筛选、限制和目标列表，并具有一致性哈希。
- 当前方案 JSON 没有持久化采集模式，城市、经验、学历、职位类型等字段仍是扁平字段。
- 当前运行时会把部分扁平字段同时用于平台采集和本地推荐，字段语义不清晰。
- 继承模式已能从当前 BOSS 搜索页读取并冻结搜索范围；通用模式已能根据城市、关键词和 BOSS 原生筛选条件生成搜索目标。

## 4. 方案选择

采用“**一个版本化方案、两种采集模式、一套本地精筛**”。

没有采用以下方案：

- **只在现有扁平 JSON 上增加一个模式开关**：改动较少，但平台条件和本地条件仍然混用，任务恢复仍容易被当前方案改动影响。
- **为两种模式各建一份完整方案**：会重复保存关键词、方向、排除项和薪资偏好，用户修改其中一份后容易产生无声分叉。

选择当前方案的原因是：它复用现有 JSON 存储和执行快照，只增加一个规范化边界，不需要新表或新框架；同时能清楚回答“平台先找哪些岗位”和“RoleFlow 再如何判断这些岗位”这两个不同问题。

## 5. 用户术语与内部值

界面只显示容易理解的中文名称：

| 界面名称 | 内部值 | 含义 |
| --- | --- | --- |
| 继承模式 | `inherited` | 继承当前 `BOSS-SEARCH` 页的平台范围 |
| 通用模式 | `generated` | RoleFlow 按保存的平台条件生成 BOSS 搜索地址 |

“通用模式”不是另一套推荐算法。两个模式取得 JD 后，都进入同一套本地证据匹配、分析和推荐流程。

## 6. 筛选方案 v2

### 6.1 规范结构

新保存的 `plan_json` 使用 `schemaVersion: 2`。规范结构如下：

```json
{
  "schemaVersion": 2,
  "name": "目标岗位筛选计划",
  "acquisitionMode": "inherited",
  "platform": {
    "site": "boss",
    "generated": {
      "cities": ["广州"],
      "salaryLanes": ["10-20K"],
      "experience": ["1-3年"],
      "jobTypes": ["全职"],
      "degrees": ["本科"]
    }
  },
  "directions": ["AI 应用开发"],
  "keywords": [
    { "word": "RAG", "priority": "A", "reason": "核心方向" }
  ],
  "salary": { "minK": 12, "maxK": 20 },
  "salaryMode": "wide",
  "allowExperienceStretch": true,
  "bossActiveDays": 14,
  "workSchedulePreference": "prefer_double_weekend",
  "excludeWords": [],
  "hardExcludes": [],
  "scan": {
    "maxCards": 60,
    "maxDetailTotal": 300,
    "browserPageBudget": 90
  },
  "source": "user-confirmed"
}
```

示例值不改变现有产品策略默认值和上下限；实现必须继续从 `PRODUCT_POLICY` 取得实际默认值。

### 6.2 字段归属

| 字段 | 继承模式 | 通用模式 | 是否参与本地精筛 |
| --- | --- | --- | --- |
| 城市、BOSS 薪资档、经验、学历、职位类型 | 从当前 BOSS 页面读取，方案不保存其当前值 | 保存于 `platform.generated` 并用于生成搜索地址 | 不作为重复的第二组表单条件；实际岗位字段仍由统一分析器判断 |
| 关键词及优先级 | RoleFlow 保存并替换页面关键词 | RoleFlow 保存并生成查询关键词 | 是，也是本地匹配信号 |
| 扫描数量与浏览器预算 | RoleFlow 保存 | RoleFlow 保存 | 控制执行量，不改变推荐标准 |
| 目标方向、匹配偏好卡、排除项 | RoleFlow 保存或引用 | RoleFlow 保存或引用 | 是 |
| 期望薪资、薪资严格度、活跃度、作息偏好、经验放宽 | RoleFlow 保存 | RoleFlow 保存 | 是 |

关键词只有一份，避免出现“平台关键词”和“本地关键词”互相漂移。界面必须说明：关键词既用于 BOSS 查询，也会作为本地匹配信号。

匹配偏好卡继续保持独立的确认与版本机制。方案页只显示摘要和进入匹配偏好卡的入口，不把整张卡复制进 `plan_json`。

`bossCityCode` 不再作为 v2 的独立事实保存；它可由已支持城市映射在启动时生成，并在任务快照中冻结，避免城市名称和代码不一致。

### 6.3 校验规则

保存时先规范化，再按当前 `acquisitionMode` 校验：

- 两种模式都必须通过关键词、方向、薪资关系、排除冲突和扫描预算校验。
- 继承模式不要求 `platform.generated.cities` 有值，也不因未启用的通用模式字段而阻止保存。
- 通用模式至少需要一个受支持城市；其他 BOSS 原生筛选项可以为空，空值表示不额外限制。
- 通用模式保存时只依赖本地结构和已有筛选目录做校验，不为了保存而导航 BOSS。
- 如果执行时缓存目录缺失或过期，可以按第 10 节的安全约束刷新；任何已保存标签无法解析成明确平台参数时，在扫描开始前明确停止，不静默忽略。
- 用户切换模式时，未启用模式的配置保留，但只校验并执行当前模式。

## 7. 旧数据兼容

采用读取时惰性规范化，不批量改写数据库：

- 没有 `schemaVersion` 或 `acquisitionMode` 的旧方案，读取时视为 `schemaVersion: 1`，默认规范化为继承模式。这保留当前“执行一轮”的实际行为。
- 旧字段 `cities`、`platform.salaryLanes`、`experience`、`jobTypes`、`degrees` 被复制到规范化读模型的 `platform.generated`，因此用户以后切到通用模式时不会丢失原有设置。
- 旧 `bossCityCode` 只作为兼容输入校验，不作为 v2 写回字段。
- 用户下一次明确保存方案时才写回完整 v2 JSON。
- 历史任务不能根据当前方案重新推断模式。已有 `planner_json.acquisitionMode` 和扫描执行快照继续是历史执行事实。
- 历史任务缺少或包含无效模式时继续安全阻断，不能因为旧方案默认继承而猜测任务模式。

规范化函数是 v1/v2 的唯一读取入口。业务代码不再分别猜测扁平旧字段和 v2 字段，写入端也不同时保存两份同义字段。

## 8. 方案页交互

### 8.1 页面结构

方案页按下面顺序展示：

1. **采集模式**：继承模式 / 通用模式单选，并用一句话说明差异。
2. **平台采集范围**：只展示当前模式对应的范围。
3. **关键词与扫描规模**：两种模式共用。
4. **RoleFlow 本地精筛**：方向、匹配偏好卡摘要、排除项、期望薪资、活跃度、作息和经验放宽。

### 8.2 继承模式

- 平台范围显示为只读预览，来源是当前绑定的 `BOSS-SEARCH` 页。
- 预览只读取当前 URL 和已验证 DOM，不点击、不导航、不激活标签页。
- 能确定的城市、薪资、经验、学历和职位类型显示为明确标签；未知参数显示“未能识别”，不能伪装成“无限制”。
- 浏览器未连接、页面不是可信搜索页或登录/风控状态异常时，页面仍可编辑本地方案，但“执行一轮”明确阻断并给出可恢复说明。

### 8.3 通用模式

- 城市、BOSS 薪资档、经验、学历和职位类型可编辑。
- 选项优先使用已缓存的 BOSS 筛选目录。
- 目录暂时不可用时不编造选项；已有值保留并标记需要在执行前解析。

### 8.4 切换与任务不可变性

- 切换模式不清空另一模式的设置。
- 保存后只影响下一次新任务。
- 如果已有任务运行中，页面明确显示“当前任务仍使用启动时快照”，并提供其模式和主要条件摘要。
- 页面不再无条件显示“平台已继承”；文案必须来自实际模式和实际解析状态。

## 9. 新任务启动与不可变快照

### 9.1 启动顺序

“执行一轮”读取规范化后的方案，并按方案内的 `acquisitionMode` 分支：

1. 校验共同的本地条件和当前模式条件。
2. 解析当前模式的平台采集上下文。
3. 把完整规范方案、模式、平台采集上下文和哈希写入 `workflow_runs.planner_json`。
4. 创建任务后再启动扫描进程。

如果第 2 步不能得到完整且可信的平台上下文，则不创建可执行任务，也不启动扫描。

### 9.2 `planner_json` 合同

为减少迁移范围，保留现有顶层执行字段，并增加完整方案快照：

```json
{
  "acquisitionMode": "generated",
  "planSnapshotVersion": 2,
  "planSnapshot": {},
  "planHash": "stable-hash",
  "searchTemplate": {},
  "keywordSource": {},
  "cityScopes": [],
  "nativeFilters": {},
  "nativeFilterCatalogRevision": "revision-or-hash",
  "modelProfiles": {}
}
```

两种模式的必备内容不同：

- **继承模式**：冻结 `searchTemplate`、`searchScope`、`platformPolicy`、`keywordSource`，以及从当前页面解析出的实际平台范围。
- **通用模式**：冻结 `cityScopes`、精确的 `nativeFilters`、筛选目录版本或哈希、生成式搜索模板、`keywordSource`。

`planSnapshot` 是规范化后的完整 v2 方案；`planHash` 对确定性内容计算，不包含时间戳。现有关键词分配、预算、模型配置修订和任务规划字段继续保留。

### 9.3 与扫描执行快照的关系

- `planner_json` 证明“用户启动任务时选择了什么”。
- 扫描批次执行快照证明“这一批实际要跑哪些精确目标”。
- 首次扫描从 `planner_json` 构造执行快照；一旦执行快照存在，恢复必须继续使用该快照。
- 两者的模式、关键词、城市范围和平台筛选哈希不一致时必须阻断，不能重新读取当前方案来修补。

## 10. 两种模式的浏览器行为

### 10.1 共同边界

- 真实 BOSS 浏览器采集只使用一个已登录 Edge 配置和当前绑定的 `BOSS-SEARCH` / `BOSS-COMMUNICATION` 固定标签页；离线 JSON 输入和假浏览器测试不受此句影响。
- 本课题的扫描只操作 `BOSS-SEARCH`；不创建第二个窗口、第二个会话或并行岗位标签页。
- 不调用 `Page.bringToFront`，不激活 BOSS 标签页，不做前台焦点恢复。
- 保留用户主动运行工作区启动助手时那一次有意义的引导聚焦；本课题不删除、扩展或复用该唯一例外。
- 正常详情读取继续只用 `trusted_pane`。
- 所有导航、翻页、滚动和详情读取保持串行，并继续使用随机间隔、周期冷却、访问预算、检查点和登录/风控/页面丢失立即停止机制。

### 10.2 继承模式

- 启动时重新解析当前绑定搜索页的 URL 与可信 DOM，证明页面身份后冻结范围。
- 不为了补齐方案字段而改变当前页面筛选条件。
- 扫描期间只替换关键词，并保持继承范围中的其余平台参数。

### 10.3 通用模式

- 优先使用本地缓存的 BOSS 筛选目录把用户标签解析为精确参数。
- 只有目录缺失或过期时，才允许沿用现有受控的目录刷新行为；刷新计入访问预算，遵循随机节奏和冷却，并在开始前重新绑定固定标签页。
- 每个实际搜索跳转都使用启动时冻结的城市、筛选参数和关键词，不读取后来保存的方案。
- 任何标签不能唯一解析、筛选未实际生效、页面身份变化或风险信号出现时，保留未完成目标并停止本轮。

## 11. 恢复规则

- 恢复任务先读历史 `planner_json` 和已有扫描执行快照，不读取当前方案来决定模式或平台条件。
- 用户在任务暂停后修改方案，只影响下一次新任务。
- 尚未创建扫描批次时，从 `planner_json.planSnapshot` 和冻结的平台上下文继续。
- 已创建扫描批次时，以通过哈希校验的执行快照为准，继续其中未完成的目标。
- 当前固定标签页必须重新绑定并通过身份检查；数字标签页 ID 不从历史记录复用，也不转成字符串。
- 当前环境无法满足历史快照时明确阻断并保留进度，不降级到另一模式，不改用 `standalone_detail`，也不自动缩小逻辑质量目标。

## 12. 错误与可见状态

错误必须指出是“方案问题”“平台范围无法解析”“浏览器状态问题”还是“历史快照不一致”，并给出用户可执行的下一步。以下情况不能静默回退：

- 模式缺失或无效。
- 通用模式没有有效城市。
- 保存的 BOSS 筛选标签不能解析成唯一参数。
- 继承模式当前页不是可信搜索页，或范围无法完整确认。
- 任务快照和扫描执行快照不一致。
- 页面失效、登录失效、风控信号、访问预算或冷却要求阻止继续。

日志和界面错误不得暴露完整 BOSS URL、`securityId`、Cookie 或其他敏感标识。

## 13. 质量基线与决策门

通用模式上线不能只证明“能跑”，还要证明没有用更少 JD 或更窄结果换取表面速度。

### 13.1 样本隔离

- 继承模式和通用模式各使用一份新的空岗位历史作为运营基线。
- 两份基线保留同一候选人画像、简历版本、匹配偏好卡、模型设置和产品策略。
- 旧岗位历史只可作为恢复证据，不进入本次召回率、准确度、活跃度或耗时比较。
- 比较必须记录运行时间、方案快照哈希和实际平台范围，避免把不同条件伪装成模式差异。

### 13.2 必须报告的数字

每种模式分别报告：

- 发现岗位数、去重后岗位数。
- 人工标注相关岗位并集中的命中数与相对召回率；该指标只表示两种结果集之间的相对覆盖，不宣称绝对召回率。
- 需要完整 JD 的岗位数、成功读取数、仍待读取数、最终完整 JD 覆盖率。
- `primary`、`apply`、`caution`、`not_recommended` 的数量和比例。
- 人工确认的硬性错误推荐数。
- BOSS 页面跳转、详情读取、滚动的实际访问次数。
- 总耗时、冷却耗时、登录/风控/页面丢失等中断次数。

### 13.3 决策规则

- 不设置会自动接受质量下降的容差。
- 若通用模式或任何默认值变更降低召回、完整 JD 覆盖或推荐准确度，必须把具体差值和节省的访问次数/时间交给用户决定。
- 新用户和旧方案继续默认继承模式。只有新基线证据充分且用户明确决定后，才可以另行设计默认模式变更。

## 14. 验收标准

### 14.1 自动化回归

至少证明以下合同：

- v1 方案读取时默认继承，并正确映射到 v2；只有明确保存才写回 v2。
- v2 往返保存不产生扁平同义字段，也不丢失未启用模式的通用配置。
- 两种模式使用各自校验规则；继承模式不再被空城市阻断。
- 页面按实际模式分组展示平台采集与本地精筛，不再始终显示“平台已继承”。
- 新任务按方案模式分支，并冻结完整方案、模式、关键词来源和平台上下文。
