# RoleFlow 参考项目功能整合设计

**日期：** 2026-08-03
**状态：** 待用户书面确认
**参考项目：** `santifer/career-ops`、`Yht20927/BossZhipin-cli`

## 1. 目标

在不破坏 RoleFlow 已冻结的四档匹配、真实模型验收结果和 BOSS 安全边界的前提下，选择性吸收两个参考项目中有价值的产品能力和工程思路。

整合采用以下总原则：

> 补充为主，覆盖为例外；复用现有数据，扩展现有界面，不建立第二套系统。

本设计只确定整合架构、模块边界和实施顺序。每个子项目在实施前还需要独立的详细计划、失败测试和验收标准。

## 2. 已确认的产品边界

### 2.1 四档推荐保持唯一

RoleFlow 继续使用以下四档：

- `主投`
- `可投`
- `慎投`
- `不推荐`

模型语义分析负责提取岗位要求、候选人证据、缺口和风险。代码根据已确认的二维表和权重生成最终四档建议。

本轮整合不得：

- 引入 Career-Ops 的另一套岗位评分体系作为最终推荐。
- 新增与四档推荐并行的第二套投递分组。
- 根据求职结果自动修改二维表。
- 未经用户确认调整二维表、核心权重或严重偏差定义。

### 2.2 BOSS 安全边界保持不变

不得移植 BossZhipin-cli 的以下能力：

- 油猴脚本注入。
- 浏览器内任意 JavaScript 执行桥。
- Cookie、Token 或 `__zp_stoken__` 读取与缓存。
- BOSS 内部接口调用。
- 自动批量打招呼。
- 自动发送聊天消息。
- 自动交换微信或手机号。
- 自修复脚本注入。

RoleFlow 继续遵守固定标签页、串行操作、页面身份复核、不可变沟通批次、首次真实点击单独授权、风险信号立即停止等规则。

### 2.3 当前匹配基线保持冻结

以下能力不能因为参考项目整合而发生隐式变化：

- 模型提示词和结构化输出契约。
- 四档决策规则。
- 已确认二维表。
- 默认沟通选择规则。
- 已冻结的真实模型验收基线。

如果后续子项目确实需要改变这些内容，必须建立独立设计、独立验收和用户确认，不得夹带在普通功能整合中。

## 3. 整合方法

每项候选功能必须先归入以下四类之一。

### 3.1 保留

现有能力已经承担正确职责，第三方项目只能作为产品表现参考，不能替换底层实现。

适用范围：

- 四档匹配。
- 简历与匹配卡版本。
- 扫描批次和断点恢复。
- 沟通批次与执行门禁。
- BOSS 浏览器适配。
- 本地隐私存储。

### 3.2 扩展

RoleFlow 已有数据和流程，但缺少统计、检查、历史或更清楚的用户界面。扩展必须继续使用现有数据源和模块。

适用范围：

- 求职进度。
- 跟进记录。
- 数据健康检查。
- 审计和模型指标。
- 缓存查看。
- 报告导出。
- Dry-run 预演展示。

### 3.3 新增旁路能力

现有核心流程没有该职责，新功能应作为独立模块消费已有结果，不得反向改变四档推荐。

适用范围：

- 岗位可信度与时效风险。
- STAR 面试故事库。
- 面试问题。
- 岗位专用简历草稿。
- 公司调查。
- Offer 与薪资比较。
- 公开 ATS 招聘源。

### 3.4 拒绝

与账号安全、数据隐私、产品边界或现有架构明显冲突的能力不进入 RoleFlow。

适用范围：

- Cookie 和 Token 自动化。
- BOSS 内部接口。
- 绕过可见页面证据的执行。
- 自动沟通或自动交换联系方式。
- 第三方推荐体系覆盖四档决策。

## 4. 覆盖现有实现的准入条件

默认不得覆盖现有实现。只有同时满足以下条件，才允许提出替换方案：

1. 现有实现存在已复现的产品缺陷、安全问题或结构性阻塞。
2. 该问题不能通过增加字段、增加小模块或扩展现有接口解决。
3. 新实现具有旧数据迁移方案。
4. 新实现具有关闭开关或明确回滚路径。
5. 新旧行为具有可比较的回归测试。
6. 现有离线测试和冻结验收基线不得意外退化。
7. 涉及二维表或匹配权重时，已经获得用户单独确认。

“第三方项目功能更多”或“第三方项目 Stars 更多”不能单独构成替换理由。

## 5. 现有能力与候选能力映射

| 候选能力 | RoleFlow 现有基础 | 整合决策 | 数据权威来源 |
|---|---|---|---|
| 求职进度管理 | 投递状态、跟进记录、工作流运行 | 扩展状态历史和统计 | 现有岗位与工作流数据 |
| 数据健康检查 | 一致性测试、恢复机制、自检 | 增加用户可见的体检报告 | 现有数据库与运行记录 |
| 岗位真实性检查 | 风险和质量标签 | 新增独立可信度评估 | 岗位快照与只读外部证据 |
| 求职结果反馈 | 反馈、跟进、投递状态 | 增加按四档和方向汇总 | 现有反馈与状态记录 |
| STAR 面试故事 | 简历证据、画像、匹配卡 | 新增证据派生层 | 已确认简历证据 |
| 岗位专用简历 | 简历版本管理 | 增加草稿类型和差异确认 | 主简历及目标岗位快照 |
| 安全短引用 | 岗位 ID、扫描与沟通批次 | 增加不可变显示别名 | 真实岗位 ID 和批次快照 |
| 审计和模型指标 | 脱敏日志、模型调用指标 | 扩展现有事件字段和汇总 | 现有 observability |
| Dry-run 预演 | 沟通批次确认 | 改善现有预览界面 | 不可变沟通批次 |
| CSV/JSONL 导出 | Markdown、HTML 报告 | 扩展现有报告模块 | 现有报告查询结果 |
| 公开 ATS 岗位源 | BOSS 来源适配 | 新增独立来源适配器 | 各公开 ATS 接口 |
| 公司调查 | 无完整模块 | 后期新增旁路能力 | 公开来源及岗位快照 |
| Offer 和薪资比较 | 无完整模块 | 后期新增旁路能力 | 用户确认的 Offer 数据 |

## 6. 总体架构

新能力围绕现有核心形成四层，不建立第二套主流程。

```text
现有权威数据层
  岗位、JD 快照、简历版本、匹配卡、四档建议、批次、反馈
                    |
                    v
现有核心工作流层
  扫描、分析、四档决策、批次确认、跟进、恢复
                    |
          +---------+---------+
          |                   |
          v                   v
增强检查层              新增旁路能力层
健康检查、统计、审计      可信度、STAR、简历草稿、公司调查
          |                   |
          +---------+---------+
                    v
现有界面与报告层
  在现有页面增加区块、筛选、警告和导出
```

### 6.1 单一数据权威

- 岗位真实身份继续由现有岗位 ID、平台 ID 和 URL 确定。
- 四档建议继续由现有决策链产生。
- 简历事实继续来自已确认简历版本和匹配卡。
- 沟通目标继续由不可变沟通批次确定。
- 第三方功能不能创建与这些对象竞争的主记录。

### 6.2 派生结果可重新生成

岗位可信度、STAR 故事、面试问题、统计报告和短引用都属于派生数据。

每条派生结果必须记录：

- 来源对象 ID。
- 来源内容哈希或版本。
- 生成规则或模型版本。
- 生成时间。
- 当前是否过期。

来源发生变化后，旧结果显示为过期，不得伪装成最新结果。

### 6.3 争议能力使用开关

只有可能影响成本、稳定性或用户判断的能力需要开关，例如：

- 岗位可信度模型分析。
- STAR 故事模型生成。
- 岗位专用简历生成。
- 公开 ATS 来源。

状态统计、数据健康检查和安全短引用属于确定性本地功能，不增加无意义的开关。

## 7. 子项目与实施顺序

每个子项目独立设计、实施、测试和提交。前一个子项目通过后，后一个子项目才能依赖其公开接口。

### 7.1 子项目一：求职进度与系统体检

目标：

- 补充状态变化历史。
- 检查重复岗位、缺少完整 JD、分析过期、批次不一致和长时间未处理。
- 展示缓存来源、分析版本和更新时间。
- 在现有工作流页面增加健康摘要，不增加第二套管理页面。

明确不包含：

- 模型提示词修改。
- 四档规则修改。
- BOSS 操作修改。

### 7.2 子项目二：岗位可信度与时效风险

目标：

- 在四档建议之外增加独立的岗位可信度。
- 区分已观察事实、规则判断和模型推断。
- 展示需要用户核实的问题。

输出示例：

```text
四档建议：可投
岗位可信度：需要核实
风险：相同岗位疑似长期重复发布
```

可信度不得自动修改四档建议或默认沟通勾选。

### 7.3 子项目三：结果统计与反馈闭环

目标：

- 按主投、可投、慎投、不推荐统计回复和面试结果。
- 按岗位方向、分析版本和时间段进行对比。
- 标记样本量过小，避免把偶然结果当成规律。

第一版只读展示，不自动调权重，不自动修改二维表。

### 7.4 子项目四：面试证据库

目标：

- 从已确认简历证据生成 STAR 故事草稿。
- 针对岗位要求生成可能追问和核实问题。
- 明确显示每个故事引用的简历证据。
- 允许用户编辑和确认。

不得补造未出现在简历或用户确认信息中的经历、数据和成绩。

### 7.5 子项目五：安全短引用与导出增强

目标：

- 为不可变批次中的岗位生成短引用。
- 增加 CSV 和 JSONL 导出。
- 补充运行摘要、缓存命中、模型耗时和停止原因。

短引用只用于显示和人工命令输入。执行前必须解析为真实岗位 ID，并重新验证批次、URL 和岗位身份。

### 7.6 子项目六：岗位专用简历草稿

目标：

- 从主简历和目标岗位生成独立草稿。
- 展示逐项修改差异和证据来源。
- 用户确认后保存为新的简历版本。

不得覆盖主简历，不得自动写入未经证明的能力。

### 7.7 子项目七：公开岗位源及后期工具

目标：

- 接入 Greenhouse、Lever、Ashby 等公开 ATS 来源。
- 后续增加公司调查、Offer 对比和薪资谈判准备。

公开来源适配器与 BOSS 适配器保持隔离。失败的公开来源不得影响 BOSS 工作流，也不得降低现有 JD 覆盖质量。

## 8. 数据迁移原则

- 优先新增字段或独立派生表，不重命名现有关键字段。
- 数据库迁移必须可以识别旧版本数据。
- 旧数据缺少新字段时使用明确的“尚未评估”，不能伪造默认结论。
- 删除或替换字段需要单独迁移设计。
- 岗位专用简历、STAR 故事和可信度结果必须关联来源版本。
- 新数据表不得复制完整简历、Cookie、Token 或不必要的敏感信息。

## 9. 界面整合原则

- 优先在现有岗位详情、工作流、简历版本和诊断页面增加区块。
- 不为每个新功能创建独立首页。
- 四档建议始终保持最主要的位置。
- 岗位可信度使用独立标题和颜色，避免被误解为第五档推荐。
- 派生结果必须显示来源、生成时间和过期状态。
- 模型生成内容必须标记为草稿，并提供用户确认入口。
- 可能触发真实沟通的页面继续使用不可变批次和最终身份复核。

## 10. 错误处理

- 健康检查失败只影响对应检查项，不阻断历史数据查看。
- 可信度分析失败时显示“尚未评估”，不能改变四档建议。
- STAR 或简历草稿生成失败时保留原始简历和已有确认内容。
- 短引用过期、来源批次变化或身份不一致时必须拒绝解析。
- 公开 ATS 来源失败时隔离该来源，其他来源继续工作。
- 所有模型错误使用现有脱敏日志记录，不输出简历全文、密钥或敏感配置。

## 11. 测试与验收

每个子项目必须满足：

- 先补失败测试，再写实现。
- 功能关闭时保持原有行为。
- 现有离线测试继续通过。
- 数据迁移覆盖旧数据库样本。
- 派生数据过期规则有确定性测试。
- 不新增 BOSS Cookie、Token 或内部接口访问。
- 不扩大真实沟通权限。
- 冻结的四档匹配基线不得发生非预期变化。

涉及模型的新子项目采用以下验收顺序：

1. 本地契约和解析测试。
2. 固定离线样本。
3. 少量真实模型样本。
4. 完整验收样本。

岗位可信度、STAR 和简历草稿的验收指标各自独立，不能用匹配准确率替代。

## 12. 复杂度控制

为避免项目再次陷入无限调试和提示词膨胀：

- 一个子项目只解决一个明确问题。
- 确定性逻辑优先由代码计算。
- 模型只负责语义提取、草稿生成和难以规则化的判断。
- 新模型任务优先使用独立调用，不继续加重岗位匹配提示词。
- 能通过字段、权重或本地统计解决的问题，不增加提示词规则。
- 第一版不追求覆盖所有边缘场景。
- 子项目没有真实使用价值时可以停止，不因为参考项目有该功能而继续开发。

## 13. 首个实施目标

第一个实施计划只覆盖“求职进度与系统体检”。

选择该子项目的原因：

- 最大程度复用现有岗位、状态、跟进和工作流数据。
- 不需要新增模型调用。
- 不影响四档匹配结果。
- 不扩大 BOSS 权限。
- 可以尽早发现数据库、批次和分析版本问题。
- 能为后续结果统计和反馈闭环提供可靠基础。

岗位可信度、STAR、岗位专用简历和公开 ATS 来源分别编写后续设计与计划，不夹带在第一个实施计划中。

## 14. 成功标准

本轮参考项目整合成功的判断标准不是“复制了多少功能”，而是：

- 用户可以更清楚地知道岗位和求职流程当前处于什么状态。
- 新功能复用现有权威数据，不产生相互矛盾的记录。
- 四档匹配和默认沟通规则保持稳定。
- 模型任务没有继续无边界膨胀。
- BOSS 账号安全边界没有退化。
- 每个新能力都可以独立测试、关闭和继续演进。
