# RoleFlow 首次使用与 Dashboard 产品体验设计

**日期：** 2026-08-13
**状态：** 概念方案已获用户确认，书面规范待用户复核
**所属：** beta.4 人工验收整改子项目 B

## 1. 目标

让新用户按“配置模型 → 上传简历 → 检查匹配卡 → 确认本地筛选方案 → 执行任务”
自然前进，并让五分钟级简历处理和四十分钟级岗位流程都有可理解、可刷新恢复的
状态。

本设计沿用服务端渲染页面、SQLite 和现有模型适配器，不引入 SPA 框架、消息队列
服务或新的前端依赖。

## 2. 首次启动路由

根路由按以下顺序决定：

1. `deep_analysis` 模型未验证：
   `/settings?firstRun=1&next=%2Fonboarding`；
2. 模型已验证，但没有候选人画像：
   `/onboarding`；
3. 有未完成的简历处理：
   `/onboarding/progress?runId=...`；
4. 有画像但没有已确认匹配卡：
   `/match-card?...`；
5. 有匹配卡但没有活动筛选方案：
   进入筛选方案确认；
6. 画像、匹配卡和方案均可用：
   进入今日任务。

直接访问简历页仍允许查看已有内容；深度模型不可用时，解析按钮禁用并提供前往
模型设置的唯一主要动作。老用户模型仍可用时，不在每次启动强制经过设置页。

## 3. 模型设置页

### 3.1 布局

- 顶部：共享厂商、API Key 和保存说明。
- 桌面端主体两列：
  - 左：简历深度分析；
  - 右：岗位批量筛选。
- 小于 760 px 时自然变为单列。
- 批量备用模型继续放在折叠的“高级与容错”区域。
- 不把超时、推理强度等高级字段放在主要连接按钮之前。

### 3.2 引导

- 提供官方 DeepSeek 开放平台链接：
  `https://platform.deepseek.com/`。
- 外部链接新开页，并使用 `noopener`/`noreferrer`。
- `deep_analysis` 验证成功后显示“下一步：填写简历”。
- `batch_screening` 未验证不阻止填写简历，但在执行首轮岗位任务前继续使用现有
  服务端硬门。
- 连接失败在当前卡片内显示中文原因和具体修复动作，不把用户送到诊断日志。

## 4. 持久化简历处理

### 4.1 为什么必须异步

人工日志证明一个简历请求可能持续近五分钟，而且两个模型步骤发生输出截断重试。
继续让浏览器等待同一个 POST 会导致转圈、刷新丢失反馈和重复提交风险。

### 4.2 持久化记录

新增 `onboarding_runs`，只负责一次简历处理生命周期：

```text
id
profile_id
resume_document_id
status: queued / running / completed / failed
stage: parsed / analyzing_profile / building_match_card / building_plan / ready
progress_revision
profile_version_id
matching_card_id
search_plan_id
error_code
error_message
heartbeat_at
created_at / updated_at / finished_at
```

原始简历仍只保存在现有 `resume_documents` 和受控源文件目录，不复制到
`onboarding_runs`。模型密钥、模型输出正文和简历正文不得写入任务记录。

新候选人上传时，在一个事务中：

1. 本地解析和脱敏诊断；
2. 创建仅供此次 onboarding 使用、尚无 profile version 的本地候选人记录；
3. 写入 `resume_documents`；
4. 创建 `queued` onboarding run；
5. 提交后由隐藏子进程处理模型步骤。

没有 profile version 的处理记录不属于可用候选人：根路由、候选人选择器、今日
任务和方案列表都不得展示它，只能通过对应 onboarding run 进入进度页。任务失败
后用户可以基于同一文档重试；用户明确放弃时，只有在仍无 profile version、匹配
卡和方案的情况下，才允许事务性删除该占位候选人与简历文档。

更新已有候选人时，旧画像、旧确认卡和旧方案继续有效，直到新匹配卡由用户确认。

### 4.3 子进程和检查点

Dashboard 启动隐藏的单任务子进程，不新增常驻服务。子进程按顺序：

1. `parsed`：文件已接收并完成本地解析；
2. `analyzing_profile`：生成画像，成功后立即持久化画像版本；
3. `building_match_card`：生成匹配卡；失败时继续使用现有确定性 fallback；
4. `building_plan`：仅在首次使用且没有活动方案时生成初始方案；
5. `ready`：至少已有画像版本和匹配卡草稿。

每一步在同一事务内更新结果 ID、阶段、heartbeat 和 revision。页面每 2.5 秒轮询
只读状态。

模型调用期间子进程维持 heartbeat。Dashboard 重启后：

- 仍有健康子进程：继续显示当前阶段；
- 任务失去 heartbeat：标记为可重试失败，不自动重复调用付费模型；
- 用户点击“重试当前处理”后复用同一简历文档和已完成检查点；
- 已完成画像时不重复分析画像；
- 已完成匹配卡时不重复生成匹配卡。

同一 `profile_id + resume content hash` 继续幂等，重复上传不得新建第二份模型任务。

### 4.4 页面反馈

上传后进入独立进度页，显示：

- 文件已接收；
- 当前阶段；
- 已耗时；
- 本步骤是否发生安全重试；
- 已完成成果；
- 明确错误与可执行的重试动作。

不显示虚假百分比。匹配卡完成后即显示“先检查匹配偏好卡”，筛选方案仍在后台
生成时也不阻止用户检查卡片。方案生成失败只影响方案步骤，可单独重试，不把已
完成的画像和匹配卡判为失败。

按钮统一为“解析简历并生成筛选方案”。

## 5. 简历耗时优化

优化不删字段、不缩短简历事实、不换模型：

- `analyzeResume` 和 `recommendSearchPlan` 当前从 4096 response tokens 起步，收到
  `MODEL_OUTPUT_TRUNCATED` 后才提升到 8192；人工运行已分别证明第二次在扩大上限
  后成功。
- 这两个结构化任务直接从 8192 上限开始，保留一次可恢复重试。
- 其他岗位理解和匹配任务保持现有上限与拆分策略。
- 继续记录种类、耗时、尝试次数、finish reason 和脱敏长度，不记录模型正文。

验收比较同一组脱敏 fixture 的字段完整性和调用次数。真实简历效果由用户在下一次
人工流程中确认；没有量化证据时不得通过删除经历、项目或证据字段来提速。

## 6. 本地姓名与模型隐私边界

### 6.1 本地显示

- 在脱敏前用现有标签、首行和文件名规则提取本地显示名。
- 本地显示名单独存入 `candidate_profiles.display_name`。
- 页面优先使用 `display_name`；无法识别时显示“候选人”。
- `[姓名已隐藏]`、`姓名已隐藏`、`[已隐藏]` 等占位符不得写入 display name。

### 6.2 模型输入

- 简历原文在发送画像模型前继续遮盖姓名、手机、邮箱、身份证号和详细地址。
- `profile_json.candidate.name` 不保存真实姓名，只保留中性值。
- 生成匹配卡、筛选方案和消息草稿时使用统一的 model-safe profile，显式移除姓名。
- 用户在本地画像页编辑姓名时只更新 display name，不把真实姓名重新写回后续
  模型输入。
- 日志、诊断和导出继续脱敏。

这样消除本地页面上的无意义占位符，同时不削弱云端隐私边界。

## 7. 今日任务页

### 7.1 首屏

1280×720 首屏只回答：

1. 现在处于哪一步；
2. 用户现在需要做什么；
3. 今天得到多少可用结果；
4. 是否有真实阻塞。

首屏保留：

- 一张主要动作卡；
- 最多三个核心指标：今日已核验沟通、可用候选、当前轮次；
- 只有存在真实阻塞时才显示一张恢复卡。

没有阻塞时不显示“当前数据安全”“质量护栏”等重复宣传性卡片。

### 7.2 次要信息

- “本地筛选方案”摘要；
- 当前 BOSS 继承条件的只读摘要；
- 候选人摘要折叠或链接；
- 详情预算、维护扫描、诊断和历史反馈进入“高级信息”。

页面不再同时呈现两套主要扫描入口。日常主流程只使用“执行一轮”；维护扫描保留
在折叠区。

## 8. 筛选方案的产品定位

普通入口把 Search Plan 命名为“本地筛选方案”：

- BOSS 页面负责城市、区域、学历、经验和平台原生粗档；
- RoleFlow 负责关键词顺序、薪资精细规则、排除词、岗位方向、工作节奏和匹配偏好；
- 完整平台参数生成模式保留在代码和高级入口，本轮不继续扩展参数表。

继承模式的主表单不要求城市，也不把平台薪资档当成本地精确薪资。页面同时显示：

```text
平台已继承：广州 · 天河 · 10-20K · 1-3 年
本地再筛选：期望 8-15K · 有交集才推荐 · 优先双休
```

### 8.1 薪资区间

新增显式的“区间有交集才推荐”模式：

```text
job.max >= desired.min && job.min <= desired.max
```

- 薪资面议、缺失或无法解析时进入“薪资待确认”，默认不硬排除。
- 现有方案的 `wide/strict` 语义不静默改变。
- 新模式先用当前已保存的 89 个岗位离线重放，报告会减少多少
  primary/apply/caution，以及低于、超过、未知三类分布。
- 它先作为用户明确选择的模式上线，不在没有质量量化和用户决定时替换所有现有
  方案默认值。

## 9. 页面与可访问性

- 模型、简历、今日任务和进度页继续使用现有共享 shell 和 CSS token。
- 桌面布局优先，无水平滚动；375×812 保持单列。
- 长任务状态使用 `aria-live="polite"`，错误使用可聚焦的状态区域。
- 主要按钮每页最多一个；页面轮询不得抢焦点。
- 外部链接、文件选择、连接测试和下一步按钮均有明确可访问名称。
- 页面文案不展示 raw enum、内部字段名或模型错误堆栈。

## 10. 回归合同

### 首次路由和模型

- 空数据库且模型未验证时，根路由进入 settings。
- 深度模型验证后出现简历下一步。
- 已有完整资料的老用户仍直接进入今日任务。
- 桌面模型卡双栏，窄屏单栏，备用模型默认折叠。

### 简历任务

- POST 在本地解析和任务创建后快速返回，不等待模型。
- 刷新进度页能恢复同一 run。
- 每个阶段的结果 ID 与状态原子提交。
- 失去 heartbeat 不自动重复模型调用。
- 相同简历重复上传复用现有 run、画像或匹配卡。
- 没有 profile version 的处理中候选人不出现在正常候选人和任务列表。
- 方案失败不抹除画像和匹配卡。
- 人工日志中的两个截断种类首轮使用 8192 token 上限。

### 隐私

- 本地页面显示本地姓名，不显示遮盖占位符。
- 画像、匹配卡、方案和消息模型输入都不含真实姓名和联系方式。
- 数据库任务表和日志不含简历正文、模型正文或 API Key。

### 今日任务和方案

- 1280×720 首屏可看到唯一主要动作和三项核心指标。
- 无阻塞时不渲染“现在卡在哪里”大卡。
- inherited 空城市不显示阻塞。
- 平台继承条件与本地精细条件分开显示。
- 薪资 overlap 对边界、完全低于、完全高于、未知四类结果稳定。

## 11. 验收

1. 使用临时数据库和假模型完整走
   settings → onboarding → progress → match card → plan → today；
2. 用延迟和截断 fixture 验证进度、刷新、重试和部分成果；
3. 使用本机 Edge 仅验收 RoleFlow 本地页面，不操作 BOSS；
4. 记录 1440×900、1280×720、375×812 截图；
5. 运行完整离线套件；
6. 最终真实模型和真实简历耗时由用户下一次人工流程确认。

## 12. 不在本子项目范围

- 自动调整用户筛选规则；
- 默认启用新的薪资 overlap 模式；
- 删除生成搜索 URL 的历史代码；
- 前端框架迁移；
- 自动保存或发送沟通内容；
- 自动更新和安装器；
- Wave 5。
