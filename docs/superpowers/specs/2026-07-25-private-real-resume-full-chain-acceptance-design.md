# 真实简历完整链路验收设计

## 状态与目的

本文定义 RoleFlow 通用证据匹配功能的最终产品验收方式。设计已经过用户逐段确认，但本文本身不授权代码实施、真实模型调用或招聘平台访问。

现有 `2026-07-25-live-model-benchmark-v3-design.md` 及其脱敏 fixture 继续承担稳定、可提交、可重复的离线回归职责，但不再单独作为“对当前真实用户可用”的最终结论。最终产品门禁必须补充：

```text
真实招聘平台 PDF
  -> 本地按视觉阅读顺序提取
  -> 本地遮盖身份与联系方式
  -> 真实模型生成画像
  -> 真实模型生成匹配偏好卡草稿
  -> 用户一次性确认
  -> 同一批新鲜真实 JD 上进行基线/候选比较
  -> 候选工作台完整流程复核
```

所有工作继续在隔离 worktree 中完成，不修改正在使用的主项目 `D:\Guo\ZhiPing`，不读写主项目 `data/jobs.sqlite`，不启动或操作 8787。

## 已确认的现场证据

用户提供了一份招聘平台导出的两页文字型 PDF。只读预检确认：

- 文件不是扫描件，文字层完整；
- 当前项目能够提取约 2900 个字符；
- 教育、经历、项目、技能和个人优势五类内容均被检测到；
- 没有乱码、截断或缺页；
- 视觉渲染中的版面和章节顺序正常。

但当前 `src/core/resume_parser.js` 使用 `pdf-parse` 的 `getText()` 直接拼接 PDF 内部文本对象。该依赖按内容流顺序返回文本，不按页面坐标重新排列。在这份招聘平台 PDF 上稳定复现：

- 实习公司标题被移动到姓名之前；
- 第二页的项目标题、时间、教育信息先于项目正文出现；
- 项目标题与各自正文之间的关联被破坏。

使用坐标感知的本地解析进行对照，同一文件可以恢复与视觉页面一致的顺序。因此问题发生在本地 PDF 文字排序层，而不是模型画像生成层。模型可能猜回部分结构，但不能把这种猜测视为可靠输入。

文档不得记录真实姓名、电话、邮箱、公司、项目正文、真实文件名或其完整路径。真实输入只存在于仓库外私有目录。

## 目标与非目标

### 目标

1. 招聘平台生成的文字型 PDF 能按视觉阅读顺序稳定提取。
2. 任何模型调用前，姓名、手机号和邮箱均在本地被遮盖。
3. 候选版本使用生产核心函数从真实简历生成画像和匹配偏好卡。
4. 画像、匹配卡和岗位分析使用同一份已确认的真实证据。
5. 基线与候选在同一模型、同一份已遮盖简历文本和同一批真实 JD 上公平比较。
6. 只访问招聘平台一次取得新鲜 JD 快照，之后所有模型双跑均离线复用快照。
7. 私有输入和完整模型输出不进入 Git；代码、脱敏回归样本和非敏感结论可提交。

### 非目标

- 不实现扫描件 OCR；
- 不做通用 PDF 排版引擎；
- 不覆盖所有招聘平台的任意多栏简历模板；
- 不从聊天页或招聘者消息采集数据；
- 不点击沟通、投递、收藏或其他会改变平台状态的动作；
- 不自动确认匹配偏好卡；
- 不用旧岗位历史评价新筛选规则；
- 不让真实简历取代现有脱敏离线回归。

## 方案选择

### 被否决：基线和候选分别访问招聘平台

两次访问会得到不同时间、排序和库存下的岗位，无法公平比较，还会增加账号风险与页面操作次数。

### 被否决：只使用现有 31 条人工 JD

固定 fixture 适合验证契约、比较器和回归保护，但不能代表当前用户真实搜索结果，也不能暴露真实简历解析问题。

### 采用：一次只读扫描、两侧复用同一私有快照

只在候选工具准备完毕后进行一次串行、低频、只读扫描。扫描结果保存为仓库外私有 JD 快照。基线与候选随后在无招聘平台访问的条件下使用同一快照运行。

候选版本另做一次从原始 PDF 开始的端到端验证；基线/候选 A/B 比较则共同使用已经确认顺序正确、已经遮盖身份信息的规范化简历文本。这样既验证真实上传路径，又避免把 PDF 解析差异混入匹配算法比较。

## 组件设计

### 1. 坐标感知的 PDF 文字提取

修复位于共享 `resume_parser`，使工作台、CLI 和验收工具自动获得相同行为。

实现优先复用现有 Node 依赖链中的 PDF.js 能力，取得每个文字对象的页码与坐标，并在每页内按视觉阅读顺序分组：

- 先按纵坐标聚合为行；
- 同一行按横坐标排序；
- 保留自然换行、项目符号和分页边界；
- 不把页码标记作为简历正文；
- 继续沿用现有 5MB、60,000 字符、30 秒超时和质量诊断限制。

`pdfjs-dist` 若被业务代码直接导入，应成为 `package.json` 的显式依赖，不能依赖某个间接依赖永久存在。生产路径不新增 Python、Poppler、OCR 服务或操作系统级安装要求。

此设计只承诺修复单栏招聘平台简历和同类布局。若未来需要处理复杂多栏模板，再以新的真实失败样本扩展列检测；本轮不预先实现通用版面分析。

### 2. 本地隐私遮盖门

原始 PDF 只在本地进程内读取。模型输入使用遮盖后的文本：

- 姓名替换为稳定占位符；
- 手机号替换为稳定占位符；
- 邮箱替换为稳定占位符；
- 公司、项目、技能、时间、教育和经历正文保持原样。

遮盖发生在模型适配器初始化和任何网络调用之前。执行器必须在遮盖后再次扫描：

- 中国大陆手机号模式；
- 邮箱模式；
- 本次私有身份清单中明确列出的姓名与联系方式。

只要任一敏感值仍存在，立即以可定位错误码停止，不初始化模型、不写临时数据库、不产生网络请求。

身份清单保存在私有目录，命令行只传文件路径，不把真实值写入 shell 历史、日志或 Git。日志只记录遮盖字段计数和输入 SHA-256，不记录原文。

### 3. 私有数据包

固定根目录：

```text
D:\DevData\RoleFlow-private-benchmark\full-chain-v1-20260725\
```

建议结构：

```text
input\
  identity.private.json
  resume.redacted.txt
  jobs.private.json
labels\
  jobs.reviewed.json
runs\
  baseline\
  candidate\
reports\
  full-chain-compare.json
  full-chain-compare.md
temp\
```

原始 PDF 保持在用户原位置，不复制进仓库或 Git。预检产生的页面 PNG 和未遮盖文字属于临时材料，确认后删除；长期保存的文本必须已经遮盖。

除用户显式提供的只读原始 PDF 外，所有生成的私有输入和输出路径必须经过门禁：

- 位于明确的 `D:\DevData\RoleFlow-private-benchmark\` 根目录下；
- 不位于项目仓库、主项目 `data\`、用户目录或系统临时目录；
- 路径经真实路径规范化，防止 8.3 短路径、链接或相对路径绕过；
- 输出目录必须显式提供，不使用隐式默认值。

### 4. 完整链路执行器

执行器只负责编排，不复制业务逻辑。它直接复用生产路径中的：

- `parseResumeUpload`；
- 简历画像分析；
- 匹配偏好卡草稿生成与规范化；
- `profileToRuntimeConfigs`；
- 岗位理解与岗位匹配；
- 现有模型配置加载器；
- 现有比较器的行级指标派生和验收门禁。

执行器使用仓库外临时数据库或纯临时上下文，不接触主数据库。若某生产函数必须依赖存储，则为每侧创建独立测试数据库，禁止两侧共享可变缓存。

执行结果分为：

1. `parse`：解析结构、章节顺序、遮盖统计和非敏感 hash；
2. `profile`：画像结构与证据摘要；
3. `matchingCardDraft`：待用户确认的匹配卡；
4. `jobRows`：逐岗位推荐、分桶、证据和失败状态；
5. `metrics`：从逐行结果重新派生的汇总；
6. `identity`：提交、模型、输入 hash 和执行器版本。

### 5. 候选工作台复核

自动比较通过后，只在候选版本上运行一次工作台流程：

- 使用随机空闲端口；
- 使用独立临时数据库；
- 上传同一真实 PDF；
- 检查解析诊断；
- 查看画像和草稿卡；
- 用户确认后检查搜索计划门禁；
- 不启动或占用 8787；
- 不连接招聘平台执行扫描或沟通。

该步骤验证路由、页面和存储接线，不重复真实模型双跑，不写主项目状态。

## 新鲜真实 JD 快照

### 搜索设置

用户在已有登录态的 Edge 中手动打开并设置 `BOSS-SEARCH`：

- 城市、薪资、经验、学历等使用真实求职偏好；
- 页面筛选条件保持不变；
- 项目通过继承模式只替换关键词；
- 关键词覆盖 `AI应用开发`、`RAG`、`Agent`、`Python AI 后端`。

### 样本规模

每个关键词最多采集约 6 个不重复岗位，总体目标为 20–24 个。样本应同时覆盖：

- 看起来适合的岗位；
- 标题相关但核心主栈不合适的岗位；
- 年限、外包、实施或驻场条件需要确认的岗位；
- JD 信息不足的岗位。

数量是验收样本规模，不降低正式扫描的逻辑质量目标，也不修改正式搜索计划。

### 浏览器安全

- 使用用户现有登录态和固定 `BOSS-SEARCH` 标签页；
- 不新建逐岗位标签页、第二窗口或第二登录会话；
- 全程串行，一次只处理一个岗位；
- 每次打开详情后核对 jobId、标题、公司和 URL；
- 只读标题、公司、地点、薪资和 JD；
- 不读取招聘者聊天、消息正文或个人资料；
- 不点击沟通、投递、收藏或其他写操作；
- 保留随机节奏、冷却、去重和断点；
- 登录、验证码、风控、页面身份不一致或详情缺失时立即停止。

真实扫描必须在代码、离线测试和当次用户确认之后才可执行。设计确认不等于浏览器操作授权。

## 人工标准与画像确认

### 画像和匹配卡

候选模型输出以中文核对页展示。用户一次性确认：

- 目标方向；
- 实习、项目、技能和教育是否完整；
- 公司、职位、项目和时间是否正确；
- “参与”“独立完成”“了解”是否保持原边界；
- 强证据、可迁移能力、谨慎转向和排除偏好是否合理；
- 用户偏好是否被错误当成简历事实。

必须满足：

- 不虚构经历；
- 不遗漏主要实习和项目；
- 不串联不同项目的标题与正文；
- 不把参与经历夸成主导；
- 未证明的架构、高并发、生产运维、售前或客户管理能力不能成为强证据。

草稿未经用户确认不得用于最终岗位结论。相同简历与相同已确认卡后续可复用，不要求每次确认。

### 岗位标签

每个真实 JD 由执行器提出初始解释，用户集中确认最终标签：

- `apply`：较适合，可以投；
- `caution`：方向相关，但存在需要确认的软风险；
- `review`：JD 信息不足；
- `skip`：存在明确硬阻断。

只有以下情况可以直接硬阻断：

1. 明确资格不符；
2. 岗位不可替代的核心能力明确缺失；
3. 明确安全或诚信风险。

年限、工具罗列、“优先”“加分”“最好具备”等愿望条件不能单独形成硬阻断。高于目标的薪资、外包、实施比例和可放宽年限进入软风险或待确认。

人工标签在第一次 live 运行前冻结。看到模型结果后不得原地修改标签并继续沿用同一结论；如确认原标签确有错误，应提升私有数据包版本并让两侧重跑。

## 基线与候选的公平比较

### 共同输入

两侧必须使用：

- 同一份顺序正确且已遮盖的简历文本；
- 同一份用户确认的事实口径；
- 同一批真实 JD；
- 同一组冻结人工标签；
- 同一模型 provider、模型名和参数；
- 同一完整链路执行器版本；
- 各自独立的模型缓存和临时数据库。

### 分离 PDF 修复与匹配比较

- A/B 比较从共同的规范化已遮盖文本开始，隔离匹配算法差异；
- 候选端到端验证从原始 PDF 开始，证明 PDF 修复确实进入生产路径；
- 报告分别记录两种运行，不能把其中一种冒充另一种。

### 身份门禁

每份结果至少记录：

- `runMode`；
- `authorizationGatePassed`；
- `fullChainHarnessVersion`；
- `evaluatedCommit`；
- `baselineBehaviorCommit`；
- 已遮盖简历文本 SHA-256；
- 身份清单 SHA-256，不记录内容；
- JD 快照 SHA-256 与岗位 ID 集合；
- 人工标签 SHA-256；
- 非敏感模型身份；
- 工作树干净状态；
- 逐行结果和派生指标。

比较器必须拒绝版本、提交、模型、输入、岗位集合、人工标签或执行器不同的结果。

## 验收条件

候选版本必须全部满足：

- PDF 章节和标题/正文关联正确；
- 模型请求中不存在姓名、手机号或邮箱；
- 用户确认画像和匹配卡无重大遗漏、串线或夸大；
- `failed === 0`；
- `stale === 0`；
- `pending === 0`；
- 不存在 `partial -> primary`；
- `primaryWithoutEvidence === 0`；
- recommendation accuracy 不低于基线；
- bucket accuracy 不低于基线；
- `hardFalsePlacement` 不高于基线且不新增样本 ID；
- `falseHardExclusion` 不高于基线且不新增样本 ID；
- 明显适合岗位不得被错误硬排除；
- 明显错栈、算法、销售、培训等岗位不得进入主推；
- 逐样本人工复核没有不可接受的严重回归；
- 候选工作台完整流程通过；
- 全量离线测试和 `git diff --check` 通过；
- 工作树干净。

聚合指标通过不能掩盖单个严重错误。最终报告必须列出所有从正确变错误、进入或退出 `not_recommended`、进入 `primary` 以及 hard blocker 发生变化的样本。

## 失败处理

以下任一条件触发立即停止：

- PDF 阅读顺序仍不正确；
- 遮盖后仍检测到身份或联系方式；
- 输入或输出路径不安全；
- 工作树不干净；
- 模型配置、鉴权、契约或网络失败；
- 画像出现虚构、项目串线、时间错误或证据边界错误；
- 浏览器出现登录、验证码、风控、页面丢失或身份不一致；
- 岗位详情与预期 jobId 不一致；
- 主数据库或 8787 可能受到影响；
- 比较器身份或完整性门禁失败。

失败时保留已完成的非敏感检查点和待处理岗位，不重试真实页面动作，不自动降低样本质量，也不伪造缺失结果。

## 测试策略

### PDF 修复

先增加失败回归，再实现：

- 创建不含真实身份内容的两页招聘平台式 PDF；
- PDF 内部对象顺序与视觉顺序故意不同；
- 修复前稳定复现标题前置和项目正文串线；
- 修复后断言章节、公司标题、项目标题、正文、教育和证书顺序；
- 继续覆盖短文本、乱码、超时、大小限制和扫描件提示。

### 隐私门

- 姓名、手机号、邮箱均被遮盖；
- 变形或遗漏的明确身份值导致安全失败；
- 失败发生在 provider 初始化之前；
- 日志、错误和结果不包含原值；
- 危险私有路径被拒绝。

### 完整链路

- 用注入模型覆盖画像、卡草稿、用户确认门禁和岗位分析；
- 未确认卡不得进入最终岗位分析；
- 两侧输入 hash 或标签不同则比较失败；
- 汇总必须从逐行结果派生；
- 截断、重复 ID、伪造 pass、非法枚举和汇总伪造继续安全失败；
- 工作台使用随机端口和临时数据库完成离线流程；
- `npm.cmd test` 全量离线检查通过。

测试 fixture 必须完全脱敏；不得把真实 PDF、已遮盖的真实正文、真实 JD、公司名、岗位 URL 或模型输出加入测试目录。
