# 已被替代：岗位根基能力与工作对象证据设计

> **状态：不得单独实施。** 用户确认应先根据岗位职责判断主体方向，再结合岗位要求证据综合
> 分桶。本设计中的 `foundation` 规则保留为要求层的一部分，最终设计见
> `docs/superpowers/specs/2026-07-29-role-direction-requirement-evidence-design.md`。

## 历史状态

本文记录上一轮设计过程，不再作为实施依据。

## 背景与现场证据

当前轻量匹配链路每个岗位只有两次正常模型调用：

1. `understandJob` 概括岗位主线并拆分要求；
2. `matchJob` 使用已确认画像与匹配卡，为要求选择候选人证据。

本地规则随后检查 `central=true` 的要求中是否至少有一条
`matched` / `transferable`。存在一条就解除岗位主线未证明保护；一条都没有则进入
`backup`。

三个独立缓存的真实保存 JD 结果表明，这个边界不能稳定区分以下两个岗位：

- **AI 辅助前端岗位**：模型稳定识别出 UI 组件库和 Vibe Coding 两条主线，但候选人没有
  前端、组件库或多端视觉落地证据，合理结果是 `backup`；
- **AI 辅助全栈岗位**：候选人有 Python/FastAPI、接口、测试、调试和需求拆解证据，但没有
  前端和完整全栈交付证据，合理结果是 `talk`。

AI 辅助全栈岗位在相同 JD 与相同画像下曾得到一次 `talk` 和两次 `backup`。变化来自：

- `understandJob` 每次选择的 `central` 要求不完全相同；
- “全栈技术基础”有时被合成一条，导致后端已匹配却无法单独计入；
- `matchJob` 有时选中需求拆解或 Debug，有时省略这些证据；
- 当前已确认画像没有明确记录真实的 AI 编程工具实践；
- 本地规则只判断“零条或至少一条主线证据”，没有判断候选人是否具备岗位的基本交付能力。

旧设计试图用中文双字片段和技术词重合在本地救回省略证据。预检证明它会让两个岗位都命中，
无法判断 AI 用于前端组件、业务系统、视觉生成还是其他工作对象，因此废弃。

## 目标

- 稳定表达“AI 是工作方法，前端、后端、视觉、运营等是工作对象”；
- AI 辅助前端岗位在没有前端根基证据时保持 `backup`；
- AI 辅助全栈岗位在已有后端根基证据、但前端不完整时保持 `talk`；
- “先聊”维持召回优先，“优先岗位”继续要求更完整证据；
- 每个岗位仍只有现有两次正常模型调用；
- 不引入职业分类表、行业模板、模糊文本救回、第三次模型裁判或新依赖；
- 不放宽学历、资格、安全、地点、实习、薪资下限和用户排除词等现有硬边界。

## 非目标

- 不要求模型把所有合适岗位绝对准确排序；
- 不因单个技术名词缺失直接淘汰岗位；
- 不把未知经历伪造成候选人证据；
- 不自动把聊天记录中的事实写入正式画像；
- 不修改真实招聘平台数据、真实沟通流程或生产数据库。

## 核心概念

### 岗位根基能力 `foundation`

在现有 requirement 对象中增加一个必填布尔值：

```json
{
  "label": "Python 后端开发能力",
  "central": false,
  "foundation": true,
  "indispensable": false,
  "evidence": "JD：熟悉 Python（Flask/Django/FastAPI）"
}
```

`foundation=true` 表示：这项能力直接支撑岗位主要交付物，缺少全部此类能力时，候选人无法从事
该岗位的基本工作。

以下内容不能单独标成根基能力：

- 学习、沟通、责任心、自驱力；
- Git、办公工具、通用代码规范；
- 没有工作对象的“使用 AI”“熟悉大模型”；
- 仅表示年限、学历、证书或偏好的条件。

根基能力不等于硬门槛。缺少一部分根基能力可以进入 `talk`；只有现有结构化硬冲突规则才有权
直接淘汰。

### 岗位主线 `central`

`central=true` 继续表示能区分相邻岗位的主要工作或交付结果。它与 `foundation` 相互独立：

- Vue/React 前端开发可以是根基，但不一定是岗位特色；
- 企业级 UI 组件库建设可以同时是根基和主线；
- AI 辅助开发可以是主线，但在没有明确工作对象时不能单独充当根基。

### 明确硬条件 `indispensable`

`indispensable=true` 仍只表示 JD 明确写出的不可替代要求。它不因本设计自动产生硬阻断，
现有“双侧明确冲突证据”规则保持不变。

## 要求拆分规则

`understandJob` 必须把可独立核对的复合要求拆成原子要求。

错误示例：

```text
全栈技术基础
```

正确示例：

```text
前端开发能力
后端开发能力
数据库与接口能力
AI 编程工具实践
```

“Python 或 Node.js 或 Java 后端”仍可保留为一条替代关系，因为满足其中任意一种即可证明同一
后端根基。前端、后端、数据库不能合成一条，因为候选人可能只覆盖其中一部分。

输出上限继续沿用现有要求数组上限，不增加新的嵌套对象。

## 工作方法与工作对象必须共同核对

`matchJob` 必须结合以下三部分判断一条要求：

1. `roleSummary`；
2. requirement 的 label；
3. requirement 的 JD evidence。

不能只根据 label 中的“AI”“工作流”“Agent”等词匹配。

具体边界：

- RAG、Agent 项目不能证明“使用 AI 开发 UI 组件”；
- 通用 AI 编程工具实践不能证明 UI 组件库、多端视觉或前端框架能力；
- Python/FastAPI、接口、测试和调试证据可以证明业务系统的后端交付根基；
- LangGraph 工作流不能证明 ComfyUI、图片生成、ERP、前端或其他未出现的工作对象；
- `userNotes` 继续只表达偏好，不能充当经历证据。

不再实现任何中文双字片段、技术词集合或相似度本地救回。

## 本地决策规则

新增一个共享的岗位根基状态计算，供分析保护、存储分桶和工作流库存共同调用，避免三处规则
漂移。概念输出如下：

```js
{
  foundationRequirementCount,
  foundationEvidenceCount,
  foundationUnresolvedCount,
  centralRequirementCount,
  centralEvidenceCount,
  state: "none" | "unproven" | "partial" | "complete"
}
```

状态含义：

- `none`：模型没有提取任何根基要求，兼容地回退到现有主线证据规则；
- `unproven`：存在根基要求，但一条根基正向证据都没有；
- `partial`：至少一条根基要求为 `matched` / `transferable`，但仍有根基要求未证明；
- `complete`：全部根基要求都有正向证据；其中存在 `transferable` 时仍由现有规则降级为先聊。

分桶行为：

- `unproven`：进入 `backup`，默认不勾选；
- `partial`：最多进入 `talk`，允许默认保留，但不能进入 `primary`；
- `complete`：继续经过现有证据完整性、岗位质量、置信度、经验和风险规则，满足全部条件后才可
  进入 `primary`；
- `none`：沿用现有 `roleCoreEvidenceState()`，避免老数据和异常输出被静默放宽；
- 任何结构化硬阻断仍优先得到 `not_recommended`。

只要新分析中存在合法的根基要求，`foundation` 状态就是 `backup` / `talk` 的唯一岗位主体边界，
旧的“主线证据零条或至少一条”规则不得再次把 `partial` 降回 `backup`。`central` 仍用于说明
岗位特色、约束证据语义，并参与现有的推荐质量判断。

这里不使用百分比阈值。根基要求已经被拆成可独立核对的交付能力，“零条、部分、全部”足以
表达当前产品所需的宽松分层，也避免为不同职业维护人为权重。

## 两个争议岗位的预期结果

### AI 辅助前端

根基要求包括前端框架、UI 组件库和多端视觉落地。候选人即使具有 AI 工具经验，也没有任何
前端根基证据：

```text
foundation state = unproven
最终分桶 = backup
默认勾选 = 否
```

### AI 辅助全栈

根基要求被拆成前端、后端、数据库与接口等条目。候选人的 Python/FastAPI、接口、测试和调试
可以证明后端交付根基，但前端与完整全栈仍未证明：

```text
foundation state = partial
最终分桶 = talk
默认勾选 = 是
primary = 不允许
```

## 候选人事实补充

用户现实中已使用 Claude Code、Codex 等 AI 编程工具完成代码阅读、修改、测试、调试和问题
定位，但当前已确认画像没有明确记录该事实。

实现时只生成一条待确认的匹配卡建议，不自动写入已确认卡：

```text
AI 编程工具实战｜在真实项目中使用 AI 编程工具完成代码阅读、修改、测试、调试和问题定位
```

只有用户在工作台查看、修改并确认后，该事实才可进入后续匹配。确认前不得使用聊天记录或本
设计文档充当候选人证据。

## 模型契约、缓存与兼容

- `understandJob` requirement 新增必填 `foundation:boolean`；
- 缺失或非 boolean 时进入现有的一次契约修复；修复后仍非法则安全失败；
- `matchJob` 沿用现有稀疏输出，不增加返回字段；
- `requirementMatches` 在本地合并时继承对应 requirement 的 `foundation`，模型无权修改；
- 提升 `understandJob`、`matchJob` 和本地决策规则版本，旧模型缓存不得冒充新语义；
- 不修改数据库 schema，不批量改写历史岗位；
- 历史分析继续可读；重新分析时才按新版本生成结果；
- 首次重新分析会重新运行两次模型调用，之后仍按现有缓存复用；
- 不增加第三次模型调用，新增一个布尔字段带来的实际耗时必须由单条实测确认，不提前假设。

## 用户可见解释

备选岗位显示具体原因，不只显示“方向偏离”：

```text
岗位根基尚未证明：前端框架、UI 组件库、多端视觉落地。
```

先聊岗位显示已证明和待确认部分：

```text
已证明的岗位根基：Python/FastAPI 后端、接口与调试。
待沟通确认：前端开发、完整全栈交付。
```

不得显示内部字段名、模型提示词或把 `unknown` 表述为候选人明确不会。

## 测试与验收

### 离线红绿回归

先写失败测试，再修改实现。至少覆盖：

1. AI 工具匹配但前端根基为零：`backup`；
2. 后端根基匹配、前端未知：`talk`，不得 `primary`；
3. 全部根基匹配且其他条件合格：才允许继续判断 `primary`；
4. 根基全部未知：`backup`；
5. 没有根基字段的历史分析：沿用现有主线规则；
6. `foundation` 缺失或非 boolean：模型契约失败并只允许一次修复；
7. 模型试图修改 `foundation`：拒绝；
8. 结构化硬阻断、地点、实习、薪资下限和用户排除词不放宽；
9. 工作流默认勾选：`unproven` 不勾选，`partial` 可勾选；
10. 不存在中文双字片段或技术词模糊救回路径。

### 少量真实保存 JD 验证

离线全绿后，使用保存 JD 与正式模型，不访问招聘网站：

1. AI 辅助前端岗位使用三个独立新缓存各运行一次；
2. AI 辅助全栈岗位使用三个独立新缓存各运行一次；
3. 六次运行都必须只有现有两次正常模型调用；
4. 前端岗位三次均为 `backup`；
5. 全栈岗位三次均为 `talk`；
6. 记录两个模型阶段、总耗时、契约修复次数和最终证据，不记录模型密钥；
7. 任何一条结果不稳定时停止，不进入 20 条验收。

### 20 条验收

只有两条岗位的三次小样本全部稳定、离线全量测试通过且单条耗时没有不可接受回退时，才运行
新的 20 条保存 JD 验收。

人工标签新建版本，不覆盖历史结果：

- AI 辅助前端：`review/backup`，`keep`，默认不勾选；
- AI 辅助全栈：`review/talk`，`keep`，默认勾选。

20 条验收仍关注机会保留率、明显错岗排除率、硬误杀、待分析数量和耗时。空结果不得伪装成
成功，也不得为了通过验收修改人工标签。

## 安全边界

- 所有开发只在隔离 worktree 与隔离分支完成；
- 离线阶段不得访问 BOSS 或其他招聘平台；
- 保存 JD 验证不得操作浏览器；
- 不读写主项目 `data/jobs.sqlite`，不启动或操作 8787；
- 不复制、打印或提交模型密钥、端点和模型身份；
- 私有简历、画像、匹配卡、JD 与真实结果只留在
  `D:\DevData\RoleFlow-private-benchmark`，不得提交 Git；
- 本设计不授权真实沟通、投递或招聘平台写操作。
