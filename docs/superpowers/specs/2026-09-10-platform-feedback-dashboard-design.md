# 平台投递反馈页设计

用户在实际8788页面审阅后确认：后端承担复杂度，前端只呈现帮助了解进展和决定下一步的信息。2026-09-10本轮“继续”批准上一条展示方案，不再增加方向确认流程。

## 页面

- 沿用现有桌面端配色、字体和导航。一块平台对照表、一条有依据的优先建议；不堆指标卡片。
- 默认“当前方案”，同处切换“累计记录”。当前按所选求职方案、各平台当前有效策略统计；累计按当前候选人的所有方案历史统计。页面直接注明范围，不把累计误称为全平台账户完整历史。
- BOSS、智联各一行：已联系岗位、已回复（数量和比例）、索要简历、面试邀请。已联系包括已确认投递或沟通，按平台岗位去重；不是扫描数。回复比例分母是同一行所有已联系岗位，包括刚联系的岗位；零分母显示横线，不显示0%失败。
- 已有积极反馈立即显示。48小时、周末顺延、30/50/70继续在后台决定诊断强度；主页面不显示成熟样本、进度尺、策略轮次、条件转化链或计算规则。
- 有充分证据才显示一个平台的一个优先改进方向、具体依据及对应入口。不把“没有诊断”画成警报。暂不可判断用轻量状态说明；不能把旧样本不足误称刚投不久。
- 修改前后有同平台可比较结果时才展示简洁描述性变化，不声称修改导致提升。无修改/证据不足不展示空比较区。
- 投递起点不明但岗位已核验的HR消息，用简洁“其他消息中还有…”与消息入口保留。不混入回复率。未核验会话仍在消息页处理，不把内部匹配问题铺在体检页。
- “记录方案调整”为按需展开的小入口，用户选择BOSS、智联或两个平台及修改项；本机记录不修改真实平台。日常不展示完整表单。

## 统计实现

- 复用SQLite现有事件、策略快照和单一物理修订记录，不增加表、依赖或后台任务。在strategy_snapshot_json增加platformScope，旧记录视为all。
- 将物理策略修订按平台折叠：仅BOSS调整不重置智联，反之亦然；共享简历启用默认影响两平台。保留旧entry.strategy_round_id，旧岗位迟到反馈仍归旧有效策略。
- 每个平台分别投影、诊断和前后比较。累计仅展示事实，不使用混合策略/平台的比例生成诊断。简历优化消费分平台诊断，不拿混合样本凑门槛。
- 表单并发校验仍绑定最新物理修订ID；无效平台范围拒绝。历史策略查询不能因最近30条截断未改平台的有效范围。
- 已验证智联旧事件沿用原时间补接，累计范围只同步当前候选人。无可信起点、未核验发送、复制或HR主动联系不伪造投递。

## 验收与边界

真实SQLite合成场景覆盖跨批次、跨平台、跨方案累计、早回复、单平台调整、共享调整、迟到反馈、幂等和旧记录。浏览器检验范围切换、折叠调整、可读比例、移动端不溢出。完整离线门禁必须是新源码冻结SHA；本地8788只读验收，不向用户数据库写虚假策略。仅推送当前分支，不合并、不发布、不访问真实招聘平台或发送。
