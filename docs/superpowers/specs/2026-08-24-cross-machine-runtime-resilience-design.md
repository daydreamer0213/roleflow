# RoleFlow 跨机器部署与健壮启动架构设计

**日期：** 2026-08-24
**状态：** 用户已确认总体方向，待书面设计自检后进入实施计划
**设计基线：** `codex/stable-dedicated-edge@023f1ee74cced5a7aded2a8ea4b3ba9c4e2f2f89`

## 1. 结论

RoleFlow 的启动不能再是“Edge、调试端口、BOSS 标签页、登录状态、Dashboard 全部一次
满足，否则整个程序退出”的同步事务。

目标架构改为：

1. RoleFlow 工作台先启动，并始终能够展示当前状态和恢复入口；
2. 一个浏览器监督器负责发现、连接、启动、等待和监测 RoleFlow 专用 Edge；
3. BOSS 登录和工作区标签页是可恢复的业务就绪状态，不是应用进程的启动前置条件；
4. 扫描、JD、消息发现和沟通等操作在执行前各自通过安全准入检查；
5. 本地确定性失败可有限自动恢复，任何可能重复访问或写入 BOSS 的不确定操作都不自动
   重试；
6. 是否完成以多台干净 Windows 机器上的安装、首次启动、再次启动、升级和异常恢复为准，
   不以当前开发机偶然可运行为准。

本设计保留真实 Microsoft Edge、稳定专用 profile、现有 CDP 浏览器能力以及全部 BOSS
安全约束。它替代 2026-08-23 专用 Edge 设计中“启动时必须立即完成工作区整理，否则启动
失败”的部分，不推翻已经正确的浏览器身份和数据持久化决策。

## 2. 已观察到的问题与根因

### 2.1 实际失败链

第三个安装候选已经证明：

- 安装器能够安装完整程序并创建桌面快捷方式；
- 工作台能够在本机端口启动；
- RoleFlow 能启动真实 Edge，并使用稳定 profile；
- `/health` 能返回安装目录和浏览器模式；
- 中文日志和错误框能正确显示。

但用户仍先后遇到：

- CDP 监听尚未稳定时，启动器把一次连接失败当成整个程序启动失败；
- 专用 Edge 已存在且只有一个 BOSS 搜索页，但页面被其他窗口遮挡后，
  `document.visibilityState` 为 `hidden`，现有代码就把它误判为“无法确认唯一前台页”；
- 工作区标签整理失败后，已正常运行的工作台也被包装成“RoleFlow 启动失败”。

### 2.2 架构根因

当前入口按顺序执行：启动/连接 Edge、启动 Dashboard、立即整理 BOSS 标签页；外层把整段
脚本当作一个同步命令。任何一步抛错，用户看到的都是同一个致命启动错误。

这造成四个责任混在一起：

- 应用是否已运行；
- 浏览器进程是否已运行；
- 浏览器控制通道是否稳定；
- BOSS 是否登录且工作区是否适合某项操作。

`document.visibilityState` 的误判只是这种耦合暴露出来的一例。单独修正它，下一台机器仍
可能因为 Edge 安装位置、端口竞争、慢启动、首次登录、升级残留或进程退出而再次“无法
启动”。继续逐个补错误分支不能建立可部署产品。

## 3. 用户成功标准

普通 Windows 用户应该只需要：

1. 安装 RoleFlow；
2. 点击桌面或开始菜单中的 RoleFlow；
3. 工作台打开；
4. 若浏览器或 BOSS 尚未准备好，按工作台中的具体提示完成一次登录或恢复；
5. 以后再次启动时继续使用同一份数据和登录状态。

下列情况都不应让工作台退出：

- Edge 还没启动；
- Edge 启动较慢；
- 用户尚未登录 BOSS；
- BOSS 搜索页或沟通页缺失；
- Edge 被其他窗口遮挡；
- Edge 稍后被用户关闭；
- 一个可恢复的本地控制连接短暂断开。

只有 RoleFlow 自身无法加载、数据目录不可用、安装损坏或存在不能安全识别的本地实例冲突
时，才属于应用级致命失败。

## 4. 支持环境契约

### 4.1 第一版明确支持

- Windows 10 和 Windows 11 的仍受 Microsoft 支持的 64 位版本；
- 当前 Windows 用户拥有自己的 `%LOCALAPPDATA%`；
- 已安装受 Microsoft 支持的稳定版 Microsoft Edge；
- 普通用户权限即可完成日常运行；
- 单个 Windows 用户、一个 RoleFlow 数据身份、一个 RoleFlow 专用 Edge profile；
- 同一用户一次只运行一个 RoleFlow 工作台会话。

安装器应检查这些条件并给出可执行提示。不能把开发机的盘符、源码目录、Node、PowerShell
配置、历史工作树或 Edge Control 当作隐含前置条件。

### 4.2 暂不承诺

- 无 Edge 环境下自动下载或捆绑第三方浏览器；
- Windows Server、ARM64、便携解压版、多用户共享同一 profile；
- 后台 Windows 服务或开机自启；
- 浏览器崩溃后自动继续未确认完成的 BOSS 操作；
- WebView2、Playwright、Puppeteer 或 Selenium 迁移；
- 自动更新、代码签名证书采购；
- `search_page_api` 修复或验证；
- 通用 `standalone_detail` 或 Wave 5。

## 5. 责任边界

### 5.1 安装器

安装器只负责部署和维护产品所需的静态环境：

- 安装 RoleFlow、固定 Node 运行时和生产依赖；
- 创建开始菜单入口和桌面快捷方式；
- 验证真实 Microsoft Edge 是否存在；
- 验证 `%LOCALAPPDATA%\RoleFlow` 可创建和写入；
- 覆盖升级程序文件但保留用户数据和浏览器 profile；
- 卸载时默认保留数据，只有用户明确选择并看到精确范围时才删除。

安装器不访问 BOSS，不启动完整业务流程，不预造 profile，不依赖 Edge Control，也不把
一次在线检查当成安装成功的条件。

### 5.2 启动器

启动器的成功条件是“唯一的 RoleFlow 工作台可访问”，不是“BOSS 已经完全就绪”。它负责：

- 解析稳定的安装目录和数据目录；
- 通过单实例锁避免重复启动互相争用；
- 启动或复用相同安装身份的 Dashboard；
- 等待 Dashboard 自身健康检查成功；
- 将工作台交给用户；
- 触发浏览器监督器异步准备浏览器。

启动器不直接整理 BOSS 标签页，也不因 BOSS 未登录或浏览器未就绪而关闭 Dashboard。

### 5.3 Dashboard

Dashboard 是产品壳和状态中心，必须在浏览器业务未就绪时仍然可用。它负责：

- 展示应用、浏览器、BOSS 工作区和具体任务的独立状态；
- 提供“启动/恢复专用 Edge”“我已完成登录，重新检查”等明确入口；
- 接收监督器状态变化并更新页面；
- 在用户发起具体操作前调用相应准入检查；
- 提供可复制的诊断摘要和日志位置。

Dashboard 不自行拼接浏览器进程参数、猜测端口或创建第二份 profile。

### 5.4 浏览器监督器

浏览器监督器是专用 Edge 生命周期的唯一所有者，负责：

- 识别当前 RoleFlow 浏览器会话；
- 连接已存在且身份一致的专用 Edge；
- 缺失时启动真实 Microsoft Edge；
- 等待“控制端口出现”之外的稳定就绪证明；
- 监测进程退出和控制连接断开；
- 对纯本地、无 BOSS 副作用的失败做有界恢复；
- 发布状态，不把所有状态都变成异常退出。

监督器不执行扫描、读取 JD、发送消息或申请岗位。

### 5.5 工作区协调器

工作区协调器只负责把已就绪的浏览器整理为可理解的 BOSS 工作区：

- 确认登录状态和风险控制页面；
- 解析当前搜索页和沟通页；
- 在用户启动或明确恢复工作区时，按规则补齐缺失页面；
- 验证标签页身份和窗口关系；
- 发现歧义时保持现状并给出恢复提示。

它不得把被其他应用遮挡等同于标签页未选中，也不得在后台任务中抢前台。

### 5.6 操作准入器

扫描、JD、分析、消息发现和沟通批次各自拥有最小准入条件。例如分析本地缓存不需要浏览器，
扫描才要求可信搜索页，消息发现才要求可信沟通页。

这样一个环节不可用时，不会错误阻塞完全不依赖它的功能。

## 6. 状态模型

### 6.1 应用状态

- `starting`：Dashboard 进程正在启动；
- `ready`：Dashboard 可访问；
- `fatal`：RoleFlow 自身无法运行，需要修复安装或数据目录。

应用达到 `ready` 后，浏览器或 BOSS 的状态不能把它降为 `fatal`。

### 6.2 浏览器状态

- `unknown`：尚未检查；
- `starting`：正在启动专用 Edge；
- `connecting`：正在等待控制通道稳定；
- `ready`：浏览器身份和控制能力已验证；
- `unavailable`：未找到 Edge、无法启动或连接超时；
- `conflict`：端口/profile 被不匹配进程占用；
- `stopped`：先前就绪的专用 Edge 已退出；
- `needs_attention`：存在无法安全自动处理的本地歧义。

### 6.3 BOSS 工作区状态

- `unchecked`：尚未检查；
- `login_required`：需要用户登录；
- `search_page_required`：缺少可信搜索页；
- `communication_page_required`：缺少可信沟通页；
- `risk_control`：检测到登录保护、验证或风险控制；
- `ambiguous`：多窗口、多候选或身份无法证明；
- `ready`：当前操作所需的可信页面已经验证。

“浏览器 ready”不等于“BOSS ready”；“BOSS 未 ready”也不等于“RoleFlow 启动失败”。

### 6.4 任务状态

任务沿用逐岗位进度和检查点。浏览器断开时：

- 尚未发出访问的岗位保持待处理；
- 已经确认读取成功的岗位保留结果；
- 已发出但结果不明确的外部操作标记为需人工核对；
- 不自动重放不确定的导航、点击、发送或申请。

## 7. 浏览器生命周期

### 7.1 会话身份

监督器应使用一个本地会话描述保存当前受管 Edge 的可验证信息，至少包括：

- RoleFlow 安装/用户身份；
- profile 的规范化绝对路径；
- 控制地址；
- Edge 可执行文件的规范化路径；
- 进程身份和启动时间；
- 随机生成的本次会话标识；
- 描述写入时间和版本。

每次复用前都重新核验实际进程、真实 Edge 路径、profile 和控制端点，不信任过期文件。会话
描述只用于发现，不成为绕过身份检查的凭据。

第一阶段可以继续使用 9222，降低迁移风险；但业务代码不得再自行知道或假设固定端口，而应
从监督器取得当前控制地址。是否改为动态端口应在跨机器冲突样本出现后决定，不提前增加复杂度。

### 7.2 连接已有实例

如果会话描述和本地检查都证明当前是同一 RoleFlow 专用 Edge，监督器连接它，不再启动第二
个进程。仅“9222 可访问”不足以证明身份。

如果端口属于其他进程、profile 不一致或身份不能证明，进入 `conflict/needs_attention`，不结束
用户的普通 Edge，不删除 Chromium 锁文件，也不换 profile 偷偷启动另一个浏览器身份。

### 7.3 启动新实例

缺少可复用实例时：

1. 从 Windows 支持的位置发现真实 `msedge.exe`；
2. 使用稳定 `%LOCALAPPDATA%\RoleFlow\BrowserProfile`；
3. 先打开本地空白页或 RoleFlow 本地等待页，不直接反复请求 BOSS；
4. 等待进程、版本端点、目标列表和一次最小控制命令连续通过；
5. 写入会话描述并发布 `ready`；
6. 再由工作区协调器执行最多一次有明确目的的 BOSS 导航。

等待采用有截止时间的短间隔检查。超时后 Dashboard 保持运行并显示恢复入口，不能弹出笼统的
致命错误后退出。

### 7.4 运行期监测与恢复

监督器监测受管 Edge 进程和控制通道：

- Edge 被关闭：发布 `stopped`，保留 Dashboard 和所有检查点；
- 纯本地控制连接短暂中断：在没有业务操作进行时做有限重连；
- 用户点击恢复：重新做完整身份检查后连接或启动；
- 业务操作进行中断开：停止该操作，按任务检查点判断是否可恢复；
- 风控、登录失效、目标漂移或结果不确定：绝不自动重试，转为明确提示。

自动恢复不得形成无限循环。连续失败达到上限后进入稳定的 `needs_attention` 状态，等待用户
主动恢复，而不是持续启动进程或访问 BOSS。

## 8. BOSS 导航、前台与重试边界

- 浏览器准备阶段只使用本地页面，不消耗 BOSS 访问预算；
- 工作区协调器一次只做一个动作，并在动作前后验证 URL、标签和窗口身份；
- 扫描、JD、消息发现、沟通、轮询、重试和恢复始终后台运行；
- `Page.bringToFront` 仍只允许在用户主动启动工作区时调用一次，用于准备完成后引导到
  Dashboard，或需要登录时引导到 BOSS；
- 页面被其他窗口遮挡不构成错误，也不能用 `document.visibilityState` 推导 OS 前台状态；
- 标签是否为窗口内选中页，应使用浏览器窗口/标签身份的可靠证据；无法证明时停止具体整理
  动作，但 Dashboard 保持运行；
- 保留随机节奏、冷却、访问预算、逐项检查点以及风控/登录/页面丢失立即停止；
- 消息发现仍只允许一个同窗、完全后台、串行且保证关闭的临时详情页；
- 真实发送和申请仍需要针对当前不可变样本的明确授权；自动生成本地草稿不需要授权。

## 9. 数据和 profile 生命周期

稳定位置继续为：

```text
%LOCALAPPDATA%\RoleFlow\BrowserProfile
```

RoleFlow 业务数据、日志、会话描述和锁也应位于当前用户的稳定数据根下，并与程序安装目录
分离。程序升级只能替换程序文件，不能隐式迁移、清空或覆盖用户数据。

- 首次启动按需创建目录；
- 覆盖安装继续使用原数据；
- 程序移动或版本变化不改变浏览器身份；
- 正常启动、失败恢复和测试不删除 profile；
- 卸载默认保留数据；
- 只有用户明确选择“同时删除本机数据”，看到精确目录和影响后才删除；
- 旧 profile 迁移保持独立、显式、目标为空才复制，不进入普通启动路径。

## 10. 用户界面

工作台顶部只呈现用户能行动的结论，不暴露 CDP、9222、authority、target 等内部词。

示例状态：

- “RoleFlow 已启动，正在准备专用 Edge……”
- “专用 Edge 已准备好，请登录 BOSS 后点击‘重新检查’。”
- “专用 Edge 已关闭。岗位进度已保存，点击‘恢复专用 Edge’后可继续。”
- “发现另一个程序占用了 RoleFlow 的浏览器连接。没有关闭任何浏览器，请查看处理方法。”
- “BOSS 出现验证页面。RoleFlow 已停止访问，请先在专用 Edge 中处理。”

启动器只在 Dashboard 自身无法运行时显示“RoleFlow 启动失败”。浏览器和 BOSS 问题应显示在
仍可使用的 Dashboard 中，并附：发生了什么、数据是否安全、用户现在点击什么、诊断日志在哪。

## 11. 诊断与隐私

每次启动生成关联标识，使启动器、Dashboard、监督器和工作区协调器的日志可以串起来。结构化
日志至少记录：

- 阶段、状态变化、耗时和错误类别；
- 已脱敏的安装/数据根身份；
- Edge 发现来源、进程身份、控制连接结果；
- 是否发生恢复及恢复次数；
- 工作区检查结论和停止原因。

日志不得记录 Cookies、完整消息正文、简历私密内容或可复用认证信息。用户界面提供“复制诊断
摘要”和“打开日志文件夹”，不要求普通用户手工寻找端口或解析堆栈。

## 12. 安装、升级和卸载

### 12.1 首次安装

- 安装前检查受支持的 Windows、磁盘写入和真实 Edge；
- 安装程序文件、运行时和快捷方式；
- 不访问 BOSS、不预启动业务任务；
- 完成页启动 RoleFlow 时，先显示 Dashboard，再异步准备 Edge。

### 12.2 覆盖升级

- 检测正在运行的 RoleFlow，并要求安全退出程序文件占用；
- 保留业务数据、profile、检查点和用户设置；
- 会话描述带版本，升级后不盲信旧进程身份；
- 首次新版本启动执行轻量兼容检查，失败时工作台仍提供诊断和恢复。

### 12.3 卸载

- 删除程序和快捷方式；
- 默认保留用户数据和浏览器登录状态；
- 可选删除必须明确列出数据目录，不能默认勾选；
- 不结束或修改无法证明属于 RoleFlow 的 Edge 进程。

## 13. 主流方案参考与取舍

成熟浏览器自动化方案普遍把浏览器生命周期和业务页面操作分层：

- Playwright 提供持久化浏览器上下文，明确由 `userDataDir` 保存会话；
- Puppeteer 管理兼容浏览器的安装/缓存，并支持连接已有浏览器；
- Selenium Manager 负责驱动和浏览器发现、下载与缓存；
- WebView2 提供 Runtime 分发、用户数据目录和浏览器进程失败事件。

RoleFlow 第一阶段不直接迁移到这些框架，原因是：

- 当前 CDP 适配器已经覆盖所需浏览器动作；
- 换库不能自动解决 Dashboard 与 BOSS 就绪状态耦合；
- 新框架会扩大安装体积、缓存、升级和 BOSS 风控验证范围；
- WebView2 会把产品改造成内嵌浏览器，属于更大的宿主应用重写；
- Selenium 主要解决驱动管理，不负责本产品的业务状态和安全恢复。

本设计先建立浏览器监督器接口，把生命周期集中到一个边界。以后只有跨机器证据证明现有 CDP
传输仍是主要故障源时，再用同一接口评估替换，不重写上层工作流。

## 14. 跨机器验收矩阵

发布候选至少覆盖以下环境和场景，且每项保存安装日志、启动状态和人工观察结论：

### 14.1 环境

- 干净 Windows 10 普通用户；
- 干净 Windows 11 普通用户；
- Edge 位于不同受支持安装范围；
- 中文 Windows 用户名或包含空格的路径；
- 安全软件开启的普通环境；
- 无开发工具、无 Node、无 Edge Control 的电脑。

### 14.2 首次运行

- 安装后桌面和开始菜单入口存在；
- Dashboard 先出现；
- Edge 缺失时给出安装指引，Dashboard 不退出；
- Edge 存在时能自动启动专用实例；
- 首次未登录时引导登录，不循环访问 BOSS；
- 登录完成后重新检查即可进入就绪。

### 14.3 再次运行和并发

- 第二次启动复用同一工作台或将已有工作台交给用户；
- 复用同一 profile，登录状态保留；
- 专用 Edge 已运行时不创建第二身份；
- 端口被无关进程占用时不结束对方、不假连接；
- profile 被不匹配进程占用时给出安全提示。

### 14.4 异常恢复

- 慢启动不会过早报致命失败；
- Edge 被其他窗口遮挡不影响后台操作准入；
- Edge 关闭后 Dashboard 和任务检查点保留；
- 用户恢复 Edge 后可从安全检查点继续；
- 登录失效、风险控制、目标漂移和不确定外部结果都立即停止且不自动重试；
- 机器重启后不会信任过期会话描述。

### 14.5 安装生命周期

- 覆盖升级保留数据和登录；
- 安装目录变化不改变 profile；
- 卸载默认保留数据；
- 明确选择删除时只删除列出的 RoleFlow 用户数据；
- 所有错误提示中文正常，不出现乱码或内部堆栈。

## 15. 分阶段落地

### 阶段一：解除启动耦合

先让 Dashboard 的成功启动不再依赖浏览器和 BOSS 工作区。建立独立状态模型和用户可见的
恢复入口，保留现有底层启动逻辑作为被调用能力。

### 阶段二：集中浏览器生命周期

加入浏览器监督器、单实例锁、会话描述、稳定就绪证明、进程退出监测和有界本地恢复。业务
调用者只通过监督器取得浏览器连接。

### 阶段三：工作区协调与操作准入

将现有 `workspace-tabs` 从启动前置步骤改为可重入的工作区协调器；修正标签选中状态证据，按
扫描、消息和沟通的实际需要分别准入，不降低 BOSS 安全边界。

### 阶段四：部署、界面和诊断闭环

完善安装前置检查、升级/卸载语义、开始菜单和桌面入口、工作台状态文案、诊断摘要及日志关联。

### 阶段五：跨机器发布验收

先完成离线生命周期测试，再在独立 Windows 10/11 环境执行安装矩阵；最后只做低量、只读的
BOSS 人工验收。任何真实沟通或申请仍需单独明确授权。

## 16. 兼容与迁移

- 在当前 `codex/stable-dedicated-edge` 集成分支继续开发，避免重建已经验收的四课题和专用
  Edge 基础；
- 保留内部 `portable` 名称，暂不做无收益的大范围重命名；
- 复用现有稳定 profile、CDP 适配器、Dashboard readiness、检查点和安全策略；
- 新监督器先包住现有能力，再逐步移除启动器对工作区细节的直接依赖；
- 旧命令行入口在迁移期继续可用，但普通安装入口只走新启动编排；
- 不在重构过程中触碰 `search_page_api`，也不恢复通用 `standalone_detail`。

## 17. 明确拒绝的方案

### 17.1 继续逐条修启动报错

能暂时让本机通过，但无法定义不同机器的支持契约、进程生命周期和恢复语义，拒绝作为主线。

### 17.2 遇错自动反复重启或访问 BOSS

可能造成异常导航、风险控制和不确定操作重放，违反账户安全，拒绝。

### 17.3 立即全面换 Playwright/Puppeteer

会增加依赖和迁移面，却不解决应用与业务就绪耦合。先建立监督器边界，后续凭证据决定。

### 17.4 改为 WebView2 内嵌浏览器

需要新的 Windows 宿主、运行时分发和完整 BOSS 行为验证，工作量与风险远超本阶段，拒绝。

### 17.5 依赖 Edge Control

它未包含在安装包、来源仓库已归档且无再分发许可，不能作为普通用户默认环境，拒绝。

## 18. 完成标准

本课题只有同时满足以下条件才算完成：

1. Dashboard 能在浏览器/BOSS 未就绪时稳定启动并给出恢复路径；
2. 专用 Edge 能被统一发现、复用、启动、监测和安全恢复；
3. 同一用户重复启动不会产生多个工作台或多个浏览器身份；
4. BOSS 工作区和具体操作采用分层准入，不因页面被遮挡而误判；
5. 所有 BOSS 安全、冷却、后台和授权边界保持不变；
6. 覆盖安装、升级、卸载和数据保留语义经过验证；
7. 离线自动化验证通过；
8. 跨 Windows 10/11 干净环境验收矩阵通过；
9. 用户完成一次低量只读真实验收；
10. 所有改动先本地验证和必要人工验收，再提交；不自动推送、合并或发布。
