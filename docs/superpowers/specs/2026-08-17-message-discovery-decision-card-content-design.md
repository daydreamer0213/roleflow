# 消息发现决策卡内容设计

日期：2026-08-17

状态：已实现并完成自动回归与真实后台只读验收

范围：消息发现完成后的岗位结果卡内容、可信数据投影和展示顺序

## 1. 问题

当前结果卡把 `fitReasons`、`hardBlockers`、`softGaps` 和 `questionsToVerify` 等分析过程直接展示给用户。这些字段适合质量审计和岗位详情页，不适合用户收到招聘方消息后快速判断是否值得继续沟通。

消息页真正需要回答五个问题：

1. 这个岗位具体做什么；
2. 公司或岗位所在业务是什么；
3. 候选人与岗位的匹配度怎么样；
4. 薪资范围是多少；
5. 这份机会是否值得继续聊。

消息分类、人工处理原因和安全回复草稿仍保留，但不再与岗位分析过程混在一起。

## 2. 已验证的数据边界

当前完整岗位上下文已经提供：

- 岗位名称、公司名称、薪资、地点、经验、学历和完整 JD；
- `roleSummary`、`industryContext`、`businessScenario`；
- `fitLevel`、`recommendation`、`confidence`；
- `fitReasons`、`hardBlockers`、`roleGaps`、`softGaps`；
- `jobQuality.level`、`jobQuality.concerns` 和 `hiddenRisks`。

这些数据足以生成岗位职责、匹配度、薪资和岗位机会结论，不需要再次访问 BOSS，也不需要增加模型调用。

当前没有可靠的公司画像。消息详情链路只保存公司名称，没有完整公司业务、规模、融资、经营状况、员工评价或公开口碑。本功能不得根据公司名称、常识或单条 JD 猜测整家公司，也不得把岗位业务场景包装成公司全貌。

## 3. 方案选择

### 方案 A：使用现有可信数据生成决策卡

采用本方案。服务端把已经完成的岗位分析压缩成五项用户结论，不增加浏览器访问、模型调用、数据库迁移或第三方依赖。

优点是结果稳定、可解释、无新增风控成本，而且修改范围最小。限制是公司资料不足时只能明确说明未知，并把最终评价限定为这份岗位机会。

### 方案 B：增加一次模型摘要调用

不采用。它只能改写现有信息，不能补足公司事实，同时增加成本、等待时间和前后结论不一致的风险。

### 方案 C：扩展 BOSS 公司页或公开网络调查

本轮不采用。该方案需要新的公司身份核对、数据来源、访问节奏、缓存、失败处理和质量验收，属于独立课题，不应并入消息结果卡改版。

## 4. 决策卡内容

结果卡按以下固定顺序展示。

### 4.1 这个岗位是做什么的

- 主体内容来自已完成分析的 `roleSummary`。
- 控制为一至两句话，必须说明工作对象、主要动作和交付结果。
- 如果 `roleSummary` 缺失，不从职位名称猜测，显示“岗位职责分析尚未完成”。
- 不在消息卡重复完整 JD、责任证据或要求清单。

### 4.2 公司及业务

- 始终显示已核验的公司名称。
- `businessScenario` 有有效内容时，显示“JD 显示该岗位服务于……”。
- `businessScenario` 缺失但 `industryContext` 有有效内容时，显示“JD 显示该岗位属于……相关业务场景”。
- `未明确`、`未知`、`无`、空字符串等占位值都视为没有公司业务证据。
- 没有有效证据时固定显示：“JD 未说明公司具体业务，建议面试时确认业务线、产品和盈利模式。”
- 即使存在岗位业务场景，也明确说明它不能代表公司整体经营情况。

### 4.3 你的匹配度

匹配度只显示一个等级和一句总结，不展示证据数组。

等级按最终分析字段映射：

- `fit` 或 `A`：高；
- `mostly_fit`、`partial_fit`、`B` 或 `C`：中；
- `no_fit` 或 `D`：低；
- 缺失、分析未完成或未知值：待确认。

总结句使用现有结论压缩生成：

- 高：优先使用第一条可靠 `fitReasons`；
- 中：优先说明主要匹配方向和最重要的一项 `roleGaps` 或 `softGaps`；
- 低：优先使用最终规则保护写入的结论、第一条 `hardBlockers` 或 `roleGaps`；
- 没有可靠句子时只显示等级，不补写推断。

所有总结最多一至两句话。详细匹配依据继续保存在岗位库，不在消息卡重复展示。

### 4.4 薪资范围

- 直接显示经过岗位身份核验后保存的原始薪资文本，例如 `15–25K·13薪`。
- 本轮不自行换算年薪，不推断奖金、股票、福利或税后收入。
- 没有可靠薪资字段时显示“薪资未说明”。

### 4.5 这份机会值不值得继续聊

标题和措辞明确评价的是“这家公司提供的这个岗位机会”，不是整家公司。

按最终 `recommendation` 映射：

- `primary` 或 `apply`：值得继续聊；
- `caution`：可以了解，但要先确认关键问题；
- `not_recommended`：不建议优先投入时间；
- 其他值、分析待完成或资料不完整：信息不足，暂时无法判断。

结论下只显示一条最重要原因，优先使用最终规则保护结论，其次使用岗位质量风险或匹配度总结。不得把低置信度内容写成确定事实。

公司资料不足时追加固定说明：“公司资料不足，当前结论只针对这份岗位机会，不能评价公司本身是否值得加入。”

## 5. 消息处理内容

岗位决策卡之后继续显示消息分类和下一步动作：

- 面试邀请、薪资、隐私和身份不明仍只显示人工处理提示，不生成草稿；
- 普通沟通仅在事实完整且安全契约通过时显示最多两份草稿；
- 页面仍只提供本地复制和本地状态记录，不提供填写、粘贴、发送、沟通或投递动作。

消息分类使用面向用户的中文标签，不直接显示 `interview_invitation` 等内部枚举值。

## 6. 页面取舍

消息结果卡删除以下可见列表：

- 匹配依据；
- 硬性阻断；
- 待补信息；
- 建议核实。

这些数据没有删除，仍保留在岗位分析和岗位库中。消息页不增加“展开详细分析”，避免重新制造信息噪声；需要审计时直接进入岗位库查看已有完整记录。

页面现有布局、导航、只读发现按钮和消息安全操作保持不变，只替换结果卡内容结构。

## 7. 数据流与实现边界

数据流保持为：

`稳定消息岗位身份 → 同观察完整 JD 与分析 → 安全结果投影 → 决策卡渲染`

实现只需调整现有安全投影和消息结果视图：

- 安全投影从岗位和分析中输出岗位说明、业务说明、匹配等级、匹配总结、薪资、机会结论和机会原因；
- 视图只消费这些已经裁剪和转义的字段；
- 原始 JD、完整分析对象、消息正文、`securityId` 和浏览器错误不得进入页面状态接口。

不得增加：

- 新的 BOSS 页面、标签、导航或详情读取；
- 公司页读取或公开网络调查；
- 新模型调用或新的提示词流程；
- 数据库字段或迁移；
- 新依赖或新的通用摘要框架。

## 8. 失败和资料不足处理

- 岗位分析未完成：匹配度和机会结论显示“待确认/信息不足”，不使用基础字段猜测。
- 公司业务资料不足：显示固定未知说明，不根据公司名推断。
- 薪资缺失：显示“薪资未说明”。
- 未知匹配等级或推荐枚举：安全降级为“待确认/信息不足”。
- 消息模型结果不合法：岗位决策卡仍可见，消息部分显示人工处理提示，不生成草稿。

## 9. 验收标准

### 自动回归

- 完整岗位结果只显示五项决策内容和消息处理区，不再渲染四类分析列表；
- 岗位职责、薪资、匹配度和机会结论都来自现有岗位或分析字段；
- 公司业务缺失时出现固定未知说明，不出现根据公司名生成的描述；
- 匹配等级和机会结论的所有允许枚举都映射正确，未知值安全降级；
- 面试邀请等人工类别仍无草稿；普通安全类别仍最多两份草稿；
- 轻量状态接口和页面不泄露完整分析、消息正文或 `securityId`；
- 回归证明没有新增浏览器命令、BOSS 访问、模型调用、数据库写入类型或外部动作。

### 本地人工验收

使用隔离数据库重放一个已验收的真实消息样本，确认：

- 页面一眼能看到岗位职责、公司/业务说明、匹配度、薪资和是否值得继续聊；
- 公司资料不足时措辞诚实，不评价公司整体；
- 面试邀请仍显示人工处理提示且没有草稿；
- Dashboard 保持前台，两张固定 BOSS 标签不变，没有临时详情页和外部写；
- 用户确认内容比旧版更直接、易于做决定。

## 10. 非目标

- 不评价公司经营、文化、管理、口碑或稳定性；
- 不读取 BOSS 公司页，不搜索公开网络；
- 不设计公司评分体系；
- 不修改岗位推荐算法、消息分类、安全草稿规则或 BOSS 风控策略；
- 不调整当前页面视觉风格和整体布局。
