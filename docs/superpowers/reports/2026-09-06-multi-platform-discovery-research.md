## 1. 当前授权与沿用的方向

用户同意先对智联招聘、前程无忧做小范围只读调研，再确定首个平台及具体实现方案。本轮不修改产品行为，不填简历、不投递、不发消息，不重新发布版本。此前 BOSS 的批次授权不适用于新平台。

直接相关历史设计已通读：

- `docs/superpowers/specs/2026-07-23-multi-platform-readonly-search-design.md`
- `docs/superpowers/specs/2026-07-23-cross-platform-common-filters-design.md`

沿用其中的核心：每个平台保留用户自己的筛选条件，统一岗位分析及结果列表，区分实际平台能力，跨平台相似岗位只提示、不自动合并。历史文档明确写着尚未实现；不能把它当作当前已具备的能力。

本次建议比旧设计先缩小一步：首版每轮只选一个平台，不先建设跨多个平台自动轮转的调度框架。用户仍可在一天内多轮找岗、换平台继续找；完成一轮不是完成整个求职周期。

区分三种证据：当前代码、公开网页抓取、用户已登录浏览器中的真实操作。此次前两种有结果，第三种尚未取得。

### 公开资料暴露的具体风险

1. 智联样本的薪资栏是遮蔽值，而非“面议”。正文另有收入描述，读取时需要保留字段来源，不能把遮蔽值当成零薪资，也不能猜测平台薪资栏的实际数值。
2. 同一公开详情的抓取文本同时含登录入口、成功弹窗文案和引导 App 沟通的文案。静态页面中存在一句“发送成功”，不证明当前用户发出过操作，也不证明该弹窗当前可见。后续发送结果必须绑定当次操作、岗位身份和实际状态变化。
3. 岗位正文之后还有相似岗位、公司介绍等区块。不能把整页文字拼成该岗位的 JD，导致其他岗位薪资、实习标签或要求串入。
4. 前程无忧的简历中心模板有多种简历入口。后续必须核对平台实际选中的简历，不能用 RoleFlow 当前启用版本代替这项证据。
5. 部分前程无忧公开搜索结果返回访问验证页。没有尝试解决或绕过验证；这只能说明此次公开抓取的局限，不能据此断定用户登录后的浏览器同样受阻。

没有使用校园网申说明代替社会招聘流程，也没有使用第三方教程或旧选择器作为实现证据。

### 首轮公开调研时的浏览器限制

本任务可见的浏览器只有 Codex 内置浏览器，没有暴露用户已登录的 Edge 标签。创建智联页及再次读取该页均在 30 秒超时，创建前程无忧页在 45 秒超时；原因尚未定位，不能归因为平台休眠、账号风控或用户未登录。已安排智联调研页在任务右侧展示，并请用户确认页面能否正常显示；展示请求返回 queued，尚未验证用户实际看到页面。

在浏览器页面结构可读、取得实际登录后页面证据前，不编写真实平台选择器，不声称从搜索到反馈的真实流程已经走通。

## 3. 从用户使用角度建议怎么做

### 首次使用某个平台

1. 在现有找岗入口选择“智联招聘”。原有 BOSS 条件继续保留。
2. RoleFlow 使用当前求职方向的关键词打开该平台搜索入口；关键词构造规则要以实际页面验证为准。用户自行登录并设置城市、区域等原生条件。
3. 回到 RoleFlow，显示读到的关键词和筛选摘要，使用这组条件开始本轮。之后复用这份平台设置，不要求每轮重新配置。
4. 读取岗位及必要的完整详情，使用现有简历、精筛规则和二维表分析。没有可靠完整详情的岗位保留待处理，不拿列表摘要冒充完整分析。
5. 结果进入现有岗位列表，卡片标明来源，允许按平台筛选。首个里程碑只提供查看分析、打开原岗位等只读入口，不显示尚未实现的“批量投递”按钮。

一轮结束后可以继续下一轮，或者换平台。平台的搜索条件分别保存，不把 BOSS 的城市编号、薪资档位、活跃度要求套给其他平台。暂停、结束本轮和重启恢复沿用用户已经熟悉的使用逻辑；恢复时核对的是该轮真实搜索范围。

筛选策略继续保持：兼职默认不接受，薪资默认留空；有明确工资单位时保留元/小时、元/天、月薪、年薪的区别。没有薪资要求时不偷偷增加限制；没有可靠活跃度信息时标为不可获取，不能自动当作不活跃而排除。

### 浏览器与页面数量

只在用户使用某个平台时准备其所需页面，不在启动时一次性打开所有平台搜索页和消息页。新平台的详情究竟在侧栏、当前页还是新标签打开，以实际页面为准，不强套 BOSS 的详情布局。BOSS 现有固定页和后台运行路径不变。

同一时间只运行一项浏览器任务；另一平台登录未完成时，不影响已经保存的岗位分析、简历、面试训练，也不要求用户退出整个项目。真实风险或身份异常时停止当前浏览器操作，不自动切换平台绕过风险。

## 4. 为什么不只是增加两个网站地址

| 当前代码证据 | 可复用或需要调整的地方 |
| --- | --- |
| `src/storage/job_store.js:147` 按 `source + source_id` 查找岗位 | 已有来源隔离基础，延用，不重建岗位数据库 |
| `src/cli.js:2636` 的工厂只创建 BOSS 适配器 | 扩展真实首个平台，同时核对所有实际调用入口 |
| `src/dashboard/server.js:397` 等位置直接创建 BOSS 适配器 | 只改首版涉及的工作区、搜索和详情路径；不全面重构消息系统 |
| `src/core/search_plan_schema.js` 当前仍是单个平台配置 | 保留旧 BOSS 配置，增加按来源保存搜索上下文的最小兼容设计 |
| `src/core/platform_filters.js` 有通用目录结构，`platform_runtime_policy.js` 仍含 BOSS 编码与分支 | 复用目录表达；先继承平台原生条件，不急着建设所有通用筛选映射 |
| `src/core/funnel_observation.js:33`、`candidate_progress.js:1103` 等只接受 BOSS | 新平台消息与反馈属于后续独立适配，不能仅放开字符串校验 |
| `src/storage/funnel_store.js:219` 的查询没有平台过滤参数 | 接入新平台求职结果前，补齐按来源分组和分母验证 |

推荐在接入首个真实平台的过程中抽出必要共用入口，使用现有模块、数据库及假浏览器测试。不先引入插件框架、ORM、服务拆分或额外浏览器运行时；也不复制整套 BOSS 产品代码作为新平台。

三个方案的取舍：复制 BOSS 代码短期易上手但后续修复容易分叉；先造完整多平台框架投入大且缺少实站证据；推荐随首个平台抽出确实需要复用的入口，边界够用即可。

## 5. 后续投递与反馈必须保留的设计

这部分明确方向，不在只读首版顺带实现。

- 投递阶段按“平台、岗位、动作、实际使用简历、必要文字”冻结用户确认的清单，后台串行执行。用户点击确认即授权这份清单，不再逐岗二次确认。
- 先核对实际动作语义。申请职位、发送简历、打招呼、回复消息可能独立，也可能一个按钮触发多项动作，不能一律记为“已沟通”。额外表单或站外网申单独标明，不算自动投递成功。
- 平台简历与本地简历分开记录。用户在 RoleFlow 启用新简历不等于更新所有平台；未核实版本的申请可以计入真实动作数量，但不能作为“新简历更有效”的比较证据。平台若不提供版本标识，也不能假称已自动核实全文一致。
- 当前 48 小时、周末顺延、可配置的 30/50/70 三档保留。样本从实际求职动作开始，不从发现或分析岗位开始；迟到反馈仍归属原投递与原策略，不混入修改后的新样本。
- 总览可以合计工作量，效果诊断要区分平台、方向、策略和动作类型。BOSS 40 条与智联 30 条可以显示共 70 条，不能因此声称两个平台都达到了 70 条证据强度。平台比例改变时，不能把汇总变化直接归因为简历或招呼语改进。
- 平台不提供的“已读/送达”属于不可观测，不是零，也不是已拒绝。时间已成熟但没有可靠近期观察的样本，不能仅凭页面没有记录就判成没有回复。
- 跨平台同公司同名岗位保留独立来源、投递及反馈；足够相似时提示可能重复，不自动合并，更不把一次投递广播到所有平台。

## 6. 实施顺序建议与继续条件

推荐智联作为首个平台：第 9 节已验证同页列表与详情、岗位身份切换及关键词搜索，消息页也已有真实结构依据。这不是“智联一定更容易”的结论，也没有充分证据对两家作可靠工期排名。

1. **完成最小实站探查**：在可读取的已登录页面核对搜索条件、一个普通岗位的完整详情、稳定岗位标识及详情返回路径。再只读查看简历、投递历史和消息入口，不点击可能发送或申请的按钮。
2. **确认首个平台的只读实施设计**：补齐真实读取方式、字段映射、停止条件和用户入口，再提交用户审阅。若智联的搜索/详情无法稳定只读取得，则先用同样标准核对前程无忧，不凭猜测决定替代路径。
3. **实现找岗与分析**：平台设置、列表与完整详情、现有分析、来源可见、暂停结束与恢复。最小实站采样后使用脱敏 fixture、假浏览器、临时数据库验证，不用真实网站跑常规测试。
4. **首个平台独立投递阶段**：取得真实动作与结果证据后实现确认投递，专门验证简历选择、成功证明、歧义中断和重启不重复执行。
5. **消息与反馈阶段**：按网页实际可观测状态接入消息草稿和分平台诊断。App 独有能力明确标注，不为了“功能齐全”额外引入手机自动化。
6. **第二个平台**：复用第一个平台已证明有价值的共用部分，再做独立适配与验收。

第一阶段验收至少覆盖：旧 BOSS 配置无损、同一原生岗位编号在不同平台不串数据、关键词变化保留其他筛选、完整 JD 与当前岗位绑定、薪资遮蔽和单位区别、默认兼职策略、缺失活跃度、登录或页面丢失时保留已得结果、暂停/结束/恢复，以及没有平台写能力的来源不会进入 BOSS 发送清单。

## 8. 用户已登录 Edge 的首次后台只读核对（后续交互见第 9 节）

用户随后提供同一 Edge 窗口中的智联搜索页、智联消息页和前程无忧搜索页，并明确要求不要抢占前台。

### 连接与实际操作边界

- 通用浏览器工具仍只列出内置浏览器；本机原有 Edge Control 配置、程序与依赖均存在，连接服务最初不可达。
- 复用项目已有启动入口恢复本机回环地址的后台连接服务，没有重新安装扩展、修改凭据、打开新浏览器或另建 profile。扩展随后返回 `healthy`、`readyExtension=true`、`healthyExtension=true`。
- 使用已有浏览器适配器逐页读取 DOM。没有点击、输入、导航、滚动、投递、聊天、收藏或修改任何筛选。三页均返回 `document.visibilityState=hidden`、`document.hasFocus()=false`，每次记录的活动标签编号前后一致。
- 一次后台裁切截图调用超时，未切前台、未调用 `Page.bringToFront`、未采用前台补救。因此下述结论属于实时 DOM 观察，尚不构成带截图、身份切换和结果复核的完整实站验收。

### 智联：优先接入的依据更具体了

1. 当前入口是 `https://www.zhaopin.com/jobs/`，真实布局为左侧 `.job-list-panel` 与右侧详情，已加载 20 个 `.job-card`，其中一个为 `.job-card--active`。
2. 右侧当前岗位有独立的 `.job-detail-summary`，能够读取岗位、薪资、公司、城市、学历、经验，正文另有职位描述、工作地点、公司信息等区块。这给沿用现有完整 JD 分析提供了实际结构基础；尚未切换第二个岗位验证详情身份变化。
3. “先聊聊”和“立即投递”是两个不同按钮，不能合并成一种动作；本轮均未点击。
4. 当前搜索输入框为空，页面还显示已保存的求职期望，地区标签为“广东”。不能把这个页面自动解释成已经按某个关键词完成搜索，也不能只保存 `/jobs/` 的地址作为完整搜索范围。
5. 已核对的 `.job-card` 外层没有直接给出岗位 ID，卡片内所见普通链接是公司链接。不能拿公司 ID 当岗位 ID；稳定岗位标识、详情 URL 与切换后的绑定仍需后续核验。

### 智联消息页：独立的网页会话列表确实存在

- 入口为 `https://i.zhaopin.com/im`，分类包含全部、未读、新招呼、沟通中、不合适。
