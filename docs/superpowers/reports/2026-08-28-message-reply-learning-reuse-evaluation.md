# 消息回复学习：外部方案复用评估

日期：2026-08-28  
结论：`reference_only`

## 1. RoleFlow 真正需要的能力

本阶段不是建设一个通用 Agent 记忆平台，而是完成一个边界明确的本地闭环：

1. 模型根据当前画像生成回复草稿；
2. 用户可以修改草稿；
3. 用户复制或标记已手动发送时，最终文字成为一次已完成回答；
4. 只有用户实际修改的内容可以提升为权威回答和候选人事实；
5. 同一事实的新修改成为当前值，旧值保留为历史；
6. 后续草稿可以使用仍然有效的用户修改和当前事实；
7. 提取、模型或检索失败不得丢失最终回答，也不得阻塞复制和手动发送。

RoleFlow 已经有 Node.js 22、内置 SQLite、候选人画像、`candidate_facts`、消息意图分类、模型 JSON 适配器和本地 Dashboard。外部组件只有在能明显减少代码，同时不接管这些权威数据时才值得直接引入。

## 2. 候选方案

### 2.1 Mem0

[Mem0 官方仓库](https://github.com/mem0ai/mem0)使用 Apache-2.0 许可证，提供 Python/npm 库、自托管服务和云服务。其当前官方说明显示，基础记忆仍依赖 LLM，并默认使用 Embedding 模型；自托管服务还引入 Docker、Postgres/pgvector、身份验证和单独的服务进程。当前主线的 ADD-only 设计还明确把 Agent 生成事实作为一等记忆。

优点：

- 提供“提取—保存—检索”的完整通用思路；
- 有用户/会话级记忆和检索接口；
- Apache-2.0 可与本项目许可证兼容。

不适合直接接入的原因：

- 默认让模型决定和生成记忆，不符合“模型原稿不是权威事实，只有用户修改才是权威”的规则；
- 需要额外 LLM、Embedding 和向量存储，或引入独立自托管服务；
- 会与 RoleFlow 已有 SQLite、模型配置、事实有效期和修订历史形成第二套数据所有权；
- 官方仓库仍可见 Node OSS 本地历史库路径等集成问题，例如 [Node OSS historyDbPath 问题](https://github.com/mem0ai/mem0/issues/4096)；
- 对首阶段预计的几十到几百条用户回答而言，集成成本远高于检索收益。

复用层级：参考思路。采用“语义回答记忆与当前结构化事实分层”，不采用其运行时、存储或 Agent 自动写入规则。

### 2.2 LangMem（Python）

[LangMem 官方仓库](https://github.com/langchain-ai/langmem)使用 MIT 许可证。它提供热路径记忆工具、后台记忆管理器和可替换存储接口；官方示例使用 Python、LangGraph、Embedding，持久化建议使用 Postgres 存储。

优点：

- 清楚区分语义记忆、情节记忆和过程记忆；
- 强调记忆管理、检索和更新，而不只是保存完整对话；
- 存储接口概念可借鉴。

不适合直接接入的原因：

- 官方实现是 Python，而 RoleFlow 是 CommonJS/Node.js 桌面应用；
- 示例由 Agent 自行决定何时管理记忆，RoleFlow 已经明确使用复制/已发送作为完成触发；
- 持久化和语义检索会额外引入 LangGraph、Embedding 与 Postgres 或等价后端；
- 为单一回复学习闭环引入第二运行时会增加安装包、诊断和跨机器交付复杂度。

复用层级：参考思路。采用“热路径完成后提取”和“记忆可管理/撤回”的概念，不采用 Python/LangGraph 运行时。

### 2.3 langmem-ts

[langmem-ts 官方仓库](https://github.com/ereztdev/langmem-ts)使用 MIT 许可证，目标是提供 TypeScript 原生的 `extract → embed → store → retrieve` 原语。

优点：

- Node.js 可用，接口边界比大型 Agent 框架小；
- 提取、Embedding、存储和检索可替换；
- 消费方保留数据库连接所有权。

不适合直接接入的原因：

- 官方状态仍是早期开发，当前 npm 版本为 0.1.0；
-默认实现需要 OpenAI、Postgres 和 pgvector；
- 官方路线图显示情节记忆尚未实现，而 RoleFlow 恰好需要保存“问题摘要—原稿—用户最终回答—适用范围”；
- 接入后仍需自行实现幂等、当前事实投影、撤回重算、权威顺序和 Dashboard 管理，未实际减少核心代码。

复用层级：参考思路。采用“提取器与存储器解耦”的接口思想，不直接添加包。

### 2.4 sqlite-vec

[sqlite-vec 官方仓库](https://github.com/asg017/sqlite-vec)使用 MIT/Apache-2.0 双许可证，支持 Node.js 和 Windows，可把向量检索放在 SQLite 内。

优点：

- 本地运行，不需要独立向量数据库；
- 将来回答记忆达到较大规模后，可作为语义检索候选；
- 保持 SQL 元数据过滤能力。

当前不采用的原因：

- 官方明确标记为 pre-v1，可能发生破坏性变化；
- 仍需选择、下载和运行 Embedding 模型或调用外部 Embedding API；
- Node/Windows 发布包近期存在 [平台与包路径问题](https://github.com/asg017/sqlite-vec/issues/272)；
- 当前记忆规模可以把最多 12 条经过范围筛选的回答直接交给现有草稿模型判断，不需要近似向量检索；
- 原生扩展会增加安装包和跨机器验证成本。

复用层级：暂不接入。只有当实际活跃回答显著增长并通过带标签的召回基准证明现有有界检索不足时，才重新评估。

### 2.5 jsdiff

[jsdiff 官方仓库](https://github.com/kpdecker/jsdiff)使用 BSD-3-Clause 许可证，提供成熟的字符、词、句子和数组差异算法。

优点：

- 中文可使用字符差异，能力完整；
- 维护历史长，许可证兼容。

当前不直接接入的原因：

- RoleFlow 不需要展示精细 diff，只需要保守地确定用户新写的证据片段；
- 最长公共前缀/后缀可以用少量标准 JavaScript 完成，并由固定夹具验证；
- 新依赖不会减少数据库、提取、幂等或撤回逻辑。

复用层级：参考算法目标，不添加依赖。若后续产品要做逐字可视化修改历史，再单独评估。

### 2.6 Vercel AI SDK

[Vercel AI SDK 官方仓库](https://github.com/vercel/ai)使用开源许可证，支持 Node.js 和结构化模型输出。

优点：

- 多模型提供商抽象完整；
- 结构化输出和验证工具成熟。

当前不直接接入的原因：

- RoleFlow 已经有 OpenAI-compatible 与 mock 适配器、模型配置、连接检查、JSON 修复和回归夹具；
- 引入 AI SDK 还需增加 provider 和 schema 依赖，并迁移现有模型设置；
- 它不提供本阶段的权威顺序、SQLite 历史或撤回重算能力。

复用层级：不接入。继续扩展当前 `chatJson` 适配器的一个窄方法。

## 3. 六个固定行为对比

| 行为 | Mem0 | LangMem | langmem-ts | sqlite-vec | 现有 SQLite + 窄服务 |
|---|---|---|---|---|---|
| 原稿未改不成为权威事实 | 需重写默认策略 | 需自定义触发/工具 | 需自定义 | 不负责 | 直接由完成契约保证 |
| 用户纠正到岗时间 | 可提取，但需二次映射 | 可提取，但需二次映射 | 可提取，但需二次映射 | 不负责 | 保存回答后按证据投影 |
| 同一最终稿重复完成幂等 | 需额外业务键 | 需额外业务键 | 需额外业务键 | 需额外业务键 | SQLite 唯一键直接保证 |
| 第二次纠正保留旧值 | 通用历史不等于当前事实投影 | 需自定义 | 需自定义 | 需自定义 | 事实修订表 + 当前投影 |
| 提取器不可用仍保留回答 | 需包装降级 | 需包装降级 | 需包装降级 | 不负责 | 先保存回答，提取可失败 |
| 撤回答案后不再用于草稿 | 需同步 RoleFlow 事实 | 需自定义 | 需自定义 | 需自定义 | 撤回记忆并重算当前事实 |

没有一个外部候选能在不保留 RoleFlow 自身数据契约的前提下覆盖六项行为。直接接入仍要写最关键的业务代码，同时增加运行时和存储复杂度。

## 4. 采用的设计

结论为 `reference_only`：

- 数据所有权继续放在现有本地 SQLite；
- 回答记忆与当前结构化事实分层；
- 用户复制或标记已发送是唯一完成触发，不让 Agent 自主写权威记忆；
- 提取器是现有模型适配器上的可选窄接口，失败只影响结构化事实数量；
- 每个被模型提取的事实必须带用户修改片段中的原文证据；
- 后续草稿只读取未撤回的用户编辑回答，并返回实际使用的记忆 ID；
- 当前只做有界元数据筛选，不引入 Embedding 或向量数据库；
- 中文差异使用标准 JavaScript 的保守前后缀算法，不添加 diff 包。

这个方案复用了成熟项目最有价值的产品思想，但避免引入第二套事实系统、第二数据库、Python/Docker 运行时和当前没有量化收益的向量检索。

## 5. 以后重新评估的条件

只有同时满足以下条件才重新评估语义检索组件：

1. 单个候选人的活跃回答记忆超过当前有界输入能够稳定处理的规模；
2. 建立了真实但脱离平台的标注问题—回答召回夹具；
3. 当前元数据筛选在固定夹具上的召回明显不足；
4. 候选组件在 Windows/Node 22 安装包内可稳定离线加载；
5. 引入后的召回提升、延迟、成本和安装复杂度已经量化。

在此之前，向量数据库属于没有被产品数据证明的复杂度，不进入首阶段实现。
