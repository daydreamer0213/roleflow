# RoleFlow Wave 0–4 实机人工验收增量报告

- 日期：2026-08-11
- 范围：Wave 0–4 完成后的真实 Edge 人工验收、真实 BOSS 只读检查、两次明确授权的单岗位沟通校准、消息页读取，以及用户反馈归档。
- 约束：不启动 Wave 5；本报告只记录事实、判断和后续设计，不修改产品代码。

本报告是
[Wave 0–4 consolidated evaluation](2026-08-11-wave-0-4-consolidated-evaluation.md)
的实机增量证据。它只覆盖本轮实际观察到的行为，并取代旧报告中“Edge 不可用、真实沟通 E2E 尚未开始”这一局部状态；旧报告的离线测试和架构测量仍然有效。

## 结论

Wave 0–4 不能直接进入 Wave 5。下一步应先做一轮 **Wave 4 验收修复**，优先解决三个断点：

1. BOSS 页面采集条件覆盖了 Search Plan 的逻辑推荐边界，导致部分低于目标薪资的岗位进入“主投/可投/慎投”。
2. 自动沟通第二次单岗位 happy path 在真实 Edge 上成功，但第一次失败时没有记录决定建联结果的异步请求响应；成功路径已证，失败诊断、歧义恢复和稳定性仍未通过完整验收。
3. 消息页底层 reader 能读取真实普通 Edge，会话身份和消息方向核验通过；Dashboard 的“消息只读发现”却固定连接 CDP `9222`，没有复用当前 Edge Control，产品入口以 `BROWSER_DISCONNECTED` 停止。

前端方向不是继续零散改样式，而是按“用户只关心结果、进度和下一步”的原则重新收敛信息架构。侧栏倒字、流程体检过密、原始未解析参数、自动沟通入口不明确都属于同一批信息架构问题。

许可证方面，**AGPLv3 合理，但不符合“禁止他人用于盈利”这一目标**。AGPLv3 允许商业使用和销售；它主要要求修改后的网络服务向远程用户提供对应源码。若“禁止商业/盈利使用”是硬要求，应选非商业 source-available 许可证，而不能把项目称为 OSI 定义的开源软件。

### 根因分层

**已确认的代码事实：**

- `communication_executor` 在真正操作页面前把 item 从 `verified` 写为 `click_dispatched`，并记录一次点击审计。
- BOSS adapter 的真实派发动作通过页面上下文执行 `candidates[0].click()`。
- 该函数返回 `{ clicked: true }` 只证明 JavaScript 调用了 DOM `.click()`，不证明 BOSS 接受了动作。
- 当前真实页面的“立即沟通”没有直接绑定处理器，而是由父容器的 jQuery 委托处理。
- 委托处理器先异步读取 `/wapi/zpchat/config/get`；本轮只读复核得到 `code=0`、`unreadBubble=false`，因此会进入 `Detail.startChat()`。
- `Detail.startChat()` 随后向按钮 `data-url` 指向的 `/wapi/zpgeek/friend/add.json` 发起建联 POST。只有该 POST 返回成功，页面才会改为“继续沟通”，并显示招呼语成功提示或跳转聊天页。
- RoleFlow 没有观察或保存该 POST 的 HTTP 状态、BOSS 业务码和错误信息；页面脚本启动异步流程后就返回了 `{ clicked: true }`。
- 第二次使用同一个 DOM `.click()` 路径成功，因此“DOM 合成点击在当前 BOSS 一定无效”这一假设已被否定。当前实现已有 `EdgeControlAdapter.clickAt()`，但没有证据支持仅替换为 CDP 鼠标事件就能解决第一次失败。
- 结果核验没有发现“继续沟通”、成功弹窗或已发送消息，所以正确落入 `ambiguous`。

**能够得出的根因结论：**

第一次 BOSS 建联成功分支没有发生，第二次相同派发路径成功。失败可能来自第一次建联 POST 的网络错误、非零业务码或岗位/账号条件；由于 RoleFlow 没有捕获第一次关键响应，事后无法精确区分。可以确认的产品根因是：**状态机把“已调用 DOM 点击”当成派发完成，却没有观测真正决定建联结果的异步请求。**

### 推荐修复设计

保留现有身份、安全和最多一次点击约束，补齐派发与结果观测：

1. 页面脚本只负责最后一次读取并返回：tab、URL、岗位 ID、标题、公司、唯一按钮、按钮中心坐标和聊天身份参数。
2. 点击前注册一次性、严格过滤的请求观测，只捕获当前岗位对应的聊天配置请求和建联 POST；日志必须移除 `securityId`、聊天身份值和其他敏感查询参数。
3. 紧接着再次用 `elementFromPoint` 确认坐标下仍是同一个按钮，避免页面在检查与点击之间漂移。
4. 保留当前已被成功样本证明可用的 DOM `.click()`，除非后续证据显示输入事件本身不稳定；不要在没有证据时只为“更像人工”改成 CDP 点击。
5. item 仍只能拥有一次点击机会；派发后不允许自动补点。
6. 建联 POST 明确失败时记录脱敏后的 HTTP/业务码和用户可理解的原因，进入新的“平台拒绝/动作失败”终态，而不是只留下无上下文的 `ambiguous`。
7. 建联响应成功后，仍必须用“继续沟通”、成功提示、内嵌聊天或目标消息会话做第二层身份一致核验，不能只信接口响应。
8. 任一请求或页面证据不唯一仍落入 `ambiguous`，不自动认定成功。
9. 修复后先跑离线回归，再用失败注入或后续明确授权样本验证错误码、超时和歧义恢复。

当前 `acceptance` 必须继续保持 `e2e_pending`。

## BOSS 消息页读取验收

### 底层 reader：真实 Edge 通过

使用 `boss_message_reader` 直接连接当前普通 Edge 的固定消息 tab：

- 成功解析 40 个会话；
- 当前未读 0；
- 分类数量为 `self_delivered=8`、`self_read=6`、`platform_notice=3`、`possible_hr_reply=23`；
- 会话 key、招聘方 key、预览 digest 和瞬时签名均通过结构校验；
- 能稳定选择第二次校准生成的第 0 行会话；
- 选中后唯一会话身份为“林女士—趋势智能”；
- 岗位、公司、薪资、城市与校准岗位一致；
- 读取到 2 条文本消息，方向为对方 1、本人 1；
- 页面存在编辑器和发送按钮，但 reader 只报告存在性，没有填入、点击或发送。

这证明消息列表 DOM、会话选择守卫、身份复核和消息方向读取在当前真实页面可用。

### Dashboard 产品入口：失败

`/messages?profileId=1` 能渲染“BOSS 消息只读发现”页面，但启动真实任务后在约 57ms 内停止：

```text
status      = needs_user_action
queued      = 0
processed   = 0
reasonCode  = BROWSER_DISCONNECTED
```

根因已经定位：`message_discovery_controller` 默认执行
`new CdpBrowserAdapter({ port: 9222 })`，而当前项目实际使用普通 Edge Control。Dashboard 创建 controller 时没有注入 `EdgeControlAdapter` 或浏览器模式，因此页面入口没有连接到已经通过实机验证的 reader。

前端还有两个伴随问题：

1. 页面提交脚本不检查 POST 响应，失败时重新加载，用户最初只看到“尚未开始”。
2. `BROWSER_DISCONNECTED` 没有专门的中文原因映射，刷新后只显示泛化的“本次发现已停止，请查看本地进展后再继续”。

结论应分开记录：消息读取底层能力实机通过；Dashboard 消息发现产品链未通过。

### P0：采集范围污染推荐边界

真实搜索页使用 BOSS 的 5–10K 薪资筛选，而 Search Plan 保存的是严格 9–14K。`applyPlatformRuntimePolicy` 当前把平台采集条件写回运行时推荐配置，同时覆盖部分经验、求职类型、风险规则、排除词、BOSS 活跃度和作息偏好。

54 个 `primary/apply/caution` 岗位按正确 Search Plan 重算后，有 6 个违反严格薪资边界，占 11.1%。其中包括：

- `ai人工智能工程师`，5–8K，当前 primary；
- `agent工程师（智能体+电商类）`，7–8K，当前 apply；
- 另外 4 个 caution 低于 9K。

还观察到至少 3 个明显跨技术栈的 primary，包括 Java、Go 和泛研发岗位；它们主要依靠“可迁移证据”被二维表提升。

### 推荐修复边界

平台条件只能决定“去哪里采集”，Search Plan 才能决定“什么值得推荐”。两者必须成为两个不可相互覆盖的对象：

```text
Acquisition Policy  -> 采集范围、页面筛选、读取预算
Recommendation Policy -> 薪资/地点/经验硬边界、证据、权重、阈值
```

采集可以比推荐更宽，以保留召回；推荐硬边界不得被页面当前筛选静默放宽。修复后必须以本轮 104 个岗位建立新的可复算基线，并重点检查上述 6 个边界样本和跨技术栈 primary。

## 前端信息架构建议

### 今日任务

只回答四件事：

1. 今天目标是多少；
2. 已完成多少；
3. 当前处于哪一步；
4. 用户现在唯一应该点什么。

### 本轮执行

主区域建议保留：

```text
当前阶段
总进度
已获得可用推荐
剩余数量
预计剩余时间
阻塞/暂停原因
唯一下一步操作
```

“采集了多少卡片、读了多少详情、模型重试、超时计数、最近处理岗位、历史健康”等都放入“技术详情”折叠区。绿色健康项默认不展开，只有异常主动出现。

### 自动沟通

新增明确的“自动沟通”产品入口，但不扩大权限：

- 待确认：展示不可变清单和影响；
- 运行中：只展示当前岗位、批次进度、已成功/已跳过/不明确；
- 需处理：把 `ambiguous` 放在最上方，要求用户选择；
- 已完成：展示结果汇总和审计；
- 历史：按批次查看，不与当前批次混合。

“自动”表示确认后系统串行执行，不表示可以绕过清单确认、身份校验、额度、冷却或人工处理。

## 许可证决策

### 当前状态

- 仓库根目录没有项目许可证文件；
- `package.json` 有 `"private": true`，它只能阻止误发到 npm，不能替代版权许可证；
- 没有许可证时，其他人通常没有复制、修改和再发布代码的明确许可，因此不能把仓库视为正常开源发布。

### AGPLv3 是否合理

如果目标是“允许使用和商业化，但修改后作为网络服务提供时也必须向用户提供对应源码”，AGPLv3 很合理。GNU AGPLv3 第 13 节要求修改版通过网络与用户交互时向这些用户提供对应源码：
[GNU AGPLv3](https://www.gnu.org/licenses/agpl.en.html)。

但 AGPLv3 **不能禁止盈利或商业使用**。OSI 的开源定义要求许可证不得限制商业领域，并明确说明所有开源软件都可以用于商业目的：
[Open Source Definition](https://opensource.org/osd)、
[OSI FAQ](https://opensource.org/faq)。

### 与当前意图最匹配的选择

| 真实优先级 | 建议 | 含义 |
| --- | --- | --- |
| 必须是标准开源；不接受闭源 SaaS 改造 | `AGPL-3.0-only` | 允许商业使用，但强化网络服务源码回馈 |
| 不允许第三方商业/盈利使用 | `PolyForm-Noncommercial-1.0.0` 或律师定制的非商业许可证 | 更接近当前表达，但属于 source-available，不是 OSI 开源 |
| 社区免费使用，同时保留商业授权收入 | 非商业社区许可证 + 单独商业许可证 | 商业用户需要向版权方购买授权；需要清楚的版权归属和授权流程 |

PolyForm Noncommercial 的官方文本只授权许可范围内的非商业用途：
[PolyForm Noncommercial 1.0.0](https://polyformproject.org/licenses/noncommercial/1.0.0/)。

本项目当前表达的是“不太希望被他人用于盈利”，因此推荐 **暂不直接加入 AGPLv3**。先决定是“坚持标准开源”还是“禁止商业使用”；若后者是硬要求，优先评估 PolyForm Noncommercial，并在公开发布前做一次简短法律审阅。非商业限制不得继续标注为“开源”。
