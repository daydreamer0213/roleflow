# 每日筛选与沟通工作流

本文描述 RoleFlow 当前的主使用路径。参数权威来源是 `src/core/product_policy.js`，状态规划逻辑位于 `src/core/workflow_run.js`。

## 一轮任务

```text
用户点击“执行一轮”
  -> 计算当天成功数、可用候选、候选缺口和剩余预算
  -> 库存不足时选择关键词并扫描；库存足够时跳过扫描
  -> 本地并发完成岗位理解与简历匹配
  -> 生成默认勾选的沟通清单
  -> 用户取消不想沟通的岗位并确认清单
  -> 用户点击“开始沟通”
  -> 串行打开岗位、核验身份、单次点击并核验结果
  -> 保存成功、已沟通、失效、歧义和未访问替补状态
```

RoleFlow 不在后台定时运行。每一轮都由用户主动启动，外部沟通还需要用户确认清单并再次点击开始。

## 进度面板：五个阶段

打开本轮页面（工作台中的“本轮”链接）后，进度面板会显示“第 N 阶段 / 共 5 阶段”。五个阶段的含义如下：

| 阶段 | 页面显示 | 你会看到什么 |
| --- | --- | --- |
| 1 | 准备本轮 | 已创建本轮，正在检查当天目标、候选库存和预算。 |
| 2 | 读取搜索结果 | 读取当前 BOSS 搜索结果中的岗位卡片并保存来源。 |
| 3 | 获取完整 JD | 打开需要的详情并把完整 JD 保存到本地，供后面的模型分析使用。 |
| 4 | 分析岗位 | 使用 `batch_screening` 配置分析已经保存的 JD，不再增加 BOSS 页面访问。 |
| 5 | 等待确认 / 执行沟通 | 分析完成后等待你确认沟通清单；只有你点击开始沟通后才会进入外部操作。 |

扫描状态可能从“准备本轮”直接显示为第 3 阶段，这是当前实现把正在扫描的工作按“获取完整 JD”作为用户可见交付物展示，并不表示第 2 阶段漏掉了。

已完成、失败和停止等终态沿用第 5 阶段标签；中断状态按已到达或可恢复的阶段显示“准备本轮”“获取完整 JD”“分析岗位”或“等待确认 / 执行沟通”。此时应以页面的“本轮已完成 / 未完成 / 已停止 / 已中断”状态标题和错误提示为准，不表示系统还会自动进入沟通。

### 成功、失败、重试和剩余

岗位分析区域的数字来自数据库，不是内存中的临时计数：

- **总数**：本轮 `workflow_job_tasks` 中的岗位任务总数。
- **成功**：模型分析已成功保存的任务（`succeeded`）。
- **处理中**：当前有 worker 正在处理的任务（`running`）。
- **等待重试**：第一次可重试失败后，正在等待冷却或下一恢复周期的任务（`retry_pending`）。
- **失败**：已经不能再重试，或发生不可重试错误的任务（`failed`）。
- **剩余**：尚未完成的 `pending` + `running` + `retry_pending`，所以失败不会再次算入剩余。

进度条还会把“已按本地规则处理”（`skipped`）算作已完成，但它不会冒充模型“成功”。同一岗位在一个恢复周期内最多两次岗位级尝试；成功保存后不会重复分析。

### 什么时候只显示“正在估算”

ETA 的样本来自“分析岗位”阶段。分析中，当前模型配置版本下完成样本少于 3 个时，面板显示 **“正在估算”**；样本达到 3 个后，才会显示“预计剩余 X～Y（基于最近 N 个完成岗位估算）”的区间。切换模型配置版本会重新积累样本。暂停时（包括从扫描阶段暂停）不会倒计时：有足够的分析样本会冻结区间，没有足够样本会显示“已暂停；样本不足，正在估算”。未暂停的其他阶段显示“当前阶段不估算剩余时间”是正常的。

### “暂停本轮”和“结束本轮…”

- **暂停本轮**：安全暂停，可恢复。系统先停止领取新任务，让当前扫描动作或当前岗位级模型尝试落库，再释放租约并把状态变为“本轮已暂停”。暂停和继续仍属于同一轮，不会额外增加当天轮次数。
- **结束本轮…**：不可恢复的终止操作。点击后会先显示“确认结束本轮”，其中列出已采集、已分析、失败、未完成和已用网页预算；只有再点击 **“确认结束本轮”** 才会结束。已保存的岗位和分析结果会保留，但不能再点击“继续本轮”。

如果页面提示“任务可能失去活动”或“无法读取任务状态”，先看“诊断”，不要连续点击控制按钮或重复启动同一轮。

### 为什么第 10 个最终超时会自动暂停

同一岗位在一个恢复周期内第一次 `MODEL_TIMEOUT` 会自动再试一次；只有第二次仍为 `MODEL_TIMEOUT` 才算一个“最终超时岗位”。当前恢复周期累计到第 10 个最终超时后，系统设置 `MODEL_TIMEOUT_CIRCUIT_OPEN`，停止领取新岗位，等待当前安全单元落库，然后自动暂停。第一次超时后重试成功的岗位不计入 10 个；本轮累计超时数会保留，但不会让系统自动创建无限恢复周期。

面板“超时保护”会显示类似“当前恢复周期最终超时 10 / 10 · 本轮累计超时 10”。其中前一个数字决定本次是否熔断，后一个数字只记录本轮历史，不会单独触发新的恢复周期。

### 自动暂停后的准确恢复顺序

只有暂停原因是模型超时熔断或模型配置问题时，按下面顺序操作；不要先点“继续本轮”：

1. 在暂停页面点击 **“测试批量模型连接”**（或顶部 **“模型设置”**），打开 `模型设置` 的 `batch_screening` 区块。
2. 检查批量筛选的模型、超时和“并发数”，必要时调整；点击批量筛选卡片中的 **“测试连接并保存”**，看到连接状态变为已验证/保存成功。
3. 回到原来的工作流页面（地址形如 `/workflow?runId=...`），确认暂停原因和本轮 ID 仍一致。
4. 点击 **“继续本轮”**。系统会创建新的恢复周期，顺序处理上一周期的最终超时任务，再处理其他 `retry_pending`、异常中断恢复任务，最后才处理 `pending`。

手动暂停没有模型故障时，不需要重复测试模型；可在确认状态后直接点击“继续本轮”。

### 结束是否占用今天的轮次

“确认结束本轮”对话框会明确显示 **“会占用今天一轮”** 或 **“不会占用今天一轮”**：

- 结束前从未导航、滚动、读取岗位卡或读取详情：不会占用当天轮次。
- 已发生任一 BOSS 页面访问：会占用当天轮次；已消耗的网页预算不会返还。
- 暂停、恢复本轮不额外占用轮次。

### 沟通不会自动开始

分析结束后，页面停在“等待确认 / 执行沟通”。你必须先逐项审核并点击 **“确认清单”**，再在清单审阅页明确点击 **“开始沟通”**；RoleFlow 不会因为分析完成、恢复本轮或打开 Dashboard 而自动访问 BOSS、填写或发送消息。

## 每日目标与轮次

- 每日成功沟通目标：70 个。
- 每轮成功目标上限：40 个。
- 每天最多创建 3 轮；前 2 轮是主要工作轮次。
- 第一轮通常目标为 35；第二轮根据当天剩余目标动态计算。
- 第三轮只在可用候选少于 30，或本轮候选缺口至少为 8 时追加扫描；库存够用时不会为了凑数再扫。
- 两次扫描开始时间至少间隔 2 小时。无需扫描、直接使用库存的轮次不消耗网页访问预算。

轮次上限是防止同一天反复测试和重复抓取，不要求用户必须跑满 3 轮。

## 工作流预算

工作流每日共享预算：

| 项目 | 每轮上限 | 每日上限 |
| --- | ---: | ---: |
| 右栏详情读取 | 120 | 360 |
| 搜索页导航 | 20 | 60 |

已结束的扫描按实际访问量结算；正在创建、扫描或分析的轮次暂时预占完整计划预算。预算按北京时间自然日统计，跨日后重新计算。

高级入口中的独立“日常扫描”仍使用单次 `240` 个详情和 `40` 次页面预算，它是诊断与维护入口，不等同于上表的主工作流预算。

BOSS 访问控制还有独立硬上限和短窗口冷却。正常模式下右栏详情最多为 10 分钟 45 次、1 小时 240 次、24 小时 360 次；达到短窗口时等待，发现登录、验证或风控异常时立即停止。

## 扫描前检查

- 确认当前活动匹配偏好卡：扫描、工作流和岗位分析只使用已确认卡绑定的画像版本；没有确认卡时扫描会被拒绝，先到工作台的匹配偏好卡页面确认现有草稿。
- 核对简历版本：匹配偏好卡绑定具体简历版本，沟通时使用的投递版简历应与卡片证据一致。
- 确认过新的草稿卡后，受影响的 Search Plan 会变 stale，需要重新保存方案再开始扫描。
- 重复上传同一份简历不会要求再次确认；内容不同的简历只会生成新草稿，不会悄悄替换当前匹配依据。

## 搜索条件与关键词

双击 `Start.bat` 后，BOSS 与 RoleFlow 工作台位于同一个项目专用 Edge 窗口。工作台每 5 秒只读检查一次现有 BOSS 页面：未登录、非搜索页或安全验证状态都会禁用“执行一轮”。登录并设置好搜索结果页后，切回工作台等待状态变为“继承模式已就绪”，再由用户手动启动。

当前项目专用 Edge 停在有效 BOSS 搜索结果页时，RoleFlow 继承该页面的城市、区域、薪资、经验、学历、行业等 URL 参数，只删除页码并逐次替换 `query` 关键词。首次使用只需在这个 Edge 中登录一次，后续登录状态保存在 `.runtime\edge-profile`。

主工作流不会自动切换到日常 Edge，也不依赖 Edge Control。高级扫描入口仍可显式选择“当前 Edge”，用于兼容已有环境。

如果当前页面不是有效的 BOSS 搜索结果页，继承模式主工作流会停止，并提示操作者先在项目专用 Edge 中打开有效搜索结果页。只有明确使用 Search Plan 生成扫描条件的高级扫描入口，才会按该入口自身规则使用 Search Plan URL；这不属于继承模式主工作流。扫描快照会保存本轮实际继承的搜索模板，恢复时沿用同一套条件，避免中途漂移。

每轮最多选择 3 个关键词，优先使用当天尚未使用、历史有效率更高的关键词。日常扫描只使用 A/B 关键词；A/B 主档每词最多采集约 50/33 张卡片，右栏详情上限约 45/30。跨关键词和薪资档按岗位 ID 去重。

## 模型调用

首次使用通常包含两类模型调用：

1. `analyzeResume`：把脱敏后的简历文本整理为 CandidateProfile。
2. `recommendSearchPlan`：根据画像推荐岗位方向、关键词、薪资和经验范围；城市由用户选择。

对一个没有命中缓存、且已取得完整 JD 的岗位，语义分析通常包含：

1. `understandJob`：仅理解岗位，把 JD 拆成核心工作、核心要求（含是否必备）、加分项、成果期望、明确资格、岗位质量关注点和风险信号。
2. `matchJob`：结合已确认匹配偏好卡、候选人画像和具体简历版本，对每条核心要求逐项比对并给出 JD 与简历双侧证据；职责膨胀、愿望清单式 JD 记为岗位质量风险，通常对应谨慎投递，而不是直接判候选人不匹配。

查看岗位分析时先看“匹配分支”和“岗位主体”，再看逐项要求。若 JD 同时招聘多类人，当前结论只代表系统选中的一支，不代表候选人满足其他分支。

岗位分析使用 `batch_screening` 配置；设置页“并发数”只能选择 1 或 2，推荐值为 2。当前并发只处理已经保存到本地的 JD，BOSS 页面操作始终串行。结构化输出不合约时会追加一次契约修复；仍失败的岗位进入待语义分析，不伪装成推荐结果。模型、契约、画像、简历版本或 JD 变化时缓存会失效。

定制招呼语、HR 回复和无回复跟进只在用户主动点击后调用 `draftCommunication`，不在海投扫描阶段批量生成。

## 清单与批量沟通

- 系统默认勾选可沟通岗位，用户可以逐项取消。
- 清单保存岗位 ID、公司、标题和链接快照，执行时不重新接受一份已变化的列表。
- 用户确认清单后，还要点击“开始沟通”才会访问 BOSS。
- 每个岗位先核验岗位身份和“立即沟通”状态，再执行一次点击；点击后再次核验聊天或按钮状态，无法确认时记录为歧义而不是成功。
- 同一岗位已投、已沟通、失效或存在歧义记录时，不会再次自动进入执行队列。
- 单项之间随机等待 15–20 秒；10 分钟最多 30 个、30 分钟最多 60 个、24 小时最多 150 个。
- 达到本轮成功目标后，未访问替补以零点击停止，继续保留为后续候选。

批量沟通使用 BOSS 平台已有的通用招呼语。模型生成的定制招呼语只供用户查看和手动使用，当前执行器不会自动把生成文本填写或发送给 HR。

## 中断与恢复

- 扫描批次按关键词目标保存检查点；中断后恢复原轮次，不额外占用新轮次。
- `review_required` 阶段可以关闭程序，稍后继续确认清单。
- 沟通执行支持暂停和恢复；遇到未完成的点击状态会要求人工复核，不盲目重放。
- 登录失效、风控、浏览器断开、页面结构变化或岗位身份不一致会立即中断。
- 重启只校准本地状态，不会自动导航、刷新、点击或继续沟通。

## 日常建议

通常一天执行 1–2 轮即可。每轮完成后先看推荐数量与沟通结果；只有候选明显不足且已经满足两小时间隔时，再考虑条件式第三轮。不要为了达到固定数量连续重跑扫描。

正常日常顺序：双击 `Start.bat` -> 在 BOSS 标签页登录并设置搜索条件 -> 切回 RoleFlow 工作台，等待“继承模式已就绪” -> 点击“执行一轮” -> 审核并确认清单 -> 点击“开始沟通”。

## 开发验证说明

### Offline acceptance boundaries

- Text-based PDF resumes preserve visual reading order; scanned files require pasted text.
- Local redaction removes names and contact details before a model is used.
- Users must confirm a matching card before it is used for scanning or matching.
- The private full-chain benchmark is a merge gate, not part of daily scanning.
- Real inputs and outputs are never committed to Git.

开发与回归验证使用保存的页面 fixture、注入式假模型和临时测试库，不访问真实 BOSS 页面，也不需要启动工作台。私有完整链路基准仅作为合并验收门禁；日常扫描始终使用离线检查。


## 消息回复与求职进展（可选）

1. 在“当前岗位”队列中打开岗位卡，可查看/纠正求职进展阶段。
2. 在“消息发现”页手动启动一轮只读发现，生成草稿后复制并到 BOSS 手动发送。
3. 发送后回到页面点“已手动发送”，进展卡会进入“等待招聘方回复”。
4. GAP、离职原因、短期项目解释始终要求用户确认，不自动复用历史措辞。
