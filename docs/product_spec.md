# RoleFlow 产品规格

## 定位

RoleFlow 是面向普通求职者的本地岗位筛选和投递决策助手。它把“逐条看岗位”的高消耗流程拆成：简历理解、搜索计划、只读采集、岗位理解、证据化匹配、队列确认和结果记录。

产品优化目标不是尽可能少投，而是只拦截明显无效岗位，并把更值得优先沟通的岗位排在前面。

## 核心原则

1. 简历驱动：不同候选人从各自画像生成关键词和条件，不内置固定 AI 岗位模板。
2. 模型负责语义，规则负责确定性边界；关键词命中不能代替完整 JD 判断。
3. 放宽可投池，收紧不推荐：经验可冲、外包和工作制未知可以保留；主投需要
   可核对的总体 JD 与简历证据，但不要求每个正向条目重复同一证据。
4. 状态不丢失：跨关键词去重、重复扫描、详情刷新和重新分析都不能覆盖人工决策。
5. 低打扰：不重复确认用户已经提交的事实，不在海投阶段批量生成无价值话术。
6. 安全优先：BOSS 操作串行、随机等待、分段冷却；发现风控立即停止。
7. 本地优先：数据库、Key、简历和日志留在本机；云模型调用边界明确告知。

## 用户流程

1. 配置并测试模型。
2. 上传简历或粘贴文本。
3. 查看结构化画像，不接受越界点评和无关追问。
4. 确认由简历事实生成的匹配偏好卡；重复上传同一份简历直接进入现有流程，不会要求再次确认。
5. 查看模型推荐的岗位方向、关键词、经验和薪资范围。
6. 用户选择城市，按需调整其他条件并保存 Search Plan。
7. 用户在默认的“RoleFlow 专用 Edge（推荐）”中主动执行一轮；系统优先使用已有有效候选，库存不足时再扫描。
8. 本轮固定的 BOSS 搜索页有效时继承页面筛选条件，只替换关键词；否则从 Search Plan 生成原生筛选 URL。
9. 读取左侧卡片；按优先级串行点击卡片，读取右侧完整详情。
10. 本地并行执行岗位理解和 JD-简历匹配。
11. 在队列中查看主投、先聊、备选、待分析、待刷新和不建议。
12. 用户检查默认勾选清单，可以取消任意岗位并确认批次。
13. 用户再次点击开始后，系统串行核验岗位、执行单次沟通并验证结果。
14. 对推荐异常提交原因；反馈只做诊断，不自动改模型或排序。

## 功能模块

### 模型配置

- DeepSeek、通义千问、OpenAI 预设和自定义 OpenAI-compatible 接口。
- 每个提供商独立 DPAPI 密钥槽。
- 保存前做真实最小调用；区分鉴权、余额、限流、模型不存在、超时和服务异常。
- 模型未就绪不封锁历史岗位和投递记录。

### 简历与画像

- TXT、MD、DOCX、PDF 和文本粘贴。
- 提取字数、方式、质量、预览和明确失败原因。
- 画像包含基本意向、教育、经历、技能、项目、证书、优势和简历版本。
- 用户文本视为事实；模型推断不得成为对外口径。

### 匹配偏好卡

- 匹配偏好卡从简历事实生成：目标方向、强证据、可迁移能力（含尚未证明的限制）、谨慎转向和用户备注；模型只归纳画像中明确出现的事实，不得编造经历或方向。
- 扫描、工作流和岗位分析只使用**已确认**的匹配偏好卡及其绑定的画像版本；没有确认卡时扫描被阻止，错误会指引到工作台确认现有卡，而不是要求重新上传简历。
- 同内容不重复确认：重复上传同一份简历（相同内容哈希）时，已确认卡直接进入计划页，未确认草稿直接重新打开。
- 不同内容先草稿后切换：上传内容不同的简历只生成新草稿卡，旧确认卡继续作为当前匹配依据，直到用户明确确认新卡；确认新卡后受其影响的 Search Plan 需要重新保存。
- 卡片始终可编辑：保存草稿不改变当前匹配依据；对已确认卡的人工修订会产生一条新的已确认记录，历史版本全部保留。
- 老用户升级：系统会用已保存画像生成一张可编辑的草稿匹配卡；确认前扫描被阻止，但草稿入口始终可用，无需重新上传或修改简历。

### Search Plan

- 平台、城市、薪资、经验、全职类型、学历、方向、A/B/C 关键词、排除词和扫描规模。
- 城市由用户选择；平台参数由适配器转换为 BOSS URL，不暴露城市编号。
- 3–5 年可冲进入抓取池，本地结合薪资和 JD 判断优先级。
- 画像版本变化使旧方案失效。
- 日常扫描自动取 A/B 关键词、首选薪资档和收敛预算；广泛扫描取 A/B/C 全部关键词、全部薪资档和方案高级预算。

### 浏览器与登录资料

- 当前版本默认使用“RoleFlow 专用 Edge（推荐）”，不需要 Edge Control。内部仍使用 `portable`、CDP 和 `9222` 标识实现身份，但这些不是普通用户要配置的入口。
- 第一次登录保存在 `%LOCALAPPDATA%\RoleFlow\BrowserProfile`。该目录不随安装目录变化，覆盖升级或换安装目录后仍可复用。
- 稳定范围只有浏览器登录资料。数据库、简历、模型设置、日志和报告仍保存在各自安装目录，不会悄悄跨安装目录迁移。
- “使用当前 Edge（高级，需要浏览器连接组件）”必须显式选择，并要求已有 Edge Control 扩展与桥接健康；默认模式失败时绝不自动回退或切换 authority。
- 静止基线是同一窗口内一个 `BOSS-SEARCH` 和一个 `BOSS-COMMUNICATION` 固定页。消息发现只有在新会话缺少完整可信本地 JD 时，才可串行打开一个 `active: false` 的后台临时详情页，核验、保存并关闭后恢复基线。
- 用户启动工作区且未选择 `-NoOpen` 时，启动助手可在就绪检查后引导一次前台。扫描、JD 读取、分析、消息发现、沟通、轮询、重试和恢复均不得激活 BOSS 页或恢复前台焦点。
- 旧 profile 迁移必须由用户明确确认，只复制到稳定目录并保留源目录。普通卸载和静默卸载保留稳定 profile；删除浏览器登录资料需要独立确认。

### BOSS 采集

- 预读并缓存平台原生筛选目录，生成可追溯的 filter snapshot。
- 左侧卡片只读取页面实际提供的标题、公司、地点、薪资、经验、学历和链接；可选在线图标只代表当前在线，图标缺失时活跃度仍为未知，周/月等状态必须读取右栏文字。
- 左栏只做无效链接、明确异地、用户未选择时的实习岗位和用户硬排除词等确定性硬排除。其余唯一岗位点击左卡并等待右侧目标岗位切换，再读取完整 JD、技能标签和招聘者活跃状态；必要时才滚动右栏。
- A/B/C 关键词使用不同列表采集规模和详情上限。跨关键词和薪资 lane 按岗位 ID 去重，同一岗位每轮最多尝试一次右栏。
- 日常扫描默认 A/B 每词最多约 50/33 张卡片、45/30 个右栏详情。主工作流每轮详情/页面上限为 120/20，每日共享 360/60；高级入口的独立日常扫描使用单次 240/40，广泛扫描使用 Search Plan 的高级预算。
- 未读到右栏的岗位只能进入待读详情，不能产生语义推荐；单轮安全上限只防止异常长任务，不作为质量配额。

### 岗位分析

- 岗位主视图先给推进结论，再回答岗位主要做什么、公司业务、匹配度、薪资和基于当前资料可支持的机会评价；逐项证据和内部判定来源留在次级明细。
- 首轮模型分析失败、随后同一方案重试成功时保留失败历史，但当前流程显示“失败后已解决”，不再误计为待语义分析；真实未完成仍保留未解决状态。
- 一份 JD 明确包含多个独立招聘方向时，系统先拆分方向，再只选择与已确认简历证据最接近的一支做匹配。
- 页面会显示“匹配分支”；其他招聘分支的要求不会变成候选人的缺口。
- 职责决定主体工作，任职要求做逐项证据匹配；宽泛通用职责只解释，不单独淘汰。
- 每条岗位要求同时区分“是否定义岗位主线”和“是否为不可替代硬门槛”。主线要求即使写成“熟悉、了解、优先”，仍可用于判断岗位实际方向；它不会单独形成硬阻断。
- 完整 JD 已识别出岗位主线、但当前简历对所有主线要求都没有直接或可迁移证据时，岗位进入备选并取消默认勾选。它仍可查看和手动选择，不会被写成候选人明确不能胜任。
- `JobUnderstanding` 只看岗位：把 JD 拆成核心工作、核心要求（含是否必备）、加分项、成果期望、明确资格、岗位质量关注点和风险信号，不套用固定职业分类或技术栈模板。
- `MatchDecision` 使用匹配偏好卡、画像、具体简历版本和完整岗位理解，对每条核心要求输出逐项状态（matched / transferable / missing / unknown / not_applicable）和 JD 与简历双侧证据。
- `foundation`、`central` 与 `indispensable` 是独立维度。模型负责普通技能、
  行业和复杂同句语义；规则只校验“仅限、不得上岗、不予录用、优先、非必要”
  等跨岗位通用的明确边界，不维护领域关键词表。明确软条件标 true、明确单一硬
  边界标 false 或可可靠拆开的软硬条件混在一项时触发契约修复；其他含糊语义
  有限度保留模型判断，不得由 `foundation` 或 `central` 自动推导。
- 四档建议由方向匹配度与核心要求符合度矩阵产生；`apply` 表示优先投递，
  `caution` 表示可沟通，`review` 表示需要人工审核，`skip` 表示方向和核心证据
  组合明显不合适。结构化核心硬性阻断必须同时具备模型 `indispensable=true`、
  JD 明确不可协商边界和简历明确不兼容事实；安全风险仍具有更高优先级。
- 岗位质量与人岗匹配相互独立：职责膨胀、愿望清单式 JD 标记为岗位质量风险，通常意味着谨慎投递，而不是判候选人不匹配；它不会单独造成 `skip`。
- 年限偏好、辅助技能、城市与工作制默认是可沟通差距；薪资只与用户在 Search Plan 中的偏好比较，不凭市场猜测升级为硬性阻断。
- 完整 JD 和总体 JD/简历双侧证据是主投必要条件；单个正向条目缺少重复证据
  字段不再机械阻止主投。
- 生产判定继续使用二维表。职责 40% + 要求 60% 的连续积分只作为独立影子结果；冻结样本比较尚无人工确认标签和同岗位重复模型组，不能据此宣称积分更准确或更稳定，也不能切换生产。

### 队列和 CRM

- 主投、先聊、备选、待语义分析、待详情、活跃待核验、不建议。
- 本轮新增、本轮重复和历史未处理分开查看。
- 已投、跳过、稍后、无回复、约面、拒绝、无效、薪资不匹配。
- 30 条分页和紧凑卡片，首屏只显示决定所需信息，完整 JD 和沟通工具折叠。

### 沟通助手

- 普通岗位使用平台通用招呼语。
- 仅证据完整的主投岗位按需生成定制招呼语。
- HR 回复保留原问题；缺少 GAP、离职、到岗等事实时只问用户一个问题。
- 无回复岗位按需生成一次跟进。
- 模型生成的定制招呼语、HR 回复和跟进文案不会自动填写或发送。
- 消息发现把正式面试邀约、意向询问、信息请求、信息补充、普通沟通和人工判断分开；只有明确邀请参加、确认或选择一场面试才推进面试阶段，正文仅出现“面试”不构成邀约。
- 已验证的附件简历请求卡片转换为固定的 BOSS 人工待办；它不进入模型，也不会自动点击“同意/拒绝”。同一轮还有纯文字时，人工待办与本地回复草稿同时显示。
- BOSS 岗位竞争情况卡片作为平台提示静默排除；语音、图片、普通附件和任何未经真实 DOM 证据验证的卡片安全停止。
- 批量沟通必须先由用户选择并确认岗位清单，再由用户明确点击开始；执行器逐项核验岗位身份、按钮状态和点击结果。
- 外部操作串行执行并受 15–20 秒随机间隔、时间窗口额度和风控即停约束；不后台定时触发。

### 诊断与反馈

- 推荐异常可选择方向、技术栈、年限、薪资、地点、公司、活跃度、工作制等原因。
- 反馈和投递状态独立保存。
- 反馈不直接在线学习；开发者通过具体样本定位根因并加入标注集。
- 日志记录脱敏错误和模型性能指标，不记录业务正文。

## 决策层级（2026-07-31 更新）

硬边界只处理已确认事实：无效链接、明确异地、明确过期、用户未选择实习时的
实习岗位、用户硬排除词和薪资底线。本地规则不预设职业方向；岗位是否匹配由
语义模型按匹配偏好卡判断。只有明确资格不符、安全风险，或同时具备模型硬性
判断、JD 明确不可协商边界和简历明确冲突的核心要求，才进入不建议。

### 四档建议

| 建议 | 含义 |
|------|------|
| 主投（primary） | 方向匹配 + 要求充分对上，默认沟通 |
| 可投（apply） | 值得沟通但存在有限缺口，默认沟通 |
| 慎投（caution） | 不完全匹配或需要人工确认，不默认沟通 |
| 不推荐（not_recommended） | 明显不合适或命中确认硬边界，不可选择 |

### 判定规则

根据两个维度查表：**方向匹配度**（角色匹配判断，roleAlignment）× **核心要求符合度**（核心要求对上比例）

详见 `docs/roleflow-decision-matrix.md`

### 执行优先级

1. 本地已确认的基础条件不满足：直接不推荐
2. 模型失败、过期、等待、局部 JD、刷新或总体证据不完整：`null + needs_retry`
3. 完整语义结果中的合法硬阻断和岗位安全风险：不推荐
4. 本地按核心 70% + 支持 30% 计算，再查冻结二维表
5. 年限/薪资跨度、确认硬性要求仅可推导、中高语义风险和普通非核心缺口只向下封顶
6. 普通非核心缺口从 5 条起降一级；明确优先、加分、非必须或可选项不计数

### 运行时分桶

- 最终 recommendation 与业务 bucket 统一使用
  `primary / apply / caution / not_recommended`，不得分叉。
- `primary` 和 `apply` 默认勾选，`caution` 不默认勾选，
  `not_recommended` 不可选择。
- 技术桶 `analysis_pending / refresh` 必须配 `recommendation=null`。

## 非目标

- 未经用户确认清单和明确启动的自主投递或后台沟通。
- 自动填写或发送模型生成的定制招呼语、HR 回复和跟进文案。
- 绕过登录、验证、风控或平台访问限制。
- 训练招聘推荐模型或根据单个用户反馈在线调权。
- 代替用户决定是否接受 offer。
- 从简历猜测对外敏感口径。

## 发布验收

### Resume privacy and acceptance boundaries

- Text-based PDF resumes are extracted in visual reading order. For scanned files, paste the text before analysis.
- Names and contact details are redacted locally before any model call.
- A matching card takes effect only after the user confirms it.
- The private full-chain benchmark is a merge gate, not a daily scanning command.
- Real inputs and outputs never belong in Git.

- v1.1.0 注册 108 项离线检查；每次发布必须在标签所指精确提交上重新全部通过。启动边界测试使用注入的进程与 HTTP 探针，不再创建假的 `msedge.exe`。
- 31 条脱敏离线 fixture 通过；冻结真实 20 条岗位池必须另走私有 runner 验收，
  不得用离线 fixture 冒充真实模型结论。
- 主数据库备份后迁移，`PRAGMA quick_check` 为 `ok`，岗位和人工决策数量不下降。
- 绿色包在干净目录可启动，不包含 Key、数据库、简历、日志或浏览器 profile。
- 留足冷却后使用已登录 Edge 串行读取 3–5 条，验证卡片和右栏字段一致；沟通执行另用 1 条已确认岗位做单次校准，不能与采集验收混跑。
- 当前 dedicated Edge source candidate 尚未执行新的真实 BOSS 验收；历史发布或旧分支记录不能替代本候选验收。
